What this page does

A plain-language description, written for someone deciding whether this page belongs on a blocklist.

Summary. This page asks a visitor for permission to use one background thread to search for a mathematical object. It asks before it uses any processor time and before it contacts anything. It shows what it is doing in a bar that cannot be dismissed while it runs, and a single control ends the thread. It handles no currency of any kind.
Who made this. Built by Alexander Fedin. It is the work of one named author rather than an anonymous project, and the source is public.

What it computes

A colouring of the whole numbers 1 to N in two colours, such that no three numbers with a² + b² = c² are all the same colour. This is a known problem in combinatorics; the largest N for which such a colouring exists is 7824, proved in 2016. The work is integer arithmetic in a small WebAssembly module whose source is in the repository.

A visitor can check any answer the page produces without trusting this site or any other participant: the check is a loop over the definition, and it runs in their own browser.

Consent

  • Nothing runs until the visitor presses a clearly labelled button.
  • No processor time and no network request is made before that — not even to discover a relay. The visitor's address is not disclosed to any third party until they agree.
  • There is no pre-ticked box and no consent implied by scrolling or waiting.
  • The agreement records which version of the disclosure it answered. If what the page does changes, the agreement stops applying and the visitor is asked again.
  • A "no" is a control on the page, not the absence of one.

While it is running

  • A bar is fixed to the bottom of the window for as long as a node exists. It cannot be collapsed or dismissed. It shows what is running, how much of one thread is in use, how many tasks have completed, and how many peers are connected.
  • Work happens in a Web Worker, not on the page's main thread, so the page stays responsive and the thread can be ended outright.
  • When the tab is not in front, the duty cycle drops to a tenth. The figure in the bar changes as this happens, so the throttle is visible rather than asserted.
  • Stop calls Worker.terminate() and closes the network connections. Processor use reaches zero because the thread has ended, not because a loop agreed to exit. Work in flight is abandoned; the fabric re-runs it elsewhere and no data is lost, because every result is a pure function of its inputs.

What leaves the device

The visitor's own data never leaves their device. That is what the whole system is for, and it is a property of how the work is arranged rather than a promise: the code that runs here is handed a public question and computes an answer, so there is nothing of the visitor's for it to send. What follows is the complete list of what does leave.

  • The results the visitor's machine computes, which are small integers and bit arrays.
  • A peer key. It is not derived from anything about the device, and it does not persist across origins. Since 2026-09-04 it persists across visits again, encrypted. The page now asks a visitor to register with a passphrase of their own choosing before anything runs; the key is stored in that browser sealed under a key derived from the passphrase, and the passphrase is held in page memory for one visit and written nowhere at all — not to this browser, not into a link, and not to any server, because there is none. So a returning visitor who enters the same passphrase is the same node, and a person who copies the browser profile has an encrypted blob rather than an identity. Nobody can recover a forgotten passphrase, including the author: the page offers to start over as a different node instead, and states on that control what starting over costs. Until a visitor registers or logs in, nothing runs and no key is made. One carry-over: a browser that already holds a key from an earlier version of this page keeps that same key and seals it in place on registration, rather than having its node identity deleted out from under it. Clearing this site's data in the browser removes all of it.
  • Optionally, and only if the visitor ticks the box: one line recording the browser family and major version, and whether the node started or was blocked. This exists so that blocking is visible as a number rather than as an unexplained absence of participants. It is not a fingerprint — a family and an integer cannot distinguish visitors from one another.
  • Nothing else. No files, no browsing history, no cookies, no advertising identifiers. Note that "no cookies" is a statement about cookies and not about storage in general: this page does keep the visitor's own answer to the consent gate in this browser's storage for this site, so that they are not asked again on every visit, and — for a visitor who joins a provider — the signed statement recording that. Neither is sent anywhere by this page; both are removed by clearing this site's data.

What this page is not

  • It does not handle, produce, transfer, or account for currency of any kind, and it never has. There is no payment, no settlement, no balance, and no wallet.
  • It sets no cookies and uses no third-party analytics service — the counts described below are taken by this project's own collector and go nowhere else. It does keep values in this browser's storage for this site: the visitor's own answer to the consent gate, and the signed statement from a provider they chose to join. It no longer keeps a peer key, so a returning visitor is a new node rather than the same one.
  • A visitor who does not agree is not counted anywhere, by anything. Nothing is sent before the consent gate is answered, and answering it "No" ends the matter.
  • A visitor who does agree is counted, coarsely, and here is the whole of it. Six named steps between opening the page and running a first task — page load, consent, the connection to a relay, the search for a network route, the classification of the connection that resulted, and the first task run — so that the people building this can see where visitors get stuck. For the two steps where one browser tries to reach another, three more values travel beside the count: a two-letter country code, a rough label for the kind of connection, and the hour of the day in UTC. That is the entire record. It holds no identifier of any kind: nothing joins two visits together, and nothing joins a step to a person. The network address the request arrives on is used to work out the two-letter country and is not stored — which is checked against the store itself rather than against this paragraph, by dumping every value the collector holds and searching it.
  • With the optional start report left off, that line is not sent and not held. The opt-out reaches both places it has to: the line is not contributed when peers are asked, and the visitor's own node does not hold it for a peer to ask for either. Those two were once out of step — the page withheld the line and the node served it — and the disclosure states both because stating only the first would be the same defect written down.
  • All of that rests on your permission, and on nothing else. The counters begin when you allow the work to run; the optional start report begins only if you also tick its box; and a visitor who does neither is not counted on some other footing instead, because there is no other footing here. Withdrawing either permission stops what that permission covers — which is what makes it a permission rather than a notice. This was an open question in this project's own records until 2026-09-04 and the disclosure deliberately named no ground while it was open; the ground is now settled and stated, and the code did not have to move for it, because the counters were already taken only after a yes.
  • It runs no server-side process. It is a static file. The only infrastructure it uses is a relay peer, which carries the connection handshake between browsers and then drops out of the data path. This survives the sign-in described above, and it survives because of it. Stated explicitly so a reader does not assume the claim was overlooked when the page grew a way to log in: the credential is a local passphrase, chosen deliberately over an email-and-password account and over a third-party login precisely so that logging in adds no server, no account database and no other company. Registering here contacts nothing.
  • It does not run in a hidden frame, a background tab it opened, or a service worker.
  • It is not obfuscated or minified beyond ordinary bundling, and its source is public.

If you believe this page should be blocked

Please open an issue on the project's public repository describing what you observed, or contact the address listed there. The intention is to meet the standard a reviewer would set, so a specific objection is more useful than a block, and will be acted on.

If this page has already been blocked, the same channels are the appeal path. Please state which list, which rule, and which behaviour triggered it — "cryptojacking" heuristics sometimes fire on any page that uses a Worker and a WebRTC connection, and if that is what happened it is worth both parties knowing.
