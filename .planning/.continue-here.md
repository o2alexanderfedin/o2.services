### The result worth reading first

**Native elfconv is not reproducible against itself. The wasm-hosted translator is.**

Four runs each, one machine, one input, nothing else touching the box:

```
native   f6eb6063…  7 375 076      wasm   d7b67545…  7 352 360
native   4c2a9def…  7 372 256      wasm   d7b67545…  7 352 360
native   11bd0a4c…  7 373 600      wasm   d7b67545…  7 352 360
native   c80f35e4…  7 374 204      wasm   d7b67545…  7 352 360
```

`cross-machine.node.test.ts` records `CROSS_MACHINE_BLIND_SPOT` — elfconv iterates containers
keyed by pointer, so its output follows the allocator and the allocator follows the host — and
the repository carries that as structural rather than as a bug. A wasm linear memory is flat
and program-determined: no ASLR, no host allocator, the same allocation sequence landing at
the same addresses on every instantiation. **The dependency does not disappear; it stops
varying.**

So running the translator as a wasm job is not merely portable. It is the configuration in
which its output is reproducible — which is what addressing an artifact by the hash of its
content requires.

The two arms disagree in exactly the shape that theory predicts: both define 2015 functions,
declare 220, carry 1560 globals, same datalayout, same triple — but where several symbols
share one address they pick different aliases for it,
`@____strtoul_l_internal…_406160` against `@____strtoull_l_internal…_406160`, same address
`406160`.

**Not claimed:** determinism across HOSTS. That still needs the second machine AOT-03 is
blocked on. What is measured is: identical across runs, fresh process each time, this host.

`tools/aot/elflift-wasm-determinism.node.test.ts` holds both arms, 5/5. The proof was watched
failing — one random byte planted on the runner's write took it to `3 runs -> 3 hash(es)`,
`expected 3 to be 1`, restored by the inverse of that edit and `cmp`-verified against a
snapshot taken immediately before planting.

## What the wall actually was

Not glog, and not threads. **wasi-libc removes the POSIX process and signal API behind
`#ifdef __wasilibc_unmodified_upstream`, a macro it never defines.** `struct sigaction`,
`sigprocmask`, `fork`, `execve`, `dup2`, `pipe`, `<sys/wait.h>`, `pwd.h`, `umask`, `getsid`,
`alarm`, `posix_madvise` and the fcntl lock constants are all present in the headers and all
fenced off. `-D_WASI_EMULATED_SIGNAL` gets past the `#error` at the top of `<signal.h>` and
yields `raise` and `signal` — nothing more.

`tools/aot/wasi-compat/` supplies exactly that surface, force-included. Read its header
comment before touching it; in particular it deliberately does **not** declare `sigaltstack`,
`getrlimit`, `setrlimit` or `posix_spawn`, because cmake probes those by compiling AND
linking, so declaring them flips `HAVE_*` on and compiles code back in. The build script
diffs `config.h` across every reconfigure to catch precisely that.

**Threads were measured irrelevant, twice.** `signal.h` in `wasm32-wasi-threads` is
byte-identical to the threadless one, `fork`/`exec` are fenced identically, and `sys/wait.h`
and `spawn.h` are absent in both — so the threads target would not have helped. And elflift
creates no thread: zero `pthread_create` across all 27 objects and all 37 archives.

### Three LLVM source changes, each extending a chain LLVM already maintains

```
HandleLLVMOptions.cmake   WASI counts as a unix (LLVM 17 has this upstream)
Unix/Program.inc          ru_maxrss joins the __HAIKU__ exclusion
Unix/Path.inc             wasi arms for GetMainExecutable and is_local_impl
```

All three are applied by `build-wasi-llvm.sh` as idempotent python patches. glog and gflags
take four more of the same kind, in `build-wasi-deps.sh`.

### Two build settings that are structural, not preference

- **`LLVM_ENABLE_RTTI=ON`.** remill subclasses LLVM types, so its objects reference
  `typeinfo for llvm::ErrorInfoBase`, which `-fno-rtti` never emits. 2 of exactly 5
  unresolved symbols at the link.
- **`LLVM_ENABLE_EH=OFF`, with `wasi-eh-abort.c` supplying the throw side.** Measured: across
  all 27 objects and all 37 archives the only EH symbols are `__cxa_throw` and
  `__cxa_allocate_exception`. No `__cxa_begin_catch`, no `_Unwind_Resume`, no
  `__gxx_personality_v0` — **there is not one landing pad in the program**, so every throw
  already terminates and aborting directly is the same behaviour. If `__cxa_begin_catch` ever
  appears as undefined, that reasoning has expired and the answer is a libc++abi built with
  exceptions, not a bigger stub.

### The 16 MiB shadow stack

`wasm-ld` defaults to 64 KiB and a wasm linear memory has no guard page, so LLVM's recursive
passes walk the stack pointer past zero and the next write lands out of bounds. The first
real lift did exactly that, after completing all 845 analysis steps.

## Ideas this opens

- **The reactor shape.** `link-elflift-wasm.sh` already has `MODE=reactor` for when
  `elfconv_lift` exists. `main()` is ~100 lines and only four are process-shaped; with the
  in-memory filesystem the runner already provides, the two I/O ends need no C++ change.
  Now that determinism is measured, this is the difference between a job and a process.
- **AOT-03 may be reachable after all.** It is blocked on a second machine for
  cross-machine reproducibility. If wasm determinism holds across hosts — untested, needs
  that machine — the blind spot closes rather than being documented.
