## 🔴 THE CONSTRAINT THAT WOULD HAVE BEEN A BUG

**`docs/superpowers/specs/2026-08-12-visitor-identity-security-constraints.md` — read it
before writing any code for this.**

The headline: **derive the USER key from the passphrase. NEVER the node seed.**

`identityFromSeed` derives `nodeKey`, `peerId` and the libp2p private key from the seed
alone, so a passphrase-derived node seed gives two tabs the **same `peerId`** — destroying
the `nodeKey ↔ peerId` binding that both admission seams recompute from the Noise handshake.
That binding is the single strongest property in the trust model and the only thing keeping
the ratification gap from being an impersonation gap.

The model already supports one owner across many nodes (`NodeCertificate.userKey`:
*"Several nodes may share one"*, and AUTH-05 is met).

Also in that document, each with a line to check it against:

- **The enrolment response is not ratified.** `enrol-client.ts:132` returns the certificate
  verbatim; `browser-node.ts:594-604` persists it unchecked. The **persisted** path already
  does the check on reload (`:553-560`); the **fresh** path does not. Severity is
  self-inflicted identity confusion, not impersonation. **Ratification is part of the change.**
- **The page must never choose `operatorId`.** It is the sole input to quorum anti-affinity
  and is bound to nothing scarce.
- **A stable `userKey` wakes a limiter that has never fired.** Functional regression to size.
- **Do not design against `cert-lifecycle.ts`** — imported by nothing in production, and a
  guard forbids barrel exports declared in it.
