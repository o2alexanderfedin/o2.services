## AOT-06 — x86-64. **VERDICT REACHED 2026-08-07: elfconv cannot lift x86-64 today, and the gap is NOT instruction semantics.**

Owner: *"We must support x86-64 if possible!"* The recorded *constraint* was stale; the
*capability* is still absent, and now for a located reason instead of an inferred one.

### The finding, in one line

**`lifter/TraceManager.cpp`'s entry-point discovery is hardcoded AArch64 byte patterns with
no amd64 branch**, so an x86-64 ELF aborts before any bitcode is produced.

```
  __wrap_main_size = AARCH64_OP_SIZE * 3            // Lift.h:3 -> #define AARCH64_OP_SIZE 4
  for (i = 0; ...; i += 4)                          // fixed 4-byte stride
      nop      == 1f 20 03 d5                       // AArch64 encodings, matched literally
      bti c    == 5f 24 03 d5
      b <label>== (byte & 0xfc) == 0x14
  elfconv_runtime_error("__wrap_main code block is not found. entry_point: 0x%lx")
```

x86-64 has variable-length instructions, so the stride is meaningless and those bytes can
never match. The PLT scan just above it (`ins_i += AARCH64_OP_SIZE`, `br` pattern `1f d6`) is
AArch64-only in the same way.

### How far x86 support actually reaches — the boundary, not a gesture

| layer | state |
|---|---|
| CI / packaging | **works** — `ELFCONV_X86=1`, `arch: AMD64` in `tests.yml`, `:amd64` published |
| Remill semantics | **works** — amd64 supported for years |
| `--arch` flag | **accepts** `x86, amd64` (`lifter/Lift.cpp:47`) |
| ELF loader | **classifies it** — `bin_arch = BinaryArch::ARCH_AMD64` (`lifter/Binary/Loader.cpp:209`) |
| **entry-point / PLT discovery** | **AArch64 only, aborts** (`lifter/TraceManager.cpp:181,203,211,228`) |

### Measured, twice, with the compiler as a control

`TARGET=amd64-wasi32` — **`amd64` is the arch token, not `x86_64`**; `arch_name=${TARGET%%-*}`
is what reaches `elflift --arch`, and the runtime macro case tests `amd64-*`.

| build | entry point | result |
|---|---|---|
| `gcc -static -O2` | `0x401670` | `LIFT_EXIT=134` (SIGABRT), **no `.bc`, no `.wasm`** |
| `clang-16 -static -O2` | `0x401590` | `LIFT_EXIT=134`, identical message, no artifacts |

Same abort from two toolchains at two entry points, exactly as the source reading predicts.
**The verdict is carried by the source, not by the runs** — which matters, because the amd64
image runs emulated on this arm64 host and an emulation artifact would otherwise be a live
alternative explanation. It is not one: a byte pattern that cannot match, cannot match.

### The old null result is explained, and it was a wrong invocation

The previous session recorded `LIFT_EXIT=0`, empty output, no artifact, and correctly refused
to read it as a limitation. The cause is now known: **`elfconv.sh`'s second `case` has no `*)`
branch at all** (the target dispatch, `*-native` / `*-wasm` / `*-wasi32`). A `TARGET` matching
none of them falls straight through and `main` returns **0 having produced nothing**. The
first `case`'s `*)` only *echoes* "Unsupported architecture" and does not exit either. So
`exit 0` + no artifact is this script's signature for *"you named a target I do not handle"*.

### Two hypotheses tested and refuted, both worth recording

- **"Missing LLVM dynamic lib in wasm."** Refuted: `ldd elflift` resolves `libLLVM-16.so.1`
  with **0 not-found**, and the failure is a `std::runtime_error` thrown from elfconv's own
  `elfconv_runtime_error` — a loader failure happens before `main` and cannot produce that
  message. *But it lands on something real for the wasm idea below.*
- **"It is the compiler / the glibc static layout."** Refuted by the clang control above.

### What it would take

Not a flag and not a rebuild. Someone has to **write amd64 entry-point discovery** — find
`main` from `_start`/`__libc_start_call_main` on x86-64, where the call is `mov`+`call` with
variable-length encoding rather than a fixed `nop`/`b`/`nop` triple. That is upstream work, or
a patch carried in this repo's submodule. It is tractable and it is not small.

**Upstream has not done it**: `main` is one commit ahead of the pinned `5319dd8` and that
commit is `Bump actions/checkout`. Nothing in the range touches `lifter/`.

**If it ever lands**, the o2-side work is unchanged from what was already written down: widen
`packages/aot/src/elf.ts`'s hardcoded `EM_AARCH64` screen to the machine the selected target
accepts, carry the machine in the cache key so artifacts cannot collide (`elf.real.node.test.ts`
and `elf-fixtures.node.test.ts` gate on `arch() === 'arm64'`), and **re-measure both floors** —
5.40 MiB and 43 ms are properties of elfconv's emitted runtime and machine-state init, and the
x86-64 `State` struct is a different size.

## elfconv ITSELF to wasm — FILED AS PHASE 26, and the open questions are now MEASURED

Owner instruction 2026-08-07: *"compile to Wasm"* (asked as "compile to Wasm to work with
RISC-V" — the reading taken, and confirmed, is **compile elfconv itself**, so it runs on any
host with a wasm engine, RISC-V included; **not** lifting RISC-V binaries).

**Why not "lift RISC-V", stated so it is not re-proposed by accident.** Remill has **no RISC-V
support at all** — `grep -ri riscv` over the whole vendored tree returns nothing. It implements
AArch32, AArch64, PPC, SPARC32/64 and X86. Its Sleigh backend vendors **no `.slaspec`** and is
not wired into this build. Making RISC-V a *source* architecture means writing RV64GC semantics
from scratch, which is a different and far larger project than the five amd64 front-end fixes.

### Measured 2026-08-07 — every line is a reading

| question | answer |
|---|---|
| Reuse the image's LLVM archives? | **No.** `readelf -h` on a `libLLVMCore.a` member: `Machine: Advanced Micro Devices X86-64`. LLVM must be cross-compiled to wasm32-wasi from source — the dominant cost. |
| Full dependency set | Read off `build.ninja`: `libLLVM-16.so.1`, `-lbfd`, `-ldwarf`, `-lelf`, `libgflags.a`, `libglog.a`, `libxed.a`. **Seven ports.** |
| Threads | **Work** — `wasm32-wasi-threads -pthread` built a `std::thread`/`std::mutex` program, 1 175 165 bytes. |
| C++ exceptions | **Absent** — `wasm-ld: undefined symbol: __cxa_allocate_exception`. Survivable: LLVM defaults to `LLVM_ENABLE_EH=OFF`/`RTTI=OFF`, and `utils/Util.cpp:11` **already** has a `#if defined(__wasm__)` branch that `abort()`s instead of throwing, so all 17 error sites funnel through a helper that is already wasm-aware. |
| **Memory64 / the 4 GB ceiling** | **CLOSED, and the answer is no.** wasi-sdk-24.0 has **no `wasm64-wasi` sysroot**; `--target=wasm64-wasi` fails at `'memory' file not found`. The 4 GB address space is a **hard bound on this toolchain** regardless of browser support. Whether it actually binds is still owed: the 900-function static-glibc lift yields 4.4 MB of bitcode, so peak residency may sit well under it. |

**"elfconv to wasm" understates the target and the phase says so.** The pipeline is
ELF → bitcode (`elflift`) then bitcode → wasm (`wasi-sdk clang++` + `lld`). **Both halves are
LLVM.** A node running only the first half still needs a toolchain host for the second, so the
phase must state whether it ships the lifter alone or the whole toolchain, and price them apart.

**Not started.** This is an LLVM cross-build plus six dependency ports; it is filed, measured
and scoped, not begun.

### Prior art settles feasibility — and rules out reusing it

**Wasmer ships the FULL clang compiled to WebAssembly**, running in Chrome, Safari and Firefox
([wasmer.io/posts/clang-in-browser](https://wasmer.io/posts/clang-in-browser)). So *"LLVM cannot
be compiled to wasm"* is **false** and must never be written down as a blocker.

But it targets **WASIX**, not plain WASI, and is **~100 MB uncompressed**. WASIX is a superset
of preview1 adding fork/exec, signals, sockets and setjmp/longjmp-via-asyncify
([announcing-wasix](https://wasmer.io/posts/announcing-wasix)). **This fabric executes
preview1** — V8 plus `@bjorn3/browser_wasi_shim` — so that artifact does not run on this tier.
Feasibility: proven. Reusability: no.

**The reason clang needed WASIX probably does not apply to `elflift`** — inferred, not yet
measured, and labelled that way in the phase. The clang *driver* spawns `cc1` and the linker,
which is fork/exec. `elflift` links LLVM as a **library**, reads one ELF, writes one `.bc`, in
one process. **First experiment of the phase: build `elflift` for wasm32-wasi and find out.**

Stage 2 may dodge the driver too: `llc` + `wasm-ld` are single-process, and elfconv's C++
runtime sources **do not change per job**, so they can be compiled to bitcode once, natively,
and shipped as a fixed input — leaving the fabric a backend and a linker, no frontend.

### Owner idea 2026-08-07 — clang-in-wasm as a DEMO SERVICE

Filed in Phase 26 (item 9). It fits unusually well: compilation is embarrassingly parallel
across translation units, and the **source is the owner's data**, so it compiles on the owner's
node as `owner-attested` and only the artifact crosses egress — the sovereignty split on a
workload people already care about.

**Blocked on the same ABI gap.** Cheapest honest route is shipping `llc` + `wasm-ld` and saying
plainly that the demo compiles **bitcode, not C++**. A WASIX shim in the executor is the route
to **reject unless argued**: it would hand guest code fork/exec and sockets, which is the
sandbox surface Phases 13.1 and 24 spent their effort narrowing. Do not widen it for a demo.

## TWO CONVENTIONS BOUGHT THIS SESSION — both now in CLAUDE.md

- **Restore a plant by SURGICAL INVERSE, not `cp`.** `cp` restores a whole file to a
  snapshot; safe only if you were the sole writer for the whole window, which was false
  twice. **And the hunk count is a ONE-WAY test** — more hunks proves another writer,
  **equal hunks proves nothing** (a plant dropped inside a hunk you already had open leaves
  the count unmoved). `cmp` against a pre-plant snapshot is the check.
- **Agents that plant must not run in parallel on shared source.** Disjoint `files_modified`
  is not sufficient: a plan says what will be *edited*, not what will be *mutated and
  restored*. The cost was not a lost edit but a **false security finding** — one agent read
  another's live plant as an intermittent fail-open in the admission gate; refuting it took
  111 executions, a `node_modules` patch, and a reading of the library's call ordering.
