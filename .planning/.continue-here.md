## THREE FINDINGS THAT REVERSED OUR OWN ANSWERS — read these before touching the RFC

1. **`attenuates` does not exist here, and its absence is a FEATURE.** We first called the missing
   subset check a live defect. It is not. `verifyChain` never compares a link to its parent — it
   tests the **requested** ability against **every** link and folds expiry with `Math.min`. A child
   that widens its abilities is **inert**. The repo reached Biscuit's monotonicity property without
   looking for it. **So a soundness bug in `attenuates` is not a privilege escalation in this
   design** — it is issuance-time hygiene. Keep the fold as the boundary.
2. **The reservation TTL is NOT the revocation surface.** We first said it was the natural expiry
   lever. Wrong on the cardinal rule: `relayIds` is empty when `direct`, so a direct peer holds no
   reservation and the gate never runs for it. A relay-enforced mechanism is keyed on **how a peer
   is discovered**. Short lifetimes survive as the recommendation on the *opposite* ground.
3. **The binding number is not the 30 s floor** — it is `certificateLifetimeMs` defaulting to
   **30 days**, three orders of magnitude coarser than the mechanism enforcing it. Recommended 1 h,
   sited against the existing `DEFAULT_ISSUANCE_WINDOW_MS`.

## THE LARGEST STRUCTURAL FINDING

**§9's registration protocol cannot be implemented as written.** `denyInboundRelayReservation`
receives a `PeerId` **and nothing else**; the HOP `RESERVE` message carries no certificate field
and there is no reply channel for a challenge. Every element of §9's signed payload has no
carrier. What exists instead is **stronger**: a peer id derived from an Ed25519 key *is* the node
key, already proved over Noise, available with **zero I/O**, and channel-bound in a way a
nonce-signature is not.

## ONE REAL DEFECT SURFACED (not just a doc issue)

`possessionChallenge` is `encodeCanonical({ purpose: 'o2-enrol', nodeKey, userKey })` — **static.
No nonce, no timestamp, no server input.** An observed enrolment request is a fixed replayable
byte string; the only control is `IssuanceBudget`. Praxis is right about the defect and wrong
about the placement: it belongs at the **enrolment RPC**, not the gater.

## A SECOND, LARGER REVOCATION HOLE THAN THE ONE ASKED ABOUT

`peer-verifier.ts`: *"A settled acceptance is never re-asked."* For block-fetch selection the
window is the **connection lifetime**, not the certificate lifetime. Asymmetric by design —
`expired` sits outside `FINAL` so a refusal can be promoted, but nothing demotes an acceptance.
Minimum fix: re-ask a settled acceptance once its `expiresAt` passes. **Fabric-wide, owner-ruling
class.**

## NEXT STEP — the reviewer named it and it is the right one

A small **RFC-0003 testable profile**, not code: an exact `AuthorityRule` schema + attenuation

## A FOURTH OWNER RULING, ON TOP OF THE THREE ALREADY OWED

**Is X.509 worth its cost here?** Adopting it ships an ASN.1 parser into the **browser** trust
path. Today's surface is `@noble/curves` + `@ipld/dag-cbor`, both already present; `pkijs` +
`asn1js` is a few hundred KB of exactly the code that generates CVE classes, at the one boundary
that must fail closed. And `critical` extensions buy little — there is **no generic validator** in
this system, every verifier is this project's own code against pinned anchors, while the one place
a standard validator would sit (§2's optional external CA) is guaranteed to reject a chain
carrying critical unknown extensions. **§2 and §4 pull against each other.**
