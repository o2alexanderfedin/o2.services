## The production bug, which is why the branch mattered

`rpcAdmission` **could never admit the node running it.** It asked itself over RPC and the
transport correctly answered `Can not dial self`, so every shard carried
`unreachable: … Can not dial self` against the submitter's own id.

It hid because every caller until now was a **pure requestor outside its own candidate
pool** — `bin/bench.ts:1885` and every fixture in `discovery.test.ts`. A browser tab both
submits *and* executes, so CHURN-04 wiring `admit` into the demo exposed it, and six
requirement cases across DEMO-01, NET-06 and VER-09/VER-10 failed at once.

Fixed at `d547e6c`: `rpcAdmission` takes a `local` port and answers a self-addressed offer
from it — the same non-reserving `would()` call `serveAgent` makes for a remote peer. Given
no port it refuses **by name**, because the transport error is what sent the investigation
to the wrong layer for an hour.

## What NOT to do, each earned

- **Do not widen `TIMEOUT_MARGIN`, `RPC_TIMEOUT_MS`, or VER-10's assertion string.** Every
  one survived this session untouched. Three reds now name their own regime instead.
- **Do not polyfill a non-extractable key.** Any JS implementation holds the material where
  the origin can read it, so a shim supplies the API shape without the property — worse than
  absence, because it looks safe. `subtle-digest-fallback.ts` installs `digest` and nothing
  else for the same family of reason.
- **Do not add an export with no production caller** to dodge a refactor's cost.
  `reachability-guard.node.test.ts` reddens on exactly that, and it is the trap that has
  caught this work before.

## The specification, kept for its cost estimate and its open questions

**Task #21 (visitor identity) is no longer blocked on cryptography.** Measured 2026-08-16 in
chromium, firefox and webkit on a plain `http://127.0.0.1` origin, **no HTTPS**:

- `generateKey({name:'Ed25519'}, extractable=false, …)` succeeds in all three
- **`exportKey('pkcs8', privateKey)` is REFUSED in all three** — the origin serving the page
  cannot read the key, which is the direct answer to why design round 1 was rejected
- the signature **verifies under `@noble/curves`**, which is what the provider uses

Full working: `.planning/consults/2026-08-16-visitor-device-key-is-cryptographically-available.md`

**`localhost` and `127.0.0.1` ARE secure contexts**, and the e2e harness already serves the
demo from one — so this is buildable and provable today. Task #24's HTTPS is needed for **a
phone on the LAN and nothing else**. My earlier "blocked on HTTPS" framing was too broad.

### The blocker is an API, not the platform

`requestEnrollment` (`packages/core/src/enrollment.ts:398`) takes `userPrivateKey: Uint8Array`
and uses it for exactly two things — `ed25519.getPublicKey` at `:407`, `ed25519.sign` at
`:417`. A `CryptoKey` does both and **can never produce those bytes.**

```ts
interface UserSigner { readonly userKey: PublicKeyHex; sign(message: Uint8Array): Promise<Uint8Array> }
```

**Cost, measured so it is budgeted rather than discovered:** 2 production call sites
(`browser-node.ts:640`, `fabric-node.ts:1111`), ~15 test files calling `requestEnrollment(`,
and WebCrypto signing is async so the function must become async and every caller must
`await`. Roughly 30 mechanical edits, then `--project node` and `--project browser`.

**Still open and NOT answered by any of this:** whether accepting a certificate should pin
its issuer — the objection that killed design round 2 — and where the key lives across
sessions (IndexedDB stores `CryptoKey` handles structurally; unmeasured here).
