# OPEN DECISION 1 — the integration timeout ordering. **I tried this and broke it.**

`tools/aot/lift.node.test.ts` holds `INTEGRATION_TIMEOUT_MS = 15 min` (:1091) around a
`beforeAll` that runs a 5-minute compile plus two `liftElf` calls on the shipped
`DEFAULT_TIMEOUT_MS` of 20 min each (`lift.ts:108`). **45 minutes of internal budget inside
a 15-minute framework budget**, so the framework is always the timer that fires and a wedge
reports `Test timed out`, naming no step.

**Do not "just fix" this. I did, and six integration tests went red.**

I passed an explicit `timeoutMs: 5 * 60 * 1000` to both lifts and raised the outer bound to
20 min. Result: `AssertionError: elfconv did not finish within 300s`, six failures, 639 s
run. **Reverted; the tree above is the working version.**

The mistake was sizing against "~95 s", a figure taken from this file's own comment and from
an agent's report — a quiet-host number I never measured myself. **The one real datum this
produced: a lift exceeds 300 s at load average 89.**

So the trade-off is real, and it is the one originally stated:

- **Leave it.** A wedge hangs at most 15 min but is reported as an anonymous framework
  timeout. This is the shipped state and it has never actually bitten — a lift measures
  ~95 s on a quiet host.
- **Fix the ordering.** Needs a lift budget well north of 5 min, hence an outer bound well
  north of 15 min, hence a longer worst-case hang. A middle exists — e.g. lifts at N min,
  outer at N*2+5 — but **N must be measured first, at representative load.**

**Before setting any number here, time a real lift.** That is the whole lesson.

# OPEN DECISION 2 — perf test for elfconv-lifted native code (this is AOT-04)

Asked for: end-to-end timing, task dispatched by a node through to results received, for
elfconv-converted native code. **It cannot be measured today**, for two reasons that were
checked rather than assumed:

1. **No lifted artifact returns a result the fabric accepts.**
   `packages/aot/src/wasi-real.node.test.ts:147` runs a real artifact — it instantiates,
   `_start` runs to completion, the guest writes bytes — and the test's own assertion is
   that the outcome is a **failure**, `not-dag-cbor`. A lifted hello-world writes ASCII;
   the result path requires canonical dag-cbor. There is no "result received" to time.
2. **No production node can construct the executor.** `grep WasiExecutor packages/node/src
   packages/browser/src` returns nothing, and `@o2/node` does not depend on `@o2/aot` at
   all. `WasiExecutor` *does* `implements Executor` (`wasi-executor.ts:739`), so it is a
   drop-in — it is simply never dropped in.

This is exactly what `REQUIREMENTS.md:341` records: **AOT-04 unchecked**, blocker stated as
*"a production node able to construct a `WasiExecutor`"*.

**What building it takes:**

1. A lifted binary that returns a real answer. The integration `beforeAll` already compiles
   C inside the elfconv container (`int main(void){ return 42; }`); emitting dag-cbor
   instead is trivial C — the integer 42 is the two bytes `0x18 0x2a`. That turns
   `not-dag-cbor` into an accepted result.
2. Wire `WasiExecutor` into a node so a dispatched task can reach it.
3. Measure the full leg, following the existing `packages/bench` methodology, which is
   already sound: median of 20 runs, p50 gated, p95 recorded-not-gated, plus a paired ratio
   that survives CPU contention (`perf-baseline.ts` documents why).

**A cheaper first step, if the full phase is not wanted:** time a real lifted artifact
through `WasiExecutor` standalone. It runs to completion today, so this yields a genuine
execution number for elfconv code, separates execution cost from fabric overhead, and
produces the lift-duration datum Decision 1 needs. Not started — awaiting a decision.

# THE RULES THIS SESSION COST THE MOST TO LEARN

1. **A test arms two clocks — its own internal budget and the framework's `testTimeout` —
   and the framework's must be the larger.** Inverted, the internal timer can never fire and
   a wedge reports nothing. Four files had this backwards in both directions, and **two of
   the inversions were introduced while fixing the opposite error in a different file.**
   Written into the headers of `worker-executor.browser.test.ts` and `lift.node.test.ts`.
2. **Size a bound against the worst case the file can construct, not the typical one.**
   `kernel.test.ts` got 60 s chosen against its ~25 s idle cost — the exact mistake the
   comment being written at that moment warned against. It failed hours later and is now
   120 s.
3. **Never set a timing bound from a number you did not measure yourself.** Broken three
   times this session; the third broke tests (Decision 1 above).
4. **Check `uptime` before trusting any suite reading.** Another project held this host at
   load 30-160 on 8 cores all session. A reading taken at load 130 is not a reading.

# HARNESS LESSONS

- **A `pipeline()` stage returning `null` DROPS the item** and skips its remaining stages. A
  conditional "skip the design contest for uncontested items" silently killed 5 of 6 work
  items; only 5 of 21 agents ran. Return a sentinel object, never `null`.
- **An agent can die on its structured output *after* doing the work.** B18's implementation
  sat in the tree with no report and no verification. **Always `git status` after a workflow
  and account for every changed file**, including from agents that errored.
- **Two long background runs were killed mid-flight** by the harness. `nohup sh -c '...' &`
  survives; a plain background tool call did not.
