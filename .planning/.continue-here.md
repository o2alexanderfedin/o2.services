### The three fixed causes, in order

1. **`set -e` hid the first failure entirely.** It exits on the failing `cmake` line *before*
   the `EXIT=$?` that reads it, so a real failure printed nothing and looked like a clean
   finish. Removed. Every command now reads its own code on the next line, no pipe.
2. **`llvm-min-tblgen` does not exist in LLVM 16** — it arrives in 17. `ninja: error: unknown
   target`. That was the actual first failure, invisible because of (1).
3. **LLVM 16 predates WASI.** cmake does not set `UNIX` for `CMAKE_SYSTEM_NAME=WASI`, so
   `HandleLLVMOptions.cmake:150` reaches `MESSAGE(SEND_ERROR "Unable to determine platform")`.
   One-line patch; LLVM 17 has the branch upstream.

### NET-03 is the one finished feature

The blocker — *"AutoTLS needs a publicly reachable host with a real DNS name"* — was a fact
about **Let's Encrypt** restated as a fact about the mechanism. The owner said so and was
right. `local-acme.ts` is a real RFC 8555 authority on loopback: every JWS verified against
the account's own RSA key, a UDP DNS zone the CA genuinely queries for the dns-01 record, and
a p2p-forge stand-in that authenticates callers through libp2p's own PeerID-auth handshake.
`@ipshipyard/libp2p-auto-tls` runs against it unmodified.

Two findings the code carries: **`announce` suppresses the certified address** (address-manager
returns the announce list and returns early, never reaching the DNS-mapping fold — the option
is `appendAnnounce`), and libp2p publishes the certified name as an **SNI component inside an
existing `/tls` address**, not as `/dns4`.

### AOTW-06 — libc++ was the wall, not glog

6/27 → 27/27 on threadless preview1, in three steps:

```
 6/27  glog/logging.h:51 includes <thread>; libc++ #errors the whole header
13/27  glog's own INTERFACE names std::thread::id at logging.h:123
27/27  remill's ArchLocker needs std::mutex; LLVM's RWMutex <shared_mutex>
```

`lock_guard`, `unique_lock` and the lock tag types reference **no** `__libcpp_*` symbol and are
gated anyway. Only `std::mutex` genuinely wraps `__libcpp_mutex_t`, and with no second thread
a no-op is the correct implementation, not a stub.

**And none of it was needed:** `llvm-nm --undefined-only` over all 27 objects finds **zero**
references to `pthread_create`, `thread_spawn`, `pthread_join` or any `std::thread` member.
That measurement retires two claims made earlier in the session — that threads would break
determinism here, and that the threads route needed a wasi-threads host. Neither survives a
translator that never creates a thread.

## Ideas raised that are worth keeping

- **Run elflift as a reactor, not a process.** `main()` is ~100 lines and only four are
  process-shaped; with a memory filesystem the two I/O ends need no C++ change at all.
  `link-elflift-wasm.sh` has `MODE=reactor` ready for when `elfconv_lift` exists.
  **The strong argument is determinism**: a wasm module's linear memory is flat and
  program-determined, so elfconv's pointer-keyed iteration — the *structural* cause of
  AOT-03's `CROSS_MACHINE_BLIND_SPOT` — stops varying. This may fix a hole the project
  currently carries as unfixable.
- **Bootstrap: lift elflift with elfconv.** Static link spike FAILED at cmake configure,
  undiagnosed. Even if it worked: ~6 h, ~300 MB of wasm, ~10 000 untranslated addresses
  extrapolated from hello_static's 174. Not the shipping path.
- **COOP/COEP via service worker** (coi-serviceworker) genuinely works on GitHub Pages, but
  is the wrong lever here — the threads target was never about wanting threads.
- **Emscripten route**: 5 of 6 LLVM archives already built at
  `hapyy/libclang-wasm/out/build/lib`, and glog already has an `__EMSCRIPTEN__` branch. About
  a day to a working translator that needs JS glue and won't run under preview1. The fallback
  if the WASI build proves too costly.
