## THE RULE THAT CAME OUT OF ALL THIS — read it before touching any timing bound

**A test arms two clocks: its own internal budget, and the framework's `testTimeout`. The
framework's must be the larger.** Inverted, the internal timer can never be the one that
fires, so a case that means to observe a bound — or to be immune to one — dies as
`Test timed out`, which names nothing and asserts nothing.

Four files were wrong about this, in both directions, and **two of the inversions were
introduced by me tonight while fixing the opposite error in a different file**. That is the
reason the rule is now written into the headers of `worker-executor.browser.test.ts` and
`tools/aot/lift.node.test.ts` rather than merely corrected in place.

Second rule, from the same wreckage: **size a bound against the worst case the file can
construct, not the typical one.** `kernel.test.ts` got 60 s chosen against the ~25 s it
measures idle — which is precisely the mistake the comment being written at that moment
warned about. It failed hours later at 60 s and is now 120 s.

Fixed in `30d9823`, `c30c33e` and `24935ef`:

- `worker-executor.browser.test.ts` — four pairs of `deadlineMs: 60_000` inside `}, 30_000)`,
  now 60 s inside 120 s.
- `tools/aot/lift.node.test.ts` — six cases handed `resolveImage` a budget of *exactly* the
  5000 ms framework default; two more passed a 700 ms total lift budget that a contended
  process spawn beats on its own. Measured: 40 spawns of the stub cost p50 200 ms, max
  **425 ms**. Now named constants bounded on both sides. Verified **73/73 at load 104–163**.
- `named-refusal.node.test.ts` — asserted a refusal in under 1,000 ms when the property is
  "not the 30 s RPC budget expiring". Measured 2815 ms: still 10× under the budget, so the
  property held and the 30× proxy failed anyway. Now a third of the budget, named.
- `kernel.test.ts`, `worker.browser.test.ts` — watchdogs sized to the typical case; both 120 s.

## STILL OPEN FOR THE OWNER — an inverted race in the integration block

`tools/aot/lift.node.test.ts`'s integration `beforeAll` (~line 1114) has the same defect the
other direction, and worse: `INTEGRATION_TIMEOUT_MS` is 15 min, while the work inside it is a
5 min compile plus two `liftElf` calls at `DEFAULT_TIMEOUT_MS` = 20 min each — **45 min of
internal budget inside a 15 min framework budget**, so the driver's `timed-out` classification
can never be reported at all.

It has never fired because a lift measures ~90 s, but the margin is shrinking under exactly
these conditions: ~215 s on a quiet run (4× under budget), **~395 s at load 150 (2.3× under)**.

Not fixed, deliberately, because both answers trade one risk for another: raising the hook
above 45 min means a genuinely wedged lift hangs for three-quarters of an hour, while passing
an explicit small `timeoutMs` stops the block exercising the shipped default — arguably its
whole point. **That is a judgement about what the integration block is for. Owner's call.**

## FIXED — `tools/aot/lift.node.test.ts` (was pre-existing, NOT caused by this branch)

**8 of 73 tests fail reproducibly** — in the full suite *and* in isolation (`Tests 8 failed | 65
passed`). This is NOT a flake, and the diagnosis is complete. An agent is fixing it; if that
work is lost, everything needed is here.

The file declares **zero** timeouts, and makes **48 real `docker` invocations via `execFileSync`**
(per `vitest.config.ts`, which clocks it at 217 s). Two distinct mechanisms:

1. **Six tests: an internal budget equal to the framework's budget.** Durations of 5006/5002/5003
   ms against the node project's 5000 ms default `testTimeout` — while lines 725, 769, 782, 792,
   888, 923 call `resolveImage(..., 5_000)`. **The driver's own timeout can never fire before
   vitest kills the test.** A race the test can only lose. These tests assert *classification*
   (`failure.kind === 'image-digest-foreign'`), not timing, so their budgets should be generous.
2. **Two tests: a budget smaller than a contended `spawn`.** `expected 'docker-unavailable' to be
   'timed-out'` at ~707 ms. Lines 818/852 pass `timeoutMs: 700`, line 870 passes `400`.
   `stubDocker` (:638) writes a `#!/bin/sh` to `tmpdir()` and the driver spawns it; under
   contention that spawn alone exceeds the whole 700 ms lift budget, so the driver never reaches
   the `run` it is meant to time out on. These two *are* about timing, so their budget must stay
   far below the stub's `exec sleep 30` while comfortably exceeding spawn latency.

**Proof it is not simple per-test load:** the single case `-t "does not mistake a registry port
for a tag"` **passes in 3.3 s at load average 37.88**, and fails when the whole file runs. The
file's own 48 spawns plus external load is what beats these budgets.

Docker itself is healthy — `docker info` returned in **0.078 s**.

**Before re-running the full suite: check `uptime` and `pgrep -f clang`.** A reading taken at
load 31 on 8 cores is not a reading. This cost two full-suite runs tonight (~11 min) and an hour
of the previous session.

# HARNESS LESSONS FROM THIS SESSION

- **A `pipeline()` stage returning `null` DROPS the item and skips its remaining stages.** A
  conditional "skip the design contest for uncontested items" silently killed 5 of 6 work items;
  only 5 of 21 agents ran. Never return `null` from a stage — return a sentinel object.
- **An agent can die on its structured output *after* doing the work.** B18's implementation was
  sitting in the tree with no report and no verification. **Always `git status` after a workflow
  and account for every changed file**, including from agents that errored.
- **Cost control worked.** Giving the full-suite duty to the orchestrator instead of to every
  agent, and running one design contest instead of six, brought this round in at roughly 40 min
  of agent time against 4h28m for the previous one.
