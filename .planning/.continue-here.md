## The next feature, designed — G3 and G4 are ONE piece of work

`packages/demo/src/pi.ts` exists to *"project a partial into the partial shape **the fabric's one
combiner accepts**"* — **π is a reduce workload**. Colouring cannot demonstrate a verified reduce
because it is first-found-wins, which is exactly why `answerOf` is correct for it. So wiring π as a
second demo workload whose merge goes through `reduceJob` closes **G4** (the workload) *and* **G3**
(the verified tree-reduce), and moves the demo half of MR-03…MR-07 off `Partial`.

Shape: submit π shards → `reduceJob(job, {rpc, executors: peerIds, blockstore: node.store,
project: projectPiPartial, trustedIssuers})` → `estimatePi(total)` against `piErrorBound(terms)`.

**Two blockers found by reading, both of which change the cost:**

1. **THE TRUST ROOT — needs the owner's explicit sign-off.** There is **no signed record for the π
   kernel**, and `kernel-record.ts` states that `sign-kernel.ts` *"generates a new ed25519 key on
   every run and discards the private half immediately"*. There is exactly one anchor, and
   **`bin/agent.ts` and `bin/seed.ts` both default to `KERNEL_TRUST_ANCHOR`** — so a π record signed
   by any other key is refused by a stock agent. Adding π means extending `sign-kernel.ts` to sign
   *both* kernels under one new key and committing the new anchor and both records **together**.
   That changes what every stock node will run. Do not start it without that sign-off.
2. **A lone visitor cannot run it.** `reduce-job.ts:385` returns
   `{ok: false, reason: 'no executor to combine on'}` for an empty executor set, and the submitter
   is deliberately excluded. The panel should render that named reason — but the headline claim
   only appears when a second device is present. `runColouring`'s analogue is
   `onQuorumShortfall: 'runs-at-available-redundancy'`; the reduce path has no such degradation.
