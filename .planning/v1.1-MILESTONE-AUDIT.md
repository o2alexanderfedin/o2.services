### Item 1 was attempted 2026-08-18 and `bin/bench.ts` is REFUTED as the host — measured twice

Phase 20's gap plan G1 named `bin/bench.ts` as *"the natural site"* for criterion 7's write half
**on the premise that it already opens a durable `FsBlockstore`**. That premise is false and this
file's own source says so: `realFabric` builds every node under `mkdtemp(tmpdir(), 'o2-bench-')`
and `release()` ends with `rm(root, …)`, so *"a handle published from here would name a block that
no longer exists by the time anything could resume from it."*

A `--checkpoint-dir` flag was built to answer that — a caller-named root the rig does not delete —
and it **worked for the write half**: a run published confirmed handles (each round-tripped through
`readCheckpoint`) and the directory survived with `node-0`, `node-1`, `requestor` in it. Both
refusal arms fired correctly.

**The read half is where it fails, and the cause is structural rather than a bug.** `bin/bench.ts`
is a multi-workload *sweep*: it submits many jobs, and a job id is derived from its input CIDs, so
one handle cannot name them all. Applying a single `--resume-from` to the sweep made `resumeState`
refuse every rung with `checkpoint-names-another-job`; every job returned `ok: false`; and the
driver **printed a full benchmark report over nothing and exited 0** — 61 lines, zero attestations,
`BENCHMARK-RESULTS.md` written. Collapsing the ladder to one job to fix that then tripped the
driver's *own* `HarnessIntegrityError`: *"the shard status vector is empty against a rung of 16
shards … an instrument that read nothing rather than a fixture that ran uniformly."*

**The instrument refused the shape, which is the instrument working.** The change was reverted
whole — `bin/bench.ts` is byte-identical to its pre-attempt state (`cmp` exit 0), and the two
benchmark artifacts the runs overwrote were restored.

**Where the supplier belongs instead, and the demo's own source already named the missing piece.**
`demo/main.ts` writes checkpoints into an `IdbBlockstore` that survives the tab closing, and one
Run is one job — the single-job property the sweep lacks. Its comment states the remaining gap
precisely: *"A blockstore is content-addressed, so there is no stable key under which the newest
handle could be left for a returning tab to find … discovering that CID unaided needs a **mutable
key space this port does not have**."*

So closing B4 needs three things, none of them in `bin/bench.ts`:
1. **Export `jobIdOf`** from `@o2/core` — it is `async function jobIdOf` at `submit.ts:1266`, module-private today, and without it a page cannot compute the key it would file a handle under.
2. **A mutable one-record store** for `jobId → newest handle` (the tab already has `IdbIdentityStore` as precedent for a small mutable store beside the blockstore).
3. **Pass `resumeFrom` on the next run of a matching job.** Keying by job id is what avoids the failure mode measured above: an unkeyed handle produces `checkpoint-names-another-job`, and `demo/main.ts` turns that into a thrown `submit failed`.

This is a **correction to G1's routing, not a descope**: the write half is closed on the demo path
already, and the read half now has a scoped design instead of a site that cannot host it.

### B4 is CLOSED — the three items above were built on the demo path, 2026-08-17

All three, in order, and nothing else was needed:

1. `jobIdOf` is exported from `@o2/core` (`submit.ts:1266`, `index.ts`). Its own docblock carries
   why the scope changed and what the second-derivation hazard is.
2. `packages/browser/src/idb-checkpoints.ts` — `IdbCheckpoints`, `jobId → newest confirmed
   handle`, a separate IndexedDB database named `${blockstoreName}-checkpoints` on the same
   convention `-identity`, `-sovereign` and `-issuance` already use.
3. `demo/main.ts#runColouring` looks the handle up before submitting, reads it back through
   `readCheckpoint` first — so an evicted block forgets the pointer instead of throwing
   `submit failed` at a visitor — passes `resumeFrom`, and files the newest **confirmed** handle
   afterwards.

**Measured, not asserted.** `colouring-demo.e2e.test.ts` runs one job twice in one tab through
`window.o2.runColouring`: the second run is offered exactly the handle the first stored, carries
9 of 9 cubes as `carried-from-checkpoint`, still finds the answer, reports `complete: false`
(a carried shard is `agreed` at `replicas: 0`), and finishes faster than the first. The wiring
line was planted to a no-op and that case failed alone — *"expected +0 to be 9"* — then was
restored by the surgical inverse with `cmp` exit 0.

It is also **visible**: C23 `colouring/resume` renders it on the colouring surface, UI-SPEC §5.6,
because a resume nobody can see is a resume nobody can tell from a restart.

`break_at: packages/core/src/job/submit.ts:2428` now has a production supplier at
`packages/browser/demo/main.ts:1324`. What remains open under CHURN-03 is narrower and is not
B4: `checkpointChain` and `remainingWork` still have no production caller, and six of the seven
