# Phase 14 — Signed Artifact Resolution · Plan 03

**Closes (in part):** DET-03, DATA-08 — the Node tier's half
**Wave:** 3 · **Depends on:** 14-01, 14-02 · **Autonomous:** yes

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

Wiring. This is the plan where `signName`/`SignedNameResolver` stop being unreached.

The production call site added: `packages/node/src/fabric-node.ts`, inside
`FabricNode.start`'s single executor composition, at the line that today reads
`registerSovereignInputs(guardSovereignty(new WasmExecutor(...), sovereignty), ...)`.
The tests that fail if that call site is deleted, in the order they would notice:
`packages/node/src/trust-anchors.node.test.ts` (Task 3 below), whose comment-stripped
assertion that `guardModuleProvenance(` appears in `fabric-node.ts` fires in seconds; and
`packages/node/src/signed-artifact.node.test.ts` (Plan 14-05), where all four refusal
assertions turn green-to-red across real spawned processes, because a `FabricNode` with
anchors and no guard executes everything. The first catches the deletion; only the second
catches a call left in place that does nothing.

<objective>
Give `guardModuleProvenance` a production caller on the Node tier, and make the
absence of one impossible to arrange by accident.

`FabricNodeOptions.trustAnchors` is **required**, and its type is
`readonly PublicKeyHex[] | 'runs-unsigned-artifacts'`. That shape is not decoration:
it is `AgentOptions`'s own convention (`authorize: Authorizer |
'serves-unauthenticated'`, and five siblings), adopted in Phase 11 against
`.planning/PROJECT.md`'s Key Decision **"An optional hook with a silent default is a
hole"**. An optional `trustAnchors` defaulting to something would be exactly that hole:
whichever default were chosen, a node would get it without anyone deciding, and the
existing `FabricNode.start`/`SeedServer.start` call sites would not have to say which one
they meant.

This is per-node **configuration**, not a node kind. Every `FabricNode` has the
identical executor, transport, relay behaviour and protocol surface regardless of what
is passed here — a node has simply been told, or not told, which key it trusts, exactly
as `--owner-id` states a clearance without defining a class. Nothing anywhere branches
on what kind of node something is; the only branch is over a value an operator supplied.

**And the two binaries carry the identical default, which is the correction this plan
was revised to make.** An earlier draft had `bin/agent.ts` default to `[]` and
`bin/seed.ts` default to `[KERNEL_TRUST_ANCHOR]`. The code-level claim above was still
true, but the shipped behaviour was not: two processes started with no flags would have
answered the same dispatch differently, and the difference was not discovery. Worse, the
`[]` side was useless — a stock `o2 agent` could execute nothing at all, from any
publisher, and the plan removed its only escape hatch in the same breath. So both
binaries now write the same expression, `values['trust-anchor'] ?? [KERNEL_TRUST_ANCHOR]`,
and both import that anchor from `@o2/demo`.

Why that value rather than `[]` on both: `packages/browser/demo/index.html:311` feeds
`window.o2.computePeers()` straight into `runColouring`'s `peerIds`, so a seed a visitor's
tab is connected to **does** receive real kernel dispatches in a LAN run. A pair of
binaries defaulting to `[]` would leave DEMO-01 failing in the field with every test in
this repository green — which is the exact class of defect this phase exists to remove.
The demo key's private half is minted and discarded per regeneration (14-02 Task 3), so
this default can never authorise anything except the artifact this repository committed:
out of the box both binaries run exactly one module and refuse every other, and an
operator who wants a different authority passes `--trust-anchor`, which **replaces** the
default rather than adding to it.

Purpose: DET-03's criterion 1 says a production node refuses a bare CID. That is a
property of how nodes are built, not of how they are used.
Output: the guard composed in `FabricNode`; the same `--trust-anchor` flag and the same
default on both binaries; a benchmark whose signed call sites are guarded by a
comment-stripped source requirement; and a scan that keeps the opt-out inside tests.
</objective>
