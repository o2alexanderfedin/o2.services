# Phase 14 — Signed Artifact Resolution · Plan 05

**Closes:** DET-03, DATA-08 — the criterion-3 proof
**Wave:** 4 · **Depends on:** 14-03 · **Autonomous:** yes

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

No new mechanism. Plan 14-01 built the guard and watched it fail under three planted
defects; Plan 14-03 composed it into `FabricNode` and gave `bin/agent.ts` its
`--trust-anchor` flag. What is still missing is the thing ROADMAP criterion 3 asks for
in as many words: *"Running `bin/agent.ts` against a real signed artifact resolves and
executes it end to end, proving `signName`/`SignedNameResolver` sit on the production
dispatch path rather than only in their own spec."*

This plan is that proof, in the evidentiary form this repository has settled on for
that phrase. "Started via `bin/agent.ts`" means what `sovereignty-placement.node.test.ts`
and `egress-refusal.node.test.ts` established it means: the node under test is a genuine
operating-system process spawned from that binary, sharing nothing with the test process
but a socket. The submitter is a `FabricNode` in the test process, because the binary is
serving-only and never calls `submitJob` — there is no second process it could be.

<objective>
Prove all three ROADMAP criteria across a real process boundary, and prove the
"before `WebAssembly.instantiate`" half of criterion 2 with an instrument that exists on
the far side of that boundary rather than with an argument about layering.

The instrument: the agent's own blockstore directory. `FsBlockstore` writes one file
per block, named by its CID string (`fs-blockstore.ts:101-103`). `WasmExecutor`'s first
act is `blockstore.get(task.moduleCid)`, and the agent's blockstore is a
`FetchingBlockstore` that pulls a missing block from its peers and writes it to the
local store on the way through (`block.ts:120`). So the module block appearing in the
agent's directory is a direct reading of "this process went and got the module's bytes",
and its absence is a direct reading of "it did not". A guard that refuses before
`inner.execute` produces the second; a guard that refuses after would produce the first.

Purpose: everything before this plan is a claim about wiring. This is the measurement.
Output: one new `.node.test.ts` spawning real agent processes, with six readings and no
new production code.
</objective>

## Out of scope

- Observing `WebAssembly.instantiate` itself. No test in any process can, and this plan
  does not pretend to. The blockstore-directory reading proves the bytes were never
  fetched, which is not the same statement as "nothing was instantiated"; the file header
  says which one it makes, in those words. The complementary reading — the executor was
  never called — is `module-provenance.test.ts`'s call counter, in a different process and
  a different plan.
- A second machine. Same machine, different operating-system processes is this project's
  testing standard, and it is the standard this file meets.
- The browser tier's equivalent, which is Plan 14-04's `two-tabs.e2e.test.ts` refusal
  case between two real browser contexts.
- `packages/net`'s in-process fabrics. Their subject is the protocol; they compose their
  own executors and are unaffected by how a `FabricNode` composes its.
- Spawning `bin/seed.ts`. Its no-flag runtime behaviour is unmeasured here, and the reason
  and the recipe are both written down above rather than left as a gap to be found.
