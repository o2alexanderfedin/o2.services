# Phase 14 — Signed Artifact Resolution · Plan 01

**Closes (in part):** DET-03, DATA-08
**Wave:** 1 · **Depends on:** nothing · **Autonomous:** yes

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

The mechanism. `signName`/`SignedNameResolver` have been correct and unreached since
Phase 4. This plan builds the one thing standing between them and the dispatch path:
an `Executor` adapter that refuses before the module's bytes can become a
`WebAssembly.Module`. Nothing is wired here — Plans 14-03 and 14-04 do that. This plan
proves the mechanism is right, and proves it by watching it fail.

<objective>
Add `Task.moduleRecord` and `guardModuleProvenance`, the adapter that makes
"resolving a bare CID is refused" a property of the executor rather than a hope about
its callers.

Purpose: **three** `Executor` implementations independently turn `task.moduleCid` into
bytes, each with its own `blockstore.get(task.moduleCid)` —
`packages/core/src/executor/wasm.ts:62`, `packages/browser/src/worker-executor.ts:123`
and `packages/aot/src/wasi-executor.ts:794`. Checked by grep before this sentence was
written, because an earlier draft of this plan and of 14-CONTEXT.md said `wasm.ts:62`
was *the only* such line, and that is false: `WorkerExecutor` fetches the module on the
main thread and posts the bytes to its Worker, and `WasiExecutor` is a second `Executor`
that fetches its own. So the guarantee this adapter carries is not "one resolution
point"; it is "wrapped at every construction site". 14-03 wraps the Node tier's site,
14-04 wraps the browser's whole `worker ?? new WasmExecutor(...)` expression so the
`WorkerExecutor` arm cannot be the unguarded one, and `WasiExecutor` has no production
caller at all today — `new WasiExecutor(` occurs only in `packages/aot/src/*.test.ts`.
Phase 21 is scheduled to give it one, so 14-03 Task 3 adds a census that turns "we
enumerated three" from an assertion into a test that fails when a fourth resolver
appears or when the AOT executor is constructed outside a test.
Output: `guardModuleProvenance`, `ModuleRefusal`, `describeModuleRefusal`, exported
from `@o2/core`; `Task.moduleRecord`; and three planted mutations watched failing.
</objective>

export interface NameRecord {
  readonly name: string
  readonly cid: CID
  readonly version: number
  readonly expiresAt: number
  readonly signer: PublicKeyHex
  readonly signature: string
}
export function signName(privateKey: Uint8Array, fields: Omit<NameRecord, 'signature' | 'signer'>): NameRecord
export type ResolveFailure =
  | { kind: 'unknown-name'; name: string }
  | { kind: 'untrusted-signer'; name: string; signer: PublicKeyHex }
  | { kind: 'bad-signature'; name: string; signer: PublicKeyHex }
  | { kind: 'expired'; name: string; expiresAt: number; now: number }
  | { kind: 'rollback'; name: string; have: number; offered: number }
export function describeResolveFailure(failure: ResolveFailure): string
export type ResolveResult =
  | { ok: true; cid: CID }
  | { ok: false; failure: ResolveFailure; reason: string }
export class SignedNameResolver {
  constructor(trustAnchors: Iterable<PublicKeyHex>)
  get trustAnchors(): readonly PublicKeyHex[]
  accept(record: NameRecord, now: number): ResolveResult   // verifies AND stores
  resolve(name: string, now: number): ResolveResult        // reads what was stored
}

    Export `ModuleRefusal`, a discriminated union with exactly three variants:
    `{kind: 'no-record', moduleCid: string}`, `{kind: 'unresolvable', failure:
    ResolveFailure, reason: string}`, and `{kind: 'cid-mismatch', name: string, signed:
    string, dispatched: string}`.

    **Record the type decision in the module comment, because 14-CONTEXT.md Risk 2
    leaves it open and the alternative is the one a reader will expect.** The mismatch
    case is *not* added as a sixth `ResolveFailure` variant in `naming.ts`. The usual
    argument for putting it there — that widening an exhaustively-switched union makes
    every consumer fail loudly until updated — buys nothing here, because
    `ResolveFailure` has exactly one consumer (`describeResolveFailure`, in the same
    file), so there is no distant switch to make fail. What it would cost is real: a
    variant `SignedNameResolver` can never itself return, sitting in the resolver's own
    failure type, which is a false statement about that type. The mismatch is not a
    resolution failure at all — resolution succeeded; it is the *dispatcher* that
    attached a record for a different artifact. So it lives with the code that can
    detect it. Say this in the comment in those terms.

    Export `describeModuleRefusal(refusal: ModuleRefusal): string`, an exhaustive switch
    with no `default` arm (matching `describeResolveFailure`'s shape, so a new variant is
    a compile error rather than a silent fallthrough):
      - `no-record` → wording that names the CID and states plainly that a bare CID names
        bytes and not a publisher, and that no signed name record arrived with it. ROADMAP
        criterion 1 requires the refusal to name the missing signature, so the words
        "signed name record" must be in this string, not implied by it.
      - `unresolvable` → the resolver's own `reason`, passed through unaltered.
        `describeResolveFailure`'s five messages already read as refusal text; rewording
        them here would give the same fact two spellings.
      - `cid-mismatch` → names the record's name, the CID the record signs for, and the CID
        the task actually dispatched, in that order, and says the record vouches for a
        different artifact.

    Export `interface ModuleProvenance { readonly resolver: SignedNameResolver; readonly
    now: () => number }`. `now` is **required, not defaulted** — `capability.ts`'s
    `VerifyOptions.now` carries the same rule and states it ("injected so verification is
    deterministic in tests and has no clock port"); restate it here, and add the reason it
    is a thunk rather than a number: this is consulted once per dispatch, not once per
    node.

    Export `guardModuleProvenance(inner: Executor, provenance: ModuleProvenance):
    Executor`, returning an object literal with `nodeId` reading `inner.nodeId` and an
    async `execute(task)` that, **before any call to `inner.execute`**:
      1. refuses `{kind: 'no-record'}` when `task.moduleRecord` is `undefined`;
      2. calls `provenance.resolver.accept(task.moduleRecord, provenance.now())` and
         refuses `{kind: 'unresolvable', failure, reason}` when that is not ok;
      3. compares `accepted.cid.toString()` with `task.moduleCid.toString()` and refuses
         `{kind: 'cid-mismatch', ...}` when they differ;
      4. otherwise returns `inner.execute(task)` with the task unchanged.
    Every refusal returns `{ok: false, reason: `module provenance refused on
    ${inner.nodeId}: ${describeModuleRefusal(refusal)}`}` — the node id is in the string
    for the same reason `guardSovereignty`'s refusal carries it: a dispatcher reading a
    `failures` entry needs to know which machine said no.

    Three things the module comment must state outright, because each is a decision
    somebody will otherwise revisit:
      - **Why `accept` and not `resolve`.** `accept` verifies against the pinned anchors,
        checks expiry, checks the monotonic version, *and* stores. Calling it on every
        dispatch is what gives this guard rollback protection for free: a peer replaying
        a genuinely-signed older record for a name this node has already seen at a higher
        version is refused by the resolver, not by anything written here. `resolve` alone
        would only read what some earlier call had stored, and there is no earlier call —
        nothing on this path ever hands the resolver a record except this line.
      - **Why the CID comparison is not redundant.** `accept` returning ok says the record
        is genuine. It says nothing about whether it is a record *for this task*. Without
        step 3 a valid record for any artifact the build authority ever signed would
        authorise execution of any other CID a dispatcher chose to name. This is the whole
        check, not a belt-and-braces addition.
      - **What this is not.** It is not AUTH-03's capability chain (Phase 15): a chain
        proves the *caller* may ask, this proves the *module* is the one the build
        authority meant to ship. They compose and do not substitute — the same distinction
        `sovereignty-guard.ts` draws for its own subject, and drawn here for the same
        reason. And it is not a determinism analysis: nothing here inspects the module's
        bytes or predicts its behaviour. Divergence is detected by comparison, as it always
        was; this decides only whether these bytes are the ones that were vouched for.

    Add to `packages/core/src/index.ts`, immediately after the two existing
    `sovereignty-guard.ts` export lines: `export { describeModuleRefusal,
    guardModuleProvenance } from './executor/module-provenance.ts'` and `export type

  for the life of the node. Accepted rather than bounded: an unpinned signer's records are
  refused before storage, so a peer cannot grow the map at all, and how large it gets for a
  pinned authority is a quantity nobody has measured. Recorded here rather than left to be
  rediscovered — and not derived, because a derivation is what would go stale.
