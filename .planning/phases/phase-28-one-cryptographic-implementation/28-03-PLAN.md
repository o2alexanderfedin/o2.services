<objective>
Close the two guard defects the removal creates, and turn the WebKit finding into
something that can fail.

**Obligation 4's vacuity hole.** The differential-conformance guard
(`ed25519-backend.test.ts:330-393`) builds its backend list from `availableBackends()`,
which before this phase pushed noble and libsodium unconditionally and subtle only when a
round-trip probe passed. With libsodium gone, a host whose `crypto.subtle` is absent or
Ed25519-incapable leaves **one** backend, and every "the backends disagreed" loop passes
by comparing noble with itself. Nothing in that file asserts a minimum count — the only
cardinality assertions are `REJECT_VECTORS.length >= 7` (`:304-307`) and reject-vector
name uniqueness (`:299-301`). This is latent rather than live: every host measured so far
is Ed25519-capable, so the count stays at 2 in practice, and the hole is **INFERRED** from
reading the selection logic rather than from running the suite on an incapable host. It is
still the *"proof that cannot fail"* CLAUDE.md § Proofs refuses, and it becomes
unfalsifiable on exactly the tier libsodium was bought for. A `backends.length >= 2` floor
closes it.

**Obligation 6.** Ed25519 signature bytes are not a stable identifier in this fabric.
WebKit hardens against fault attacks with a synthetic/hedged nonce rather than RFC 8032's
deterministic one, so a subtle-signed and a noble-signed signature over the same seed and
message differ — both valid, each verifiable by both arms. Node, chromium and firefox
matched noble byte-for-byte; webkit did not. X25519 agreement *is* byte-identical
everywhere. Today the finding is prose in two places (`cert-lifecycle.ts:57-70`,
`cert-lifecycle.browser.test.ts:79-88`) and nothing prevents a future caller from
deduping, caching or comparing attestations by signature bytes — which works in Node and
CI and breaks in Safari. The roadmap asks for a guard, not a docblock.

**Both guards here are non-vacuous by construction, and neither needs a plant in shared
production source.** Each has a *live positive* it must find: the CRYPTO-01 scan must find
`packages/core/src/ed25519-backend.ts`, and the CRYPTO-06 scan must find the one
registered exception at `tools/aot/cli.ts:314`. A scan that went blind would report zero
and fail. That matters beyond elegance: CLAUDE.md § Conventions records that two verifiers
planting into one production file in parallel produced a **false security finding** that
took 111 executions to refute. This plan's only plants live inside the two files it owns.

Purpose: obligations 4 and 6 of six, plus the checkable claim behind CRYPTO-01.
Output: a differential guard with a floor it has been watched fail against; one
source-level guard file carrying two predicates, each sited against the real tree.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| malformed bytes → two independent Ed25519 implementations | Two implementations of one verification contract may disagree on a malformed input; agreement on the happy path is not the hazard |
| a signature value → a caller's identity/dedupe logic | Signature bytes crossing into a comparison, a cache key or a `Set` membership test, where cross-engine divergence becomes a correctness fault |
| the guard itself → the tree it reads | A source-scanning guard that reads nothing, or a differential guard with one backend, reports green for a reason unrelated to the property |
