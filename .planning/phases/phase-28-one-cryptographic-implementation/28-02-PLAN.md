<objective>
Take `libsodium-wrappers` out of the dependency tree, measure what that is worth in one
run rather than quoting a figure from another day, and guard the removal in a shape a
removal can actually be guarded in.

**This plan runs alone in its wave, and the reason is `node_modules`.** It mutates the
installed dependency tree. A concurrent vitest run in this shared checkout would be
reading a tree that is being rewritten underneath it, and the failure that produces looks
like a code defect. Nothing else may execute while this plan runs.

**Why 25-03's guard shape does not transfer, stated before anything is written.**
`packages/node/src/x509-bundle.e2e.test.ts` guards an *addition* with
`expect(delta).toBeLessThanOrEqual(DECODER_BUDGET_BYTES)` (`:115`, `:159`), which is sound
for a ceiling on something being added. **A ceiling on a removal is satisfiable by doing
nothing at all** — a tree that never removed libsodium also passes a generous upper bound.
So this guard asserts the absence *directly*, by name and in the built bytes, and sites
its ceiling tight enough that re-adding a 314.9 KB dependency to the verification
surface's graph reddens it.

**A correction this plan owes, and must not paper over.** Plan 28-01 already deleted the
lazy `import('libsodium-wrappers')`. From that moment the built verification surface
contained no libsodium bytes, whether or not the package was still installed. So the
manifest and lockfile removal in this plan realises the *supply-chain and install-surface*
half of obligation 2, and 28-01 realised the *bundle* half. Say that in the guard's
docblock. Claiming that this plan's `npm install` is what removed 314.9 KB from a page
would be the widening-what-counts-as-passing failure CLAUDE.md § Proofs names.

Purpose: obligation 2 (the manifest half) and obligation 5, of six.
Output: a dependency-free manifest and lockfile; two measured numbers with their
conditions; one e2e guard whose three assertions have each been watched red.
</objective>
