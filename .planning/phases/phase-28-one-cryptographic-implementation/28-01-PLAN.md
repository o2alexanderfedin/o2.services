<objective>
Collapse the two Ed25519 backend-selection mechanisms in `packages/core` into one, keeping
the stronger of the two gates, and take `libsodium-wrappers` out of the code path.

`packages/core/src/ed25519-backend.ts` (Phase 25, Plan 25-04) selects with a
**presence-only** check — `typeof globalThis.crypto?.subtle?.sign === 'function'`
(`:197`) — and falls back to a lazily-imported libsodium.
`packages/core/src/cert-lifecycle.ts` (2026-08-10) selects with a **real round-trip
probe** — `await subtle.generateKey({name:'Ed25519'}, false, ['sign','verify'])` inside a
`try` (`:566-568`) — and falls back to noble. The two gates are not equivalent and the
weaker one is the presence check: it selects subtle on an engine that advertises
`SubtleCrypto` and refuses `Ed25519`. Phase 25's own test file already compensated for
this outside production code (`ed25519-backend.test.ts:309-328`,
`subtleSupportsEd25519()` — *"a real round-trip probe, not a presence check"*). **The
merged module carries the probe.** Merging toward the presence check would be merging
toward the weaker gate.

**What this plan may and may not claim.** The ROADMAP entry as originally filed said
*"two implementations in one trust path"*; it was corrected the same day it was written,
by reading the tree. Neither implementation is in the trust path. Production verification
calls `@noble/curves` directly at six sites — `capability.ts:219`, `enrollment.ts:702`,
`:740`, `:759`, `:874`, `discovery.ts:122` — and routes through neither selection layer.
Nothing anywhere calls `initEd25519()`, `getSyncVerifier()` or `createCryptoBackend()`
from production. **So this merge is behaviour-neutral in production**, which is what makes
it safe, and is also the ceiling on what it may claim: it removes a duplication from the
package, not a hazard from the trust path. Write it that way in the merged module's
docblock, and do not restate the corrected framing.

**Two things this plan must not decide by implementing.** It does **not** wire the port
into `verifyChain`/`verifyCertificate` — that is a fail-open/fail-closed ruling on a trust
path and the owner's, not this plan's. It does **not** barrel-export the facades or the
moved crypto-backend symbols — also an owner non-decision, with a counted cost of 12
callable exports (the hard-coded `75` → 87, `OPEN_FINDING_CEILING` 49 → 61). The moved
symbols stay module-level exports that `cert-lifecycle.ts` and the test files import
directly.

Purpose: obligation 1 of six, and the code half of obligation 2. The manifest half, its
measured bundle delta and its guard are Plan 28-02; the guards that must survive the merge
are Plan 28-03; the `CRYPTO-01…06` ledger mint is Plan 28-04.
Output: one selection module with the surviving probe; `cert-lifecycle.ts` importing it;
a barrel two callable exports lighter; the reachability guards reconciled against a
measured reading.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host engine → capability gate | An engine's advertised `crypto.subtle` surface is untrusted input to the backend decision; an engine may expose `subtle` and refuse `Ed25519` |
| attacker-supplied bytes → `verifyEd25519` / sync `verify` | Signature, message and public key of arbitrary length and content cross into whichever backend the gate selected |
| `cert-lifecycle.ts` → the merged module | The facades now depend on a port declared elsewhere; a wrong argument order at the adapter is a silent verification defect |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-01 | Spoofing | The capability gate | mitigate | The surviving gate is a real round-trip `subtle.generateKey({name:'Ed25519'})` probe, not a presence check, so an engine that advertises `SubtleCrypto` and refuses `Ed25519` selects noble instead of a backend that cannot verify. Proved by a planted engine whose `generateKey` rejects (Task 1) |
| T-28-02 | Tampering | Async-port argument order | mitigate | The async port is an adapter over the single `CryptoBackend.verifyEd25519` and reorders `(signature, message, publicKey)` → `(publicKey, signature, message)` in exactly one place; Task 1's behaviour case requires port and backend to agree on the same inputs, and the sync/async reject-vector case (`ed25519-backend.test.ts:569-589`) checks the same seam against all seven malformed vectors |
| T-28-03 | Denial of Service | Structural inputs to `verify` | mitigate | Both surviving adapters keep the try/catch refusal boundary (`ed25519-backend.ts:98-102`, `cert-lifecycle.ts:498-505`): `@noble/curves` throws rather than returning `false` on a wrong-length signature or key, and a structural throw must read as a refusal, never as an unhandled exception on a verification path |
| T-28-04 | Elevation of Privilege | The no-implicit-default ports | mitigate | `getSyncVerifier()`/`getAsyncVerifier()` continue to throw `Ed25519NotInitializedError` before `initEd25519()` resolves rather than defaulting; a caller that forgets to initialise fails loudly instead of receiving a plausible-looking wrong answer |
| T-28-05 | Repudiation | Guard drift after the merge | mitigate | The three pinned collision entries follow the declarations to the merged module and both reachability ceilings are lowered to a measured reading (Task 3), so the guards keep reading the tree that exists rather than the tree that did |
</threat_model>
