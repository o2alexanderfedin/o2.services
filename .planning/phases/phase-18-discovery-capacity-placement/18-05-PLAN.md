# Phase 18 · Plan 05 — From a CID to a candidate set, and offers on the submit path

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Builds:** the production halves criteria 1 and 2 need. Plan 18-06 runs them across real
processes.

<objective>
**18-CONTEXT.md's open question, answered against source rather than by preference.**

Criterion 2 requires offer-based placement on the path a real job takes, and production
`submitJob` places with `planPlacement` from `sovereignty.ts` (`job/submit.ts:24`,
`:219`). Whether that is **replaced** by `planWithOffers` or **composed** with it is a
design decision, and criterion 5 constrains it: sovereignty must be filtered *before* cost
is scored.

Read from source, the answer is **neither, and the reason is that they are two
arrangements of one gate.** `placeWithOffers` calls `eligibleNodes(request, nodes)` as its
first act (`placement.ts:169`), before any sampling and before `leastLoaded`
(`placement.ts:130-132`, applied at `:183`); `planPlacement` calls the identical function
(`sovereignty.ts:169`) before its own load ordering at `:184`. `eligibleNodes` is exported
*"so that there is exactly one of it"* (`sovereignty.ts:124-128`) precisely so a second
placer cannot drift from the rule. So **criterion 5 holds on either path, for the same
reason, and it is not what decides between them.**

Composing them is the arrangement to reject, and on evidence: `planPlacement` returns
`ordered.slice(0, redundancy)` (`sovereignty.ts:185`), so feeding its output into
`placeWithOffers` would hand the offer loop a pool already narrowed to exactly the nodes
it chose — leaving **nothing to re-pick onto**, which is the one thing criterion 2 asks to
observe. It would also score cost twice.

So the two are **alternatives selected by the caller**, and the selector is whether a
caller supplied an admission control. That is not a compromise: a caller with no way to
ask a node anything genuinely cannot place by offers, and `submitJob` runs in the
**requestor's own process** — the same argument `JobSpec.moduleRecord`'s own doc
(`job/submit.ts:38-55`) already makes for an optional field on this same interface. It
also keeps ~60 existing `submitJob` call sites placing exactly as they do today, which is
the difference between a change that can be reviewed and one that cannot.

The second half of this plan is the piece 18-CONTEXT.md identifies as missing outright:
nothing turns a discovery answer into the `executors` and `nodes` `submitJob` takes.
`discoverExecutors` returns node **keys**; `RemoteExecutor` dispatches to **peer ids**.
Somebody has to bridge them, and today nobody does.

Purpose: build both halves and wire neither. Output: `JobSpec.admit` and
`discoverCandidates`.
</objective>

## Recorded decisions

- **18-CONTEXT.md's open question is answered: neither replace nor compose.**
  `planPlacement` and `planWithOffers` are two arrangements of one gate — both call
  `eligibleNodes` first, and it is exported so that there is exactly one of it. Criterion 5
  therefore holds on both and does not decide between them. Composing them is rejected on
  evidence: `planPlacement` slices to `redundancy` before returning, so the offer loop would
  have nothing to re-pick onto.
- **The selector is whether the caller supplied an admission control**, which is a fact
  about what the caller can do rather than a preference. `submitJob` runs in the requestor's
  own process, which is the reasoning `moduleRecord`'s doc already established on this same
  interface.
- **`d` is not a new `JobSpec` field.** `DEFAULT_D` is 2 and criterion 2 asks for
  *multiple* candidates.
- **Which peers to ask is the caller's, and this module recommends `verifiedPeers`.**
  Choosing here would be wrong for one of the two configurations a node can be in.
- **The sovereign owner-id seam is named, not fixed.** AUTH-05 / Phase 19 owns unifying
  `OwnerId` with a user key.
