# Phase 18 · Plan 08 — A cap an operator can move on a running node

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Closes:** criterion 3, Node tier. Plan 18-09 closes the browser tier.

<objective>
`FabricNode` composes **no governor** — its stack is
`new CountingExecutor(guardSovereignty(provenance(compute), sovereignty))`
(`fabric-node.ts:1202`) — so SCHED-04's *"honoured by the executor"* half has never been
true on this tier, and its *"user-adjustable"* half has never been true anywhere. Plan
18-07 built a governor whose cap can move and a `LocalCapacity` whose slots follow it. This
plan composes them and gives an operator a way to turn the knob on a process that is
already running.

**The control channel is a file and a signal, and the alternatives were worse.** A wire
frame would let a peer — an *unauthenticated* peer, since `serveAgent` serves
unauthenticated — throttle a node it does not own, which needs an authorization surface this
phase has no reason to open. A start-time flag alone does not meet the criterion, which says
*"set at runtime on a running node"*. A file under the directory the operator already passed
as `--dir` is protected by exactly the permissions that already protect `.identity.key` and
`.provider.key`, and `SIGHUP` is the conventional "re-read your configuration" signal. No
new bytes cross the network.

**One recorded decision is deliberately reversed here, and it must be reversed in the open.**
`browser-node.ts:885-894` says the visibility duty cycle is *"deliberately not passed as
`dutyCycle`"* to `LocalCapacity`, on the grounds that *"two independent throttles on one path
produce a number nobody can predict"*. Criterion 3 requires the opposite — the advertised
capacity must drop with the cap — and `LocalCapacity`'s own doc already argues for the
coupling: *"A node at 25% does not run a quarter of a task; it runs fewer of them"*
(`placement.ts:249-255`). The resolution is that these are **not two throttles**: the pacing
is the mechanism and the slot count is the *statement about* that mechanism, advisory and
non-reserving. One cap, two views. Plan 18-09 rewrites the browser comment; this plan states
the reasoning both will cite.
</objective>

  requires it and `CapacityOptions`' own doc argues for it. The resolution is that the pacing
  is the mechanism and the slot count is the advisory statement about it — one cap seen
  twice. Plan 18-09 rewrites the browser comment to match; the reasoning is stated here and
  both cite it.
- **The counter moves inside the governor on the Node tier**, matching the browser tier, for
  the reason that tier already recorded: a counter outside would count parked tasks as in
  flight.
- **The runtime control is a file plus `SIGHUP`, not a wire frame.** `serveAgent` serves
  unauthenticated; a frame that set a CPU cap would need an authorization surface this phase
  has no reason to open.
- **A bad control file is named and non-fatal**, the opposite disposition from
  `--provider-addr`'s fatal one, because one happens before the node exists and the other
  while it is serving.

## Out of scope

- The browser tier — Plan 18-09. Criterion 3 names both and this plan closes one.
- Putting a capacity figure into `CapabilityRecord`. Signed document, changing figure; the
  observable is the offer answer.
- Any authenticated control channel. The file-and-signal channel is bounded by filesystem
  permissions and is stated as such; a remote one is a design decision no criterion here
  asks for.
- Making the duty cycle affect anything other than pacing and the advertised slot count. It
  does not change the task deadline, the inbound limits, or the relay reservation capacity,
  and the summary says so.
