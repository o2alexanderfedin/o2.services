# Phase 18 · Plan 02 — A node answers for what it holds

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Implements:** owner ruling **D1** (18-CONTEXT.md) — *each node answers `providers(cid)`
from its own blockstore, and `RpcRecordIndex.providers` unions across peers.*

<objective>
Criterion 1 cannot be met by wiring, and this is the half that does not exist.

`discoverExecutors` (`core/src/discovery.ts:237-296`) intersects two lookups on the
`RecordIndex` port (`:137-142`). `recordsFor` is live on both tiers since Phase 17
(`fabric-node.ts:1106`, `:1278`; `browser-node.ts:778-781`, `:988`). `providers` is
**empty, always**: `MemoryRecordIndex.provide` (`:362-368`) has zero callers outside test
files, which the grep in Task 1 records, and `fabric-node.ts:1272-1274` says so in its own
comment — *"`providers` still answers `[]`, because `provide()` is never called."*
`packages/net/src/discovery.test.ts:157` hand-calls `index.provide(inputCid, nodeKey)` in
its fixture, which is why the existing discovery tests pass over a mechanism production
does not have.

D1 settles what fills that gap: **a node is authoritative about what it holds**, so the
answer is computed at ask time from the store rather than replicated in advance. That
needs no port change and no new wire frame — `providers` is already a request kind
(`protocol.ts:93`, parsed `:658-662`) and already served (`agent.ts:593-599`).

D1's second consequence is the one a plan will otherwise forget.
`RpcRecordIndex.providers` returns the **first non-empty** answer
(`net/src/discovery.ts:44-51`), and its class doc argues for that. With every node
answering only for itself, first-non-empty finds exactly **one** provider — and
power-of-d sampling with one candidate is not sampling. It must union.

Purpose: give `providers` a production answer and give the merge somewhere to merge.
Output: `SelfRecordIndex` in `@o2/core`, and a `RpcRecordIndex` that asks everyone.
</objective>

## Recorded decisions

- **`providers` answers about the store, filtered by the same set the `block` branch
  consults.** The alternative — answering from the raw store — would let a peer confirm
  that a node holds a sovereign block without asking for it, which is a side channel around
  a refusal the owner ruling at `egress.ts` deliberately made indistinguishable from
  absence.
- **A node with no certificate still answers `providers`.** `discoverExecutors` excludes
  such a provider by name; silence would produce an unnameable exclusion, which the module
  comment's *"every exclusion is named"* rule exists to prevent.
- **`recordsFor` deliberately keeps first-non-empty.** A record is signed and verified by
  the caller; a second copy can only agree.
- **The union pays the slowest peer, and a dead peer costs the full RPC budget on every
  lookup.** Accepted and stated. No probe deadline is invented for it.

## Out of scope

- **NET-06 is advanced by this plan and is not closed by it.** Every node — browser tier
  included — now answers a provider lookup about its own store, which is the "browser peers
  participate in routing as full peers" half. What NET-06 asks for beyond that is two
  browser peers discovering each other on a static bundle with nothing dialled by a harness,
  and **Phase 19 criterion 4 owns it**. This plan does not claim the requirement and its
  frontmatter deliberately does not list it.

- Wiring either node factory to serve from a `SelfRecordIndex` — Plan 18-03. This plan
  builds the mechanism and leaves `fabric-node.ts` and `browser-node.ts` untouched, so the
  two can be reviewed apart.
- Any production caller of `discoverExecutors` — Plan 18-05.
- A DHT, delegated HTTP routing, or any transitive provider lookup. D1 rejects both, and
  **Phase 21's open question owns whether Helia enters this repository at all**; this plan
  adds no dependency.
- Populating `CapabilityRecord.features`. No feature-detection dependency exists here
  (`wasm-feature-detect` is recommended in `CLAUDE.md` and is not installed), and
  `discoverExecutors` only excludes on features a caller asked for, so `[]` excludes
  nobody. Unchanged from Phase 17 and still honest.
