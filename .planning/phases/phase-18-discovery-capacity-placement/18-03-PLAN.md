# Phase 18 · Plan 03 — Both tiers answer for what they hold

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Implements:** owner ruling **D1**, serving side, on both tiers.

<objective>
Plan 18-02 built `SelfRecordIndex` and left both node factories untouched, deliberately.
This plan gives it its production callers, and it is where the standing rule bites
hardest: **all nodes have equal functionality; the only difference is discovery.** Phases
16 and 17 each shipped a violation of that rule and neither was caught by an in-process
test, so this plan changes both factories in one go and asserts the two expressions are the
same rather than trusting that they are.

Two facts fix the shape. `fabric-node.ts:1106` builds `records` only when a certificate
exists and `:1278` passes `records ?? 'serves-no-records'`; `browser-node.ts:778-781` and
`:988` do the same. Under D1 that conditional is wrong on the `providers` half: **holding
blocks is not a capability enrollment confers**, and a node that answered `[]` for blocks
it really holds would be lying about itself in order to keep a sentinel true.

So the index becomes unconditional and `'serves-no-records'` leaves both files. That is a
visible change to `serve-agent-hooks.node.test.ts:81` and `:131`, which count the literal
and expect one each. **The counts are not simply lowered.** A count that goes to zero with
nothing replacing it is a guarantee deleted, so this plan replaces each with an assertion
that the hook receives an index unconditionally — which is the stronger statement and the
one D1 actually makes.

Purpose: make `providers` answer something in production for the first time since the
request kind was added in Phase 6. Output: both factories serving a `SelfRecordIndex`, and
a test that reads the answer off a real wire in both directions.
</objective>

## Recorded decisions

- **The index is unconditional and `'serves-no-records'` leaves both factories.** There is
  no node these factories can build that has nothing to answer: one with no certificate
  answers `records: null` and a real provider list, which are two truthful statements
  rather than a refusal to speak.
- **A count lowered to zero is a guarantee deleted unless something replaces it.** Both
  lowered counts in `serve-agent-hooks.node.test.ts` gain a paired positive assertion.
- **The withholding predicate reads the same set `refusedReason` reads.** Any other set
  would let the two serving branches disagree, and the disagreement would be a side channel
  around a refusal the owner ruling deliberately made indistinguishable from absence.

## Out of scope

- **NET-06 is advanced by this plan and is not closed by it.** Every node — browser tier
  included — now answers a provider lookup about its own store, which is the "browser peers
  participate in routing as full peers" half. What NET-06 asks for beyond that is two
  browser peers discovering each other on a static bundle with nothing dialled by a harness,
  and **Phase 19 criterion 4 owns it**. This plan does not claim the requirement and its
  frontmatter deliberately does not list it.

- `bin/bench.ts` and `bench/src/perf-workload.ts`, which pass `'serves-no-records'` twice
  each. They are production `serveAgent` call sites and they are **deliberately unchanged
  here**: whether the benchmark's own workers answer provider lookups is a decision about
  what the published curve measures, and Plan 18-06 takes it behind an opt-in flag with the
  default curve unmoved.
- Any caller of `discoverExecutors`. Plan 18-05.
- Gating `providers` on `verifiedPeers`. **Unmeasured, not descoped.** A node currently
  answers `providers` to any peer that can dial it, exactly as it answers `block` and
  `records`; whether an unverified peer should be able to ask is a question this phase
  raises and does not settle, and the summary must say so in those words.
