# Phase 18 · Plan 01 — A flag that dials a peer

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Closes:** criterion 2d — *`bin/agent.ts` gains a flag that makes a spawned agent dial
a named peer, and a spawned node started with it verifies that peer's certificate and
accepts it.* Routed here from Phase 17's criterion 2 by owner ruling 2026-08-01.

<objective>
This is **first in the phase and the ordering is measured, not preferred.**
`bin/agent.ts` parses eleven flags (`bin/agent.ts:52-180`) and **none of them dials a
peer**. `--provider-addr` (`:108`) reaches `resolveCertificate`, whose dial
(`fabric-node.ts:537`) exists to carry one enrollment round trip and establishes no
ongoing peering — and the provider's own handshake carries `certificate: null` unless it
too was enrolled. A node started by this binary therefore has **zero peers**, so nothing
in this phase can be exercised through it: there is nobody to ask for providers, nobody
to ask for records, and no peer whose certificate could be accepted.

The mechanism already exists and has no caller from this binary: `FabricNode.dial`
(`fabric-node.ts:1416-1419`) returns the remote peer id, and `PeerVerifier` subscribes to
`peer:connect` (constructed at `fabric-node.ts:1118-1123`) so a peer dialled *after*
`start()` returns gets a verdict without any seeding. This plan supplies the caller.

`certificate-verification.node.test.ts` states the gap this closes in its own header —
*"criterion 2's **accepting** side is **UNMEASURED through `bin/agent.ts`**"* — and names
the remedy as this phase's. Read that file before writing the test; it is the fixture to
follow, including how it spawns, how it signs a `NameRecord`, and how it kills a provider.

Purpose: make peer-to-peer acceptance measurable across a real process boundary, for this
phase and for every later one. Output: `--peer-addr`, the `peers` field on the handshake
line, and a spawn test that reads acceptance from its consequence rather than from a log.
</objective>

      meaning; they are deliberately two flags because they are two mechanisms.
    - **Why `node.stop()` before `refuse`.** `refuse` calls `process.exit(2)`, and a

## Recorded decisions

- **The dial runs after `start()` returns rather than becoming a `FabricNodeOptions`
  field.** `relayAddrs` already occupies the factory position and means something else
  entirely — it asks for a reservation and switches the node's whole reachability topology
  (`fabric-node.ts:887-905`). A peer dial changes nothing about how this node is reachable.
- **Acceptance is read from its consequence, not from a verdict.** `verdictFor` does not
  cross a process boundary, and adding a frame that would carry it is a protocol change
  this criterion does not need. The consequence — a block fetched from the accepted peer —
  is what the gate actually controls, so it is the stronger reading anyway.
- **The three-flag fold `bin/agent.ts:74-78` asks for is deliberately not done**, because
  three plans in this phase add a flag to that object in three waves.

## Out of scope

- Gating anything other than the block source on `verifiedPeers`. **Unmeasured, not
  descoped**, and the summary must use that word. Dispatch candidate selection gets a
  production caller in Plan 18-05; whether it reads the verified subset is that plan's
  decision to state, not this one's.
- `--relay-addr` and reservation failure reporting — NET-05, Plan 18-11.
- A control channel that changes a running agent's configuration — Plan 18-08 adds one for
  the duty cycle only, and states its own bound.
