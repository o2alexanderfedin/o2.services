# Phase 18 · Plan 10 — Sovereignty survives the offer loop

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Closes:** criterion 5 — *under artificial load pressure applied during a live run, a
sovereignty-pinned task still lands on its owner even though a lower-cost non-owner node is
available, proving the cost heuristic is filtered after the sovereignty constraint rather
than scored against it.*

<objective>
This criterion is already met on the **old** placement path.
`sovereignty-placement.node.test.ts` places a sovereign shard across real `bin/agent.ts`
processes with alice's node described as saturated (`load: 1`) and bob's as idle
(`load: 0`), and it lands on alice's. Plan 18-05 gave `submitJob` a second placement
arrangement, and a criterion met on one arrangement is not met on the other until it is
measured there.

What genuinely changes is the **shape of the risk**. `planPlacement` has no branch that can
widen under load — it orders an already-narrowed set (`sovereignty.ts:169`, `:184`), and
there is nowhere for a cheaper node to come from. `placeWithOffers` adds a *loop*: a
candidate refuses, it is dropped, and the next `d` are sampled from what remains
(`placement.ts:181-195`). A loop that re-derived its pool from the full node list on each
iteration would leak a sovereign shard onto a foreign node on the second pass, and every
existing assertion would still pass, because no existing test makes an owner's node refuse.

The code is right — `pool` is built once from `eligibleNodes` at `:169` and is *only ever
shrunk* (`:186`), which the comment beside it says in those words. **The property is
untested.** `placement.test.ts`'s sovereign cases (`:213`, `:239`, `:249`, `:261`) place
successfully or find nobody eligible; none of them has an eligible node refuse and then
checks where the shard did not go.

Purpose: measure the property the loop makes newly possible to break, in the kernel and
across real processes. Output: two files, no production change.
</objective>

## Recorded decisions

- **The strong reading of *"a foreign node was never offered the shard"* lives in the kernel
  test, not the process test.** The offer branch reserves nothing, so a spawned node that was
  asked and refused is indistinguishable from one that was never asked. The two files carry
  different halves and each says which.
- **The fixture keeps its operator-label owner id.** Unifying `OwnerId` with a user key is
  AUTH-05 / Phase 19's, and Plan 18-05 records the seam; changing this fixture to a hex key
  would hide the seam rather than close it.
- **A stalled sovereign shard is the correct outcome** and is asserted as such — the reason
  `sovereignty.ts`' module comment gives, measured rather than quoted.

## Out of scope

- A sovereign job placed from `discoverCandidates`' own descriptors. That path needs the
  shard's `ownerId` to be the owner's user key, which is the seam Plan 18-05 names and Phase
  19 owns. **Unmeasured, not descoped**, and the summary says so.
- Owner-domain attestation and replica sets — AUTH-05, VER-09, Phase 19.
- Changing any production source. If a behaviour under test turns out to be wrong, that is a
  stop-and-report rather than an edit inside this plan.
