# Phase 17 · Plan 03 — Identity and enrollment on the startup path

**Closes (in part):** AUTH-01 — *the identity key is generated on-device and its public
half is signed into a provider-issued certificate*. AUTH-04's provider side gets its
production construction site here; its cross-process measurement is Plan 17-05's.

<objective>
A running node's identity today is the libp2p peer id and nothing else: `FabricNode.peerId`
is `this.libp2p.peerId.toString()` (`fabric-node.ts:430-432`), the executor id is the same
string (`:377`), and `createLibp2p` (`:303`) is called with **no `privateKey`** — so libp2p
mints a fresh ephemeral key on every process start and nothing on disk survives a restart
except blocks.

This plan puts Plan 17-01's seed into `createLibp2p`, and Plan 17-02's `enrolOverRpc` and
`EnrollmentAuthority` onto the startup path between `rpc` and `serveAgent`.

Three things are load-bearing and each is written down rather than inferred
(17-CONTEXT.md decision 9):

| Configuration | Behaviour |
|---|---|
| no provider address | identity key still generated and persisted; `certificate` is `null`; the node starts |
| provider address given, enrollment fails | `start()` rejects with the refusal reason; no listening socket is left behind |
| no directory | identity generated fresh per process and not persisted — a deployment choice, not a kind of node |

The middle row is the one that matters. `.planning/PROJECT.md`'s Key Decision **"An
optional hook with a silent default is a hole"** is exactly the failure being avoided: a
node told to enrol, unable to, and running anyway is a node whose identity claim is
silently absent.

The regression bar for the whole plan is the third row of decision 9's table:
`two-process.node.test.ts`, `egress-refusal.node.test.ts`,
`sovereignty-placement.node.test.ts`, **`fabric-node.node.test.ts`**, `bin/bench.ts` and
`SeedServer.start` (`seed-server.ts:191-195`) all construct nodes with no new options, and
**all of them must keep passing unchanged**.

`fabric-node.node.test.ts` is on that list for a specific, non-obvious reason and is named
rather than left to the end-of-plan sweep: it is the only test in the repository that reads
`FsBlockstore`'s block count across a reopen — `sizeBeforeRestart = worker.store.size` at
`:206`, `expect(reopened.size).toBe(sizeBeforeRestart)` at `:214` — and this plan is what
first puts a non-block file (`.identity.key`, and with `--issues-certificates` plus
enrollment, `.provider.key` and `.certificate.json`) into a real node's blockstore
directory. Plan 17-01 Task 2 dot-prefixes those names and widens `FsBlockstore.open`'s
filter so the count is unaffected; this plan's job is to **run** that test, in Task 2's
verify command and not only in the final sweep, so a regression surfaces where it was
caused. This phase does not modify that file — Phases 14, 15 and 21 all edit it
(`CONFLICTS.md`).

Purpose: give `requestEnrollment`, `EnrollmentAuthority` and the identity seed their first
production callers.
Output: `FabricNode` gains `nodeKey`, `certificate` and `issuerKey`; `FabricNodeOptions`
gains `enrollment` and `issuesCertificates`; the certificate lands on disk and is reused.
Plan 17-04 adds the verification gate; Plan 17-05 adds the flags and the cross-process
measurement.
</objective>

The leading dots are load-bearing, not style. `FsBlockstore.open`'s `filter` **is** the
block counter — every entry it keeps becomes part of `size` — so an undotted `identity.key`

that filter to `!name.startsWith('.')` on the ground that a block file name is
`cid.toString()`, base32-lowercase, which never begins with a dot.
