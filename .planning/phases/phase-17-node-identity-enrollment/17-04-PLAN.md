# Phase 17 · Plan 04 — Serving an identity, and refusing one

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Closes:** AUTH-02 — *a node verifies a peer's provider-signed certificate offline, with
no live certificate authority*. Together with Plan 17-03 this completes AUTH-01's
certificate half as well: a certificate nobody can fetch is not an advertised identity.

<objective>
Two mechanisms, both already written and both dead in production.

The `records` request kind, its wire encoding and its handler branch all exist
(`protocol.ts:66`, `:92`, `agent.ts:176-181`) and every production call site passes
`'serves-no-records'`. `MemoryRecordIndex` (`discovery.ts:358-382`) and
`publishCapabilities` (`discovery.ts:101`) have no production callers at all. Plan 17-03
gave each node a certificate; this plan makes it fetchable, which is what turns criterion
1's "advertised identity" from a thing a binary prints into a thing a peer can read.

`verifyCertificate` (`enrollment.ts:265`) likewise has no direct production caller.
`RpcRecordIndex` (`packages/net/src/discovery.ts:35-69`) has none either, and **this plan
does not give it one** — its `#ask` swallows the transport error and returns `null`
(`:62-68`), so `recordsFor` answers `undefined` both for a peer that could not be reached
and for one that answered `records: null`. A per-peer verdict has to tell those apart, and
the plan says so out loud rather than reusing the adapter and quietly losing a failure
kind.
17-CONTEXT.md decision 8 identifies where the gate belongs, and it is not in the
transport: `fabric-node.ts:359` already passes the peer list to `RpcBlockSource` as a
**thunk**, and replacing `() => transport.peers` with `() => verifier.verifiedPeers` means
an unverified peer is never asked for a block and never appears as a dispatch candidate —
structurally, with no `if` anywhere that could be forgotten. `Transport` stays a
three-member datagram port that knows nothing about certificates, which is the property
`libp2p-transport.ts`'s module comment exists to protect.

Every refusal already has a named reason and a kind: `untrusted-issuer`
(`enrollment.ts:270-276`), `bad-signature` (`:284-290`), `not-yet-valid` (`:292-298`),
`expired` (`:299-305`). Criterion 2's "named reason" needs no new vocabulary; it needs
those strings surfaced where a test can read them.

Purpose: give `verifyCertificate`, `publishCapabilities` and `MemoryRecordIndex` their
first production callers, and make "before treating it as a legitimate peer" a structural
fact rather than a claim. `RpcRecordIndex` is deliberately **not** on that list — see the
interfaces block for why it cannot carry a per-peer verdict, and "Out of scope" for the
statement that its first production caller is Phase 18's.

Two limits, stated here rather than left in the small print. **"Legitimate peer" means
block fetching and nothing else this phase**, because `RpcBlockSource.fetch`
(`packages/net/src/agent.ts:46`) is the only production consumer of `verifiedPeers` there
is; dispatch candidate selection, quorum membership and relay use are **unmeasured**, not
descoped. And **a verdict is asynchronous**: `libp2p.dial` resolving does not mean a
records round trip has finished, so every test that reads a verdict must first wait for it
to be defined, with a stated deadline, and assert that it is.
Output: `PeerVerifier`; `FabricNode.verifiedPeers` and `verdictFor`; the `index` hook
holding this node's own records; the block source reading the verified subset.
</objective>

async #ask(peer: string, body: CanonicalValue): Promise<AgentResponse | null> {   // :62-68

A single-element thunk does ask exactly one peer — but the `catch` erases the error, and
an unreachable peer and a peer answering `records: null` both fall out of the loop as
`undefined`. There is no surviving error object for an `unreachable` verdict's `detail` to
come from, so that arm is not constructible through this class at all. Skip-and-continue
is correct for a multi-peer lookup and wrong for a per-peer verdict; `PeerVerifier` issues
its own request instead (Task 2), and `RpcRecordIndex`'s first production caller stays
Phase 18's `discoverExecutors` wiring.

## Recorded decisions

Two things this plan **accepts**, and one disclosure it makes deliberately. Recorded here
because each is a decision somebody would otherwise re-litigate or discover.

- **A node pinning an issuer cannot fetch any block during the window between connect and
  verdict, and that is the intended behaviour.** Fail-closed is the right default for a
  gate, and the window is one RPC round trip. It costs nothing durable because
  `FetchingBlockstore`'s block source is a **thunk read per fetch** — so a retry after the
  verdict lands succeeds without reconnecting and without any invalidation step. State that
  in the thunk's own comment rather than leaving it to be discovered by whoever first sees
  a fetch fail and then succeed.
- **A peer that never answers a records request is not retried forever.** The verdict is
  memoised per peer, `unreachable` included, and dropped only on `peer:disconnect` — one
  request per connection, not per fetch.
- **Turning the `index` hook on makes every node holding a certificate answer questions it
  used to decline, including nodes nobody reconfigured** (`agent.ts:174` answers `[]` and
  `:180` answers `null` for every production node today). Accepted, because what it now
  answers with is its own provider-signed certificate and its own signed capability
  record — both public statements whose entire purpose is to be read by a stranger — and
  `providers` still answers `[]`, because `provide()` is never called. Nothing secret
  crosses this boundary and nothing may later be added that does. The belief that the blast
  radius is zero is *checked* rather than asserted: 17-CONTEXT.md Risk 3's grep for existing
  `providers`/`records` response consumers is a required step of Task 1, and its command and
  full output go in the summary.
