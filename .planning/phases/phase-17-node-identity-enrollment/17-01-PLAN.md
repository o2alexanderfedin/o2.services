# Phase 17 · Plan 01 — One seed, two namespaces

**Closes (in part):** AUTH-01 — *a node's identity key is generated on-device*.
The certificate half of AUTH-01 lands in Plan 17-03; this plan builds the key it will
be issued over, and proves the assumption everything after it rests on.

<objective>
17-CONTEXT.md decision 1 makes a node's libp2p peer id and its `NodeCertificate.nodeKey`
two encodings of **one** 32-byte ed25519 seed generated on the device. Four properties
fall out of that and none of them needs extra machinery: the peer id ↔ nodeKey mapping
becomes a pure function in both directions, the Noise handshake becomes the standing
proof of possession for the certificate's subject key, the peer id becomes stable across
restarts, and "the advertised identity is a certificate rather than a bare libp2p peer
id" becomes structurally checkable instead of a matter of what a binary prints.

All four rest on `ed25519.getPublicKey(seed32)` (noble) and
`generateKeyPairFromSeed('Ed25519', seed32).publicKey.raw` (`@libp2p/crypto`) returning
the same 32 bytes — and **the dependency source settles that, so this plan does not treat
it as an open question.** `node_modules/@libp2p/crypto/dist/src/keys/ed25519/index.js:2`
imports `ed25519 as ed` from `@noble/curves/ed25519.js`; `:13-15` is
`derivePublicKey(privateKey) { return ed.getPublicKey(privateKey) }`; `generateKeyFromSeed`
calls it at `:41` under the comment *"the seed is used directly as private key"*. The
browser build is identical at `index.browser.js:31-38`. Both sides of the equality are the
same noble call on the same bytes. Confirmed empirically for `0x00`, `0x07` and `0xff`
seeds — equal in all three.

Task 1 still writes the assertion, because three lines that pin a dependency against a
future rewrite are worth having. What it does **not** do is gate the phase on it: there is
no stop-and-report protocol here and no wire-format contingency, because there is nothing
to contend with. The priority those consumed is re-spent on the two things that are
genuinely unsettled and that this plan now closes — the `FsBlockstore` block-count
collision (17-CONTEXT.md Risk 1, Task 2) and `fromHex`'s silent zero-fill on non-hex input
(Task 1's `parseKeyHex`).

Purpose: give every later plan in this phase one identity to work from, and one validator
every key string in the phase passes through.
Output: `@o2/libp2p` gains an `identity` module (dual-target, no `node:` imports);
`@o2/node` gains the file-backed seed store beside `FsBlockstore`, and `FsBlockstore.open`
stops counting non-block files as blocks. Nothing is wired into `FabricNode` here — Plan
17-03 does that.
</objective>

From `packages/core/src/capability.ts` (unchanged; exported from the `@o2/core` barrel):
```ts
export type PublicKeyHex = string          // an ed25519 public key, hex-encoded
export function toHex(bytes: Uint8Array): string
export function fromHex(hex: string): Uint8Array<ArrayBuffer>   // NO validation — see below
```
**`fromHex` performs no validation, and `try/catch` is not the mitigation.** It does not
throw on non-hex — it zero-fills, so there is nothing to catch. Measured on this machine
before this plan was written: `fromHex('z'.repeat(64))` is 32 zero bytes,
`publicKeyFromRaw` accepts them as a valid Ed25519 key
(`node_modules/@libp2p/crypto/dist/src/keys/index.js:73-76`), and the peer-id derivation
returns a confident, wrong `12D3KooW9pNAk8aiBuGVQtWRdbkLmo5qVL3e2h5UxbN2Nz9ttwiw`.
Uppercase is the same edge from the other side: `Number.parseInt('AB', 16)` is `171`, so an
uppercase key parses to bytes that differ from the lowercase form `toHex` emits, and the
round trip breaks with no error anywhere. Both hazards are **length-64** inputs, so a test
that feeds `''` and `'zz'` measures neither — those two fail on length inside
`publicKeyFromRaw` (verified: `InvalidParametersError: Could not extract public key from
raw bytes`) and would fail identically with no validator present at all. Hence
`parseKeyHex` below, and every hex-key string in this phase routed through it.

From `@noble/curves/ed25519.js` (`@noble/curves@2.2.0`, already a dependency of `@o2/core`):
```ts
ed25519.keygen(): { secretKey: Uint8Array; publicKey: Uint8Array }   // secretKey is the 32-byte seed
ed25519.getPublicKey(seed: Uint8Array): Uint8Array                   // 32 bytes
```
`keygen()` bottoms out in `@noble/hashes`'s `randomBytes`, which reads
`globalThis.crypto.getRandomValues` and throws if it is absent

`Ed25519PrivateKey` has `.raw` (64 bytes) and `.publicKey` (`Ed25519PublicKey`, whose
`.raw` is 32 bytes) — `node_modules/@libp2p/crypto/dist/src/keys/ed25519/keys.js`.

From `@libp2p/peer-id@6.0.12` (already a declared dependency of `@o2/libp2p`):
```ts
export declare function peerIdFromString(str: string): Ed25519PeerId | Secp256k1PeerId | RSAPeerId | URLPeerId
export declare function peerIdFromPublicKey(publicKey: Ed25519PublicKey): Ed25519PeerId
export declare function peerIdFromPrivateKey(privateKey: Ed25519PrivateKey): Ed25519PeerId
```
An Ed25519 `PeerId` carries its public key in an identity multihash, so `peerId.publicKey`
is present without a network call.

From `packages/node/src/fs-blockstore.ts:65-69` — the durable-write pattern to copy:
```ts
const tmp = join(this.#dir, `.tmp-${process.pid}-${this.#tmpSeq++}`)
await writeFile(tmp, bytes)
await rename(tmp, target)
```

**`FsBlockstore.open`'s filter is not a safety net — it is the block counter**, and this
is the single most important line in this plan's interfaces:
```ts
static async open(dir: string): Promise<FsBlockstore> {        // :42-47
  await mkdir(dir, { recursive: true })
  const entries = await readdir(dir)
  const blocks = entries.filter((name) => !name.startsWith('.tmp-'))
  return new FsBlockstore(dir, blocks.length)
}
```
Every entry that is not `.tmp-` prefixed **is counted as a block**. Drop an
`identity.key` in that directory and `size` reports one more block than exists. The
consequence is already asserted in a test this plan does not otherwise touch:
`packages/node/src/fabric-node.node.test.ts:206` captures
`sizeBeforeRestart = worker.store.size` — the in-memory counter, which only ever counted
real `put()`s because the directory was empty at `open()` — and `:214` asserts
`expect(reopened.size).toBe(sizeBeforeRestart)` after reopening the same directory. With
an identity file present that is N+1 against N, and it fails.

So Task 2 dot-prefixes the file names **and** widens that predicate to
`!name.startsWith('.')`. A block file name is `cid.toString()`, base32-lowercase, which
never begins with a dot — so the widened form excludes exactly the non-block entries and
subsumes the `.tmp-` case rather than replacing it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the device's RNG → the node's whole identity | Every certificate, every proof of possession, and the peer id itself derive from these 32 bytes. A weak or absent RNG is not a degraded identity, it is a forgeable one |
| the filesystem → the running node | `.identity.key` is the only thing that makes a restarted process the same node. Anything that can read it can impersonate that node to every peer that has pinned its issuer |
| a peer id off the wire → an expected `nodeKey` | `nodeKeyForPeerId` turns an authenticated connection into a claim about which certificate that peer is allowed to present. A wrong answer here is a verification gate that checks the wrong key |
