# Phase 17 · Plan 02 — Enrollment on the wire, and the eighth hook

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Closes (in part):** AUTH-01 (the issuance half), AUTH-02 (the wire-level refusal
proofs), AUTH-04 (the rate-limit mechanism). The production entry point that calls all
of it arrives in Plans 17-03 and 17-05.

<objective>
`requestEnrollment`, `EnrollmentAuthority` and `verifyCertificate` have existed and been
unit-verified since Phase 6, and nothing outside a test has ever called any of them
(17-CONTEXT.md's classification table). The certificate half of the wire is likewise
complete and unexercised: `certificateToValue` (`protocol.ts:150`) and `parseCertificate`
(`:172`) are reached from `encodeResponse` (`:449-454`) and `parseResponse` (`:501-508`),
and in production every one of those paths returns `null` because all four production
call sites pass `'serves-no-records'`.

This plan adds the one thing genuinely missing — a way for a node to *ask* — and the one
hook that decides whether a given process answers.

Enrollment travels as an **eighth request kind** rather than as a standalone provider
binary. `.planning/ROADMAP.md`, section `### Phase 22: Reachability Guard`, fixes Phase 22's reachability-guard universe at five
runnable entry points; a sixth would put Phase 22 in conflict with Phase 17 on day one
(17-CONTEXT.md decision 4). Issuance is an **eighth `serveAgent` hook** rather than a
class, because every node has the identical code and whether a given process holds a
provider signing key is a per-node setting — the same shape, and the same sentence,
`bin/agent.ts:26-31` already uses about `--owner-id` (decision 5).

Purpose: make the enrollment mechanism reachable over the fabric's own protocol, and
make "this process issues no certificates" something a call site has to write down.
Output: `enrol` on `AgentRequest`/`AgentResponse` with parsers held to
`parseCertificate`'s discipline; `enrolOverRpc` as the requesting half; `AgentOptions.enroll`
as the eighth required hook, stated at all four production call sites and every test one.
Plan 17-03 gives it a real value on the startup path; this plan proves the mechanism.
</objective>

Behaviour the parsers and the burst test depend on:
- `enrol()` checks possession **first** (`enrollment.ts:192-211`), then the window
  (`:213-227`). A forged request is refused before it can consume budget, so a burst of
  forged requests cannot lock out a legitimate one.
- The window is per **`userKey`** (`#history` keyed at `:173`, filtered at `:213`), not
  per node key and not per connection.
- Issuance defaults, as shipped by `@o2/core` and left alone by this phase:
  `maxPerWindow = 5`, `windowMs = 3_600_000`, `certificateLifetimeMs = 30 days`
  (`enrollment.ts:178-180`). **Their one home is `enrollment.ts:178-180`** — they are
  `@o2/core`'s constants, not this phase's — and this interfaces block is the one place in
  the phase's *plans* that quotes them (17-CONTEXT.md's "Existing Code Insights" quotes
  them once more, with the same citation, because it is the document a planner reads first);
  17-03 and 17-05 cite instead of restating, so nothing here can drift from the source. How
  a burst of a given size divides between accepted and refused is **not** derived here —
  Task 3 measures it and the summary records what was measured.
- The clock is a parameter everywhere, *"so the limiter's behaviour is deterministic in
  tests and the module stays free of platform time"* (`:162-165`).

## Recorded decisions

Three things this plan **accepts** rather than fixes. They are written down here so the
next reader finds them recorded rather than rediscovering them, and so a later change that
makes one of them worse is visibly a regression.

- **One user key cannot exhaust an authority's issuance budget for everyone.** The window
  is per `userKey` (`enrollment.ts:213`, `#history` keyed at `:173`), so one key only
  exhausts its own; and possession is checked first (`:192-211`), so a burst of forged
  requests consumes none of anyone's budget. Accepted as adequate; nothing in this phase
  strengthens it.
- **Mass fake-node creation is rate-limited, not made costly, and this plan does not
  pretend otherwise.** An attacker holding many user keys is not slowed at all — Task 3's
  second measurement asserts exactly that rather than describing it. `enrollment.ts:22-30`
  names what would change it: a proof-of-work, a payment, or an out-of-band identity
  check, all of which plug in at the limiter. Out of scope for v1.1, and reported as
  *rate-limiting measured; cost unmeasured*.
- **The `enroll` hook makes stating the configuration unavoidable; it does not make
  stating it *correctly* unavoidable.** A process that should not hold a provider signing
  key can still be handed one — the type cannot tell. What the required hook buys is that
  omission is a compile error and re-widening it to optional is a compile error too
  (Task 2's eighth `@ts-expect-error` case). Whether the value is *right* is Plan 17-03's
  problem, at the one production construction site.

Two rejected alternatives, with the reason each was rejected:

- **A standalone provider binary** — refused because `.planning/ROADMAP.md`, section
  `### Phase 22: Reachability Guard`, fixes the reachability guard's universe at five
  runnable entry points, and a sixth would put Phase 22 in conflict with Phase 17 on day
  one (17-CONTEXT.md decision 4).
- **A provider class rather than a per-node hook** — refused because every node has the
  identical code and whether a process holds a provider signing key is a per-node setting.
  This is the same shape, and the same sentence, `bin/agent.ts:26-31` already uses about
  `--owner-id` (17-CONTEXT.md decision 5).

## Out of scope

- Any `FabricNode` behaviour beyond the one hook line. The provider key, the enrollment
  round trip on start, and the certificate on disk are Plan 17-03's.
- Persisting the authority's issuance history. `#history` (`enrollment.ts:173`) is a `Map`
  in the object, so a provider that restarts forgets every issuance and the stated
  threshold is a threshold per provider *uptime*, not per wall-clock window. Nothing in
  the criteria asks for durability; the scope of the limit is stated in Task 3's test
  comment and in the summary rather than left for a reader to infer.
- A `--forge` flag or any test-only branch in a binary. Criterion 2's forged case, and its
  self-signed case, are both constructible at the wire with production code only, which is
  what Task 1 does.
- Routing `parseCertificate`'s hex fields through Plan 17-01's `parseKeyHex`. `@o2/net` is
  a portable package and may not import `@o2/libp2p`'s transitive `@libp2p/*`
  (`purity.node.test.ts:46-52`). The key-shape check is applied one layer out, in
  `@o2/node`'s `loadCertificate` (Plan 17-03 Task 1), where the import is legal — so the
  wire parser keeps its existing string typing and nothing here becomes lenient by
  comparison.
