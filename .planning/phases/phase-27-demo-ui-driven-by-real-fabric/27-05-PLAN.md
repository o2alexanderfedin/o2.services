<objective>
Wire the π surface — UI-SPEC section 4.4's fourteen regions — over `TabApi.runPi`, which
already exists and already merges through a verified tree-reduce. This is the demo half
of MR-03 through MR-07: the fabric's combiner has been wired at `bin/agent.ts` and
`bin/bench.ts` since Phase 16 and has had **no button** since `runPi` landed on
2026-08-08.

The surface's difficulty is not the dispatch. It is that a lone tab **cannot run the
reduce at all** — `reduceJob` excludes the submitter from the combine executor set by
contract, so the first visitor gets `reduceAttempted: false` with the fabric's own
reason. Every visitor who opens this page first is that visitor. UI-SPEC section 5.3
rules how it reads: **a condition of the topology, not a failure and not a zero.** No
refusal colour, no error tone, no `0` — a panel headed *This claim needs a second
device.* carrying `reduceReason` verbatim, because the page has no better words for it
than the fabric's.

Three things this surface must refuse to draw, each because the reading does not carry
them: per-combine node states in the tree diagram, per-shard partial rows, and an
attestation panel. `runPi` returns no attestation field, unlike `runColouring`, and a
receipt borrowed from the colouring run would be a receipt for a different job.

Purpose: give the fabric's one verified aggregation a surface, and make the lone-tab
case read as topology rather than as breakage.
Output: `surfaces/pi.ts`, the π panel's 14 regions, `WIRED_SURFACES` gaining `'pi'`, and
`demo-pi.e2e.test.ts` covering both the lone-tab and the two-tab arms.
</objective>
