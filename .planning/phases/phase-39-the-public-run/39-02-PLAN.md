## Phase Goal

**As a** project owner, **I want to** send the first invite only after seven conditions hold on a dated
checklist with named evidence for each, and to send invites in stages by region and by cohort slice with
the funnel read between them, **so that** the fabric's headline claim is finally measured on hundreds of
independently-owned devices rather than asserted.

<objective>
A known defect stands between the funnel and criterion 2, and it is not fixed.

`funnelEndpointFromRelay` derives `https://<host>/funnel` from the relay multiaddr. That is true of the
deployed Cloudflare Worker — which is why the derivation was added on 2026-09-03 after a run of 6 615 relay
reservations reported nothing — and **false of any self-hosted seed**, which serves libp2p WebSocket on that
port and answers **400**. It fails immediately, so nothing hangs. But the funnel *looks configured and
collects nothing*.

Criterion 2's words are *"reporting live at the moment the first invite is sent, observable in its own record
with a timestamp preceding the invite — not stood up afterwards from stored events."* A silently-dropping
funnel is a criterion-2 **failure that presents as a pass**.

The fix that fits the existing scope fence is **probe before targeting**: derive the origin exactly as now,
and install the send port only once the origin has answered with a funnel-shaped body. Failure closes to
exactly today's inert behaviour, so the change can only ever make the funnel quieter than it already is.

Purpose (why this plan carries `RUN-07` rather than a funnel id): RUN-07 requires that *each stage's go/no-go
reads the funnel before the next invite is sent*. A funnel that silently drops makes the staged go/no-go
unexecutable — every stage would read zeros and the reader could not tell "nobody came" from "nothing was
collected." The staged rollout is the requirement this defect blocks.
Output: `probeFunnelTarget`, its wiring, and two behavioural arms.
</objective>

**Three existing properties the executor must not "fix".**
1. `#held` holds reports composed before arming *or* before targeting, and they keep **the hour they
   happened**, not the hour they were flushed. So a `target()` delayed by a network round trip loses
   nothing — that is the repair of 2026-09-03, and it is what makes an asynchronous probe safe.
2. `target()` is **first-install-wins**. A page that named `?funnel=` already holds a port, so a later
   relay-derived call is a no-op rather than a redirection. The probe must preserve this: probe only the
   derived branch, never the explicitly configured one.
3. `funnel-reporter.node.test.ts` scans this module's **own source** and refuses any absolute origin
   literal — *"not even a scheme joined to a host"* — and scans `demo/main.ts`'s funnel path for the same.
   That is why `funnelEndpointFromRelay` assembles its scheme from a variable. The probe must not introduce
   one.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| relay multiaddr → collector origin | An origin derived from an address the page was handed at bootstrap |
| collector response → send-port installation | An untrusted HTTP body decides whether a port is installed |
| visitor page → collector | Report bodies cross from an untrusted client into a Durable Object |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-39-06 | Spoofing | `probeFunnelTarget` | mitigate | The body must carry a `schemaDigest` string; a bare `200` from any host is refused, so a hijacked relay address cannot turn an arbitrary origin into a collector by answering at all |
| T-39-07 | Tampering | derived origin | accept | The origin comes from the relay the visit already bootstrapped through and already trusts for signalling; a compromised relay is a larger failure than a misdirected funnel, and the scope fence forbids a literal fallback |
| T-39-08 | Information disclosure | the probe request | accept | A `GET /funnel` carries no report and no identifier; it reveals only that a browser reached the origin, which the WebSocket bootstrap already revealed |
| T-39-09 | Denial of service | +1 request per visit | mitigate | Counted explicitly and fed into plan 39-04's per-stage request budget, against the measured 165-requests-per-reservation figure |
| T-39-10 | Repudiation | a silently dropped report | mitigate | This is the defect being closed: `FunnelReporter.active` reads `false` for an uninstalled port, so "inert" is distinguishable from "sent" from "already sent" |
| T-39-11 | Elevation of privilege | none | accept | The probe reads; it grants nothing |
</threat_model>
