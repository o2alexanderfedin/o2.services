**Four dispositions that will be needed, each with a named example measured on 2026-08-04:**

- **scheduled, with an owner** — `core/delegate` and `CapabilitySupplier`. Called only from
  `packages/node/src/capability-fixture.ts`, which no entry point imports. **Phase 23 criterion 5
  is scheduled to give them a real caller, and Phase 23 is numbered after this phase.** The
  ROADMAP's own Phase 22 entry says *"criterion 1 above should find `delegate` reachable by the
  time this phase runs; if it does not, Phase 23 did not finish its job and that is the finding"*.
  On the current execution order that sentence is wrong about the order. See `<open_rulings>` 3.
- **superseded by a landed phase** — `core/runResilient`, whose whole point is that nothing calls
  it. Phase 20 criterion 1 requires it to be *"either merged in or removed"*. If it is still in the
  tree at execution time, that is a Phase 20 finding, not a disposition.
- **a dynamic edge no static tracer can see** — check whether any remain after 22-01's four edge
  classes. `core/runTask` and `core/runTaskAndPost` were the two that mattered and 22-01 covers
  them; if the reading still reports them unreachable, 22-01's edges regressed and that is a
  blocking finding rather than a disposition.
- **published API surface with no in-repo caller** — e.g. `net/checkBlockstoreConformance`,
  `bench/sweepNodeCount`. These are the honest hard cases: a barrel export nothing calls *is* the

**The register's prior art**: `mutation-ledger.ts` — data with a predicate, and a cheap layer

`WITHOUT_A_CHECKABLE_CLAIM`, a *named* exemption list rather than a silent filter. 19-12 found the
mutation ledger's anti-vacuity floor stale at 23 while the ledger held 42; copy the floor and do
