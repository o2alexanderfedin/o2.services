# Phase 20 · Plan 02 — Every node keeps a real ledger, and puts its own row in it

**Closes (mechanism half):** criterion 5's clause *"because every node now supplies `serveAgent`'s
`ledger` hook and reported outcomes are recorded rather than discarded"*, and BROW-02's cross-node
merge. The **reading** — a demo tab showing counts it could only have learned from a peer — is
20-06.

<objective>
`serveAgent`'s `ledger` hook is required, and every production node passes the opt-out sentinel:
six sites, all count-pinned by `serve-agent-hooks.node.test.ts`. So the report branch answers
`counts: []`, `publishStartOutcome` merges nothing, and the demo's own UI comment says so against
its own interest.

**Handing those sites a real ledger is necessary and is not sufficient.** `serveAgent` records only
what a *peer* told it. A node's own outcome never enters its own ledger, so a peer that asks is
handed back **its own row** — and `mergeOverlapping` takes the maximum per key, so a merged report
across two tabs reads `1`, and across twenty tabs reads `1`. Read `20-CONTEXT.md` §
*"The peer ledger cannot merge above 1 until a node records its own row"*; that section works the
arithmetic through.

**The demo deferred this deliberately and named its condition. The condition is met.**
`demo/index.html`'s `refreshReport` comment defers a serve-side ledger *"behind the magnitude bound
and the label whitelist"* because publishing per-peer outcomes before those land is the
fingerprint `start-outcome.ts`'s disclosure promise exists to prevent. Both landed:
`MAX_REPORTED_COUNT` and `isStartBrowserLabel`, both enforced in `protocol.ts`'s `parseCounts`.
**This plan re-measures both rather than citing them**, because a deferral lifted on an unverified
condition is worse than one left in place.
</objective>
