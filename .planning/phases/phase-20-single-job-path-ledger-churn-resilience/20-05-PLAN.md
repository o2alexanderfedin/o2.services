<objective>
CHURN-01 has an in-process reading: `packages/net/src/churn.test.ts` kills nodes on a
`MemoryNetwork` fabric and `runResilient` recovers. **That reading is one tier below the criterion
and it is about to be deleted**, because `runResilient` is removed in 20-12. This plan is where the
property moves to real operating-system processes and to the only job path.

**The entry point takes the substitution this project has recorded three times.** `bin/agent.ts`
submits no job — zero occurrences of `submitJob`, `JobSpec` or `executeVerified`. *"Run through
`bin/agent.ts`"* is satisfiable only as **"run across `bin/agent.ts` processes"**, an in-process
requestor submitting to spawned agents. **Say that in the file's header**, not only in a planning
document.

**"Correct" is the word to be careful with.** A pinned expected output is an absolute reading that
encodes the fixture, and it goes stale the first time the kernel changes. Take the comparison
instead: the identical job over the identical inputs with nobody killed, in the same run. A ratio
or an equality taken inside one run cancels the host, the load and the fixture at once — the
standing rule in `CLAUDE.md` § Measurement.
</objective>

From `packages/node/src/tree-reduce-agents.node.test.ts` — the fixture and, more importantly, the
**distinction between two ways of ending a process**, which this plan depends on:

- `stopAgent` — SIGTERM. `bin/agent.ts` installs SIGTERM/SIGINT handlers that call `node.stop()`,
  so a SIGTERMed agent **leaves**: it closes its connections and its peers learn it is gone.
- `killAgent` — SIGKILL. The process **vanishes**: nothing is closed and the requestor discovers it
  the way it would discover a closed laptop, by asking and getting nothing back.

**Criterion 2 says "killing", and a graceful leave is the easier case.** Use `killAgent`. That file
also records that its kill is *"a vanish, not a shutdown"* and that **no deletion in production code
turns that assertion red** — it measures the test's own kill and is a precondition, not evidence.
Copy the precondition and copy the sentence that says what it is.

The mid-flight staging technique in that file is worth copying exactly: the kill is triggered from
a wrapper around the **production** dispatch, so it happens at a known point in the run rather than
after a sleep.

From `packages/net/src/churn.test.ts` — the behaviours the in-process reading currently holds, each
of which this file should be able to state about real processes: a node that is *gone* costs an
attempt and the next node recomputes; a node that dies *between placement and dispatch* costs a
full timeout; a module that traps is given up on rather than burning the fabric. **List in the
summary which of these this file now covers**, because 20-12 has to account for every case in that
file when it is deleted.

From `packages/core/src/job/submit.ts` after 20-01 — the generation loop, the re-dispatch count and
