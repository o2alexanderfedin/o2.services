# Phase 20 · Plan 11 — The job survives its requestor

**Closes:** CHURN-03 — *coordinator state is checkpointed to content-addressed storage so a
departed requestor does not lose the job.* **No success criterion names this**; see the wave note
and `20-CONTEXT.md`.

<objective>
`checkpoint.ts` is complete, unit-verified, and imported by nothing outside its own test and
`churn.test.ts`. `coordinator.ts` does not import it at all — so even the second job path, the one
nothing calls, does not checkpoint. Its REQUIREMENTS row says exactly that.

**The property that makes this cheap is already the fabric's.** `PROJECT.md`'s recorded invariant:
*liveness changes who computes a task and when, never what the answer is*, because a result is a
pure function of `(module, input, partition)` and is content-addressed. So a checkpoint does not
have to carry state — it names CIDs, and resuming is "do the shards nobody has done yet."
`churn.test.ts`'s existing resume case says this against itself: *"the checkpoint names results, it
does not carry them. That is the whole [point]."*

**The interesting failure is not the happy path.** A checkpoint written after every shard is a
write per shard on a path that is otherwise pure; a checkpoint written once at the end is useless.
Where the writes go, and what a *torn* or *lost* checkpoint does, is the content of this plan —
and `recoverCheckpoint` and `checkpointChain` exist precisely because the newest block can be the
one that is gone.

**And there is a scope line to hold.** This plan does not build requestor failover, leader
election, or a job registry. It writes a record and reads it back. If the design starts needing
two requestors to agree on which of them owns a job, stop: that is shared mutable state requiring
consensus, and `19-CONTEXT.md`'s NO BLOCKCHAIN ruling covers exactly this shape.
</objective>
