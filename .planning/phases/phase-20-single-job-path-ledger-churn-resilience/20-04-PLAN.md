From `packages/node/src/discovery-agents.node.test.ts`, the `criterion 2 — sample, refuse,
re-pick, complete` describe. Two mechanisms already exist in it and both are reusable:

- **`admitThenSaturate`** — an `AdmissionControl` wrapper that lets the first node accept the
  offer, then occupies that node with a real long-running `exec` the file does not await, then
  polls `untilFull` until the node reports itself full. So the dispatch that follows meets a node
  **genuinely at its limit**, not one about to be. The file's own comment: answering an offer
  reserves nothing, so an accepted offer is a statement about the past by the time the exec arrives.
- **`EXEC_STAGE_VALUE`** and `SHARD_VALUE` — deliberately different slot keys, because
  `serveAgent`'s exec slot key is derived from `inputCid:partitionIndex` and a same-key occupation
  would produce a *duplicate* refusal rather than an *over-committed* one. The file documents the
  distinction; two different refusals, and only one of them is SCHED-06's.

The refusal text asserted today is `over-committed: 1 of 1 slots in use`, composed in exactly one
place (`packages/core/src/placement.ts`, search `over-committed`).

The file also records why the reading goes through `verification.failures` and not through
`shard.rejections`: `submit.ts` fills `rejections` from `planWithOffers`' **placement-stage**
refusals only, so an exec-stage refusal is structurally invisible there. **Check whether 20-01
changed that** — a second generation produces a second placement, and its rejections may now
appear. Measure it; do not assume either way.
