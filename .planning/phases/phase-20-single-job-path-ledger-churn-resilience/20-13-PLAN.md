# Phase 20 · Plan 13 — The ledger, the rows, and the roadmap line that was wrong

**Closes:** the phase's bookkeeping — and one of this project's recorded failure modes, which is
that a correction living in a summary reaches nobody.

<objective>
Twelve plans have each watched plants go red and recorded the observed text. This plan turns them
into ledger entries that a guard can check, moves the requirement rows that changed, and fixes the
roadmap line this phase measured false.

**The ledger's own rules constrain what may be written.** `problemsWith` rejects an entry with an
empty `signature` or `caughtBy`, and `mutation-guard.node.test.ts` reddens when a `find` string no
longer matches its file. So an invented signature is a false entry, not a harmless one. Phase 19
recorded six plants deliberately **absent** from the ledger because no failure text was captured —
that is the correct treatment and it is available here.

**Greens are entries too.** Phase 19's 19-12 recorded plants that left a file green *as results in
their own right*, because a green nobody expected is the most informative thing a plant produces.
Any Phase 20 plan that reported "this plant left the file green, and here is what actually carries
the claim" gets that recorded, not dropped.

**And one roadmap line is wrong on the record.** Phase 20's `Research: None` says
*"`runResilient`'s lease/speculation/coverage machinery exists and is unit-verified in Phase 7; the
gap is that nothing calls it."* True of speculation and coverage; **false of lease renewal**, whose
`LeaseTable.renew` and `shouldRenew` had no caller anywhere, including inside `runResilient`. Phase
19 corrected its own `Research:` line in place when it was measured wrong; do the same.
</objective>
