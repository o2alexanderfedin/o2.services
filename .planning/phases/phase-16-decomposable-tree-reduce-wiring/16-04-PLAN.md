**Phase 16 — Decomposable Tree-Reduce Wiring · Plan 04 of 04**
**Closes (in part):** MR-03, MR-04, MR-05 — the reduce reaches the published benchmark.
**Satisfies:** ROADMAP Phase 16 success criterion 4, first clause. The second clause is
routed by name, not claimed — see *What criterion 4 does not measure* below.
**Depends on Plan 16-02's directed fetch-back.** The tree this shard count produces is deeper
than one level, and without that step a combine above level 1 finds its inputs nowhere: in
`memoryFabric` each worker's block source is `() => ['requestor']` (`bin/bench.ts:168`) over
a plain `MemoryBlockstore` (`:147`) that has no fallback, and in `realFabric` every node
dials the requestor so each one's `transport.peers` is `[requestor]`. Neither lets one
worker see another's store. This plan's value guards in Tasks 3 and 4 assume 16-02 landed; if
it has not, every reduce row is an em dash and Task 3's value guards fail — which is the
correct failure, and Task 4 says what to do about it rather than leaving the two tasks to
contradict each other.
**This plan also settles the requirement rows** (Task 4). The phase does not make
`REQUIREMENTS.md:581-586`'s stated reason false, and it must not be recorded as if it did.

`packages/browser/demo/main.ts:331`, which calls `answerOf` (`packages/demo/src/job.ts:231-238`),
a `for` loop over `JobResult['shards']` returning the first `'found'` colouring. Nothing

Two decisions are made explicitly here rather than left implicit, because 16-CONTEXT.md
Risk 3 requires it and because the roadmap goal offers a choice this plan has to take.

- **`makespanMs` keeps its pre-registered meaning — the bracket *and* the sample.**
  `.planning/BENCHMARK-METHODOLOGY.md:60-63` defines makespan as *"wall-clock from job
  submission to the last shard's result being available to the requestor"*. A combine happens
  **after** the last shard's result, so folding it into `makespanMs` would silently redefine
  the primary metric across every number published on 2026-07-27. The reduce gets its own
  `performance.now()` pair and its own table. The opposite case — a user waits for the
  aggregate, not for the last shard — is real, and it is recorded in the Amendments entry
  rather than suppressed; it is not taken, because a reader given two columns can add them
  and a reader given only the sum cannot subtract them.

  **An earlier draft of this plan broke the metric a second way and the fix is the reason
  this bullet is long.** It redefined `const complete = result.ok && result.job.complete &&
  reduceOk`. `SweepResult.makespan` is `summarise(completed.map(o => o.makespanMs))`
  (`harness.ts:161`) over runs filtered by `o.complete` (`:154`), so that edit would have
  conditioned every published p50/p95/p99 on the *reduce* having succeeded — a different
  population from every number published on 2026-07-27, even though each individual
  `makespanMs` still measured the same interval. Preserving the bracket while changing the
  sample is the subtler version of the same error, and a must-have truth that says "the
  primary metric keeps its meaning" while the sample moves is worse than no truth at all.
  **So `complete` is left exactly as it is** — every shard agreed — and the reduce's verdict
  travels as `reduce.ok` on the observation, which `reduceOf` filters on. A failed
  aggregation blanks the reduce row and leaves the makespan row intact, which is also the
  more useful reading: a reduce that could not find an executor says nothing about how long
  the map took.
- **`answerOf` stays; the demo's linear scan is not replaced in this phase.** The ROADMAP
  goal sentence says "replacing the demo's linear scan", but no success criterion names the
  demo — all four name `bin/agent.ts` or `bin/bench.ts`. Two facts make replacing it wrong
  here: `packages/node/package.json` has no `@o2/demo` dependency and adding one would let
  the Node agent import the colouring kernel's host code (`@o2/browser` depends on
  `@o2/demo`; `@o2/node` deliberately does not); and `answerOf`'s semantics — first
  `'found'` colouring wins — is not `fabricCombiner`, and making it one would require the
  per-node combiner to vary by job, which Plan 16-01's decision rules out. The goal sentence
  is therefore read as naming the *class* of gap ("the only aggregation any entry point
  performs is a linear scan") and this phase closes it at the entry points the criteria
  name. See `## Out of scope` for the full disposition.

## Out of scope

Phase-wide dispositions, recorded here because this is the last plan of the phase. None of
these is deferred for difficulty; each has a stated structural reason.

- **`answerOf` is kept, not replaced and not deleted.** The choice is made explicitly:
  **keep**. It has a live production caller (`packages/browser/demo/main.ts:331`), so
  deleting it would break the demo, and replacing it would require a
  `@o2/node` → `@o2/demo` dependency that does not exist and must not be created — the Node
  agent would then be able to import the colouring kernel's host code. Its semantics (first
  `'found'` colouring wins) is also not `fabricCombiner`, and making it one would require a
  per-node combiner that varies by job, which Plan 16-01 rules out on the grounds that a
  mismatch would surface only as an undiagnosable `disagreement`. Closing this properly needs
  the deferred content-addressed combine module.
- **`colouringCombiner` in `@o2/demo` is deliberately not planned.** 16-CONTEXT.md offers it
  as a cheap partial move: a `Combiner` over the existing `partialOf` where `'found'` beats
  `'exhausted'` beats `'budget'`, ties broken by the smallest `bits` — a semilattice join,
  therefore associative, commutative and idempotent. It satisfies **no** success criterion,
  and it would add an exported function with no production caller to a repository whose
  entire v1.1 milestone exists because it has too many of those. Preferring not to invent a
  caller is the same rule that governs everything else in this phase.
- **A production late-arrival channel for combine results.** `executeReduce` stops at
  `wanted` replicas and cannot receive a result that arrives afterwards. Criterion 3's
  duplicate is staged by the test, and Plan 16-03 says so in the test itself. Building the
  channel is new machinery no criterion asks for.
- **Job-supplied combine code** — the general form of Plan 16-01's fixed combiner. Needs a
  guest that can read *k* partials, which means either a multi-input `Task` ABI or a
  CBOR-capable guest. A phase, not a step.
- **Capability chains on the `combine` request** — Phase 15, AUTH-03. Plan 16-02 makes the
  gap fail closed rather than leaving it open, and names Phase 15 at the refusal.
- **Per-request capacity refusal on `combine`** — SCHED-06, Phase 13.1. Whatever that phase
  establishes for `exec` is what `combine` should reuse; a second admission path invented
  here would guarantee the two diverge.
- **Quorum composition over combines** — Phase 19. `executeReduce`'s `redundancy` gives *k*
  replicas ranked by rendezvous; it does not give anti-affinity or a backbone-anchored
  replica, and it should not be stretched to.
- **The reduce on the browser tier.** `BrowserNode` inherits the combine handler for free,
  and Plan 16-02's `combine.test.ts` / `reduce-job.test.ts` run under real Chromium in the
  `browser` vitest project — but that exercises the portable modules, not `BrowserNode`,
  which has never been started in a browser anywhere in this repository. Compiled and never
  executed is the honest status. Phase 19's one-host multi-browser standard is where it
  becomes runnable.
- **NET-09's early-stream cliff.** Plan 16-03 carries the contingency and the finding if it
  fires. Raising `SHARDS` above 8 in `bin/bench.ts` is out of scope for exactly that reason.
- **Varying the fanout across the sweep — considered, and rejected for a stated reason.**
  This is the alternative that would make `tree depth` and `combines` carry information
  instead of standing as two columns the run may show constant, and it is recorded here so
  that a reader who asks the obvious question finds an answer rather than assuming nobody
  asked it. **The alternative — varying the fanout across the sweep so the columns carry
  information — was rejected because it would make the rungs' reduce timings incomparable
  with each other, which is the only thing the reduce table is for.** A reduce table whose
  rungs each walked a differently-shaped tree would answer no question about node count,
  which is the sweep's independent variable. So the fanout is held fixed and the two columns
  are published for legibility with the `unmet` entry saying what they are; this is the
  entry Task 1's `ReduceObservation` doc points at in one clause, and Task 2's `unmet`
  entry (b) is its artifact-side restatement.
