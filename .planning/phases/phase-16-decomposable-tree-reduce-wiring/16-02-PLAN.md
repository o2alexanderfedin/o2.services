<objective>
Give `executeReduce` a caller and `deriveReduceTree` a job.

16-CONTEXT.md's phase boundary is a table with one column of zeros: `deriveReduceTree`,
`executeReduce`, `localDispatch` and `Combiner` have **no production callers anywhere**,
and `rendezvousRank`'s single production-looking caller (`placement.ts:124`) terminates in
a test in every direction. A barrel export is not a wire.

This plan adds the three pieces that make it one, in dependency order:

1. **The handler** — `serveAgent` learns to answer a `combine`. It gains **no new
   `AgentOptions` field**, and that is a decision rather than an economy: Phase 11's rule is
   that an optional hook with a silent default is a hole, and the corollary is that a hook
   exists to record a *decision*. There is no decision here. Every node must be able to run
   a combine, or `executeReduce`'s rendezvous ranking would be selecting among nodes that
   differ in what they can do — which is the one thing this project has ruled out. The
   branch uses `options.blockstore`, which `serveAgent` already takes, and the fixed
   `fabricCombiner` from Plan 16-01.
2. **The dispatcher** — `remoteCombineDispatch`, the remote sibling of `localDispatch`,
   built on the same file-level reasoning `churn.ts` states for `remoteDispatch`.
3. **The driver** — `reduceJob` in `@o2/net`, beside `submitJobWithEgress`. It cannot live
   in `@o2/core`: `purity.node.test.ts:167` asserts `packages/core/package.json` declares
   zero `@o2/*` dependencies, and the executors a combine is ranked over are peer ids on an
   `RpcEndpoint`. This is the identical constraint that produced `submitJobWithEgress`, and
   it gets the identical resolution.

**Before any of that: a combine's inputs have to be reachable, and above level 1 they are
not.** 16-CONTEXT.md decision 1 claims the serving node resolves each `inputCid` through
`options.blockstore` "with no change to this phase's code". That is true of the *leaves*,
which the requestor stores and serves. It is false of every level above. The chain of facts,
each read off the source rather than inferred:

- A combine result is written to the **executing** node's local tier only. This plan's
  handler ends in `options.blockstore.put`, and `FetchingBlockstore.put` delegates straight
  to local (`packages/net/src/block.ts:65-67`).
- **Nothing announces it.** Every production `serveAgent` passes `index: 'serves-no-records'`
  (`fabric-node.ts:420`, `browser-node.ts`, `bin/bench.ts:152` and `:177`), so no provider
  record exists for that CID anywhere.
- **No fabric in this repository lets one executor's block source see another executor's
  store.** `distributed.test.ts:70` gives each worker `RpcBlockSource(rpc, () => ['origin'])`
  while the origin serves a plain `MemoryBlockstore` (`:52`); `bin/bench.ts:168` gives each
  worker `() => ['requestor']` over `originStore` (`:147`); and in Plan 16-03's process
  topology the submitter dials outward, so each agent's `transport.peers`
  (`libp2p-transport.ts:156-158`) is exactly `[submitter]` and the agents are not peers of
  each other.

Level 1 succeeds — its inputs are the leaves. Every level above it takes combine *results* as
its inputs, and those are reachable from nobody, so `executeReduce` walks the whole ranking
(`reduce.ts:271-279`), every executor answers the null arm, the root lands in `failed`,
`rootCid` is null and `ok` is false. The unit tests in `reduce.test.ts` hide this because
`localDispatch` is driven with **one shared** `MemoryBlockstore` (`:165-175`) and
`MemoryNetwork.peers` returns every registered node (`transport/memory.ts:116-118`).

**The mechanism chosen, and the two that were not.** Task 2 makes `remoteCombineDispatch`
fetch the result block **directly from the peer that just reported it** — one `block`
request to a known holder, hash-verified, written into the requestor's store — before it
returns the CID to `executeReduce`. Because `executeReduce` awaits a whole level's
`Promise.all` before starting the next (`reduce.ts:248`), every level's results are resident
at the requestor before the next level asks for them, and the next level's combine node gets
a **local hit** at the requestor rather than a chained fetch.

- *Rejected: carrying the result bytes in the combine reply.* It would put a payload where
  the whole design is an address, breaking the property 16-01's `Object.keys` assertion
  exists to hold.
- *Rejected: wiring the `providers` index so a combine node can find a holder.* That means
  replacing `index: 'serves-no-records'` with a real `RecordIndex` at four production call
  sites in files five other phases also edit — and supplying that hook is SCHED-01's job,
  Phase 18. Inventing a second, reduce-only record path here would guarantee the two diverge.
- *Rejected: leaning on chained fetch through the requestor.* It is what the topology would
  otherwise force, and it **deadlocks**: a non-holding agent answering a block request asks
  its only peer — the requestor — straight back, and the requestor's `#inFlight` map hands it
  the promise already blocked on that same agent (`block.ts:74-76`). The wait is circular and
  is broken only by timeout. That path survives for a CID nobody holds; its cost is **not**
  derived anywhere in this phase, and Plan 16-03 sizes its RPC budget against what it
  measures rather than against an arithmetic estimate.

  **The residue is accepted, and its closure is named rather than left implicit**, because
  Plan 16-03 points here for exactly this and a bare pointer to a phase number resolves to
  nothing. The closure is a **re-entrancy rule: never ask back the peer you are currently
  answering.** Enforcing it needs `from` — the identity of the peer whose request is being
  served — threaded through to the block source, which is a `serveAgent` hook, and
  16-CONTEXT.md decision 2 rules a new hook out for this phase. The other half, refusing the
  request at admission rather than at the block source, is SCHED-06 (Phase 13.1), and that is
  where it belongs: whatever admission `exec` gets is what `combine` should reuse. What this
  plan does instead is take the path off the reduce's happy path entirely — after Task 2's
  directed fetch-back every input a combine asks the requestor for is already resident there,
  so the request is a local hit and never enters the fan-out. The cost of a frame naming a CID
  nobody holds pre-dates this phase and applies equally to `exec`; it is recorded, unmeasured,
  and not relied on by anything here.

**The cost, stated rather than elided.** One extra small block transfer per combine, from
executor to requestor, and the requestor ends up holding every intermediate result. How many
transfers that is for a given tree is a **measurement**, not an arithmetic claim: count them
in the run and record the figure in the summary. The wire stays address-only in both
directions; what moves is a block, by CID, through the same `block` request every other part
of the fabric uses.

Everything here is proven over `MemoryNetwork`, in-process. `memory.ts:9-11` names this
exact workload in its own docstring — *"100+ nodes in one process with deterministic
delivery is how the scheduler and reduce-tree logic get exercised without a network in the
way"* — and it is the right place to get the mechanism correct with no process overhead.
It is explicitly **not** sufficient evidence for ROADMAP criterion 1, which names
`bin/agent.ts`. Plan 16-03 proves the boundary.

What does **not** change, stated so a reviewer does not go looking:
`agent-contract.test.ts`'s seven `@ts-expect-error` cases and its *'AgentOptions requires
all seven hooks'* describe block; `serve-agent-hooks.node.test.ts`'s sentinel counts; and
the four production `serveAgent` call sites (`fabric-node.ts:411`,
`browser-node.ts:264`, `bin/bench.ts:144` and `:170`). None of them needs an edit.

What *does* change in `agent.ts`, so the boundary with Plan 16-01 is unambiguous: 16-01 left
a one-line placeholder branch there — `{resultCid: null, reason: 'combine not implemented in
this build'}` — solely so the eighth union member did not reach the exec branch's
`request.task` and break `tsc`. This plan **replaces** that branch with the real handler and
deletes the `describe` in `combine-wire.test.ts` that asserted the placeholder's reply. A
grep for the placeholder reason string returning any hit after this plan means the
replacement did not happen.

Purpose: turn four unit-verified functions into a call path.
Output: a serving node that answers combines; `remoteCombineDispatch` and `reduceJob`
exported from `@o2/net`; an eight-node in-process reduce, over executors that cannot see
each other's stores, whose root CID is bit-identical to a single-process reference.

## Recorded decisions

Three dispositions this plan takes deliberately. Each is recorded because it is a decision
about what the design does **not** protect, and a reader who has to re-derive it will
re-derive it differently.

- **The requestor stores every projected partial and, after Task 2, every combine result in
  a blockstore it serves to peers.** Any connected peer can therefore fetch any leaf or any
  intermediate aggregate by CID; the directed fetch-back widens this from the leaves to the
  whole tree. **Accepted.** A partial is by construction a summary and not raw data — that is
  what `MAX_PARTIAL_BYTES` exists to keep true, and this plan makes it the first thing the
  handler enforces. **And a sovereign input never becomes a leaf**: `reduceJob` projects the
  shard's agreed *output*, and a sovereign task's raw input has never left its owner's node
  (Phase 13's `EgressGuard` refusal). Recorded because "the requestor serves the leaves" is a
  fact a reader should not have to derive, and because the sovereignty answer to it is the
  project's core claim and must not have to be reconstructed either.
- **At `redundancy: 1` the aggregation is unverified, and that is the caller's choice —
  exactly as it is for a shard.** A combine node returning a CID that is not the merge of the
  inputs it was given is a wrong answer that looks like a right one, and the mechanism against
  it is `redundancy >= 2`: two independent executors per combine, with `executeReduce`
  reporting divergence as a `disagreement` (`reduce.ts:305-307`) and `ok` false. That
  mechanism is asserted by Task 3's `minReplicas`/`disagreements` pair. What is recorded here
  is the *other* arm — the one with no assertion, because there is nothing to assert: at
  redundancy 1 there is no second executor and nothing checks the answer. The parameter is the
  caller's, and so is the exposure.
- **`remoteCombineDispatch` discards every reason a peer gave.** `CombineDispatch` is
  `Promise<CID | null>`, so an operator debugging a reduce that failed everywhere has
  `recomputes` and `executedBy` and nothing else. **Accepted.** Recovering the reasons means
  widening a `@o2/core` port no criterion asks for, and an observer callback would be an
  optional hook with a silent default, which `.planning/PROJECT.md`'s Key Decisions rule out.
  Documented in `combine.ts`'s own table so it is a known cost rather than a discovery.
