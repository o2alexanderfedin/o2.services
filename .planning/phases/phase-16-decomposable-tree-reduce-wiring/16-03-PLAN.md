public one whose shard inputs travel to the executors by CID — data does move map-side, by

<objective>
Prove the reduce across eight real `bin/agent.ts` processes.

Plan 16-02 established the mechanism over `MemoryNetwork`. That is deliberately not enough
for criterion 1, which names `bin/agent.ts`: eight endpoints in one Vitest process share a
heap, an event loop and a module registry, so a subtle shared-state dependency would pass.
`two-process.node.test.ts:17-27` argues exactly this in its own docstring, and this plan is
that argument applied to combines.

Two shape decisions are inherited from 16-CONTEXT.md decision 9 and are load-bearing:

- **The submitter dials outward, one connection per agent.** `bin/bench.ts:424-430`
  publishes why the real-transport ladder is excluded above ~5 nodes:
  `INBOUND_CONNECTION_THRESHOLD = 5` **per host** (`packages/libp2p/src/constants.ts:65`),
  and in `realFabric` every node dials the requestor, so the requestor absorbs N inbound
  connections from one host. Inverted, each agent sees one inbound connection and the
  submitter makes eight outbound dials, which nothing caps. This is what
  `two-process.node.test.ts:126-132` and `sovereignty-placement.node.test.ts:141-145`
  already do; this plan is the first to need the reason written down.
- **The submitter runs a short RPC budget, and what it has to cover has to be written down
  because the obvious reading is wrong.** NET-10 (`REQUIREMENTS.md:463-472`): a refusal
  reaches the requestor as a timeout, and `DEFAULT_RPC_TIMEOUT_MS` is 30 000 (`rpc.ts:23`).
  A killed combine node's fallthrough therefore costs a whole budget per rank step. That is
  a NET-10 symptom, **not a property of the reduce**. But the budget is asymmetric and only
  one side of it is ours:

  - The submitter's side is settable — `FabricNode.start({rpcTimeoutMs})`.
  - **The agents' side is not.** `packages/node/src/bin/agent.ts` parses exactly four
    options (`dir`, `port`, `owner-id`, `can-execute-sovereign`) and exposes **no timeout
    flag**, so every agent runs the hard-coded 30 000 default. Verify that before sizing
    anything; it is the term that decides which side gives up first.
  - The path that used to dominate is now off the reduce's happy path, and that is what
    makes a short submitter budget safe. Before Plan 16-02's directed fetch-back, a
    level-2 combine node asking the submitter for a level-1 result would make the submitter
    fan out to the agents; each non-holder answers by asking the submitter straight
    back, where `#inFlight` (`block.ts:74-76`) hands it the promise already blocked on that
    same agent. The wait is circular and breaks only on timeout. **How expensive it is is
    not derived here** — three independent attempts to derive quantities of this shape in
    this phase produced three different wrong answers — so if the run ever enters that path,
    measure what it cost and record the measurement. After 16-02, every input a combine asks
    the submitter for is already resident there, so that request is a **local hit** and never
    enters the fan-out.
  - What the budget therefore has to cover on the reduce leg: one combine round trip
    (`rpc.request` to an agent, which reads its inputs as local hits from the submitter,
    merges, and puts) plus one directed `block` round trip to the same agent. On
    the map leg it must also cover a cold-start dispatch — the agent pulling the module and
    compiling it. Size it against those, state both halves of the trade, and say plainly
    that the fan-out path still exists for a CID nobody holds and that its cost is an
    accepted, unmeasured residue rather than a number this test relies on.

`bin/agent.ts` needs **no new flag**. It already produces a node with the full serving
surface (`fabric-node.ts:411`), and 16-CONTEXT.md decision 2 means combining arrives with
it. If this plan finds itself wanting to add one, the decision has been violated: a flag
would make combining a property of *what kind of node* something is.
