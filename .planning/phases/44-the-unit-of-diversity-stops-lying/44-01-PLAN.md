# 44-01 — The provider derives the operator identity

Read `44-CONTEXT.md` first. It carries the four measurements that set this plan's scope and
the trap that decides the shape of Task 4's test.

## Task 1 — one derivation, in `@o2/core`, exported

`packages/core/src/enrollment.ts`: add `operatorIdFor(userKey: PublicKeyHex): string`
returning `` `visitor:${userKey.slice(0, 16)}` ``, exported from the barrel. Its docblock says
why the prefix is `visitor:` (the deployed browser derives it and the provider is the side
moving), and why 16 characters (an `operatorId` is compared for equality, never parsed — the
browser's own recorded reasoning at `visitor-key.ts:298`).

`packages/browser/src/visitor-key.ts`: `visitorOperatorId` becomes a call to it. **The two
spellings stop being two spellings** — that is what makes criterion 3 structural rather than
coincidental. Keep the existing docblock; add one line saying the string now comes from core.

## Task 2 — `enrol()` derives, and refuses a request that disagrees

`packages/core/src/enrollment.ts`:

- New `EnrollmentRefusal` arm `{ kind: 'operator-id-not-derivable'; supplied: string; derived: string }`,
  with a docblock in the union's existing style saying what the next action is (send the
  derived value, or stop trying to choose one).
- In `enrol()`, **after `bad-owner-proof` and before the per-user limiter**: compute
  `operatorIdFor(request.userKey)`; if `request.operatorId !== derived`, refuse. The ordering
  is deliberate and gets a comment: owner consent must be established first, because the
  derivation is only meaningful once `userKey` is proven; and it must precede the limiter so a
  mismatched request is told the specific true reason rather than `rate-limited`.
- `:1356` becomes `operatorId: derived`. It is now the same value the check passed, so the
  copy is no longer a trust decision.

**Nothing is silently overwritten** — design doc §A.2.i.

## Task 3 — the parameter leaves every client surface

The request field stays on the wire (`protocol.ts:355/:495` and the X.509 extension are
untouched). What goes is the *choice*:

- `packages/node/src/fabric-node.ts:451`, `packages/browser/src/browser-node.ts:576`,
  `packages/browser/src/tab-api.ts:970`, `packages/browser/src/capability-harness.ts:83` —
  drop `operatorId` from the enrollment options; derive it at the request-building site from
  the user key already there.
- `packages/node/src/bin/agent.ts` — remove `--operator-id`, its `:379` parse entry, the
  `:850` `--provider-addr requires --operator-id` refusal, and its slot in the `:803` usage
  string. A comment records that the flag is gone because the value is no longer the
  operator's to state.
- `packages/node/src/bin/bench.ts:1371` — drop `operatorId: bench-worker-${i}`.

Then `npx tsc --noEmit` enumerates the rest. **Fix only files this plan owns**; a whole-tree
typecheck also reports concurrent agents' mid-edit files.

## Task 4 — the case that would have caught the defect

New cases in `packages/core/src/enrollment.test.ts`:

1. **Criterion 2, hand-rolled.** One `userKey`, two requests: A carrying
   `operatorIdFor(userKey)`, B carrying `'datacentre-two'`. A is issued; B is refused
   `operator-id-not-derivable` with **both** values on the refusal. Assert the issued
   certificate's `operatorId` against a **literal** — the 16-character prefix written out, not
   recomputed from the function under test.
2. **Criterion 1's refusal text** names the supplied and the derived value.
3. **Criterion 3.** A request built the way the browser builds one — `operatorIdFor` over the
   visitor's own user key — is issued, not refused.

Task 4's cases must be hand-rolled, not built through the client builder: a builder that
already derives makes the Task 6 mutation copy an already-correct value and the plant stays
green. `44-CONTEXT.md` states this in full.

## Task 5 — `AttestationReceipt` names the issuers

`packages/core/src/quorum.ts`: `AttestationReceipt` gains
`readonly issuers: readonly PublicKeyHex[]`, built at `:402` exactly as `operators` is —
`[...new Set(agreeing.map((c) => c.issuer))].sort()`. `classifyAttestation` is **not**
changed: imposing a refusal is Phase 45's work and Phase 45 is gated on an owner decision.

Grep for whole-receipt `toEqual` and snapshot assertions before running the lane — an additive
field breaks exhaustive equality.

## Task 6 — the plant

Revert `:1356` to `operatorId: request.operatorId`. Watch Task 4 case 1 go red, record the
observed failure text, restore by the **surgical inverse** of the edit, and verify with `cmp`
against a snapshot taken immediately before planting. If it stays green, that is a blind
instrument to report, not a redundancy to accept.
