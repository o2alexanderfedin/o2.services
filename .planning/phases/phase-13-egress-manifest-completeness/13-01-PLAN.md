<objective>
Build the two pieces of `@o2/net` glue that close 13-CONTEXT.md's Risk 1 and satisfy
ROADMAP criterion 2's "retrievable from the job's own result metadata" without touching
`@o2/core`:

1. `registerSovereignInputs` — a production caller for `EgressGuard.guard()`. Today the
   only call site anywhere in the repo is `sovereign-execution.test.ts:152`, standing in
   for "the owner declared this payload sovereign." This wrapper makes that declaration
   happen automatically, on the live dispatch path, for every task labelled `'sovereign'`
   that a node is about to run — the exact registration point named in this phase's
   finding: at the moment a serving node is about to execute a sovereign `Task`, it
   already knows the input's CID and that the input is sovereign.
2. `submitJobWithEgress` — a thin wrapper over the unmodified `submitJob` that reads each
   supplied `EgressGuard`'s entry count before the call and slices the delta after, per
   13-CONTEXT.md decision 1. `JobResult` gains no manifest field (decision 2): the
   manifest is sibling metadata, computed here where `@o2/net` already imports both
   `submitJob` and `EgressGuard`.

Purpose: give `.guard()` a production caller and make a job's manifest reachable from the
call that ran the job, entirely inside `@o2/net`, with zero changes to `@o2/core`.
Output: two new exported functions, barrel-exported from `@o2/net`, each proven against
a real `MemoryNetwork` + `RpcEndpoint` + `serveAgent` fabric (not a mock) in this plan's
own tests. Plan 13-02 wires them into `FabricNode`/`BrowserNode`; this plan proves the
functions are correct in isolation first.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| serving node → its own EgressGuard | `registerSovereignInputs` is the only production code this phase adds that calls `.guard()` -- a bug here is the difference between a tap that watches and a tap that watches nothing |
| caller of `submitJobWithEgress` → the guards it supplies | The function trusts that every `EgressGuard` passed in actually wraps the transport the dispatched executors send over; it cannot verify that itself, since `@o2/net`'s job-submission layer has no reference back to how a caller composed its nodes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-13-01 | Information Disclosure | `sovereign-egress.ts` -- a sovereign task's bytes are silently never registered because the registration blockstore lookup returns undefined for a block that actually is resident elsewhere (e.g. the wrong store was wired in) | mitigate | Task 1's behavior 3 proves the skip path explicitly; Plan 13-02 wires the *local-only* store (the one that must hold owner-pinned data by construction), not the network-fallback one, and Plan 13-03 plants the "remove registration" mutation and watches the DATA-05 test fail |
| T-13-02 | Tampering | `submit-with-egress.ts` -- a caller passes guards in an order that does not match `spec.executors`/`spec.nodes`, attributing one owner's egress to another's manifest | accept | `submitJobWithEgress` takes an explicit `guards` array the caller must order correctly; it has no way to infer node-to-guard identity from `JobSpec` alone (a `JobSpec` names nodes by string id, not by `EgressGuard` reference), and misordering is a caller bug this module cannot detect without an API the phase's scope does not call for. Plan 13-03's proof test orders it correctly and this is documented in the module comment |
| T-13-03 | Repudiation | Concurrent `submitJob` calls sharing one guard interleave, so a before/after slice attributes another job's frames to this one | accept | 13-CONTEXT.md Risk 2, explicitly scoped: one job in flight per guard at a time. Documented in `submit-with-egress.ts`'s module comment rather than silently assumed |
