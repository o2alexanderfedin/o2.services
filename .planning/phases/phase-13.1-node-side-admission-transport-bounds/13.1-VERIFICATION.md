### Criterion 1 — MET

> A node at its execution slot limit refuses an `exec` request with a **stated reason** naming
> the limit, and the requestor re-picks — verified by concurrency against the real stack, not
> by a single-request unit test. Today: 4 peers × 200 concurrent `exec` requests produced 800
> simultaneous `executor.execute()` calls and **0 refusals**

**Mechanism.** The slot is taken on the `exec` branch — the one that costs a
`WebAssembly.compile` plus an `instantiate` plus a linear memory:

- `packages/net/src/agent.ts:350` — slot key derived as `${inputCid}:${partitionIndex}`,
  because an `exec` frame carries no shard id
- `packages/net/src/agent.ts:352` — `capacity.offer(...)`, the *taking* form
- `packages/net/src/agent.ts:373` — refused **before** the `try`, returning
  `{kind:'error', reason: admission.reason}`, so a refused request never reaches the executor
- `packages/net/src/agent.ts:438` — `capacity?.release(slotKey)` in a `finally` covering
  success, a failed outcome, a throw, and the `authorize` refusal that never called the
  executor
- `packages/core/src/placement.ts:389` — the stated reason names the limit:
  `over-committed: ${inFlight} of ${slots} slots in use`
- `packages/net/src/agent.ts:319-326` — the `offer` branch answers from the same counters via
  `LocalCapacity.would` and reserves nothing

### Criterion 3 — MET

> A peer cannot make a node allocate an unbounded buffer: `readMessage` enforces a declared
> maximum message size and calls `stream.abort()` past it. Today a single **64 MiB** frame was
> sent over the real transport and accepted

**Mechanism.** `packages/libp2p/src/libp2p-transport.ts:188-206` — the check sits **inside**
the `for await`, immediately after the byte count grows, not after the loop:

```
      total += flat.byteLength
      if (total > max) {
        const error = new InboundTooLarge(
          `inbound message from ${from} exceeds ${max} bytes (reached ${total}) — stream aborted`,
        )
        stream.abort(error)
        throw error
      }
```

That placement is the whole content of NET-08 — a cap applied after the loop has already paid
for the allocation it exists to prevent. The declared bound is
`MAX_INBOUND_MESSAGE_BYTES = 8_388_608` (`packages/libp2p/src/constants.ts:118`), overridable
per node via `maxMessageBytes`.

A second bound closes what the per-message cap cannot: a per-peer accumulation budget
(`libp2p-transport.ts:152-163, 256`), derived as `maxMessageBytes ×
MAX_INBOUND_MESSAGES_IN_FLIGHT_PER_PEER` (`constants.ts:157`, value 4) so a budget below one
legal message cannot be expressed. A peer that never closes write is bounded across
concurrent reads, and `InboundOverBudget` also aborts the stream (`:218`).

**Test run.**

```
npx vitest run packages/node/src/transport-bounds.node.test.ts
→ Test Files  1 passed (1)   Tests  16 passed (16)   Duration 13.29s
```

Real transport. `transport-bounds.node.test.ts:231-422` covers: refuses a frame one byte over
an overridden bound and keeps serving; **resets the stream** so a sender still holding a yamux
window is told (`:307`); records the abort reason in the receiver's own log naming peer and
counts (`:361`); delivers a frame of exactly the bound and counts no refusal (`:389`);
enforces the shipped default with no override anywhere (`:401`). `:431-531` covers the
per-peer budget, including that an in-limit message from the same peer is delivered once the
budget frees up.

### Criterion 4 — MET

> Dispatching N shards immediately after dial succeeds for N well above 12, or fails with a
> **stated, sender-attributed** reason. Today N=8 completes and N=12 fails entirely with
> `MaxEarlyStreamsError: Too many early streams were opened - 11/10` … which calls
> `muxer.abort()` and tears down the whole connection

**Mechanism.** A per-peer FIFO send gate with a bounded queue in
`packages/libp2p/src/libp2p-transport.ts` (`#gates`, `:235`), with two declared constants:

- `MAX_CONCURRENT_STREAMS_PER_PEER = 8` (`constants.ts:196`) — chosen to sit **below**
  libp2p's un-exported `maxEarlyStreams` default of 10
- `MAX_QUEUED_SENDS_PER_PEER = 256` (`constants.ts:211`) — past which the gate refuses
  immediately with a `SendRefused` (`libp2p-transport.ts:489`) rather than waiting

**Test run** (same 16/16 run as criterion 3).

`transport-bounds.node.test.ts:586-612` — **32 sends immediately after dial**, which is 2.7×
the old cliff:

- all 32 delivered
- zero `MaxEarlyStreamsError` on the receiver's capture
- connection intact afterwards, and a 33rd send still works
- `peakStreamsTo(to) <= MAX_CONCURRENT_STREAMS_PER_PEER` **and** `>= 2` — the lower bound
  matters as much as the upper, since `<= 8` alone would pass if the burst never happened

The negative reading is admissible only because the paired positive runs first: `:543-585`
widens the gate to 32, reproduces the tear-down, and asserts the captured error's own
denominator is 10 — the only runtime read of libp2p's operative default available anywhere in
this repository.

**Sender-attributed refusal** where the criterion allows one: `:631` (refuses past the queue
bound at once, naming this node, rather than waiting) and `:697-724` (over the real transport,

### Criterion 5 — MET

> A connection torn down by the **sender** exceeding a stream limit is not classified by the
> coordinator as a **node** failure of the receiver

**Mechanism.** A third `DispatchOutcome.kind`:

- `packages/core/src/ports.ts:138` — `SendRefused`, the marker a `Transport` raises to say
  *this node did not send, by its own decision*
- `packages/net/src/rpc.ts:208-213` — `send-refused` produced **only** when the caught cause
  is a `SendRefused`; every other rejection stays `send-failed`
- `packages/net/src/churn.ts:72-83` — `RpcFailure{send-refused}` → `kind: 'sender'`, with the
  reason naming the refusing node: `dispatch to ${nodeId} refused by ${cause.detail.by}`
- `packages/core/src/coordinator.ts:122,186,238,291,355` — `'sender'` carried through the
  outcome, attempt, failure and record types
- `packages/core/src/coordinator.ts:487-492` — the single policy read, with a comment stating
  that `'sender'` falling through to the same retry treatment as `'node'` is a decision, not
  an omission: the value of the third kind is that the **record** names it

**The contrast case is preserved, which is the half most easily lost.** A failed dial to an
unreachable peer arrives as `send-failed` and keeps its `'node'` classification
(`churn.ts:29-44`) — classifying that as `'sender'` would record a dead peer as a failure of
this node, the same misattribution pointed the other way.

**Test run** (same 16/16 run). `transport-bounds.node.test.ts:697-724` and `:726-745` produce
both sides of the distinction over a real transport, not from a hand-constructed
`RpcFailure`. The unit-level cases passed in the 890-test batch (`packages/net/src/rpc.test.ts`,
`packages/net/src/churn.test.ts`).

**Recorded residual, deferred:** production-path attribution is not observable until
`runResilient` and `submitJob` merge — WIRE-04, Phase 20, named in 13.1-CONTEXT.md's deferred
ideas. The shipped gate at 8 sits below libp2p's 10, so the tear-down the criterion describes
is prevented rather than reclassified; when the sender's own bound refuses, the attribution is
correct and named.

### Criterion 7 — PARTIAL

> A node asked for a raw sovereign block refuses, **whether or not it executed a task over
> that block**. Measured today: a submitting node that never ran the task holds no
> registration and serves the raw 95 bytes inside a 138-byte frame

**What is genuinely closed, and it is real.** `packages/net/src/submit-with-egress.ts:142-175`
registers every sovereign shard's canonical bytes on every supplied `EgressGuard` before
`submitJob` runs — `:155`, `held.push(guard.guard(label, encoded.bytes))` — under the label
`canonicalCid(shard.value).cid.toString()`, matching `takeSovereignHold`'s label exactly so
the two registration paths cannot produce two labels for one payload. Released in a `finally`
on every exit. The `block` branch then refuses via `agent.ts:257`.

`packages/node/src/sovereign-block-refusal.node.test.ts` proves it against two real
`FabricNode`s over TCP, with the production 30,000 ms RPC budget live and unshortened. The
claim is checked against **every frame that reached the owner**, not inferred from an outcome,
with the wire tap proved to be capturing before it is allowed to report an absence (`:228-250`)
and the scanner proved able to read as a separate assertion. Passed, in the 30-test run above.
A source scan at `:389-443` pins the set of production files that may call bare `submitJob` at
exactly three, so a **new** production submit path fails loudly rather than quietly inheriting
the gap.

**Why this is PARTIAL and not MET.** The criterion is worded about a *node*. What ships is a
property of one *function* over one *job's duration*. The codebase states this itself, at
`packages/node/src/sovereign-block-refusal.node.test.ts:52`:

> Criterion 7 is a property of a *node*; what ships here is a property of one *function*.

`packages/net/src/submit-with-egress.ts:77-88` says the same. Of the three routes by which a
node comes to hold raw sovereign bytes (13.1-CONTEXT.md's own framing), two are left open:

1. **At rest.** The registration is job-scoped and given back in a `finally`, so a peer asking
   for the same block after the job has finished still receives the raw bytes.
   `submit-with-egress.ts:68-75` — **unmeasured**. Closing it needs a persistent per-node set
   of sovereign CIDs surviving the job and the process. Recorded in 13.1-CONTEXT.md's deferred
   ideas but **scheduled into no later phase**.
2. **Bare `submitJob`.** It content-addresses every shard input and `put`s it into the store it
   was handed, sovereign ones included, and registers nothing — so such a submitter holds the
   row exactly as the guarded one does, unguarded.
   `packages/node/src/sovereignty-placement.node.test.ts` drives a real spawned-agent sovereign
   scenario that way and **still passes, because the gap is real**.
   `submit-with-egress.ts:79-81` — **unmeasured**. Scheduled into no later phase.
3. **The browser tier's submitter path** — unmeasured, and this one *is* scheduled: WIRE-03,
   Phase 19. Deferred, not counted as a gap.

The honest scoping is visible in the executor's own words too: `13.1-04-SUMMARY.md:7` claims
DATA-10 "**for a job in flight submitted through `submitJobWithEgress`**", not the criterion's
full wording. That is a summary that did not overclaim; the shortfall is against the ROADMAP
criterion, not against the summary.

## Amendment — 2026-08-02: criterion 7 closed, and this verification's verdict changes

**Status: `gaps_found` → `passed`.** The one gap this document found is closed. Nothing else
in it is revised — the six criteria it scored MET were met then and are met now.

### What was open

Two of the three routes by which a node comes to hold raw sovereign bytes:

1. **At rest.** `EgressGuard`'s registration is job-scoped and given back in a `finally`, so
   a peer asking after the job still received the raw bytes.
2. **Bare `submitJob`.** It `put`s every shard input into the store it was handed, sovereign
   ones included, and registered nothing.

### Why the obvious fix was the wrong one

Not releasing the hold would have closed both — and reintroduced a defect this repository had
deliberately removed. `egress.ts`'s `guard()` forbids eviction and says why: *the set is
bounded by giving holds back, which is a bound somebody can be shown.* A hold never given
back removes the only bound it has, and `submit-with-egress.ts` names that as *exactly the
unbounded scan cost Plan 13-07 was written to remove* — every later frame scanned against
every row the node ever submitted.

### What shipped instead

`EgressGuard` is keyed on **payload bytes** and answers by scanning. A `block` request names
a **CID**, so the at-rest question never needed the scan. A second mechanism — `SovereignCids`,
a durable per-node set of CIDs — answers it by lookup, and its growth costs memory rather
than per-frame work. **The two coexist**; neither replaces the other, and each answers the
question it is cheap at. `EgressGuard` stays job-scoped, which is why
`sovereign-block-refusal.node.test.ts`'s readings that `registrations` is `[]` after a job
remain true and remain valuable.

Registration happens at `submit.ts`'s blockstore-put — the boundary `submit-with-egress.ts`
itself named as the fix, in those words — which is what covers bare `submitJob` rather than
only the callers who remembered.

Both tiers: `FsSovereignCids` (dot-prefixed file beside the blocks) and `IdbSovereignCids`
(a **separate** IndexedDB database, because eviction is per-record and a set inside the
blockstore could be evicted while the blocks it guards survive — failing open).

### Evidence

`packages/node/src/sovereign-at-rest.node.test.ts`, 3/3, over two real `FabricNode`s:

| Mutation | Result |
|---|---|
| `block` branch stops consulting the durable set | ❌ both refusal cases; **control passes** |
| `submitJob` stops registering at the put | ❌ both refusal cases; **control passes** |
| the set never reaches disk | ❌ **only the restart case**, `ENOENT` |

The third is the load-bearing one: an in-memory set passes everything except the restart,
which is what proves "survives the job" and "survives the process" are separate readings.
The control — a public block from the same store, still served — is what stops "refuses
everything" scoring as a pass.

### Still open, and unchanged by this amendment

- **The browser tier's submitter path** — WIRE-03, Phase 19. `IdbSovereignCids` exists and is
  wired, but nothing measures it there. Deferred, as before, not counted as a gap.
- **IndexedDB eviction.** A tab that loses the database comes back not knowing a row was
  sovereign. Stated in `idb-sovereign-cids.ts`; unmeasured.
