# Phase 13.1 — Plan 01: Admission on the `exec` branch

**Closes:** SCHED-06's refusal half (ROADMAP criterion 1), and criterion 2's
"wired, not deleted" ruling for the mechanism itself.

**Leaves open, by design:** criterion 1's *real-stack concurrency* reading and
criterion 2's *both production factories* reading. Both need `FabricNode` /
`BrowserNode` and belong to Plan 13.1-05. This plan proves the mechanism; 05
proves the wiring.

## What changed

`serveAgent`'s `exec` branch ran `await executor.execute(request.task)` with
nothing counting what was in flight. It now:

- derives a slot key from `inputCid` + `partitionIndex`;
- takes a slot from `LocalCapacity` **before** the `try`, so a refused request
  never enters the block that calls the executor;
- replies `{kind:'error', reason:'over-committed: N of M slots in use'}` when the
  slot is refused;
- releases in a `finally` around the executor call — on success, on a failed
  outcome, on a throw, and on the `authorize` refusal that never calls the
  executor at all.

The `offer` branch moved from `capacity.offer(...)` to `capacity.would(...)`.

`@o2/core` gained `LocalCapacity.would`, `LocalCapacity.peakInFlight` and
`DEFAULT_MAX_CONCURRENT_TASKS`. `@o2/net` gained `CountingExecutor`.

## What this removes, stated rather than softened

**Wire-side multi-shard over-commit protection is removed by this plan and is
Phase 18's to rebuild.** `placeWithOffers` removes a probed candidate from the
pool for *one* shard, and `pool` is rebuilt per request, so across shards the only
thing that made wire-side placement over-commit-safe was the reservation the
offer branch no longer takes. `planWithOffers` + `rpcAdmission` will now place all
N shards of a job on one node with `maxConcurrent: 1`. That is pinned by
`discovery.test.ts`'s case *"no longer bounds anything across shards — four land
on one 1-slot node"*, which is titled for what it is and is **expected to turn red
when Phase 18 rebuilds the protection**. The two candidate mechanisms are recorded
in `agent.ts`'s own comment: carry the shard id on the `exec` request so an offer
reservation can be redeemed, or publish the node's slot count in the `offer`
response so a requestor can keep a tally across a placement generation. Both are
protocol changes; this phase makes neither.

**Refusal without a re-pick turns a previously slow job into a failed job on the
production submit path.** `submitJob` calls `executeVerified` exactly once with no
retry; `remote-executor.ts` flattens the `{kind:'error'}` refusal into
`{ok:false, reason}`; `verify.ts` records it against `executor.nodeId` and the
shard is not `agreed`, so `job.complete` is false. Before this phase a saturated
node queued the work and eventually answered. The shipped default does **not**
remove this. Whether the refusal is reached under any workload this project runs
is **unmeasured** — nothing in this repository reads a node's concurrent `exec`
count under a demo or benchmark workload. What would measure it is the
`CountingExecutor` reading Plan 13.1-05 exposes on the node, taken from a
multi-tab demo run (WIRE-03, Phase 19). What would *remove* it is a re-pick on the
production submit path (WIRE-04, Phase 20).

`DEFAULT_MAX_CONCURRENT_TASKS = 64` is a **configuration choice, not a derived
quantity**. The only other figure recorded beside it is the roadmap probe's
**measured** reading: 4 peers × 200 concurrent `exec` requests producing 800
simultaneous `execute()` calls and zero refusals. No arithmetic over shard,
replica or peer counts appears in any comment, test name or sentence here.

## Corrections made to the plan

Three claims in `13.1-01-PLAN.md` were false against the code and were fixed in
the plan file in place, each with a dated note.

1. **Task 1's verify command.** The plan ran `npx tsc --noEmit -p packages/core`.
   There is no `packages/core/tsconfig.json` — the repository has exactly one, at
   the root — so the flag fails with `TS5081: Cannot find a tsconfig.json file at
   the current directory`. Replaced with the repo-wide `npx tsc --noEmit`.

2. **Task 2's third `discovery.test.ts` case used `d: 1`.** `placeWithOffers`
   refuses anything outside `[MIN_D, MAX_D] = [2, 4]` and returns `unplaceable`
   with `d must be an integer in [2, 4], got 1` before probing anything, so the
   case as written could never have passed. With a one-node pool
   `sampleCandidates` returns one candidate whatever `d` is, so `d: 2` is the
   same test.

3. **Task 2's first `discovery.test.ts` case claimed its exact counts were
   "deterministic regardless of sampling order" at `d: 2`.** That is true for
   *which node wins* and false for `probed is 4` and `exactly 3 rejections`: if
   the sampler draws the free worker first, the loop stops at `probed === 1` with
   zero rejections. The counts are deterministic only if the free worker is
   probed **last**. Rewritten at `d: 4`, which makes `sampleCandidates` return the
   whole four-node pool every iteration, so the probe order is `leastLoaded`'s
   documented load-then-id tie-break — ascending `nodeId`, every load being 0 —
   and the test occupies the three lowest ids.

One further deviation, made for evidence quality rather than because the plan was
wrong: the paired peak/refusal readings in `admission.test.ts` are asserted with
`expect.soft`, so a mutation run reports **both** numbers instead of stopping at
whichever assertion happens to be first. Mutation A's capture below is what that
buys.
