# Phase 13.1 — Plan 04: A submitter does not serve the row it submitted

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Closes:** DATA-10 (ROADMAP criterion 7) for a job in flight **submitted through
`submitJobWithEgress`**.
**Leaves open, and says so in those words:** a node refusing a sovereign block **at rest,
indefinitely** is unmeasured; and a job submitted through **bare `submitJob` is unguarded, and
that is unmeasured**. See `## Out of scope`.
**Depends on:** Plan 13.1-03 — this plan uses `EgressGuard.violationIn` for its wire tap and
the block branch's named refusal for its fast, assertable failure.

## Execution order and shared-tree safety

**Wave 5, and wave 5 contains only this plan.** Every wave in phase 13.1 is one plan wide,
because three of the five plans plant mutations into production source and verify while the
mutation is live. Order: 01 → 02 → 03 → 05 → 04. This plan plants no mutation, but it runs
`npx tsc --noEmit` over the whole repository and a wide `packages/node` node-test sweep, both
of which would read another plan's planted edit as this plan's failure. **No task may run a
`git` command that writes.**

<objective>
Sovereignty is a property of the data, not of whether this particular node happened to
compute over it. Today only the **executing** node registers its input with the guard:
`registerSovereignInputs` (`packages/net/src/sovereign-egress.ts:63-76`) fires on the serving
side, for a task about to run, when the local store already holds the input. A **submitter**
satisfies none of those three. So a node that assembled a job containing another owner's row,
and never ran a task over it, holds no registration and serves the raw bytes on request —
measured at 95 raw bytes inside a 138-byte block-response frame.

`submitJobWithEgress` (`packages/net/src/submit-with-egress.ts:79-92`) is the one place that
already holds both the `JobSpec` — whose `ShardSpec` carries `label:'sovereign'` and
`ownerId` — and the node's `EgressGuard`. Register each sovereign shard's canonical bytes
there before `submitJob` runs; release in a `finally` after it returns.

**And that makes the guard a property of which function the caller invoked, not of the node —
which is not what criterion 7's wording says, so it is stated here rather than implied.**
`core/src/job/submit.ts:176` unconditionally does `await blockstore.put(encoded.bytes)` for
every shard including sovereign ones, so **any** submitter always materialises the raw row
into its own store, whichever entry point it used. Every *production* sovereign submission
goes through `submitJobWithEgress` today — `browser/demo/main.ts:312,552` and
`bin/bench.ts:267` are its only production callers, and the one production caller of bare
`submitJob`, `core/src/executor/task-worker.ts:43`, hard-codes `label: 'public'` shards into
a `MemoryBlockstore` inside a worker. So the gap is not currently reachable in production.
It is reachable in principle, and it is reachable today in
`packages/node/src/sovereignty-placement.node.test.ts:169`, which drives the real
spawned-agent sovereign scenario through bare `submitJob`: that file **still passes after
this plan, and passes for the reason that makes the gap real** — bare `submitJob` registers
nothing, so the submitter still holds and would still serve the row. Task 2 adds a source-scan
guard that fails if a second production submit path appears, and `## Out of scope` records the
gap in the same register as the at-rest one.

**This changes an existing behaviour and the change is the point.** In the *unseeded*
configuration — the owner does not already hold the row — the submitter today ships the raw
bytes when the owner's `RpcBlockSource` asks for the input block, and the job completes. After
this plan that block response is refused and the job fails. That is correct:
`sovereign-egress.ts:26-32` states the premise that a sovereign input is owner-pinned and
already resident, and a submitter holding another owner's raw row has broken the premise
before the fabric is involved. The *seeded* path — the one the fabric is actually designed
around — must be proved unaffected, in the same test, as a control.

Purpose: close the second of the three routes by which a node comes to hold raw sovereign
bytes. Route 1 is "it is the owner", covered at execution by `registerSovereignInputs`. Route
2 is "it submitted a job containing them", which is this plan. Route 3 is "it fetched them
over the wire", closed by construction once 1 or 2 holds on the node that would have served
them, because `EgressGuard.send` refuses.
Output: a registering `submitJobWithEgress`; a portable spec covering both configurations;
and a two-real-node measurement that checks the wire byte-for-byte rather than reading an
outcome and inferring what crossed.
</objective>

```ts
export type SubmitWithEgressResult =
  | { readonly ok: true; readonly job: JobResult; readonly manifests: readonly EgressManifest[] }
  | { readonly ok: false; readonly error: SubmitError }

export function sliceManifest(guard: EgressGuard, from: number): EgressManifest

export async function submitJobWithEgress(
  spec: JobSpec,
  blockstore: Blockstore,
  guards: readonly EgressGuard[],
): Promise<SubmitWithEgressResult> {
  const before = guards.map((guard) => guard.manifest.entries.length)
  const result = await submitJob(spec, blockstore)
  if (!result.ok) return result
  return { ok: true, job: result.job, manifests: guards.map((guard, i) => sliceManifest(guard, before[i] as number)) }
}
```

## Out of scope

- **Refusing a sovereign block at rest, indefinitely.** The registration this plan adds is
  job-scoped, so a peer asking for the same block after the job has finished still receives
  the raw bytes. Criterion 7's wording — "whether or not it executed a task over that block"
  — is about *which node*, and the defect it cites is a submitter mid-job, which is what this
  plan measures. A node refusing at rest is **unmeasured** and needs a persistent per-node
  set of sovereign CIDs that survives the job and the process. Stated in the test file's
  header and in the summary in these words.
- **A job submitted through bare `submitJob`.** The registration this plan adds lives in
  `submitJobWithEgress`, so **a job submitted through bare `submitJob` is unguarded and that
  is unmeasured** — and it is not a hypothetical: `core/src/job/submit.ts:176` puts every
  shard input, sovereign included, into the submitter's own blockstore, so such a submitter
  holds the raw row exactly as the guarded one does.
  `packages/node/src/sovereignty-placement.node.test.ts:169` drives a real sovereign job that
  way and keeps passing after this plan, for that reason. Criterion 7 is a property of a
  *node*; this plan delivers a property of one *function*, and Task 2's source-scan guard is
  what makes a new production submit path — a fourth file entering the three-file set it
  pins — fail loudly rather than quietly inherit the gap.
  Closing it properly means registering at a boundary the node owns — the blockstore-put of a
  shard labelled sovereign, or a helper both `submitJob` callers share.
- **Route 1 at rest.** The owner's own copy is covered at execution by
  `registerSovereignInputs` and is not covered at rest, for the same reason. Same follow-up.
- **Bounding `EgressGuard.#entries`.** Deliberately not done — a ring buffer would silently
  drop history a `sliceManifest` reader may be mid-slice on. This plan adds no entries beyond
  what a job already produces.
- **Concurrent jobs sharing one guard.** Inherited limitation, recorded in
  `submit-with-egress.ts`'s module comment since Phase 13: attribution assumes one job in
  flight per guard. The hold-counting in `guard`/`release` means two concurrent jobs over the
  same row stay guarded until both release, so the *refusal* composes correctly even though
  the *manifest attribution* does not.
- **Guards supplied in an order that does not match the nodes.** An accepted risk, inherited
  unchanged from Phase 13's T-13-02 and neither closed nor re-opened here:
  `submitJobWithEgress` takes an explicit `guards` array the caller must order to match, and
  it **cannot** infer node-to-guard identity from a `JobSpec`, because a `JobSpec` names nodes
  by string id and not by `EgressGuard` reference. Misordering therefore attributes one
  owner's egress to another owner's manifest, and this module cannot detect it. It is accepted
  because in production every caller passes exactly its own node's guard, and because
  detecting it needs an API this phase's scope does not call for. This plan's registration
  loop writes to *every* supplied guard, so it inherits the same assumption rather than
  narrowing it — stated here so the next reader does not mistake the new loop for a fix.
- **The browser tier's submitter path in a real tab.** `BrowserNode.start` needs a real
  `indexedDB` and a relay, so it runs in neither vitest project. WIRE-03, Phase 19.
