> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Closes:** NET-08 (criterion 3). NET-09's criterion 4 is closed for the *bound*; its
underlying safety claim is **descoped and stated below**. NET-09's criterion 5 is **descoped

<objective>
Two measurements, both against tcp + noise + yamux with real nodes, neither reasoned about:

1. `readMessage` (`packages/libp2p/src/libp2p-transport.ts:57-74`) pushes every chunk a peer
   sends into an array, sums the total, and then allocates `new Uint8Array(total)`. Both
   allocations are peer-driven and neither is bounded. A single **64 MiB** frame was sent and
   accepted. `WIRE_CHUNK_BYTES` is send-side framing only, and yamux's window paces delivery
   without capping the total.
2. `Libp2pTransport.send` (`:123-146`) opens one fresh stream per message with no gate.
   N=8 shards dispatched immediately after dial completes; N=12 fails **entirely** with a
   `MaxEarlyStreamsError`. The source is now known precisely:
   `@libp2p/utils`'s `abstract-stream-muxer` queues inbound streams in `earlyStreams` while
   the muxer has no `'stream'` listener yet, and past `maxEarlyStreams` it calls
   `this.abort(...)` — killing the whole connection, including in-limit requests and
   `identify`'s own stream. `bin/bench.ts` ships `SHARDS = 8`, one below that cliff.

   **The roadmap quotes that error as `Too many early streams - 11/10`. That string does not
   exist in the installed library.** `node_modules/@libp2p/utils/dist/src/abstract-stream-muxer.js:120`
   constructs `Too many early streams were opened - ${this.earlyStreams.length}/${this.maxEarlyStreams}`.
   The roadmap's line was paraphrased rather than captured, which is the same class of error
   this phase exists to remove — so no assertion in this plan is keyed on the roadmap's
   wording. Match on the error's `name` (`MaxEarlyStreamsError`, set as both a static and an
   instance property at `errors.js:29-31`) plus the `/10` denominator, and paste whatever the
   run actually prints into the summary verbatim. Plan 13.1-05's ROADMAP edit corrects the
   quoted string at its source.

The apparent ceiling of 256 with one peer is the **sender's** `maxOutboundStreams`. The
receiver makes no decision at all, and neither does the sender about what it opens at once.

**What the gate does and does not do, stated before it is built.** `earlyStreams` is
**cumulative** within the pre-listener window, not a concurrency count:
`abstract-stream-muxer.js:114-124` pushes every remote stream while
`listenerCount('stream') === 0` and aborts past the ceiling; `cleanUpStream` (`:128-148`)
splices only `this.streams` on close and never removes anything from `earlyStreams`; the
array is emptied in exactly one place, when a `'stream'` listener is finally added
(`:154-164`). A gate that caps *concurrent* outbound streams at 8 therefore does **not** cap
how many streams are opened in total inside that window. It bounds how many can be in flight
at once, which lowers the rate and bounds the damage, but is not a proof of
impossibility. **The claim "libp2p's early-stream ceiling cannot be reached" is therefore
unmeasured and this plan does not make it.** What would measure it is an instrument on the
receiver's muxer counting inbound streams accepted before its `'stream'` listener attached;
`earlyStreams` is a private field of a class libp2p never hands out, so that instrument is
not reachable through any public API today. What this plan measures instead is in Task 2's
behaviors: a per-destination concurrency high-water reading, and a tear-down *absence* paired
with a run of the same instrument in which the tear-down *occurs*.

**Raising `maxEarlyStreams` is not the fix, and this plan does not ship it as a belt either.**
It moves the cliff and leaves connection tear-down as the failure mode. It is also
unmeasurable from outside: `yamux()` spreads its init into `AbstractStreamMuxer`, whose
constructor uses a hardcoded `init.maxEarlyStreams ?? 10` (`abstract-stream-muxer.js:24`) —
note that `@chainsafe/libp2p-yamux`'s own `defaultConfig.maxEarlyStreams` (`config.js:9`) is
declared but **never read** by `YamuxMuxer` (`muxer.js:64-75` reads four other fields and not
this one). And a peer running default yamux still aborts at 10 regardless of what this node
sets. Shipping it would add a mechanism this phase could only *report*, not measure. The
roadmap says where the fix belongs: *"Only the per-peer send path in criterion 4 is a genuine
bounded-queue site."*

Criterion 5 then asks that a connection torn down by the **sender** exceeding a limit is not
recorded as a **node** failure of the receiver. `DispatchOutcome` today is
`{ok:false, kind:'node'|'task'}` and `coordinator.ts:450` attaches the *attempted* `nodeId`
to every failure, so with two kinds the record blames the receiver no matter what the string
says. Name the third kind rather than faking one — and read Task 3 before assuming that
closes the criterion, because it does not: the *scenario* criterion 5 names is not reproduced
anywhere, on any path.

Purpose: neither side of the wire can be driven past a bound by a peer, and the failure that
remains names whose bound it was.
Output: three declared constants, each documented as the configuration choice it is and each
sited against a measurement rather than an arithmetic; a bounded, aborting `readMessage`
with a refusal counter; a per-destination FIFO send gate of 8 with a bounded queue; a
`SendRefused` marker on the `Transport` port and a `send-refused` `RpcError` variant that
carries it; a widened `DispatchOutcome.kind`; and one `*.node.test.ts` that reproduces both
roadmap measurements against real nodes before the fixes land.

async function readMessage(stream: Stream): Promise<Uint8Array<ArrayBuffer>> {
  const chunks: Uint8Array[] = []
  let total = 0
  for await (const chunk of stream) {
    const flat = chunk instanceof Uint8Array ? chunk : chunk.subarray()
    chunks.push(flat)          // unbounded
    total += flat.byteLength   // unbounded
  }
  const message = new Uint8Array(total)   // peer-driven allocation
  ...
}

async send(to: string, message: Uint8Array<ArrayBuffer>): Promise<void> {
  if (this.#stopped) throw new Error('transport stopped')
  const signal = AbortSignal.timeout(this.#sendTimeoutMs)      // :125 — created before the dial

    signal,
    runOnLimitedConnection: true,                              // :128 — must survive any refactor
  })
  try {
    for (let offset = 0; offset < message.byteLength; offset += WIRE_CHUNK_BYTES) { ... }
    await stream.close({ signal })

    stream.abort(cause instanceof Error ? cause : new Error(String(cause)))
    throw cause
  }
}

`rpc.ts:166-177` is a **bare `.catch` on `this.#transport.send(...)`**: *every* rejection of
`Transport.send` becomes `send-failed`, whatever caused it. And
`libp2p-transport.ts:126-129` awaits `dialProtocol` inside `send`, which rejects when the
peer is unreachable, refuses the protocol, or the dial times out. **A genuinely dead receiver
therefore arrives as `send-failed`, not as `kind:'timeout'`.** Branching `'sender'` on
`send-failed` would record a dead peer as a failure of *this* node — the misattribution
criterion 5 exists to remove, pointed the other way. `churn.ts`'s module comment classifies
"the RPC threw — timeout, send failed, endpoint closed" as `node` *because "the peer never
answered"*, and that row is correct for everything in it except the one case this plan adds.

So this plan adds a **new marker**, and `send-failed` keeps its current meaning and its
current classification:

## Out of scope

- **Raising `yamux({maxEarlyStreams})`.** Not shipped, and not merely deferred: it moves the
  cliff rather than removing it; a peer running default yamux aborts at 10 whatever this node
  sets; and its effect is not readable through libp2p's public API, so it could be reported
  but not measured. If a later phase ships it, it gets pinned against a runtime value.
- **A hard bound on libp2p's cumulative `earlyStreams` count.** The gate bounds concurrency.
  Making the ceiling genuinely unreachable would need either a bound on streams opened per
  connection-lifetime window — which requires knowing when the receiver's `'stream'` listener
  attached, information the sender does not have — or a libp2p change. **Unmeasured**, and
  named here rather than left inside a confident sentence.
- **Reproducing criterion 5's named scenario.** A sender-caused connection tear-down, end to
  end through `ShardOutcome.failures`, including the requests that were in flight. Not done;
  the criterion is descoped to "the classification exists and is exercised" and the descope is
  stated in the summary.
- **An aggregate inbound-bytes budget across peers.** Accepted rather than closed: many peers
  each sending a just-under-limit frame concurrently leaves the aggregate unbounded even though
  each frame is not. NET-08 asks for a per-frame cap and that is what closes the measured
  defect; an aggregate budget is a second mechanism with its own accounting. libp2p's own
  `maxInboundStreams` of 256 per connection is the only aggregate bound today.
- **Threading `maxMessageBytes` from the node factories.** Plan 13.1-05. Neither factory
  passes `Libp2pTransportOptions` today; this plan makes the option exist and proves it at
  the layer that owns it.
- **Criterion 5 on the production `submitJob` path.** Unmeasured, not met — see Task 3.
- **A production caller for `remoteDispatch` / `runResilient`.** Both are test-only today, so
  the `'sender'` classification this plan adds has no production consumer. WIRE-04, Phase 20.
- **`bin/bench.ts`'s `SHARDS`.** Raising it above the old cliff, and measuring what the gate
  costs at nodes=1, is Plan 13.1-05's task 3. This plan changes no benchmark input.
- **A long-lived stream carrying delimited messages.** The module comment's framing-safety
  argument stands and this plan does not reopen it.
