<objective>
Phase 13 made the bytes stop. It did not make the refusal legible.

`EgressGuard.send` refuses a frame carrying a registered sovereign payload, and on the
**requesting** leg that refusal is already named — `rpc.ts:165-177` turns a rejected
`Transport.send` into `RpcFailure{kind:'send-failed'}` immediately, carrying the message.
On the **responding** leg it is not: `rpc.ts:251-259`'s catch is empty and documented —
*"The requester will time out."* So the one place the fabric's central promise is enforced
reports itself as `rpc … timed out after 4000ms`, with no label and no attribution, against
a `DEFAULT_RPC_TIMEOUT_MS` of 30,000. A requestor cannot tell *"your data may not leave that
node"* from *"that node is gone"*. Every existing test on this path shortens its budget
because the wait dominates — which is precisely how the 30 s cost stayed invisible.

**The remedy is not a change to `rpc.ts`'s responding leg.** That catch swallows by design,
because throwing there would surface inside the transport's delivery path, and changing it
would change every peer's response-leg failure semantics to fix a legibility complaint.
13.1-CONTEXT.md decision 5 sketched the alternative and declined to trust its own sketch; it
holds up. `serveAgent`'s exec branch already holds the guard, the label and the outcome. It
can encode its candidate reply, ask the guard whether that byte string carries a registered
payload, and on a match return a small `{kind:'exec', outcome:{ok:false, reason:'egress
refused: …'}}` — a frame that by construction cannot carry the payload it refuses. `rpc.ts`
is untouched.

The same treatment applies to the branch criterion 7 names: a node asked for a block whose
bytes are registered answers with a named refusal rather than a silence the requestor cannot
distinguish from absence.

Two properties must not be lost in the process, and both are asserted rather than assumed:

- **The manifest still records the refusal.** A pre-scan that returned a clean small frame
  and left the tap with nothing to record would stop the leak and leave the node with no
  record that it had. So the scan and the record are one method, and `send` is built out of
  it too, which is why the two paths cannot disagree.
- **`send` still refuses on its own.** The pre-scan is the fast path, not the guarantee.
  Remove it and the bytes must still not leave. That is the mutation this plan plants.

Purpose: close the standing principle *every exclusion is named* against the refusal path.
Output: `EgressGuard.violationIn` and `EgressGuard.refuse`; a pre-scan on `serveAgent`'s exec
and block branches; and a real-node measurement of the refusal's wall-clock at the production
RPC default.
</objective>

```ts
async send(to: string, message: Uint8Array<ArrayBuffer>): Promise<void> {
  const violation = this.#scan(message)
  // push first: a refused send is still a fact the manifest carries
  this.#entries.push(
    violation === null
      ? { to, bytes: message.byteLength }
      : { to, bytes: message.byteLength, violation },
  )
  if (violation !== null) throw new EgressRefusal({ to, violation, bytes: message.byteLength })
  await this.#inner.send(to, message)
}

/** The label of the first guarded payload contained in `frame`, or `null`. */
#scan(frame: Uint8Array): string | null {
  for (const [label, held] of this.#guarded) {
    if (held.payload.byteLength === 0 || held.payload.byteLength > frame.byteLength) continue
    if (contains(frame, held.payload)) return label
  }
  return null
}

get registrations(): readonly string[] { return [...this.#guarded.keys()] }

}
```

`encodeResponse` returns a `CanonicalValue`, not bytes — `rpc.ts` encodes the frame. So the
pre-scan encodes the candidate body itself:

```ts
// packages/core — already used as a value import elsewhere in @o2/net (churn.ts imports canonicalCid)
export function encodeCanonical(value: CanonicalValue): { ok: true; bytes: Uint8Array<ArrayBuffer> } | { ok: false; error: … }
```

**Why scanning the body is safe when `send` scans the whole frame.** `EgressGuard.send` sees
`{k:'res', id, body}` encoded (`rpc.ts:193-201`). `contains` (`egress.ts:308-317`) is a
contiguous-run search, and dag-cbor encodes a byte string as a header followed by the raw
bytes — so a payload present in the body is present as the same contiguous run inside the
frame. The pre-scan is therefore **no less sensitive** than the send-time scan, and the
send-time refusal stays in place as the backstop.

`packages/net/src/remote-executor.ts` — where the two reply shapes land, unchanged:

```ts
if (response.kind === 'error') return { ok: false, reason: `remote error from ${this.nodeId}: ${response.reason}` }
if (response.kind !== 'exec') return { ok: false, reason: `unexpected ${response.kind} response to exec request` }
return response.outcome    // {ok:false, reason} passes through verbatim
```

`packages/net/src/churn.ts` classifies the two shapes differently, which is the reason an
egress refusal is sent as `exec ok:false` and a capacity refusal as `error`
(13.1-CONTEXT.md decision 4): an egress refusal is a **task** condition — a map step that
forgot to aggregate leaks the same way on every node, and re-running it across the fabric
burns each in turn, which is exactly what `DEFAULT_MAX_TASK_FAILURES = 3` exists to cap.

## Recorded decisions

- **Refusing to serve a registered sovereign block is a deliberate decision, not a side
  effect — the owner ruling of 2026-07-28.** Its home is `packages/net/src/egress.ts`, where
  it is recorded in source, and this plan does not change it: the block branch is given the
  same refusal treatment as the exec branch *because* the ruling already says a registered
  sovereign block is not served. What the ruling accepts, and accepts knowingly, is that a
  peer cannot tell refusal from absence and could in principle retry forever. It does not in
  practice, because `RpcBlockSource` treats any non-`block` reply as a miss and moves to the
  next peer, so a multi-peer fetch degrades rather than loops, and a caller that asked this
  node directly gets a named reason. Restate the ruling and its date when touching this
  branch; do not re-derive the disposition from scratch.

## Out of scope

- **Changing `rpc.ts`'s responding leg.** Its catch swallows by design; throwing there would
  surface inside the transport's delivery path and change every peer's response-leg failure
  semantics to fix a legibility complaint. 13.1-CONTEXT.md decision 5 and this plan both
  decline it.
- **A new `{kind:'refused'}` response kind.** `{kind:'error'}` and `{kind:'exec', ok:false}`
  already carry the two retry policies these refusals need, and one new kind could not carry
  both. Deferred in 13.1-CONTEXT.md with the full cost written out.
