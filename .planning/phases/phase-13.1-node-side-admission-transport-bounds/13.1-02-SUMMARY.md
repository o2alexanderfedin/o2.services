# Phase 13.1 — Plan 02: Transport bounds — a receive cap and a per-peer send gate

**Closes:** NET-08 (ROADMAP criterion 3). NET-09's criterion 4 for the *bound*.

**Descoped, in these words:** NET-09's criterion 5 is **descoped to "the
classification exists and is exercised"**, and criterion 5's named scenario is
**unmeasured on every path**. On the production `submitJob` path criterion 5 is
**unmeasured, not met**. All three statements are expanded in "The boundary"
below.

**Not claimed:** `MAX_CONCURRENT_STREAMS_PER_PEER` bounds **concurrency**, not
libp2p's cumulative `earlyStreams` count, and the claim that libp2p's early-stream
ceiling cannot be reached is **unmeasured**.

## What changed

Three mechanisms, each landed after its reproduction was watched failing.

**1. `readMessage` is bounded during accumulation.** It pushed every chunk a peer
sent into an array and then allocated their sum; both allocations were
peer-driven and neither was bounded. It now takes a `max`, checks `total` inside
the `for await` immediately after the byte count grows, calls `stream.abort(...)`
and throws past it. The check has to be inside the loop: a cap applied after the
loop has already paid for the allocation it exists to prevent, which is the whole
content of NET-08. The registered handler catches that error, increments
`#refusedInbound`, and returns; `Libp2pTransport.refusedInbound` exposes the
count.

**2. `send` takes a per-destination slot.** At most
`MAX_CONCURRENT_STREAMS_PER_PEER` streams are open toward one peer at a time; the
rest wait FIFO, and past `MAX_QUEUED_SENDS_PER_PEER` a send is refused
immediately with a `SendRefused` naming this node, the destination, both bounds
and the current depth. The `AbortSignal.timeout` is created *before* the gate is
taken so the wait is inside the same budget as the dial and the write.
`stop()` rejects every parked waiter rather than leaving it to time out.
`peakStreamsTo(to)` is the high-water instrument. `runOnLimitedConnection: true`
survives on both the handler and the dial — `relayed-job.node.test.ts` is green.

**3. `DispatchOutcome.kind` gained a third value.** `'sender'` means *this node
did not send, by its own decision*. It is produced only by an
`RpcFailure{kind:'send-refused'}`, which `rpc.ts` produces only when the caught
cause is a `SendRefused`. `coordinator.ts`'s single policy read
(`if (failure.kind === 'task') taskFailures += 1`) is unchanged, with a comment
saying the fall-through is a decision rather than an omission.

## The two reproductions, pasted as printed

Both were captured against two real libp2p nodes over `/ip4/127.0.0.1/tcp/0` with
`tcp()`, `noise()` and `yamux()`, before the corresponding fix landed, by
asserting the reading against a sentinel so vitest printed it (vitest suppresses
`console.log` in this configuration).

### NET-08 — the unbounded receive

```
REPRO NET-08: sent 8388609 bytes, send resolved, receiver delivered 1 message(s) of byteLength [8388609]
```

An 8 MiB + 1 frame was accumulated whole and delivered to the layer above. This
is the roadmap's 64 MiB measurement reproduced at the value this plan ships.

### NET-09 — the tear-down


owns correcting the ROADMAP quote at its source.

## What the gate does not do, stated where it will be read

`earlyStreams` is **cumulative** within the pre-listener window, not a concurrency
count. `onRemoteStream` pushes every inbound stream while the muxer has no
`'stream'` listener (`@libp2p/utils/dist/src/abstract-stream-muxer.js:114-124`),
`cleanUpStream` splices `this.streams` only and never touches `earlyStreams`
(`:128-148`), and the array is emptied in exactly one place — when a `'stream'`
listener is finally added (`:154-164`).

So **`MAX_CONCURRENT_STREAMS_PER_PEER` bounds concurrency, not libp2p's cumulative
`earlyStreams` count, and "the early-stream ceiling cannot be reached" is
unmeasured.** The gate lowers the burst rate and bounds the damage. The
32-send-at-the-shipped-bound test still opens 32 streams in total, and its own
comment says so. What would measure the stronger claim is an instrument on the
receiver's muxer counting inbound streams accepted before its `'stream'` listener
attached; `earlyStreams` is a private field of a class libp2p never hands out, so
that instrument is not reachable through any public API today. The same paragraph
is in `constants.ts` beside the constant, because that is where somebody will read
it.

Raising `yamux({maxEarlyStreams: N})` is **not shipped, and not merely deferred**:
it moves the cliff rather than removing it, a peer running default yamux still
aborts at 10 whatever this node sets, and its effect is not readable through
libp2p's public API — so it would add a mechanism this phase could only report,
not measure.

## The paired instrument

"No `MaxEarlyStreamsError` was seen" is worth nothing on its own: an instrument
that was never connected reports exactly the same thing. So one capture harness —
a `ComponentLogger` wrapping `defaultLogger()` in a `Proxy`, the
`reservation-watch.ts` idiom, collecting every `Error` passed to `log.error` —
runs twice in `transport-bounds.node.test.ts`:

- at `maxConcurrentStreamsPerPeer: 32`, where `receiverErrors.errors` must be
  non-empty **and** must contain a `MaxEarlyStreamsError`;
- at the shipped bound of 8, where the `MaxEarlyStreamsError` filter must be
  empty.

The second assertion is admissible only because the first proves the harness
reads. The 32-stream run does reproduce the tear-down, so criterion 4's tear-down
is **reproduced** and the gate's necessity is **measured**.

## The muxer-default pin, split across two files on purpose

- **The operative value** is `AbstractStreamMuxer`'s hardcoded
  `init.maxEarlyStreams ?? 10` (`abstract-stream-muxer.js:24`). It is not exported
  and has no importable form. Its only runtime read anywhere in this repository is
  the denominator of the `MaxEarlyStreamsError` the reproduction throws, so the pin
  lives **inside that reproduction**, off the same captured object, matched with
  `/(\d+)\/(\d+)$/`. Separate vitest files share no runtime state, so a pin placed
  in `constants.node.test.ts` could only have re-read a `.d.ts` comment or yamux's
  unread `defaultConfig`. The reproduction *is* the pin's instrument: if it ever
  stops reproducing, the pin is gone with it, and that must be reported rather than
  absorbed.
- **The declared intent** is `@chainsafe/libp2p-yamux`'s
  `defaultConfig.maxEarlyStreams = 10`, which `YamuxMuxer`'s constructor never
  reads (`muxer.js:64-75` reads `enableKeepAlive`, `keepAliveInterval`,
  `maxInboundStreams`, `maxOutboundStreams` and not this field). That is a drift
  detector on the library's stated intent and it says so in those words, in
  `constants.node.test.ts`.
- **`@libp2p/interface`'s `@default 10` JSDoc** is not pinned at all, deliberately.
  A grep over a type declaration that reads as though a runtime value had been
  checked is exactly the shape this phase exists to delete.

Each file carries a cross-reference to the other.

## The boundary — criterion 5, in the three statements it needs

**1. On the production `submitJob` path criterion 5 is unmeasured, not met.**
`RemoteExecutor` flattens every failure to `{ok:false, reason}`
(`remote-executor.ts:41-45`) and `executeVerified` files it under
`executor.nodeId` — the receiver (`verify.ts`'s `runOne`). There is no field in
which a different attribution could be carried, so on that path the reason string
is the only attribution a reader gets.

**2. The scenario criterion 5 names — "a connection torn down by the sender
exceeding a stream limit" — is unmeasured on every path, including the coordinator
path.** The classification cases in `churn.test.ts` and `coordinator.test.ts`
construct an `RpcFailure{send-refused}` directly, and the
`transport-bounds.node.test.ts` case produces one from this node's own gate over
the real transport. **Neither reproduces a tear-down**, which is what the criterion
names. In a real tear-down the requests already written but awaiting replies fail
at `rpc.ts`'s timeout (`kind:'timeout'`) and are still attributed to the receiver,
and after this plan's gate the tear-down is supposed not to happen at all.
**Criterion 5 is therefore descoped, in these words, to: the classification exists
and is exercised.**

**3. The classification's only consumer is test-only.** `remoteDispatch` is called
only from `churn.test.ts` and `runResilient` only from `coordinator.test.ts` and
`churn.test.ts` — grep confirms both, and `bin/bench.ts:303` names `runResilient`
in a comment explaining that it is *not* exercised. So this plan widens a
`@o2/core` union and adds a classification whose sole consumer today is a test.
That is stated, not hidden, and it is the reason the criterion is descoped rather
than reported closed. What would close it properly: an optional `kind` on
`ExecutionOutcome` — a `@o2/core` port change with wide reach — or the merged job
path, WIRE-04, Phase 20.

## Corrections made to the plan

Four claims in `13.1-02-PLAN.md` were false against the code or the library and
were fixed in the plan file in place, each with a dated note.

1. **"Without the handler's `catch`, the error escapes into libp2p's delivery path,
   so the abort becomes a connection kill."** Measured false. Replacing the
   `catch` body with a bare `throw cause` leaves all three NET-08 cases green,
   *including* the clause that asserts a subsequent in-limit message is delivered —
   libp2p absorbs a rejected protocol-handler promise and the connection survives.
   Deleting the `catch` entirely does turn two cases red, but on `refusedInbound`
   reading 0, not on any tear-down. The `catch` is kept because it makes the
   refusal countable and keeps a rejected promise out of the delivery path, and the
   source comment now says that instead of the false thing.

2. **"Assert `error.name === 'MaxEarlyStreamsError'` on the 32-send burst."** The
   sender never sees it. Measured: the 32 rejected sends carry `StreamResetError`
   and `UnexpectedEOFError`. `MaxEarlyStreamsError` is raised on the **receiving**
   node's muxer, which aborts that node's streams with it, and it is observable
   only through the receiver's `ComponentLogger` —
   `AbstractMessageStream.abort` calls `this.log.error('abort with error - %e',
   err)`. The plan named no receiver-side instrument; one was built.

3. **"`libp2p.getPeers()` still contains the peer" as evidence the connection
   survived.** After the tear-down the sender's `getPeers()` still returned 1, so
   it is not a tear-down instrument. It is asserted only in the green case, as a
   positive reading; the tear-down itself is discriminated by the receiver's
   captured `MaxEarlyStreamsError` and by messages not arriving.

4. **`importInternal('@chainsafe/libp2p-yamux', 'config.js')`.** That helper calls
   `require.resolve`, and the package publishes no CJS entry, so it throws
   `No "exports" main defined in .../@chainsafe/libp2p-yamux/package.json`. The
   package's export map exposes `./config` directly, so the pin uses
   `await import('@chainsafe/libp2p-yamux/config')` — a better read anyway, because
   it assumes no path.

One deviation not caused by a false plan claim: the plan asked for the sender's
outcome on an oversize frame to be "asserted explicitly rather than left
unstated". It was measured three times at each size and is pinned to `'resolved'`,
with the mechanism recorded: a frame exactly one byte over the cap only crosses it
on its **final** chunk, so by the time the receiver decides to abort, the sender
has written everything and closed. **The sender is not told.** The receive cap is a
receiver-side guard, not a signal back down the wire.

## Follow-ups this plan deliberately leaves

- **Threading `maxMessageBytes` from the node factories.** Plan 13.1-05. Neither
  factory passes `Libp2pTransportOptions` today; this plan makes the option exist
  and proves it at the layer that owns it.
- **An aggregate inbound-bytes budget across peers.** Accepted rather than closed:
  many peers each sending a just-under-limit frame concurrently leaves the
  aggregate unbounded even though each frame is not. NET-08 asks for a per-frame
  cap and that is what closes the measured defect. libp2p's own `maxInboundStreams`
  of 256 per connection is the only aggregate bound today.
- **A hard bound on libp2p's cumulative `earlyStreams` count.** Unmeasured, and
  named here rather than left inside a confident sentence.
- **Criterion 5's named scenario, and its production-path attribution.** See "The
  boundary".
- **`bin/bench.ts`'s `SHARDS`.** Raising it above the old cliff, and measuring what
  the gate costs at nodes=1, is Plan 13.1-05's task 3. This plan changes no
  benchmark input.
- **The `peakStreamsTo` map grows with distinct destinations.** The gate entries
  are dropped as soon as a destination goes idle; the instrument retains one
  integer per destination ever sent to. Documented at the getter as a deliberate
  cost rather than left to be discovered.
