## Corrections to the plan

Every one of these is recorded in `13.1-04-PLAN.md` in place, as an HTML comment beside the
text it corrects.

1. **The "order matters" comment the plan asked for would have been false.** Task 1 said to
   place the registration before the `before` capture and to carry a comment saying *"so a
   refusal that occurs during the job lands inside the delta window and appears in the
   returned manifest."* `EgressGuard.guard()` appends no `EgressEntry` — only `send` and
   `refuse` reach `#record` — and every frame the job sends is sent after the capture in
   either order, so the two orders produce byte-identical manifests and no refusal can land
   outside the window. The order is kept; the comment now says the thing that is true (the
   delta window means *what left during this job*, and a registration is not something that
   left).
2. **Task 1's `<verify>` ran `npx tsc --noEmit -p packages/net`, which cannot pass.** There
   is no `packages/net/tsconfig.json`; the repository has exactly one, at the root, so the
   flag fails with `error TS5081: Cannot find a tsconfig.json file at the current directory`.
   The same correction Plans 13.1-01 and 13.1-03 each needed. Repo-wide `npx tsc --noEmit`
   exits 0.
3. **Three line numbers had drifted.** `submit.ts:176`, cited five times as the unconditional
   `blockstore.put` of every shard input, is **:178**. `sovereignty-placement.node.test.ts:169`,
   cited three times as the bare-`submitJob` call site, is **:170**. `bin/bench.ts:267`, cited
   once as the `submitJobWithEgress` caller, is **:320**. Every *claim* attached to those
   three lines was verified against the code and is true; only the numbers were wrong. The
   three-file `submitJob` call-site set the plan pins was verified exactly as written.
4. **The reproduction cannot be watched with hard assertions.** Task 2 asked for the tap
   capture as the reproduction and specified three ordered assertions, but with everything
   asserted hard the run stops on the *outcome* assertion — `expected 'agreed' not to be
   'agreed'` — and the byte-level capture, the whole point of the task, never prints.
   Confirmed by running it both ways. The outcome, the byte sweep and the manifest readings
   are therefore `expect.soft` (the idiom Plan 13.1-01 settled on for paired evidence); the
   liveness assertions stay hard, because every reading below them is inadmissible if the
   instrument did not fire.

## Deviations, chosen rather than forced

- **The submitter-side group uses a stub `Executor`, not the file's existing fabric.** The
  window that matters is *inside* `submitJob`, and the only object in a job with a hook there
  is the executor. The existing `buildFabric` helper runs a real `WasmExecutor` and offers no
  such hook. The file's header now says which group proves what and that neither carries the
  other's half — the two-real-node measurement of what actually crossed lives in
  `packages/node`.
- **The plan's "same value in two shards registers one label with two holds and is fully
  released only after the job ends" is asserted as a release-count property, not by reading
  a hold count.** `EgressGuard` exposes labels, not holds, so a hold count is not readable.
  Three sovereign shards over two distinct values take three holds on two labels; the
  falsifiable reading is that the guard is empty afterwards. An implementation that guarded
  per shard and released per distinct label leaves the repeated row registered for the rest
  of the process's life, and that is exactly what fails.
- **`submitJob` is made to *throw* by a blockstore whose `put` rejects**, and the snapshot
  taken inside that `put` is what makes the "released" assertion admissible: it proves the
  registration existed to be released rather than never having been taken. The plan left the
  mechanism to the executor's judgement.
- **The byte sweep runs twice** — once over the refused job's frames and once more after the
  seeded control, over everything that arrived across both. The second sweep is what turns
  Phase 13's recorded *"zero violations on both taps"* for the seeded path into a reading on
  this wire rather than a restatement, and it is non-vacuous because more frames arrived
  during the control than before it. The plan asked only for the first.
- **One assertion the plan did not ask for: the unseeded precondition is asserted, not
  assumed.** `owner.store.has(row.cid)` and `owner.store.has(moduleCid)` are both required to
  be `false` before the job. An owner that already held the row would make the refusal
  unreachable and the whole run vacuous.

## What this closes, and what it does not — stated in the required words

**Closed.** A node that submitted a job **through `submitJobWithEgress`** containing a
sovereign shard does not serve that shard's raw bytes to a peer while the job is in flight,
whether or not it ever executed a task over them. Proved byte-for-byte against a tap on the
owner's raw transport, and the tap is proved to have captured something and to have captured
a frame known to have arrived (the `exec` request) before it is allowed to report the
absence. The refusal is recorded on the submitter's own job-scoped manifest with its label.
The seeded configuration completes `agreed` with zero violations and a non-empty manifest, in
the same test, ordered second.

**Not closed, and unmeasured — three parts.**

1. **Refusing a sovereign block at rest, indefinitely, is unmeasured.** The registration is
   job-scoped and is given back in a `finally`, so a peer asking for the same block after the
   job has finished still receives the raw bytes. Criterion 7's wording — *"whether or not it
   executed a task over that block"* — is about *which node*, and the defect it cites is a
   submitter mid-job, which is what this plan measures. Closing it needs a persistent
   per-node set of sovereign CIDs that survives the job and the process.
2. **A job submitted through bare `submitJob` is unguarded, and that is unmeasured.** The
   registration lives in `submitJobWithEgress`. `submit.ts:178` puts every shard input,
   sovereign included, into the submitter's own blockstore regardless of label, so a
   submitter that used bare `submitJob` holds the raw row exactly as the guarded one does and
   registers nothing. This is not hypothetical:
   `packages/node/src/sovereignty-placement.node.test.ts:170` drives a real spawned-agent
   sovereign scenario that way. **It still passes after this plan, and it passes *because*
   the gap is real, not despite it** — its submitter is still unguarded, so the green run is
   not coverage of anything and must not be read as such. Criterion 7 is a property of a
   *node*; what ships here is a property of one *function*.
3. **The browser tier's submitter path is unmeasured.** `BrowserNode.start` needs a real
   `indexedDB` and a relay, so it runs in neither vitest project — WIRE-03, Phase 19.

**What makes (2) visible rather than silent.** A source scan in the new test file reads every
tracked, non-test `.ts` under `packages/` (87 files today; the scan asserts more than 50 and
names four it must contain, so a mis-rooted `git ls-files` cannot pass by finding nothing) and
requires the set of files containing a bare `submitJob(` call to be exactly three: the
definition, the guarded wrapper, and the in-worker caller that hard-codes public shards into a
`MemoryBlockstore`. A fourth file entering that set is a new production submit path this
plan's registration does not cover, and the failure message says so in those words. The scan
strips comments before matching — several of these files name bare `submitJob` in their own
prose — and its ability to report is proved by planting both halves: a real call is found, the
same text inside a `//` or `/* */` comment is not, and `submitJobWithEgress(` is not mistaken
for a bare call.

**What would close (1) and (2) together:** register at a boundary the node owns rather than at
one entry point — the submitting node's blockstore-put of a shard labelled sovereign, or a
helper both `submitJob` callers share.

## Behavioural change this ships, named rather than buried

In the **unseeded** configuration the submitter used to ship the raw bytes when the owner's
`RpcBlockSource` asked for the input block, and the job completed. It now refuses and the job
fails. That is correct and it is the point: `sovereign-egress.ts` states the premise that a
sovereign input is owner-pinned and already resident, and a submitter holding another owner's
raw row has broken that premise before the fabric is involved. The **seeded** path — the one
the fabric is designed around — is unaffected, proved as a control in the same test, because
an `exec` request frame carries CIDs and not bytes.

The refusal arrives fast rather than as a timeout, and no test here shortens `rpcTimeoutMs`
from the production 30,000 ms default: after Plan 13.1-03 gave the block branch a named
refusal, `RpcBlockSource.fetch` reads the non-`block` reply as a miss, asks the next peer,
finds none, and the owner's executor reports `input block missing`. A shortened budget would
have hidden a regression to the timeout, which is the mistake `named-refusal.node.test.ts`
was written to stop repeating.
