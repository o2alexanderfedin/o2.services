1. **Admission on the `exec` branch** (SCHED-06, criteria 1 + 2) — `packages/net/src/agent.ts:201-251`

## Implementation Decisions

### 1. `LocalCapacity` is wired, not deleted — and it must bite on the `exec` branch, not the `offer` branch

Criterion 2 offers a binary: constructed by both production factories, or deleted. Deleting
it is wrong on the evidence — it is a 58-line class with a full spec
(`packages/core/src/placement.test.ts:267-357`), it is the exact shape SCHED-03 named, and
`ARCHITECTURE.md` §7.2 says the same thing the requirement does: *"an over-committed node
just says no, and the requestor resamples."* So: wire it.

But wiring it *as the `offer` branch currently uses it* is the wrong half.
`packages/net/src/agent.ts:192-200` calls `options.capacity.offer(...)`, and `offer()`
**reserves a slot** (`placement.ts:305`) with no release anywhere on the wire. The `exec`
request carries no shard id (`protocol.ts:283-289` encodes `moduleCid`, `inputCid`,
`partitionIndex`, `partitionCount`, `label`, `ownerId`, `capability` — no shard id), so a
serving node cannot correlate an offer reservation with the exec that redeems it. Wiring a
real `LocalCapacity` into today's offer branch is therefore a slot leak, and there is a
live production prober that would trigger it: `packages/browser/demo/main.ts:454` sends
`{kind:'offer', shardId:'probe'}` to **every connected peer** as a liveness check. One demo
tab would permanently reserve a slot named `probe` on every peer it can see.

So the decision has two halves:
- The `exec` branch acquires and releases a slot around `executor.execute` — this is the
  branch that consumes a `WebAssembly.compile` plus `instantiate` plus a linear memory.
- The `offer` branch answers from the same counters **without reserving**.

### 2. The `exec` slot key is the task's own identity

`LocalCapacity.offer` keys on `offer.shardId` and dedupes: a second `offer` for a shard
already in flight is refused with `` `${offer.shardId} is already in flight here` ``
(`placement.ts:295-297`). The `exec` request has no shard id, so the key must be derived.

**Use `` `${task.inputCid.toString()}:${task.partitionIndex}` ``.** Two consequences, both
wanted:
- A duplicate dispatch of the *identical* task to the same node while the first is still
  running is refused with a stated reason. That is correct — it is the same work, and
  speculation is supposed to place the duplicate somewhere else.
- One requestor cannot occupy N slots on a node by replaying one task.

**Assumption:** `inputCid` plus `partitionIndex` uniquely identifies a unit of in-flight
work on one node. It does, given `submitJob` content-addresses every shard input
(`packages/core/src/job/submit.ts:164-180`) — two different jobs over identical input bytes
produce the same CID, and are the same computation.

The rejected alternative is a per-request monotonic id. It never collides, so the dedupe
never fires — which throws away the one behaviour `LocalCapacity` was built with, and
re-opens the replay hole.

### 3. `LocalCapacity` gains a non-reserving twin, so the reason string exists once

Decision 1 needs the `offer` branch to decide without mutating. `LocalCapacity` already
exposes `slots` and `inFlight` as public getters (`placement.ts:280-286`), so the `offer`
branch *could* compare them inline — but then the refusal string
`` `over-committed: ${n} of ${m} slots in use${throttled}` `` (`placement.ts:302`) would
exist in two places and drift. Add `would(offer: Offer): Admission` beside `offer()`,
sharing one private decision function; `offer()` becomes `would()` plus the reservation.

This is a `@o2/core` addition of about fifteen lines with no new dependency, and it is the
smallest change that keeps one reason string.

### 4. A capacity refusal and an egress refusal travel as **different** wire shapes, because they want opposite retry policies

This is the least obvious decision in the phase and the one most likely to be got wrong.

`packages/net/src/churn.ts:14-26` documents the classification table, and it is right:

| reply | kind | why |
|---|---|---|
| `{kind:'error'}` | `node` | "reachable, but refusing to serve this" (`churn.ts:18, :64-65`) |
| `{kind:'exec', outcome:{ok:false}}` | `task` | "a reachable node ran it, and it failed" (`churn.ts:19, :74-75`) |

- A **capacity** refusal is a node condition. The same task on another node succeeds.
  → it must be `node`. → send `{kind:'error', reason:'over-committed: N of M slots in use'}`.
- An **egress** refusal is a task condition. A map step that forgot to aggregate leaks the
  same way on every node, and re-running it across the fabric burns each in turn — exactly
  what `DEFAULT_MAX_TASK_FAILURES = 3` (`coordinator.ts:126`) exists to cap.
  → it must be `task`. → send `{kind:'exec', outcome:{ok:false, reason:'egress refused: <label>'}}`.

**Neither needs a protocol change.** Both shapes already parse (`protocol.ts:486-489`,
`:526-541`), both already classify correctly in `remoteDispatch`, and both already reach
`RemoteExecutor` as a populated `reason` (`remote-executor.ts:51-52` and `:57`). A new
`{kind:'refused'}` response kind was considered and rejected: it would touch `protocol.ts`
twice, `churn.ts`, `remote-executor.ts`, and their specs, to buy a discriminator that
`kind:'error'` vs `kind:'exec'` already provides — and it would provide it *less* well,
because one new kind cannot express the two different retry policies these two refusals
need.

The cost, stated rather than hidden: a requestor cannot tell `malformed request` from
`over-committed: …` without reading the string. That is acceptable here and it is not
acceptable everywhere — `RpcFailure` deliberately carries a typed detail
(`rpc.ts:31-39`) precisely so callers need not string-match. The difference is that
`RpcError` is consumed programmatically to decide control flow; `AgentResponse.error.reason`
is consumed as an explanation. Record the boundary in the reason vocabulary: refusals are
prefixed `over-committed: ` and `egress refused: `, and those prefixes are asserted by test
so they cannot drift silently.

### 5. NET-10's remedy is a pre-send scan inside `serveAgent`'s exec branch, not a change to `rpc.ts`'s responding leg

`13-VERIFICATION-2.md` sketched this and explicitly declined to trust its own sketch. It
holds up:

`rpc.ts:251-259`'s `catch` is documented as swallowing by design — *"throwing would surface
inside the transport's delivery path"* — and `egress.ts:119-128` gives that as the reason
the responding leg cannot name its refusal. Changing it means changing every peer's
response-leg failure semantics for a legibility complaint. Do not.

Instead: `serveAgent`'s exec branch already holds the guard (`agent.ts:232`), the label
(`agent.ts:234`), and the outcome. It can encode its candidate reply, ask the guard whether
that byte string contains a registered payload, and on a match return the small
`{kind:'exec', outcome:{ok:false, reason:'egress refused: <label>'}}` from decision 4 —
a frame that by construction cannot carry the payload it refuses. `rpc.ts` is untouched.

Two mechanical requirements this creates:
- `EgressGuard.#scan` (`egress.ts:298-304`) needs a public form. `violationIn(frame: Uint8Array): string | null`
  is the natural name; `#scan` becomes its body.
- The scan target is the encoded *body*, while `EgressGuard.send` scans the whole encoded
  frame `{k:'res', id, body}` (`rpc.ts:193-201`). That is safe: `contains`
  (`egress.ts:308-317`) is a contiguous-run search, and dag-cbor encodes a byte string as a
  header followed by the raw bytes, so a payload present in the body is present as the same
  contiguous run inside the frame. The pre-scan is therefore strictly no less sensitive
  than the send-time scan, and the send-time refusal stays in place as the backstop.

**The belt-and-braces property must be asserted, not assumed:** after the pre-scan lands,
`EgressGuard.send` must still refuse if the pre-scan is ever removed. That is the mutation
to plant.

### 6. DATA-10 registers sovereign shard inputs on the **submitting** node's guard, inside `submitJobWithEgress`

`registerSovereignInputs` (`packages/net/src/sovereign-egress.ts:63-76`) fires on the
serving side, for a task about to execute, when the local store already holds the input.
A submitter satisfies none of those three, which is exactly the 138-byte frame
`13-VERIFICATION-2.md:468` measured.

`submitJobWithEgress` (`packages/net/src/submit-with-egress.ts:79-92`) is the one place that
already holds both the `JobSpec` — whose `ShardSpec` carries `label:'sovereign'` and
`ownerId` (`submit.ts:29-31`) — and the node's `EgressGuard`. Register each sovereign
shard's canonical bytes there before `submitJob` runs, release in a `finally` after it
returns. The label is the input CID string, matching `sovereign-egress.ts:70` so the two
registration paths cannot produce two different labels for one payload.

**This changes an existing behaviour and the change is the point.** In the "unseeded"
configuration — the owner does *not* already hold the row — the submitter today ships the
raw bytes when the owner's `RpcBlockSource` asks for the input block
(`agent.ts:166-168` → `FetchingBlockstore`). After this, that block response is refused and
the job fails. That is correct: `sovereign-egress.ts:26-32` states the premise that a
sovereign input is owner-pinned and already resident, and a submitter holding another
owner's raw row has broken the premise before the fabric is involved. **The "seeded" path
must be proved unaffected** — `13-VERIFICATION-2.md:449-453` measured zero violations on
both taps there, because the exec request frame carries CIDs and not bytes
(`protocol.ts:283-289`). A control job is mandatory in the same test.

**Registration lifetime is job-scoped, not process-scoped.** Holding it forever would refuse
the block after the job too — which is closer to what criterion 7's wording asks for — but
it reintroduces exactly the unbounded scan cost Plan 13-07 was written to remove
(`egress.ts:141-149`), and it does so on a set the node's own submissions grow. Job-scoped
matches the serve path's hold/release discipline. See `<specifics>` for what that leaves
unmeasured, stated in those words.

### 7. NET-08's cap is a declared constant in `@o2/libp2p`, enforced in `readMessage`, threaded as an option

`readMessage` (`libp2p-transport.ts:57-74`) pushes every chunk into `chunks` and sums
`total`, then allocates `new Uint8Array(total)`. Both allocations are peer-driven.

Add `MAX_INBOUND_MESSAGE_BYTES` to `packages/libp2p/src/constants.ts` and check `total`
inside the `for await`, calling `stream.abort(...)` and throwing past it — the abort is what
criterion 3 names, and it must happen *during* accumulation, not after, or the cap has
already been paid.

**Value: 8 MiB.** A configuration choice, sited against figures somebody actually recorded —
not computed from any workload:
- above the 100 KiB block `fabric-node.node.test.ts:67-82` deliberately carries.
- above the largest artifact this project has actually produced: `10-VERIFICATION.md:16`
  records 5.6 MB elfconv output, `SUMMARY.md:127` records ~4.8 MB.
- below the 64 MiB frame the roadmap measured accepted.

Do not compute a payload size out of demo or job source and write the result here or in the
constant's doc. If a workload's frame size matters, measure it and record the measured figure
with its date.

`Libp2pTransportOptions` (`libp2p-transport.ts:42-54`) gains `maxMessageBytes?`, defaulted
from the constant, so a test can shrink it to a few KiB and reproduce the abort in
milliseconds rather than shipping 64 MiB through a test suite. Neither factory passes
`Libp2pTransportOptions` today (`fabric-node.ts:344`, `browser-node.ts:213` both call
`Libp2pTransport.start(libp2p)` bare), so this is the first option that needs threading —
thread it from both, as an optional field on each factory's options.

### 8. NET-09 is fixed by a per-peer send gate, not by raising `maxEarlyStreams`

The abort is real and its source is now known precisely:
`node_modules/@libp2p/utils/dist/src/abstract-stream-muxer.js:115-121` — when the muxer has
no `'stream'` listener yet, inbound streams queue in `earlyStreams`, and past
`maxEarlyStreams` the muxer calls `this.abort(new MaxEarlyStreamsError(...))`, killing the
connection. `@libp2p/interface`'s `StreamMuxerOptions` declares `maxEarlyStreams?` with
`@default 10` (`node_modules/@libp2p/interface/dist/src/stream-muxer.d.ts:31`), and
`@chainsafe/libp2p-yamux`'s `Config` extends `StreamMuxerOptions`
(`node_modules/@chainsafe/libp2p-yamux/dist/src/config.d.ts:1,14`), so `yamux({maxEarlyStreams: N})`
is available at `fabric-node.ts:309` and `browser-node.ts:200`.

**Raising it is not the fix.** It moves the cliff; it does not make the cliff impossible,
and it leaves the connection tear-down as the failure mode. The roadmap says where the fix
belongs: *"Only the per-peer send path in criterion 4 is a genuine bounded-queue site."*

So: `Libp2pTransport` gains a per-destination concurrency gate around the
`dialProtocol`/write/close body of `send` (`libp2p-transport.ts:126-145`). At most K streams
open at once toward one peer; the rest wait FIFO.

- **K sits below libp2p's operative `maxEarlyStreams` default of 10. K = 8.** The roadmap
  measured N=8 completing and N=12 aborting at `11/10`, so 8 is the largest value the existing
  evidence shows is safe, and it leaves two streams of headroom for `identify`'s own stream —
  which the roadmap notes was collateral in the tear-down. **A cap on *concurrent* streams is
  not a proof that the ceiling is unreachable**, because `earlyStreams` is cumulative within
  the pre-listener window; the plans carry that limit in full, and no comment here or in
  source may claim the gate makes the tear-down impossible.
- **The wait is bounded** by the existing `AbortSignal.timeout(this.#sendTimeoutMs)`
  (`libp2p-transport.ts:125`, default 20 s) — but that signal is currently created *before*
  the dial, so it must be created before the gate is taken or the timeout will not cover the
  queueing.
- **A bounded queue depth** past which `send` throws immediately with a sender-attributed
  message. `RpcEndpoint.request` already turns a rejected `Transport.send` into
  `RpcFailure{kind:'send-failed'}` (`rpc.ts:165-177`), which is a *named, immediate* outcome
  and distinct from `kind:'timeout'` — criterion 4's "stated, sender-attributed reason" with
  no new machinery.

**No deadlock.** `Transport` is a one-way datagram port: `send` resolves when
`stream.close()` completes (`libp2p-transport.ts:141`), never on a reply. A reply travels on
a stream opened in the other direction, through the *other* node's gate. The two gates are
independent, so a full gate can delay but cannot block its own drain.

**Assumption, and it is worth a probe before the plan commits:** the 8-stream ceiling is a
throughput cap per peer, not per node. The bench's `realFabric` shape
(`bin/bench.ts:201-236` — every worker dials one requestor, and every `RemoteExecutor` is
built over that one endpoint) means the requestor's concurrency *toward each worker* is what
the gate caps. Whether any rung of the ladder actually presents more than K sends toward one
peer at once is **unmeasured**; do not compute it from `SHARDS` and `redundancy`, and do not
write such a computation into a plan, a comment or a summary. Measure it if it matters.

**Correction, made during the second plan-revision pass: what queues is the *stream*, not
the *task*, and this paragraph originally said otherwise.** The gate delays only the opening
of a stream. `send` resolves at `stream.close()` (`libp2p-transport.ts:141`) and the
receiving handler dispatches fire-and-forget (`:101-102`, `#dispatch` at `:168-171`, and
`rpc.ts:136-137`'s `void this.#receive(...)`), so a slot is released as soon as the request bytes
land — not when the task finishes. The gate therefore does **not** serialize execution, and
no plan may derive a bound on concurrent `exec` requests from it. Whether the extra
stream-open round trips are visible in the makespan is a question for measurement, not for
derivation: measure the makespan at nodes=1 before and after and record it, with its sample
sizes, as an observation. A silent throughput regression in the benchmark rig is exactly the
shape this milestone exists to remove; so is a confident sentence about a mechanism nobody
measured.

### 9. Criterion 5 needs a third failure kind. Name it, do not fake it

`DispatchOutcome` is `{ok:false, kind:'node'|'task', reason}` (`coordinator.ts:110-112`).
Neither value is honest for a sender-side overrun: it is not the receiver's fault and it is
not the task's fault. And `coordinator.ts:450` attaches the *attempted* `nodeId` to every
failure, so with only two kinds the record says the receiver failed no matter what the
string says.

Widen to `'node' | 'task' | 'sender'`. The blast radius is small and was checked, not
assumed: `kind` is read in exactly one place for policy — `coordinator.ts:450`,
`if (failure.kind === 'task') taskFailures += 1` — so `'sender'` behaves like `'node'` for
retry (retry elsewhere is right: a different peer has a different gate) while being
*named* differently and therefore assertable. The union also appears at `coordinator.ts:172`
and `:222` as a recorded type, and is constructed at `:239` (the escaping-exception path)
and in `churn.ts` at `:55, :62, :65, :70, :75, :87`.

**Corrected 2026-07-29 — do not branch on `send-failed`.** This decision previously read:
*"`churn.ts:52-58` then branches on `cause.detail.kind === 'send-failed'` → `kind:'sender'`;
everything else stays `'node'`."* That is wrong, and Plan 02 Task 3 refuses it explicitly.
`send-failed` is produced for **any** rejection of `Transport.send` — `rpc.ts:167-178` is a
bare `.catch` around it, and `libp2p-transport.ts:126-129` rejects from `dialProtocol`
whenever the peer is unreachable, refuses the protocol, or the dial times out. So a genuinely
dead *receiver* arrives as `send-failed`, and branching `'sender'` on it would record that
peer's death as a failure of **this** node — the misattribution criterion 5 exists to remove,
pointed the other way.

The design is instead a **named marker**: `SendRefused` on the `Transport` port, carried
through as a distinct `send-refused` `RpcError` variant, set *only* when the caught cause is a
`SendRefused`. `churn.ts` branches on that marker alone. `send-failed` keeps its current
meaning and its current `'node'` classification, and a dial to an unreachable peer must still
classify `'node'` — assert that case explicitly, because it is the one the old design broke.
See Plan 13.1-02 Task 3, which owns this.

**`RemoteExecutor` cannot carry this.** It flattens to `{ok:false, reason}`
(`remote-executor.ts:41-45`) and `executeVerified` records that against `executor.nodeId` —
the receiver (`verify.ts:80-83`). On the production submit path the only thing available is
the reason string. See `<specifics>` for what that means for measuring criterion 5.

### 10. The admission limit has a declared default, a per-node override, and `bin/bench.ts` sets it explicitly

`bin/bench.ts`'s `realFabric` calls `FabricNode.start` (`bench.ts:209, :214`), so it
inherits whatever default admission limit this phase installs. A default below whatever the
benchmark workload actually puts on one node produces refusals, which `submitJob` cannot
re-dispatch (decision 11 / Risk 1), which the bench's incomplete-run rule then reports as
failed runs — a benchmark silently shaped by an admission limit nobody declared. **What that
workload actually puts on one node is unmeasured**: no reading of a node's concurrent `exec`
count under the benchmark exists, and multiplying `SHARDS` by `redundancy` does not produce
one — `planPlacement` takes `ordered.slice(0, redundancy)` over *distinct* nodes
(`packages/core/src/sovereignty.ts:185`), so no node holds two replicas of one shard.

- `DEFAULT_MAX_CONCURRENT_TASKS`, exported from `@o2/core` beside `LocalCapacity`.
  **Planning wrote 16 here; the plans ship 64.** It is a **configuration choice, not a derived
  quantity**. **13.1-01-PLAN.md Task 1 declares it and is the only plan in this phase that
  carries its value** — 13.1-05 imports it as the factories' default and deliberately does not
  restate it. Read 13.1-01 Task 1 for the value, for the bounds the spec pins it between (at
  least 64, strictly below the 800 simultaneous `execute()` calls the roadmap's probe
  measured), and for the fact that it **does not** put the refusal out of reach on the
  production submit path — whether the refusal is reached there is itself unmeasured.
- `FabricNodeOptions.maxConcurrentTasks?` and `BrowserNodeOptions.maxConcurrentTasks?`,
  both optional, both defaulting to the constant. A test that wants refusals sets it to 2.
- `bin/bench.ts` passes it **explicitly** at both `FabricNode.start` sites, with a comment
  saying the benchmark declares its admission limit rather than inheriting it — and the
  value belongs in the run's recorded configuration so a published curve states it. Whether
  that is a new `RunConfig`/`Inventory` field or a line in the rendered methodology note is
  planner's discretion; that it is recorded somewhere a reader sees is not.

### 11. Test placement follows the suffix rules, and three of the four mechanisms are Node-project-only

`vitest.config.ts` runs `packages/*/src/**/*.test.ts` in **both** the `node` and `browser`
projects; `*.node.test.ts` in `node` only; `*.e2e.test.ts` in its own serialized project.

- `LocalCapacity.would`, the reason strings, the `churn.ts` classification, the
  `serveAgent` pre-scan, and the submitter-side registration are all portable — their specs
  belong in `packages/core/src/*.test.ts` and `packages/net/src/*.test.ts` (bare suffix, run
  in both projects), reusing `MemoryNetwork` as `discovery.test.ts:72-89` does.
- Anything asserting `readMessage`'s abort, the per-peer gate, or real concurrency against
  tcp + noise + yamux needs `Libp2pTransport`, which lives in `@o2/libp2p` and is exercised
  from `@o2/node` — `packages/node/src/*.node.test.ts`.
- Criterion 1 says "verified by concurrency against the real stack" and criterion 4 says
  "immediately after dial", so both need the real transport. Two spawned `bin/agent.ts`
  processes are available (`egress-refusal.node.test.ts:62-95` is the current best template)
  but are **not** required by either criterion's wording; multiple `FabricNode.start()`
  calls in one Vitest process over real TCP is the precedent
  (`fabric-node.node.test.ts:230-236`: *"`startNode` is the same factory call `bin/agent.ts`

## Specific Ideas

### How each success criterion gets measured

**Criterion 1 — refusal under real concurrency.** Start a `FabricNode` with
`maxConcurrentTasks: 2`, dial it from ≥2 other real `FabricNode`s, fire ≥64 concurrent
`exec` requests. Measure two numbers, both off instruments inside the node under test:
(a) **peak simultaneous `execute()` calls**, from an executor decorator that increments on
entry and decrements in a `finally` and records the maximum — assert `≤ 2`; (b) the count of
replies whose reason begins `over-committed:` — assert `> 0` and that the string names both
integers. Assert *both*: peak alone passes trivially if nothing was dispatched, and refusals
alone pass if the limit is enforced by luck. **Mutation to plant:** remove the slot
acquisition; peak must jump to the request count.

*Interaction to respect — and the version of it written here first was wrong.* After
decision 8's gate lands, a sender can hold at most K=8 **streams** open toward one peer.
That is **not** a bound on peak inbound `exec` concurrency, and `peers × 8` is not a ceiling
on anything: `Transport.send` is a one-way datagram resolving at `stream.close()`
(`libp2p-transport.ts:141`), the receiving handler dispatches fire-and-forget (`:101-102`,
`#dispatch` at `:168-171`, `rpc.ts:136-137`'s `void this.#receive(...)`), so a stream is released
as soon as the request bytes land and one sender can put an arbitrary number of `exec`
requests on a node at once. That is what the roadmap's probe **measured**: 4 peers each
firing 200 concurrent `exec` requests, and the instrument on the node under test read **800
simultaneous `execute()` calls and zero refusals**. 800 is that probe's reading, not a model
of anything — no other workload's peak may be computed by imitating its arithmetic. The test
therefore needs `maxConcurrentTasks` strictly below the number of requests it dispatches, and
uses more than one requestor to show the bound is the *node's* rather than any one sender's.
This is why the limit is an option and not only a constant.

**Criterion 2 — `LocalCapacity` constructed by both factories.** Structural, and it must not
be checked structurally. `13-VERIFICATION-2.md` recorded the lesson: "the transport is
wrapped" was a composition an inspection could confirm while the behaviour had never run.
Measure it behaviourally instead — criterion 1's test proves `FabricNode`, and the same
assertion against a `BrowserNode` proves the other. **`BrowserNode.start()` needs a real
`indexedDB` and a relay to dial, so it runs in neither vitest project** (this is recorded as
the root cause of four separate deferred items under WIRE-03 in `REQUIREMENTS.md:427-432`).
So the browser half is measurable **only** through the `e2e` project, and if a plan does not
build that harness, the honest report is that the browser factory's wiring is **unmeasured,
not met** — say it in those words, and do not let a `grep` for `new LocalCapacity` in
`browser-node.ts` stand in for it.

**Criterion 3 — the receive cap.** Construct a `Libp2pTransport` with
`maxMessageBytes` set small (say 64 KiB), send a frame one byte over from a second real
node, assert: the receiving side threw/aborted, the peer's `send` rejected, the receiver's
process is still alive, and a subsequent in-limit message over a fresh connection succeeds.
The last clause is what distinguishes "aborted the stream" from "killed the connection" —
which is the exact distinction criterion 4 exists about, so it must be asserted here too.
Then a second, slower assertion at the real 8 MiB default, sending 8 MiB + 1, to prove the
shipped constant is the one enforced rather than only the test override.

**Criterion 4 — N shards immediately after dial.** Dial, then dispatch N=32 `exec` requests
with no delay, and assert every one either completes or fails with a reason naming the
sender's own bound; assert the connection is still up afterwards
(`libp2p.getPeers()` still contains the peer) and that a subsequent request succeeds.
**Mutation to plant:** set the gate's K to 32 and watch the run abort with
`MaxEarlyStreamsError` — that is what proves the gate is load-bearing rather than
decorative, and it reproduces the roadmap's own measurement inside the suite.

**Criterion 5 — sender overrun is not the receiver's failure.** This one is only partly
measurable, and the boundary must be stated rather than papered over:
- On the `runResilient`/`remoteDispatch` path it is fully measurable after decision 9:
  force a send-side refusal, assert `outcome.kind === 'sender'` and that the reason names
  the local peer id, and assert `taskFailures` did not increment.
- **On the production `submitJob` path it is not measurable at all**, because
  `RemoteExecutor` flattens every failure to `{ok:false, reason}` (`remote-executor.ts:41-45`)
  and `executeVerified` files it under `executor.nodeId` — the receiver
  (`verify.ts:80-83`). There is no field in which a different attribution could be carried.
  What *would* measure it: an optional `kind` on `ExecutionOutcome`, or a job path that goes
  through the coordinator (WIRE-04, Phase 20). Until one of those exists, the honest report
  for the production path is **unmeasured, not met**, and the reason string is the only
  attribution a reader gets.

**Criterion 6 — a sovereignty refusal as a named outcome.** Run the Phase 13 leaking-job
scenario (`MODULE_ECHOES_INPUT` over a registered sovereign input) and assert three things:
the requestor's failure reason contains the violated label; the wall-clock from dispatch to
failure is **under 1 s** measured with `performance.now()`; and the node's `rpcTimeoutMs` for
that test is left at the production default of 30 s, so a passing fast path cannot be an
artifact of a shortened budget. That last clause is the measurement — `13-VERIFICATION-2.md`
showed every existing test on this path shortens the budget, which is precisely how the
30 s cost stayed invisible. **Mutation to plant:** remove the pre-scan; the assertion must
fail on the timing bound, not only on the string.

**Criterion 7 — a node refuses to serve a raw sovereign block it never executed.** Two real
nodes. The submitter holds the sovereign bytes and never runs the task; the peer requests
that CID directly with `{kind:'block', cid}`. Assert the reply carries no bytes, the
submitter's manifest records an entry with the violation label, and — the part that makes it
a measurement rather than a report — a **byte-level assertion that the raw payload does not
appear anywhere in what crossed**, using `EgressGuard.violationIn` from decision 5 against a
tap on the wire, mirroring how `13-VERIFICATION-2.md:449-461` checked both directions.
Then the control: the same two nodes, a seeded sovereign job, completing `agreed` with zero
violations and a non-empty manifest. A clean manifest and an absent one must not look alike
— `13-CONTEXT.md` decision 3 established that rule and it applies unchanged.

**What criterion 7 does not measure, stated plainly.** Under decision 6 the registration is
job-scoped, so a peer asking for the same block *after* the job has finished still gets the
raw bytes. The criterion's own wording — "whether or not it executed a task over that block"
— is about *which node*, and the defect it cites is a submitter mid-job, which is what the
test above measures. A node refusing at rest, indefinitely, is **unmeasured** and would need
a persistent per-node set of sovereign CIDs that survives the job and the process. Name it
in the phase's follow-ups; do not let the criterion's wording imply it was closed.

### The three routes by which a node comes to hold raw sovereign bytes

Useful framing for anyone sizing DATA-10's coverage:
1. **It is the owner** — the data is pinned there. Covered at execution by
   `registerSovereignInputs`; not covered at rest.
2. **It submitted a job containing them** — closed by decision 6, for the job's duration.
3. **It fetched them over the wire** — closed by construction once (1) or (2) holds on the
   node that would have served them, because `EgressGuard.send` refuses.

So (2) is the hole this phase closes and (1)-at-rest is the one it leaves open. Say so.

### Reproduce before you fix

Every one of the four mechanisms has a measurement in the roadmap that no test in this
repository currently produces. The cheapest insurance against fixing the wrong thing is to
land the reproductions first, watch them fail, and only then change the code — the same
discipline `13-03-PLAN.md` used for the plant/watch-fail/revert cycle. In particular the
64 MiB frame and the N=12 cliff are both single-file `*.node.test.ts` reproductions against
two `FabricNode.start()` calls, and neither needs a spawned process.
</specifics>

## Risks — flagged, not resolved

**1. `submitJob` has no re-pick loop, so half of criterion 1 has nowhere to happen.**
`submit.ts:205-260` places, then calls `executeVerified` over the selected executors, then
reports. There is no retry, no generation, no resample. `bin/bench.ts:302-304` says so in a
comment: *"submitJob does not speculate or re-dispatch; those paths belong to runResilient
and are not exercised by this workload."* And `runResilient` has no production caller
(see the table). So "the requestor re-picks" is demonstrable only on the coordinator path,
which today is exercised only by tests. The planner must choose explicitly between: (a)
demonstrate the re-pick with `runResilient` + `remoteDispatch` over the real transport and
say plainly that the production submit path does not re-pick; (b) add a re-pick to
`submitJob`, which is WIRE-04's job and a much larger diff than this phase is scoped for.
**Recommendation: (a), stated in the phase summary in those words.** Do not let a passing
coordinator test read as though the production path re-picks.

**2. Wiring admission changes the benchmark, and the benchmark is about to be published.**
Decision 10 addresses it with a declared default and an explicit bench override, but the
interaction is worth naming on its own: `bin/bench.ts` builds real `FabricNode`s
(`bench.ts:209, :214`), so any default this phase installs shapes the scaling curve Phase 23
publishes. A limit below whatever the workload actually puts on one node produces refusals
that `submitJob` cannot recover from, which the incomplete-run rule reports as failed runs.
Whatever value ships, the benchmark must state it, and the makespan at nodes=1 must be
compared before and after decision 8's per-peer gate. The reason to look, at its real size:
the gate caps a requestor's concurrent *streams* toward one peer, so a burst wider than the
cap waits on stream open/close. It does **not** serialize the tasks themselves — decision 8's
correction gives the call chain — so this is a reason to measure, not a predicted slowdown,
and no figure for the cost may be computed and written down in place of the measurement.

**3. Criterion 5's honest classification requires widening a `@o2/core` union, and the
production path still cannot carry it.** Decision 9 widens `DispatchOutcome.kind` and the
blast radius was checked (one policy read, at `coordinator.ts:450`). But `RemoteExecutor`
and `executeVerified` have no field for attribution and file every failure under the
receiver's `nodeId`. So even after the widening, criterion 5 is met on one job path and
**unmeasured on the other**. The planner should decide whether to also add an optional
attribution to `ExecutionOutcome` — a `@o2/core` port change with wide reach — or to accept
the split and record it. **Recommendation: accept the split and record it**; the port change
belongs with WIRE-04, where the two job paths merge anyway.

**4. The `offer` branch's reservation leak exists today and is currently invisible.** Both
factories pass `'accepts-every-offer'`, so `LocalCapacity.offer`'s reservation never runs in
production and the missing release has never cost anything. The moment criterion 2 is
satisfied by handing the factories a real `LocalCapacity`, the leak becomes live — and
`browser/demo/main.ts:454` sends an `offer` to every connected peer on every
`computePeers()` call. Decision 3 closes it with a non-reserving read, but a plan that wires
`capacity` without also changing the offer branch will ship a node that fills its own slot
table from liveness probes and then refuses all work. This is the single most likely way to
get this phase wrong.

**5. "Research: None" is accurate about novelty and optimistic about the diff.** The four
mechanisms touch: `@o2/core` (`placement.ts`, `coordinator.ts`), `@o2/net` (`agent.ts`,
`churn.ts`, `egress.ts`, `submit-with-egress.ts`), `@o2/libp2p` (`constants.ts`,
`libp2p-transport.ts`), both node factories, `bin/bench.ts`, and — for the requirement
`ROADMAP.md` itself names — Phase 18's criterion 2. Size the work against this document.
