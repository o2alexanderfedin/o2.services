### The name is `admission`, not `capacity`

The plan said to expose `readonly capacity: LocalCapacity`. That is impossible:
`FabricNode` has had `get capacity(): RelayCapacity` since NET-05 — the relay *reservation*
capacity. Both factories therefore expose `readonly admission: LocalCapacity`. Two meanings
of one word on one object is how a reader asserts the wrong number.

### Which instrument reads which claim

- **`node.executorPeakInFlight`** is the measurement. It counts `execute()` calls that
  happened, so it can read any number at all, which is what makes an assertion about it
  falsifiable. It is a valid *bound* reading only because every dispatch in
  `admission.node.test.ts` arrives over RPC; a caller reaching `node.executor` directly takes
  no slot, because admission lives on `serveAgent`'s exec branch.
- **`node.admission.peakInFlight`** is a reachedness reading and never a bound reading.
  `LocalCapacity.offer()` returns its refusal before the reservation is taken, so
  `peakInFlight <= slots` is arithmetic and cannot fail.

`CountingExecutor` is composed **outermost** on `FabricNode` — nothing reaches that node's
executor uncounted. On `BrowserNode` it is composed **inside** `GovernedExecutor`, because
`node.executor` must stay exactly a `GovernedExecutor` for BROW-04's `.executed`/`.dutyCycle`
surface, and a counter outside the governor would count tasks parked on its serialization
chain as in flight — which is not what "how many tasks is this tab running at once" means.

The visibility duty cycle is **not** fed into `LocalCapacity`, and the reason is written
beside the construction in `browser-node.ts`: the tab already paces every task through
`GovernedExecutor`, and two independent throttles on one path produce a number nobody can
predict.

## The re-pick, and the four statements this plan owes

The coordinator-path re-pick passes: `runResilient` + `remoteDispatch` over two real
`FabricNode`s on loopback TCP, the busy one holding its only slot, the shard refused by name
and completing on the other. `shard.attempted` is `[busy, free]` in that order,
`shard.failures[0]` is `{kind: 'node', reason: '…over-committed: 1 of 1 slots in use'}`
attributed to the busy node, `shard.resultCid` is non-null and `shard.nodeId` names the free
node, and `busy.executorPeakInFlight` is 0 — it never ran the task at all.

The order is deterministic rather than lucky: with `d` defaulting to 2 over a two-node pool,
`sampleCandidates` returns the whole pool, and `leastLoaded` sorts by load then by ascending
node id, so with both loads at 0 the lexicographically smaller peer id is attempted first.
The test sorts the two nodes by peer id and saturates that one.

And the four statements, in the words the plan requires:

1. **The production `submitJob` path does not re-pick.** It places, runs `executeVerified`
   once per selected executor (`core/src/job/submit.ts:237`), and reports — no retry, no
   generation, no resample. Read from the code: `submit.ts:206` is one `Promise.all` over
   shards and there is no loop around it.
2. **Criterion 1's second clause is therefore unmeasured on every path that runs in
   production.** `runResilient`, which does re-pick, has no production caller —
   grep-confirmed: its only non-test references are its own definition
   (`coordinator.ts:283`), the `@o2/core` barrel, and a comment in `bin/bench.ts` explaining
   that it is *not* exercised by that workload. `remoteDispatch` is called only from tests
   (`churn.test.ts`, and now `admission.node.test.ts`). The re-pick demonstrated in this file
   is demonstrable only inside tests.
3. **Refusal without a re-pick turns a previously slow job into a failed job on the
   production submit path.** `remote-executor.ts:51-52` flattens the `{kind:'error'}` refusal
   into `{ok:false, reason: 'remote error from <nodeId>: over-committed: …'}`,
   `verify.ts:80-83` records it against `executor.nodeId`, the shard is not `agreed`, and
   `job.complete` is false — for `browser/demo/main.ts:312,552` and `bin/bench.ts` alike.
   Before this phase a saturated node queued the work and eventually answered. The measured
   version of "eventually" is capture 1: **32 of 64 requests answered never**, so the
   previous behaviour was not reliably slow either.
4. **The shipped `DEFAULT_MAX_CONCURRENT_TASKS` does not put that consequence out of reach,
   and this summary does not say it does.** The value is a configuration choice made in Plan
   13.1-01, not a quantity derived from any workload. Whether the refusal is reached on the
   production `submitJob` path is **unmeasured**: nothing in this repository reads a node's
   concurrent `exec` count under a demo workload. What would measure it is
   `node.executorPeakInFlight` — the reading this plan exposes — taken from a multi-tab demo
   run, which needs the browser e2e harness (WIRE-03, Phase 19). What would remove it is a
   re-pick on the production submit path (WIRE-04, Phase 20). It is **not** bounded by Plan
   13.1-02's per-peer send gate either: the gate bounds concurrent streams, not outstanding
   `exec` requests. `Transport.send` resolves at `stream.close()`, the receiving handler
   dispatches fire-and-forget, and `RpcEndpoint` subscribes with `void this.#receive(...)`, so
   a stream is released as soon as the request bytes land. Capture 1 is the demonstration: one
   requestor's 32 sends all resolved and 32 tasks were still running at once on the receiver.

### The p50 observation — and it is an observation

`node packages/node/src/bin/bench.ts --quick`, 2026-07-29, real transport:

| run | SHARDS | nodes=1 p50 | nodes=2 p50 | n |
|---|---|---|---|---|
| committed before-numbers (full run, pre-phase) | 8 | 10.3 ms | 15.4 ms | 19 |
| quick run A | 16 | 46.4 ms | 75.3 ms | 5 |
| quick run B (same machine, same session) | 8 | 25.2 ms | 41.1 ms | 5 |
| quick run C — the committed report | 16 | 27.5 ms | 40.7 ms | 5 |

**Whether the send gate cost throughput is unmeasured, and no regression threshold is being
tested.** Runs A and C are the *identical* configuration on the same machine minutes apart and
read 46.4 ms and 27.5 ms at nodes=1 — a spread wider than any difference anybody would want to
attribute to the gate. That alone settles it at n=5. On top of that: the committed
before-numbers came from a full run at n=19 on a different machine state; `SHARDS` changed
from 8 to 16 between them, so they are not measuring the same workload; and one p50 against
one p50 across different sample sizes has no error bar. Run B exists only to show that the
shard count moves the figure by a comparable amount to the run-to-run noise, and it is not a
control for the gate.

What would measure the gate's cost is a paired run of the same shard count with and without
the gate, at equal n, on one machine. That is a benchmark-methodology change and belongs to
Phase 23. Nothing was tuned to make any of these numbers look better, and none was omitted.

### Deviations, with reasons

- **Task 2's saturation is a direct reservation, not a slow module.** The plan offered a
  slow-enough module or an un-awaited dispatch. The test instead reserves a slot on the busy
  node's own `LocalCapacity` under `'held-by-this-test'` — a key no task's derived key can
  collide with, so the incoming request meets the over-committed branch and not the dedupe
  branch. Deterministic with no sleep, and every other part of the run is real: the refusal is
  composed by the node, crosses the real wire, is classified by `remoteDispatch`, and the
  re-pick is `runResilient`'s own. Stated in the test.
- **A fifth requirement was added to `bench-egress.node.test.ts`.** The plan observed that
  deleting the report line "still passes over the edited source, which is precisely the gap
  this requirement closes" — and then closed nothing. The requirement now covers all three
  halves (the constant, the two starts, the printed line) and the file's existing planting
  machinery proves it can report each one absent.
- **A third and fourth benchmark run were made that the plan did not ask for.** Runs B and C
  above. Run B is the 8-shard paired observation; run C re-ran the declared configuration so
  the committed report matches the source. `bin/bench.ts` was restored from a scratch copy by
  `cp` between them, `cmp` exit 0.
- **`.planning/BENCHMARK-RESULTS.md` and `.planning/bench/raw.json` were committed.** Task 3
  says not to `git add` them; its stated reason is a working tree shared with concurrent
  agents. None were running, and leaving them uncommitted would leave the plan's own
  done-criterion — that both declared values appear in the published report — unrecorded in the
  repository. They are exactly as run C produced them; nothing was hand-edited.
