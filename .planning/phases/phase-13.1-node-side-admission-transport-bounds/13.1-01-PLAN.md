## Execution order and shared-tree safety

This plan is **wave 1, and wave 1 contains only this plan.** Every wave in phase 13.1 is one
plan wide, on purpose: three of the five plans plant mutations into production source and
then run verification while the mutation is live. Two such plans running at once would each
read the other's planted edit as its own failure, and a repo-wide `npx tsc --noEmit` issued
by one would fail on the other's half-finished file. The waves are 01 → 02 → 03 → 05 → 04.

Task 3 plants mutations. It restores them by copying to and from the session scratch
directory and verifying with `cmp`. **No `git` command that writes may be run by any task in
this plan** — not `git checkout`, `git add`, `git commit`, `git stash`, `git reset`, or
`git branch`. Other agents hold uncommitted work in this one working tree, and
`git checkout -- <file>` restores from the index, which would discard this plan's own
uncommitted Task 1 and Task 2 edits along with the mutation.

<objective>
`serveAgent`'s `exec` branch runs `await executor.execute(request.task)` with nothing
counting what is in flight (`packages/net/src/agent.ts:224`). The roadmap's probe
**measured** the consequence: four peers each firing 200 concurrent `exec` requests, and an
instrument inside the node under test read 800 simultaneous `execute()` calls and zero
refusals. 800 is that probe's reading, not a model of anything — no other workload's peak
may be computed by imitating it. In production each of those calls is a
`WebAssembly.compile` plus `instantiate` plus a linear memory.

`LocalCapacity` (`packages/core/src/placement.ts:256-313`) is the mechanism that was
built for exactly this and never constructed outside two test files. 13.1-CONTEXT.md
decision 1 rules: **wire it, do not delete it** — 58 lines, a full spec, and
`ARCHITECTURE.md` §7.2 saying the same sentence the requirement does (*"an over-committed
node just says no, and the requestor resamples"*).

But wiring it *as the `offer` branch uses it today* is the wrong half, and getting that
wrong is 13.1-CONTEXT.md's Risk 4 — the single most likely way to break this phase.
`offer()` **reserves a slot** (`placement.ts:305`) and nothing on the wire ever releases
it, because an `exec` request carries no shard id to correlate with
(`protocol.ts:283-289`). Meanwhile `packages/browser/demo/main.ts:454` sends
`{kind:'offer', shardId:'probe'}` to every connected peer as a liveness check. Hand the
factories a real `LocalCapacity` without changing the offer branch and one demo tab
permanently occupies a slot named `probe` on every peer it can see — and every *later*
tab's probe is then refused with `probe is already in flight here`, which the demo would
read as "peer at capacity". A node that fills its own slot table from liveness probes and
then refuses all work.

So the decision has two halves and this plan lands both:

- the **`exec`** branch acquires and releases a slot around `executor.execute` — the
  branch that actually costs a compile, an instantiate and a linear memory;
- the **`offer`** branch answers from the same counters **without reserving**, through a
  new non-reserving twin `LocalCapacity.would`, so the refusal string exists in exactly
  one place and cannot drift.

Purpose: turn "the node is the only authority on whether it can take more work" from a
comment on `AgentOptions.capacity` into a decision the node actually makes on the branch
that consumes its CPU.
Output: `LocalCapacity.would`, `LocalCapacity.peakInFlight`, `DEFAULT_MAX_CONCURRENT_TASKS`
exported from `@o2/core`; an admitting `exec` branch and a non-reserving `offer` branch in
`serveAgent`; one portable spec that measures peak concurrency from inside the serving
node; and three planted mutations watched failing.
</objective>

How a `{kind:'error'}` reply lands at the two consumers, unchanged by this plan — this is
why a capacity refusal is sent as `error` and not as `exec ok:false`
(13.1-CONTEXT.md decision 4):

```ts
// packages/net/src/remote-executor.ts:51-52 — the production path
if (response.kind === 'error') return { ok: false, reason: `remote error from ${this.nodeId}: ${response.reason}` }

// packages/net/src/churn.ts:64-65 — the coordinator path

```

`{kind:'error'}` classifies as `node` — *"reachable, but refusing to serve this"* — which
is the retry policy a capacity refusal wants: the same task on another node succeeds. An
`exec ok:false` classifies as `task` and is capped at `DEFAULT_MAX_TASK_FAILURES = 3`,
which is the wrong policy for a condition that is not the task's fault. **Neither shape
needs a protocol change.**
