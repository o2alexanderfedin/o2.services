# Phase 23 · Plan 06 — The opt-in sovereign leg: AUTH-03's requestor half gets a caller

> **Numbers in this plan are configuration choices, not derived claims. Any quantity

> including in a source comment.**

> **Cite by grep-able symbol, never by line number.** Every reference below names a symbol a

> **Every proof named below states the mutation that reddens it.** A proof that cannot fail is

**Closes:** BENCH-07 criterion 5, and AUTH-03's requestor half. **Wave 4. Depends on Plans

<objective>
Phase 15 wired AUTH-03's *serving* end and verified it end to end. It left `delegate`,
`CapabilitySupplier` and `RemoteExecutor.execute`'s supplier branch as a production adapter with
**zero production callers**: all five production dispatch sites label their shards `'public'`,
and a public task has no owner, so there is no root key a chain could be rooted at. Owner ruling
2026-07-31 declined shipping that as *accepted unreachable* — naming a gap is not closing it —
and routed the fix here, because this phase already rewrites `bin/bench.ts`'s node construction
and that file is the most contended in the repository.

**The socket is already open.** `discoverCandidates`' options type is
`dispatch: ((nodeId: string) => CapabilitySupplier) | 'dispatches-unauthenticated'`, and
`bin/bench.ts` passes the sentinel today. The supplier half is one argument swap on an existing
call site. What genuinely remains is a `sovereignty` spread on each worker, one owner-labelled
shard, and the discipline that keeps all of it out of every default run.

Purpose: give `delegate` and `CapabilitySupplier` a traced call path from a runnable entry
point, without moving a single published figure.
Output: a `--sovereign` flag on `bin/bench.ts` that requires `--discover`; a per-node
`CapabilitySupplier` built from a chain the driver mints; `sovereignty` on each worker; one
owner-labelled shard; updated count pins with rewritten comments; and a four-second spawn spec
that reads the leg's own line off stdout.

**The identity chain, end to end.** Four call sites must agree on one hex key, and each reads it
from a different place. Getting any one of them wrong produces an `unplaceable` shard or a
refusal with nothing obviously wrong, which is why the whole chain is written out here.

1. `ownRecords` (`fabric-node.ts`) publishes
   `sovereignFor: canExecuteSovereign ? [certificate.userKey] : []`. Its docblock is explicit:
   *"**`sovereignFor` carries `certificate.userKey`, never `sovereignty.ownerId`** … Only
   `canExecuteSovereign` is read from `sovereignty`."*
2. `discoverCandidates` (`@o2/net`) builds each descriptor as
   `ownerId: executor.certificate.userKey` and
   `canExecuteSovereign: executor.capabilities.sovereignFor.includes(executor.certificate.userKey)`.
3. `eligibleNodes` (`core/src/sovereignty.ts`) filters
   `node.ownerId === request.ownerId && node.canExecuteSovereign` for a sovereign shard, and
   returns `[]` when a sovereign shard's `ownerId` is `undefined`.
4. `authorizeCapability` (`net/src/capability-authorizer.ts`) refuses in this order: a combine is
   admitted; a non-sovereign task is never asked for a chain; **a node with no pinned `ownerKey`
   refuses every sovereign task**; a task whose `ownerId` differs from `options.ownerId` refuses
   naming both; then `verifyChain` against `ownerKey`, `ownerId`, `audience` and
   `ability: 'execute'`. Separately, `guardSovereignty` requires
   `task.ownerId === node.ownerId && node.canExecuteSovereign`.

**So the shard's `ownerId` must be the hex public half of `BENCH_USER_SEED`**, and each worker's
`sovereignty.ownerId` must be that same string. `bin/agent.ts`'s `--owner-id` docblock records
what happens otherwise: *"a `PlacementRequest.ownerId` holding an operator label therefore
matched no discovery-derived descriptor, and a sovereign shard came back `unplaceable` **with
nothing anywhere obviously wrong**."*

**The relevant types**, by symbol:

```ts
// core/src/executor/sovereignty-guard.ts
interface NodeSovereignty {
  readonly ownerId: OwnerId
  readonly canExecuteSovereign: boolean
  readonly ownerKey?: PublicKeyHex
}

// core/src/job/submit.ts — a discriminated union, so ownerId is not optional on the sovereign arm
type ShardSpec =
  | { readonly value: CanonicalValue; readonly label: 'public' }
  | { readonly value: CanonicalValue; readonly label: 'sovereign'; readonly ownerId: OwnerId }
```

**`bin/bench.ts`'s existing `--discover` arm** is the structural precedent, and all eight of its
properties are copied here: opt-in via `process.argv.includes`; every new construction confined
behind the branch; conditional **spreads** rather than conditional fields (because
`exactOptionalPropertyTypes` makes an explicit `undefined` different from an absent key); a
printed line that says the arm ran; a throw rather than a silent zero; and a report line stating
the run is not comparable with a default one. Read the `DISCOVER` docblock in place — it is the
argument this plan needs, already written and already accepted.

**`capability-fixture.ts` is a SHAPE, never a dependency.** Its own header forbids the import:
*"This module is test-only … deliberately not re-exported from `packages/node/src/index.ts`, so
it exposes no capability that Phase 22's reachability guard could trace to an entry point. **A
barrel-exported fixture would hand that guard a real finding this phase invented.**"* Importing
it from `bin/` would manufacture the very finding criterion 5 exists to remove. Its
`chainSupplierFor` body is three lines and its `directChainFor` is one `delegate(...)` call;
copy the shape and say at the copy that it is a copy and why the import was refused.

**`discover-arm.node.test.ts` is the verification shape**, and its constraints are the ones that
make a spawn spec over this driver possible at all: `main()` writes under `process.cwd()`, so the
spawn must use a temporary cwd and assert that it is temporary; the arm's line is printed while
the first real rig is being built, so the spec kills the driver once the arm has spoken; and
*"**This is not a benchmark and must not become one** … It reads a count, which is
contention-independent, and never a duration."*

**The count pins this plan moves**, in `serve-agent-hooks.node.test.ts` over `bin/bench.ts`:
`'dispatches-unauthenticated'` at **3**, `new RemoteExecutor(` at **2**,
`await discoverCandidates(` at **1**. The file's own thesis is that each number records *"which
choice this call site wrote down"*, and it currently classifies the bench sites as a *"floor that
is also the ceiling"* because *"every one of these five dispatch sites submits `label: 'public'`
shards"*. **This plan falsifies that ground for one of them.**

**`coverage-agents.node.test.ts` already proves the leg is off by default, for free.** It spawns
`bin/bench.ts --quick` and asserts stdout contains no `covered: N/M owners`, no `PARTIAL` and no
`owner coverage (`. A sovereign shard makes `coverageReading` return a value, so if the leg ever
fired on a default or quick run, that spec goes red. It also pins `coverageReading(` at exactly
**2** and requires the literal `if (coverage === 'defines-no-owners') return null` — neither of
which this plan may disturb.

## Out of scope

- **A sovereign leg on `memoryFabric`.** Its nodes are raw `serveAgent` calls on
  `authorize: 'serves-unauthenticated'`, so a chain would be accepted without being verified and
  the leg would prove nothing there. The roadmap says so, and it is the reason the leg is on the
  real arm only.
- **A sovereign leg on the process fabric.** `processFabric` names the unauthenticated sentinel
  and pins no issuers. Extending it would need each spawned agent to be given `--owner-id`,
  `--owner-key` and `--can-execute-sovereign`, and a provider reachable from every child — a
  second enrolment topology for a criterion that is already closed by the discover arm. Named
  here so it is a scheduled absence rather than an oversight.
- **Publishing any figure taken under `--sovereign`.** The leg's run is not comparable with a
  default one and its report line says so. Plan 23-05 publishes a default full run.
- **Making the sovereign shard's data actually sovereign.** The shard carries an owner label and
  a chain; its *value* is the same fixture value every other shard carries. The egress and
  coverage machinery is what would make the data claim, and this criterion is about the dispatch
  path. Recorded rather than implied.
- **Removing the unauthenticated sentinel from the other four production dispatch sites.** They
  submit public work and the sentinel is the correct value there. AUTH-03's requirement is a
  traced call path, not the absence of public dispatch.
