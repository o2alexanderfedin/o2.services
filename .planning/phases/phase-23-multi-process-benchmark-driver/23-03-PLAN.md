# Phase 23 · Plan 03 — The saturating fixture and the process-per-node driver, wired into the published run

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Closes:** BENCH-07 criteria 1, 2 and 4 (criterion 3 is Plan 23-04; the run itself is Plan
23-05). **Wave 2. Depends on Plans 23-01 and 23-02.**

<objective>
Everything this phase needs now exists except the call sites. `@o2/bench` carries the
declared dimensions, the process-per-node report section and the integrity checker;
`@o2/node` carries a fabric that spawns N real agent processes and reports their identities.
None of it is wired, and a mechanism nobody calls from a production entry point is not
wired — this project keeps a list of exports in exactly that condition.

This plan makes `bin/bench.ts` the caller. Three things happen to it:

1. **A second fixture.** The current one is four `i32.store8`s and a shift. It cannot
   produce a speedup at any node count because there is nothing to parallelise, and the
   roadmap's own trap note says the published crossover measures the guest ABI rather than
   the fabric because of it. The replacement is not hand-assembled: this repository already
   ships a committed, integer-only, budget-bounded search kernel whose per-shard cost is a
   *declared input* rather than a property of the host. The trivial fixture stays, and the
   COST crossover and the single-threaded baseline stay defined against it.
2. **A third driver.** `processFabric` becomes a real runner with per-rung disposal, and the
   fixed-redundancy speedup sweep runs across it — with the identical sweep under the
   in-process driver as its control, because a single curve whose shape has to be
   interpreted is not a finding.
3. **A gate.** Today `main()` wraps `measure(...)` in a `try`/`catch` that converts *any*
   thrown error into an excluded row blamed on a libp2p limit. Under that shape a failed pid
   check would be published as an excluded rung with a curve around it — the exact opposite
   of criterion 1. `HarnessIntegrityError` propagates out of `main()` and the run produces
   no report at all. That propagation is a property of **every** catch block in the file,
   not of the raise site, so the gate is one function with one call site per rung and every
   catch re-throws it — held by a count assertion rather than by a presence pattern, because
   a presence pattern can only prove that one catch behaves.

Purpose: make "N nodes" mean N operating-system processes in the published run, and make a
run that did not achieve that fail loudly instead of reporting a curve.
Output: a driver that publishes three makespan tables, a process table, a two-driver speedup
comparison carrying an ideal bound derived from the run with the pre-registered expectation
printed beside it, a coordination ratio per rung, a link to the frozen earlier artifact with
the re-measurement stated, and an `unmet` list that is per-driver rather than universal.
</objective>

    **Name that array for what it measures, in a comment, because the obvious reading of it
    is wrong.** Each entry is a **dispatch-to-response** interval: `timed()` starts its clock

    is not the slowest shard's own duration. `sum(calls) / max(calls)` is therefore not

    that the quantity is the wrong one, not that it lands anywhere in particular, and a worked
    figure in a comment is a claim about runtime behaviour that nobody measured. The array is
    still published in `raw.json`, labelled as dispatch-to-response times, because it is what
    the node-seconds are made of — it is simply not the input to the ideal.

    **The four checks, per rung, before any figure from it is kept.**

    1. *Identity.* Build a `ProcessIdentity` from the rung's fabric — `expected` is
       `config.nodes`, `driverPid` is `process.pid`, `agents` maps the `AgentHandle`s,
       `executorNodeIds` comes off `fabric.executors`, `submitterPeerId` off the submitting
       node — and call `processIdentityViolations`.

       `shardComputeMs` as the rung's accumulated gross node-seconds × 1000. Document the
       proxy honestly in a comment: gross node-seconds is wall time inside each executor
       call, not CPU time, so on a genuine multi-process run it includes network wait, and the
       denominator is therefore not a CPU measurement. Say that much and stop — do not write
       into that comment what the ratio would come to under any arrangement. The share each
       rung reaches is measured, published beside the rung, and judged against the threshold
       `MAX_DRIVER_CPU_SHARE`, which Plan 23-01 declared before any of this data existed.
    3. *Fixture uniformity.* On the rung's first measured run, read every shard's output with
       `readPartial` and collect the status vector; call `fixtureUniformityViolations` with
       `expected: 'budget'` and `shards: SHARDS`. A vector that is not eight `budget` results
       means the fixture parameters are wrong for this host, and a ratio taken over
       non-uniform shards measures the search rather than the fabric.
    4. *Fixture provenance.* Call `fixtureProvenanceViolations({declared: config.fixture,
       moduleCid: fabric.moduleCid.toString(), expected: FIXTURE_CIDS})`. This is the reading

    **The gate is one call.** Concatenate the four lists and pass them to
    `assertIntegrity('<driver>, <nodes> nodes', [...identity, ...cpu, ...uniformity,
    ...provenance])`. One call site per rung, one consumer of every result. Do **not** write
    four `if (list.length > 0) throw` branches: a source-text guard matches identifiers, not
    data flow, so it cannot tell a called-and-read checker from a called-and-discarded one,
    and the property has to come from there being a single consumer whose deletion is one
    line. Put a comment at the call site saying why the error must not join the excluded rows
    — an excluded row says "this configuration could not be measured", and this says "what
    came back is not a measurement of the thing it claims", which belongs in a different
    place and at a different volume.

    **Every catch block in this file re-throws it.** `HarnessIntegrityError` propagating out
    of `main()` is not a property of the raise site; it is a property of every `catch` between
    the raise and the top. This file has one today (the real-transport sweep) and Plan 23-04
    adds more around the factorial attempts. So every catch block in `bin/bench.ts` opens
    with `if (cause instanceof HarnessIntegrityError) throw cause`, without exception, and
    Task 3's guard asserts the count of catch blocks equals the count of those re-throws. A
    plain `catch (cause)` anywhere in this file converts an integrity failure into an excluded
    row with a curve published around it — the exact failure 23-CONTEXT.md decision 6 exists
    to prevent, and the one a checker-was-called regex cannot see.

    **The control is instrumented too — checks 3 and 4 run on every saturating rung,
    whichever runner produced it.** Checks 1 and 2 are meaningful only where there are child
    processes and a driver whose CPU should stay low, so they run on the process-per-node
    sweep alone. Checks 3 and 4 run on both sweeps, because the in-process control is the
    entire basis of the published claim: if the control were quietly handed
    `MODULE_WRITES_PARTITION`, it would produce a fast, flat curve, the ratio against it would
    look like a large speedup, and `fixture: 'saturating'` would be printed beside it because
    that field is declared by the caller. Check 4 catches exactly that; check 3 catches a
    control that ran the right module on the wrong parameters. Do not run the CPU ceiling on
