# Phase 23 · Plan 04 — The excluded rung, measured instead of asserted

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

> **Cite by grep-able symbol, never by line number.** The 2026-07-29 version of this plan
> cited `bin/bench.ts` and `fabric-node.ts` by line throughout, and every one of those
> citations is now wrong. Every reference below names a symbol.

> **Every proof named below states the mutation that reddens it.** A proof that cannot fail
> is not a proof. This plan contains one measurement whose *expected* outcome is a failure —
> if that attempt succeeds, the block has no positive control and the plan says so in the
> published report rather than reporting a success.

**Closes:** BENCH-07 criterion 3, and the half of criterion 4 that says an excluded row is a
published figure too. **Wave 3. Depends on Plan 23-03.**

**This plan is a rewrite, and it is also smaller than its predecessor.** The 2026-07-29
version specified a seven-cell factorial at **two** rungs, 8 and 16, on the premise that both
were excluded. **The committed run of 2026-08-01 excludes exactly one row.** The 8-node
real-transport rung runs, at `n = 19` with `incomplete = 0`. Criterion 3's "two rungs" is one
rung today, and that changes what the factorial is for: the 8-node cell becomes a control
whose outcome is *known*, and the unknown is 16.

<objective>
Inside `main()`'s real-transport loop, a `catch (cause)` converts every error it catches into
an excluded row whose reason is a stored paragraph asserting that libp2p's per-host inbound cap
of five killed the handshake. The paragraph is attached without inspecting the error beyond
interpolating its message. **Criterion 3 cannot be satisfied by that shape at all**: it asks
for a measurement showing the cap is the cause, and the code asserts that cause for every
failure mode there is.

There is a second reason to distrust the stored paragraph. The coupling in `fabric-node.ts`
that derives a node's inbound threshold from its reservation limit landed *after* the harness
commit that produced the excluded rungs, so the published exclusion names a constant the code
does not necessarily run at. **The value a default node actually reports is unverified** —
reading the getters needs a live node, and the phase's context pass was read-only. So "the cap
is still the cause" is not the expected answer here; it is one of the possible answers, and
only a measurement can say which.

Three independent levers exist and only one of them is what BENCH-07 is about: raise the
option, stagger the joins, or change which side receives the dials. Adopting the spawn pattern
changes the dial direction *and* the process split at once. This plan separates them.

Purpose: make a published exclusion a record of an observation rather than a claim carried
forward, and find out whether the one remaining rung still fails at all.
Output: `describeExclusion` in `@o2/bench` with a production caller; an agent that can be given
an inbound limit and a dial target and that announces the limits it actually ended up with; a
`processFabric` that can be built in either dial direction with the cap pinned on whichever
node receives the dials; and a factorial at the disputed rung whose result is published in
whichever of the two honest forms the evidence supports — including the form that says the
block reproduced nothing and therefore measured nothing about the original cause.
</objective>

**The paragraph this plan deletes** lives in `main()`'s real-transport `catch (cause)` block in
`bin/bench.ts`. It reads `cause instanceof Error ? cause.message : String(cause)` into `detail`,
prints an `excluded:` line, and pushes a row whose `reason` interpolates `detail` into a fixed
sentence naming `INBOUND_CONNECTION_THRESHOLD = 5` as the cause. Only `detail` is read off the
error. **The cause is asserted for every failure mode there is.**

`Report.excluded` is `readonly { readonly config: string; readonly reason: string }[]`, rendered
as a two-column table by `renderMarkdown`. **The shape does not change; only where the `reason`
string comes from does.**

**How the limits are derived** — `fabric-node.ts`, by symbol. Read the derivation in place; it
combines `options.maxReservations ?? RELAY_MAX_RESERVATIONS`,
`options.maxIncomingPendingConnections ?? Math.max(LIBP2P_MAX_INCOMING_PENDING_CONNECTIONS,
limit)` and `options.inboundConnectionThreshold ?? Math.max(LIBP2P_INBOUND_CONNECTION_THRESHOLD,
limit)`. Both effective values are readable off a live node through
`get maxIncomingPendingConnections()` and `get inboundConnectionThreshold()`.

**Do not write either effective value into this plan, into a source comment, or into a test
assertion as a predicted constant.** The 2026-07-29 version asserted both at `15` against a
figure measured on 2026-07-28, and 23-CONTEXT.md records that reading as **unverified** because
it needs a live node. Task 2 *reads* them off a live node and Task 3 *publishes* what it read.
`inboundConnectionThreshold` is a **rate per second, per host**, which is why the constant's own
documentation records that staggering the joins fixed it while raising the reservation and
pending limits did not.

**`bin/agent.ts`'s flag block** is a single `parseArgs({ options: { … } })` with sixteen
entries. This plan adds two: `inbound-threshold` and `dial`. Its `USAGE` string is the
authoritative grammar and must be extended with them.

**`realFabric`'s dial loop**, by symbol: `for (const node of started) await
node.libp2p.dial(requestor.libp2p.getMultiaddrs())`, with the comment *"Everyone dials the
requestor, so blocks are reachable from every worker."* Under that direction the submitting node
is the one being dialled, by peers all on `127.0.0.1` — which is the population the per-host rate
limit governs. The spawn pattern dials the other way. `Libp2pTransport.send` reaches a peer with
`dialProtocol` and reuses the connection whichever side opened it, which is why flipping the
direction changes only which side receives the inbound connection and not how the RPC arrives.

**`realFabric` also carries a `--discover` arm**, which starts a provider and makes the rung
N+2 rather than N+1, and which the previous version of this plan did not know existed. Every
attempt below runs with `DISCOVER` false; state that in the recorded configuration rather than
leaving it implicit, because a reader comparing this block against a `--discover` run needs to
know the populations differ.

**The four guards over `bin/bench.ts`** are unchanged from Plan 23-03's interfaces block:
`bench-egress.node.test.ts`, `serve-agent-hooks.node.test.ts` (sixteen pinned counts, none of
which this plan moves), `discover-arm.node.test.ts` and `coverage-agents.node.test.ts` — whose
stdout heading equality means **no attempt in this block may print a line matching**
`/^ {2}(memory|real) transport, (\d+) node\(s\)…$/`, and whose 180 s `--quick` budget means the
factorial must not run on the quick path.
