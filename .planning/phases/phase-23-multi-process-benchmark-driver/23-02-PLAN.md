# Phase 23 · Plan 02 — The agent announces its pid, and the fabric that spawns N of them

**Closes:** BENCH-07 (criterion 1's mechanism — N operating-system processes, verifiable by
reading the child pids). **Wave 1. Depends on nothing.**

<objective>
`bin/bench.ts` builds every node in both published curves inside its own process.
`realFabric` calls `FabricNode.start(...)` in a loop, so N libp2p nodes share one V8 isolate
and one event loop, and `WasmExecutor.execute` is synchronous CPU work inside that loop —
which is why the published makespan column is flat across 1, 2, 4, 8, 16 and why the report
says so in its own opening section.

The remedy already exists in this repository, built for an unrelated reason. Three test
files spawn real `bin/agent.ts` child processes and drive a job across the boundary, and all
three share one `spawnAgent` shape. This plan turns that shape into a module the benchmark
driver can call, and adds the one field that makes criterion 1's check possible: `child.pid`
proves *a* process was spawned, not that the process which announced the address is that
process. One extra key on the handshake line closes it.

Deliberately **not** in `bin/bench.ts`. That file runs `main()` on import, so anything
living there can only ever be checked by reading its source text. A module can be spawned,
dialled and driven by a real job in a real test — which is the difference between "the
wiring is still written down" and "the wiring works".

Purpose: make "N nodes" mean N operating-system processes, and make that claim checkable.
Output: `pid` on the agent handshake; `packages/node/src/bench-fabric.ts` exporting the
`Fabric` seam, `spawnAgent`, `stopAgent` and `processFabric`; and a test that spawns two
real agents, runs a real job over them, and reads every identity the checker in Plan 23-01
will be given.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| driver process → agent process | The only boundary this phase adds. It is an OS process boundary, not a machine boundary: same CPU, same V8 build, same libc. Everything the fabric reports is a statement about processes and must never be read as one about machines |
| agent stdout → the parent's dial | The parent learns where to dial from a line the child printed. A child that printed someone else's address, or died and left its address behind, would be indistinguishable without the pid correspondence Task 1 adds |
| spawned children → the host | N agent processes, each holding a libp2p node, a heap and a temp directory. At the 16-node rung that is 17 node processes on an 8-core host |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-23-06 | Spoofing | The parent trusts an address announced on stdout without any evidence the announcing process is the one it spawned | mitigate | Task 1 adds `pid` to the handshake and Task 2 records it on `AgentHandle`; Plan 23-03 asserts `announcedPid === childPid` per agent through `processIdentityViolations` |

## Out of scope

- **Lifting the three existing `spawnAgent` copies onto this export.** There are four copies
  after this plan. Consolidating them is attractive and is explicitly deferred: the shared
  export would need a production caller to be reachable at all, the driver would be the only
  one, and that is the conversation Phase 22's reachability work owns. Named here so it is a
  scheduled duplication rather than an unnoticed one.
- **An agent-side inbound-limit flag, and a dial flag.** Neither is added here.
  `processFabric` takes an `agentArgs` passthrough, which is enough for a flag that only
  needs to reach the spawned agents. Plan 23-04 adds both flags and, with them, three options
  this plan's signature does not have — `inboundThreshold`, `submitterInboundThreshold` and
  `dial` — because attempts F and G there need many peers on one host dialling one node,
  which requires the agents to dial and requires the cap to be settable on the node that
  receives them. Expect that signature to grow in wave 3; do not try to anticipate it here,
  and do not build the outward dial in a way that makes the inverse ordering impossible —
  the submitting node's construction and the agent spawn are two steps, and 23-04 swaps
  their order for one of the two directions.
- **Exporting anything from `packages/node/src/index.ts`.** `bin/bench.ts` reaches
  `fabric-node.ts` by relative path today and reaches this module the same way. A barrel
  export whose only consumer is a sibling file inside the same package is an export nobody
  needs.
- **`bin/bench.ts` itself.** Plan 23-03 owns it. This plan deliberately does not edit it, so
  the two source-shape guards over it cannot be disturbed by wave-1 work.
