## Phase Goal

**As a** volunteer whose device can be lost, seized or imaged, **I want to** have every
long-lived secret this fabric writes to my device be unreadable without my passphrase,
**so that** losing the device does not also hand over the identity that speaks for me on
the fabric.

This plan's slice: **the way in.** A visitor arrives, is told what this is, chooses a
passphrase or enters the one they chose before, and their node is running.

<objective>
The page grows a way in. Not logged in: a screen that says what this is and invites you to
register or log in. Logged in: your node is already running.

Purpose: the owner ruled on 2026-09-04 that these are the two states a visitor may be in,
and that the credential is a **local passphrase** — no email, no account database, no
server, no third-party identity provider. This plan is that ruling, built.

Output: one pure state module with a spec; a `#signin` section on the demo page; a demo
whose `identityProtection` is a real passphrase for the first time; `DISCLOSURE_VERSION`
`'8'` with `policy.html` mirrored in the same commit; and one e2e file that reads the whole
journey off a real tab.
</objective>

## The ruling, and the two follow-up choices that came with it

The owner wrote, 2026-09-04:

> 1. when the user is not logged in, he/she should see a screen explaining what this is,
>    and an invite to login or register.
> 2. when the user is logged in, he/she should have the o2 p2p cloud node started
>    automatically.

and then answered two follow-ups:

- **"Log in / register" means a LOCAL PASSPHRASE.** *Register* = choose a passphrase, which
  creates and seals the identity in this browser. *Log in* = enter it, which unlocks. **No
  email, no account database, no server, no personal data held by the project.** Chosen over
  a Telegram login and over an email/password account system, each offered with its costs.
- **Auto-start after unlock, with a visible switch.** The node starts on unlock, the panel
  always shows it is running, and one click stops it. Chosen over *"consent is a step inside
  registration"*.

Both are decisions. This plan implements them and does not re-open them.

## Where the sign-in screen goes, and why it CANNOT go in front of the gate

The obvious arrangement — login screen first, consent inside registration — is the one the
owner rejected in the second follow-up, and it is also the one the tree refuses. Both
readings agree, and the second is measured:

`packages/node/src/artifact-fetch-gate.e2e.test.ts` is BROW-06's guard. Its arm A loads the
page, **waits for `#gate` to be un-hidden**, and only then asserts that the gateway server
was asked for nothing and that the refusal *names consent* rather than a node that has not
started. A login screen in front of `#gate` makes that wait time out, and the criterion it
carries is one of Phase 39's seven conditions of entry.

So: **`#gate` stays the first thing rendered, unchanged in position, id, controls and
semantics.** `#signin` is a new section, a sibling of `#gate` and `#main`, shown after the
gate is answered. The visitor's sequence is:

1. `#gate` — the disclosure. This is *"a screen explaining what this is"*: a headline and
   nine plain-language question/answer lines. It already existed and it already does that
   job.
2. `#signin` — *"an invite to login or register"*. Register (choose a passphrase) or log in
   (enter it).
3. `#main` — revealed on **unlock**, not on *"a node is running"*. The difference is
   load-bearing and it is measured: four e2e fixtures serve the page from a static host with
   **no relay** (`demo-regions.e2e.test.ts` waits for `#state`'s tone to become `'blocked'`
   for exactly that reason, and `artifact-fetch-gate.e2e.test.ts`'s `beforeAll` stands up a
   Vite server and a gateway and no relay at all). A node can never come up there. Gating
   `#main` on a *running* node would make those pages unreachable and `42-06`'s sweep
   impossible. So unlock reveals `#main`, auto-start is **attempted** immediately after, and
   a start that fails paints `#state` `'blocked'` exactly as it does today.

## There is no guest arm, and that is the plain reading rather than a gap

A *"continue without registering"* control would make the e2e sweep in `42-06` cheaper and
would keep the page usable for somebody who does not want to type twenty characters. It is
not planned, for two reasons.

The first is the ruling. It names two states, not three, and a third state that every
visitor would take is the ruling reversed while claiming to implement it.

The second is a guard that already exists and would refuse it. `consent.test.ts`'s case
*"discloses what the demo page actually does with a visitor's node key, in whichever
direction that is"* reads `demo/main.ts`'s **source** and requires **exactly one**
`identityProtection` arm to be present — `writes-no-new-secret` or `passphrase`, never both,
never neither, because it reads off that one value which of two disclosure sentences the
visitor is owed. A guest arm would put both arms in the file and the case would report a
page that had *"silently chosen a branch"*. So the no-fallback design is not a preference
here; it is what an existing guard permits.

**The consequence is named rather than buried, because it is the one product question this
ruling leaves open**: the workload surfaces are now behind registration, and twenty
characters between a Telegram link and the first thing a visitor came to see is a conversion
cliff for a cohort that is spendable exactly once. That is an owner question, not an agent's.
It does not block this plan; if the owner wants a look-around path, it is a cheap follow-up
against a surface that will by then exist. `42-06`'s summary carries it forward.

## Session-scoped unlock, and the alternative that a lost device defeats

The passphrase lives in a **module-scoped variable for this visit and nowhere else**. Never
`localStorage`, never `sessionStorage`, never IndexedDB, never a URL, never a log, never the
funnel's payload. Every fresh visit therefore shows the login field again, and *"started
automatically"* means **no further click after unlock in this visit** — never a silent start
on load.

The superseded plan already weighed and rejected the alternative, and the reasoning carries
over unchanged. A device-held wrapping key (a non-extractable WebCrypto key beside the
ciphertext, no prompt on return) genuinely defeats **a copy of the identity database** —
`exportKey` throws, and the database cannot be opened from another origin. **It does not
defeat an imaged device**, because the wrapping key lives in the same browser profile as the
ciphertext and unwraps whatever the image contains. The goal sentence is *"unreadable without
my passphrase, so that losing the device does not also hand over the identity"*, and a
mechanism a lost device hands over does not meet it. Whether a profile image actually yields
such a key is unmeasured; `42-05` task 2 measures it, and this plan does not anticipate the
answer.

## Registering is NOT enrolling, and a reader who conflates them will break a real property

Two words that both mean *"sign up"* in English name two unrelated acts here, so the plan
states the difference and the surface copy must keep it:

| | who is authenticated | to whom | with what | where the secret lives |
|---|---|---|---|---|
| **Log in / register** (this plan) | a **person** | their own browser | a passphrase they choose | in their head, and in page memory for one visit |
| **Enrolment** (`#enrol`, AUTH-01/02/04) | a **node** | a provider named in `bootstrap.json` | a key pair minted in the browser that the page cannot read | non-extractable in the browser; the private half never moves |

`packages/core/src/enrollment.ts:44-47` states the property that must not be undone: *"**The
private key never leaves the device.** `enrol` takes a public key and a self-signed proof of
possession; there is no code path here that accepts, transports, or stores a private key."*
And since 2026-08-16 the user's key need not leave the browser either — `requestEnrollment`'s
second parameter is a `UserSigner`, *"a capability to sign, not the material to sign with"*
(`:49-52`), the same mechanism `visitor-key.ts:134` already uses.

**Neither credential may reach the other.** The sign-in passphrase must never be passed to
anything under `packages/core/src/enrollment.ts`, and the enrolment key must never be
presented as a login. Enrolment stays exactly where it is, on the same control, as a separate
and optional act available to a signed-in visitor.

**What the surface copy may claim about the provider.** Use the unconditional form — *"the
provider never sees your private key"* — which is what `enrollment.ts` actually guarantees.
Do **not** write *"the provider stores nothing"*: it is true only of a provider run without a
directory. `fabric-node.ts:2503-2512` forks on `options.blockstoreDir` — undefined gives
`'remembers-only-within-this-process'` and nothing durable, otherwise `FsIssuance.open(...,
{ retainMs: DEFAULT_ISSUANCE_WINDOW_MS })`, which keeps issuance timestamps per user key on
disk for a window. A visitor cannot check which configuration they are talking to, so a claim
they cannot check must not be made.

## Why forgetting the passphrase cannot be recovered — by construction, not by policy

This is the sentence the start-over surface owes the visitor, and it can now be stated with a
reason rather than asserted. There is no server, no account database and no third party
holding anything of theirs. The one party that ever saw anything is the enrolment provider,
and what it saw was a **signature over the public half** — never the private key, never the
passphrase. So there is nothing anywhere to recover from, and there is no support channel to
go looking for. Starting over means becoming a different node, enrolling again, and
abandoning the certificate the old key holds.

The difference between that act and the defect criterion 4 forbids is **not the outcome** —
both end with a different node. It is **who decided, and whether they were told.**

## The twenty-character floor stays, and the reason is not inertia

`PASSPHRASE_MIN_LENGTH` is 20, from `42-02`, borrowed from `@libp2p/keychain`'s NIST
SP 800-132 floor (`node_modules/@libp2p/keychain/src/keychain.ts:100-102`). It applies to a
browser visitor, unchanged, and here is the weighing:

- The attacker this seal is against is **offline, holding a disk image**. Argon2id at
  `DEFAULT_KDF_PARAMS` costs ~436–501 ms per derivation on the hosts this project has
  measured, which prices a guess at roughly two per second per core. A twelve-character
  human-chosen password falls to that in days. Twenty characters is where the KDF's cost
  starts to matter.
- The two tiers must not disagree about what protects the same class of secret.
  `identity-protection.ts` exists precisely so that they cannot, and lowering the floor on
  one tier would make the shared vocabulary a lie about one of its two users.
- **The barrier is real and the answer is copy, not a weaker floor.** The field asks for a
  **passphrase** — four or five ordinary words — not a password. Four common words is
  typically 24–28 characters and is easier to remember than eight random ones. The surface
  says so, in those words, beside the field.
- Enforce it at the field with **`WeakPassphraseError`'s own message**, so two layers never
  tell the visitor two different things.

## Argon2id on the path between "enter passphrase" and "node running"

One derivation per visit, ~436–501 ms, and after `42-03` it is paid **once**: a warm start
holds the key that opens the envelope it just read, and `sealedUnderSameKey` gates on
parameter equality rather than catch-and-retry, so no second derivation happens.

What the visitor sees during it: both controls disable, and `#signin-status` says the wait is
the point — about half a second, deliberately, because it is what prices a guess for anyone
who ends up with this browser. Nothing here asserts an absolute duration. Any timing reading
in this phase is **comparative within one run** and reads the `[host conditions]` banner
first; three readings of the same parameters have spanned 34% across two hosts.

## The eight states, and why they are derived rather than flagged

The superseded plan had three states. The ruling produces eight, and a page that sets a flag
in eight places will get one of them wrong. So `packages/browser/src/signin.ts` is a **pure
function** from an input record to a state, with no DOM and no storage, and the page renders
whatever it returns.

| state | how it is reached | what the page shows |
|---|---|---|
| `awaiting-consent` | `readConsent` returns a gap | `#gate`. `#signin` and `#main` hidden |
| `declined` | the visitor pressed `#decline` | `#signin`, both controls **disabled**, a sentence saying reload to change your mind. `#main` hidden |
| `register` | consent granted, no sealed record, no legacy record | `#signin` in register mode: two passphrase fields, `#signin-register` |
| `adopt` | consent granted, no sealed record, a **legacy plaintext** record present | `#signin` in register mode **plus** the standing notice: this browser holds an identity in the clear; registering seals that same key in place, so you keep the node you already were |
| `login` | consent granted, a sealed record present, not unlocked | `#signin` in login mode: one field, `#signin-login` |
| `refused` | a passphrase was tried and did not open the envelope | `#signin` in login mode, the named refusal in `#signin-status`, and `#signin-startover` **revealed here and only here** |
| `unlocked` | register or login succeeded | `#main`. Auto-start attempted; if it fails — no relay, no network — `#state` says so and the visitor is still unlocked |
| `stale-consent` | a sealed record present **and** `readConsent` returns `terms-changed` or `anchor-changed` | `#gate` first. Same rendering as `awaiting-consent`, distinguished so the gate can say what changed |

`stale-consent` is not decoration. `DISCLOSURE_VERSION` moves to `'8'` in this plan, so
**every stored consent in existence goes stale on the first load after this lands**, and the
ordering property BROW-01 and BROW-06 both rest on is exactly the one that would be easiest
to lose here: the gate must come before the passphrase field, and nothing may start until
both are answered.
