<objective>
The node tier's half of the phase: an operator's identity seed and provider signing key
stop being files that a copied disk hands over, and start being envelopes that only their
passphrase opens — without the operator's node becoming a different node.

Purpose: criteria 1, 2, 3 and 4 on the node tier, measured across real operating-system
processes rather than in one.

Output: a sealed identity on disk, a passphrase flag on `bin/agent.ts`, a migration for the
directories that already exist, and a dump instrument with the positive control that makes
its absences readable.
</objective>

## Phase Goal

**As a** volunteer whose device can be lost, seized or imaged, **I want to** have every
long-lived secret this fabric writes to my device be unreadable without my passphrase,
**so that** losing the device does not also hand over the identity that speaks for me on
the fabric.

This plan's slice: an operator running `bin/agent.ts` on their own machine.

## `@libp2p/keychain` does not hold the node seed, and the reasons are structural

The ROADMAP records this as an open question for planning. It is settled here, by reading
both, with the reasons and the cost of the loser recorded.

**1. The bootstrap paradox, and this one alone is decisive.** The seed is resolved at
`packages/node/src/fabric-node.ts:1931`, converted at `:1932`, and handed to
`createLibp2p` as `privateKey: identity.privateKey` at `:2025`. The keychain is a libp2p
**service** — it is constructed *inside* the libp2p instance and reads and writes
`components.datastore` (`node_modules/@libp2p/keychain/src/keychain.ts:174`, `:241`). A
store that lives inside libp2p cannot hold the key libp2p needs in order to be constructed.
Ordering, not preference.

**2. Its KDF is PBKDF2, not Argon2id.** `Keychain`'s constructor derives its DEK with
`pbkdf2` from `@libp2p/crypto` (`keychain.ts:113-120`) under `DEK_INIT` —
`{ keyLength: 64, iterationCount: 10000, hash: 'sha2-512', salt: 'you should override this
value with a crypto secure random number' }` (`node_modules/@libp2p/keychain/src/constants.ts`).
PBKDF2 needs no memory, so it is nearly free on a GPU; design §3.9 asks for a memory-hard
KDF by name. Against an imaged disk, where the attacker has the ciphertext and unlimited
time, that difference is the whole claim. It also enforces NIST SP 800-132 minimums and a
20-character minimum passphrase (`keychain.ts:100-102`) — the length floor is worth
copying and is, below.

**3. Its unit of storage is a `PrivateKey` serialised to PEM, not 32 bytes.**
`importKey(name, key: PrivateKey)` calls `exportPrivateKey(key, dek, 'libp2p-key')` and
stores the PEM (`keychain.ts:202-207`). Holding a seed there would mean seed →
`PrivateKey` → PEM → `PrivateKey` → raw, and recovering the *seed* from the round trip
rather than the key. Two representations of one identity that must never disagree.

**What it would have cost to choose it anyway:** a second libp2p instance constructed only
to unlock the first, or a keychain wired to a datastore outside libp2p's lifecycle — and
either way a PBKDF2-protected secret described in Argon2id's language.

**The keychain stays where it is and nothing here removes it.** `fabric-node.ts:2155-2174`
constructs it because **AutoTLS refuses to start without it** — it holds the ACME account
key and the certificate key. No executor should read this verdict as licence to clean it
up.

<design>

## The protection vocabulary, shared by both tiers

`packages/libp2p/src/identity-protection.ts`:

```
export type IdentityProtection =
  | { readonly kind: 'passphrase'; readonly passphrase: string }
  | { readonly kind: 'writes-no-new-secret' }
```

Two arms, named for what they guarantee rather than for how they are implemented. The
second is not "off" — it is a promise: **this node will not write a new secret to this
device.** A node holding it persists nothing new, adopts a pre-existing plaintext identity
if one is already there (so an operator who upgrades keeps their PeerId), and mints a
per-process identity otherwise.

## The behaviour matrix, enumerated — every cell is a case in task 1's spec

| directory holds | protection | outcome |
|---|---|---|
| a sealed envelope | `passphrase`, correct | opens; same seed, same PeerId |
| a sealed envelope | `passphrase`, wrong | throws `SealedIdentityUnlockError`. **No mint branch is reachable.** |
| a sealed envelope | `writes-no-new-secret` | throws `SealedIdentityNeedsPassphraseError`. Never mints over an identity that exists. |
| a legacy plaintext `.identity.key` | `passphrase` | reads it, seals **the same bytes**, writes the envelope, verifies the envelope opens, **then** unlinks the plaintext. Same PeerId across the migration. |
| a legacy plaintext `.identity.key` | `writes-no-new-secret` | adopts it and returns `{ seed, unprotected: true }`. **Does not delete it** — deleting somebody's identity because they did not supply a passphrase is worse than the defect. Reported, not repaired. |
| neither | `passphrase` | mints, seals, writes the envelope |
| neither | `writes-no-new-secret` | mints, **persists nothing** |

The last row is the behaviour change that will redden existing specs, and task 3 handles
that deliberately rather than by surprise.

## Why the envelope is a new filename and not new content in the old one

`.identity.key.enc` and `.provider.key.enc`. Both dot-prefixed, because
`FsBlockstore.open`'s filter **is** the block counter — `entries.filter((name) =>
!name.startsWith('.'))` at `packages/node/src/fs-blockstore.ts:60`, and its own comment
says the predicate is not a safety net. A `.enc` suffix on a dotted name still starts with
a dot, so neither file is counted among the blocks; `node-identity.node.test.ts:147`
already asserts that property for the plaintext file and gains a case for the envelope.

A distinct name makes *"is the plaintext gone?"* a direct `existsSync` question rather than
an inference about a file's contents, which is what criterion 1's instrument needs.

## The provider key is in scope, and the ROADMAP's parenthetical about it is stale

Criterion 1 reads *"(the provider key where the tier stores one; the node tier persists only
the seed)"*. That parenthetical is wrong against the tree:
`packages/node/src/fabric-node.ts:2438` calls `loadOrCreateSeed(options.blockstoreDir,
PROVIDER_FILE)`, so a node started with `--issues-certificates` writes a **second** raw
32-byte secret to the same directory. `AUTH-06`'s own text — *"the identity seed, and the
provider key where a tier stores one"* — covers it, and it is the higher-value of the two:
a provider signing key is the trust root every certificate it ever issued verifies against.
Sealed here. `42-05` records the ROADMAP correction.

## The certificate is deliberately not sealed

`.certificate.json` stays exactly as it is — plain JSON, no `mode` restriction, and
`identity-store.ts:102-106` already states why the asymmetry with the seed's `0o600` is a
decision rather than an oversight. It is public material: transmitted on the wire, published
into DHT records, and verified offline against pinned provider keys by
`packages/core/src/enrollment.ts`'s `verifyCertificate`. Encrypting the local copy would
break that verification while protecting nothing. What a stored certificate leaks is the
*fact of membership* — a different problem, and not this phase's.
