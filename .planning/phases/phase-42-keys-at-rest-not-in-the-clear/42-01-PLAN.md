## Phase Goal

**As a** volunteer whose device can be lost, seized or imaged, **I want to** have every
long-lived secret this fabric writes to my device be unreadable without my passphrase,
**so that** losing the device does not also hand over the identity that speaks for me on
the fabric.

This plan's slice of that goal: a passphrase can seal 32 bytes and open them again, on
every runtime this project ships to, and the envelope survives a future change to the
default cost.

## This repository has written Argon2id before, and it was deleted. Do not re-derive it.

`packages/core/src/cert-lifecycle.ts` carried a complete, tested Argon2id implementation
until commit **`0c49c42`** (2026-08-24) removed it by owner ruling. Recover and read it:

```
git show 0c49c42^:packages/core/src/cert-lifecycle.ts
```

**Do not restore that module.** It served a different construction — its `Certificate` is
a different type from `NodeCertificate`, and the deletion was deliberate. What must be
reused is the set of decisions it already made and documented, cited by commit so a reader
sees the basis rather than taking this plan's word:

- **`ARGON2_PARAMS = { t: 2, m: 19_456, p: 1, dkLen: 32 }` — sited, not picked.** Basis
  recorded in its docblock: the OWASP Password Storage Cheat Sheet's Argon2id **first
  recommended option**; the memory-constrained second option (`m=12288`/`t=3`) was named
  and rejected because *"this fabric's node processes are not memory-constrained the way
  the cheat sheet's second option targets."*
- **The KDF runs on both arms unconditionally, and that is not a preference.** Verbatim
  from `0c49c42^`: *"`crypto.subtle` has no Argon2id, only PBKDF2/HKDF. If the KDF varied
  by arm, the same passphrase would derive a DIFFERENT identity depending on which engine
  ran it, destroying the exact property `deriveFromPassphrase` exists for."*
- **The AEAD runs on both arms unconditionally, for the same reason** — a value sealed on
  one tier must open on any other, and *"because there is only ever one AEAD, there is no
  cross-arm ciphertext to mismatch, by construction — not by a check that could be
  forgotten."*

## Why Argon2id (noble) for the KDF and xchacha20poly1305 (noble) for the AEAD

The alternative considered and refuted was a **mixed** shape: Argon2id from noble deriving
32 bytes, imported into `crypto.subtle` as an AES-GCM key, with `subtle` doing the
encryption. It is attractive — no new dependency, hardware-accelerated, standardised — and
it was measured working before it was refused. Both readings below were taken in this
session on this host, Node v23.11.0, and are recorded so the refutation is against numbers
rather than taste.

**Measured, the mixed shape, one run:**

```
argon2idAsync t=2 m=19456 p=1 dkLen=32        ->  436 ms
subtle.importKey('raw', dk, {name:'AES-GCM'}) ->  accepts 32 raw bytes, extractable:false
subtle.encrypt AES-GCM over a 32-byte seed    ->  48 bytes (32 + 16-byte tag)
round-trip                                     ->  equal
wrong passphrase                               ->  DOMException "The operation failed for an
                                                   operation-specific reason"
tampered header used as additionalData         ->  the identical DOMException
```

**Measured, the chosen shape, one run:**

```
xchacha20poly1305(key, nonce, aad).encrypt(seed)  ->  SYNCHRONOUS, 48 bytes (32 + 16 tag)
round-trip                                         ->  equal
wrong key                                          ->  Error("invalid tag")
tampered aad                                       ->  Error("invalid tag")
12-byte nonce                                      ->  '"nonce" expected Uint8Array of length 24'
```

**The KDF half cannot move to `crypto.subtle` at all.** Argon2id, Argon2i, Argon2d, scrypt
and bcrypt are all `"Unrecognized algorithm name"` there; only PBKDF2 and HKDF exist.
PBKDF2 is not a substitute for this threat, and the reason is not speed — it needs no
memory, so it is nearly free on a GPU, while Argon2id at these parameters costs 19 MiB per
attempt. Against an **imaged disk**, where the attacker holds the ciphertext and has
unlimited time, that is roughly two orders of magnitude of parallel capacity and it is the
difference between days and years.

**The AEAD half does not move either, and the deciding reason is one a Node-only probe
cannot see.** `IdbIdentityStore.loadOrMintSeed` (`packages/browser/src/idb-identity-store.ts:122-129`)
states a hard constraint in its own doc: *"`mint` **must be synchronous.** Awaiting
anything that is not part of an IndexedDB transaction lets that transaction commit."* That
constraint is not decorative — it is the fix for a measured cross-tab race where four tabs
of one profile minted four identities and three of them came back as somebody else
(`cold-start-seed-race.e2e.test.ts`). Sealing has to happen **inside** that transaction,
beside the `put`. `subtle.importKey` and `subtle.encrypt` are both `Promise`-returning and
would commit the transaction out from under the write; `xchacha20poly1305(...).encrypt` is
synchronous, measured above. Argon2id is async and slow either way, which is fine because
the key is derived **once, before** the transaction opens, and only the seal happens inside
it.

Secondary, and recorded because it will be asked: `crypto.subtle` is `undefined` on
non-secure origins — this repository measured that and built
`packages/browser/src/subtle-digest-fallback.ts` around it. That does not decide the
question here, because the browser tier only reaches the sealing path after an enrolment
that already requires `crypto.subtle`; it is a reason the noble path is the more robust of
two acceptable ones, not the reason it won.

**`@libp2p/keychain` is not the answer either, and the reasons are structural.** See
`42-02-PLAN.md`'s `<keychain_verdict>` block, which is where the node seed actually lives.

</mechanism_decision>
