<design>

## The one constraint that shapes everything here

`loadOrMintSeed`'s doc (`idb-identity-store.ts:122-129`) states it and it is not
negotiable: **`mint` must be synchronous.** Awaiting anything outside an IndexedDB
transaction lets that transaction commit, and the `put` then lands in a second transaction
with the check no longer covering it — the same cross-tab race, one level further in and
harder to see. That race is measured, not hypothetical: four tabs of one profile opening one
cold origin minted four identities and three came back as somebody else, which is what
`cold-start-seed-race.e2e.test.ts` reads.

Argon2id is async and takes hundreds of milliseconds. So the work is split, and the split
is the whole design:

1. **Outside any transaction:** read-or-create the salt, then `deriveSealKey` (async).
2. **Inside one `readwrite` transaction:** read the sealed record; if absent, `mint()` and
   `sealWithKey(...)` — both synchronous — and `put`. Nothing is awaited that is not part of
   the transaction.
3. **Outside again:** `openSecret` on whatever envelope came back.

## A salt record, and what it does to criterion 1's claim

Argon2id needs a salt, the salt must be the same on every start or the key is different
every time, and the envelope cannot supply it before the envelope has been read. So the
store gains one more record: `SALT_KEY = 'kdf-salt'`, 16 bytes from
`crypto.getRandomValues`, created in its own small `readwrite` transaction so two cold tabs
cannot end up with two salts.

**This changes what the phase can honestly claim, so it is written here rather than
discovered by a reader of the dump.** The claim is *"the store holds no secret at rest"*,
not *"the store holds nothing"*. A salt is not a secret — it exists to stop one precomputed
table covering many users, and it is useless to an attacker without the passphrase.
Criterion 1 forbids seed bytes and provider-key bytes, and a salt is neither. The dump
instrument asserts the salt record is exactly `SALT_BYTES` long **and** that it is not a
prefix, suffix or subsequence of either secret — an assertion that would catch the one way
this could go wrong.

The same salt is written into the envelope's own `salt` field, so the envelope stays
self-describing and criterion 5 is untouched.

## The behaviour matrix

| store holds | protection | outcome |
|---|---|---|
| a sealed record | `passphrase`, correct | opens; same seed, same PeerId |
| a sealed record | `passphrase`, wrong | throws `SealedIdentityUnlockError`. **No mint branch is reachable.** |
| a sealed record | `writes-no-new-secret` | throws `SealedIdentityNeedsPassphraseError` |
| a legacy raw `node-seed` | `passphrase` | in **one** transaction: read raw → seal → put sealed → delete raw. Same PeerId. |
| a legacy raw `node-seed` | `writes-no-new-secret` | adopts it, reports `unprotected: true`, **does not delete it** |
| neither | `passphrase` | mint + seal + put, one transaction |
| neither | `writes-no-new-secret` | mint, persist nothing |

The migration is one transaction for the same reason the mint is: a tab that crashed between
the `put` and the `delete` would hold both a sealed and a plaintext copy, and criterion 1
would fail on a store nobody had touched since.

## `identityProtection` is required on `BrowserNodeOptions`, with no default

The `whenSeedIsGone` precedent, in that field's own words: the factory refuses to make this
decision for its caller. A default here would be a default about where a secret lives, which
is exactly the class of decision that must be written down by somebody.

The cost is bounded and was counted before it was chosen: `whenSeedIsGone:` appears at 22
call sites across 12 files (`grep -rc "whenSeedIsGone:"`), and every one of them is a place
`identityProtection:` goes too. That is affordable; the node tier's 169 `blockstoreDir:`
sites were not, which is why `42-02` made the node-tier option optional and this one
required. The asymmetry is measured, not stylistic.

**`writes-no-new-secret` together with `whenSeedIsGone: 'refuses-to-start-without-its-seed'`
is a contradiction** — a node that will not write a secret and will not start without a
stored one can never start at all — and is refused at `start` with a named error rather
than left to produce a confusing absence.

## The provider seed, and the certificate

`loadOrMintProviderSeed` gets the identical treatment under the identical passphrase. Its
own doc already says why it was fixed in the same pass as the seed: *"the other one has the
same shape"* is how a closed defect comes back.

`saveCertificate`/`loadCertificate` are untouched. The certificate is public material,
verified offline against pinned provider keys, and sealing the local copy would break that
while protecting nothing.

## Out of scope by mechanism, not by omission

The visitor's owner key at `packages/browser/src/visitor-key.ts:134` is generated
**non-extractable**. `exportKey` fails on it; there is nothing at rest to encrypt. It is
excluded because the mechanism already excludes it, and this plan says so rather than
silently skipping it.
