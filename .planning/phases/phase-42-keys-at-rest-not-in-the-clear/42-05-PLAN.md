    **A. Record the three-shape weighing.** Add a paragraph to `AUTH-06`'s ledger row in
    `.planning/REQUIREMENTS.md` — dated, in this repository's style of retiring a claim by
    dating it rather than deleting it — stating which shape was taken on each tier and what
    the losers would have bought. The three:

    - **(a) Encrypt a stored random seed** — Argon2id derives a key from the passphrase; the
      randomly generated seed is sealed under it. **Taken, on both tiers.**
    - **(b) A non-extractable WebCrypto wrapping key, no passphrase** — defeats a copy of
      the identity database; does **not** defeat an imaged device, because the wrapping key
      is in the same profile as the ciphertext. Rejected against the goal sentence
      (*"unreadable without my passphrase, so that losing the device does not also hand over
      the identity"*), and **not described in criterion 1's language anywhere in this
      phase**. What it would have bought: no prompt at all, and therefore no conversion cost
      on the browser tier. Task 2 measures the question its rejection turns on.
    - **(c) Derive the seed from the passphrase and store no seed at all** — measured
      viable: Argon2id's 32-byte output is a valid Ed25519 private key with no range check
      (`ed25519.getPublicKey` accepts all-zero and all-`0xff`), and `identityFromSeed`
      already turns 32 bytes into a full identity, pinned at `identity.test.ts:40-64`.
      Rejected, for three reasons, each of which must appear:
      1. **Criterion 4 has nothing to fail against.** A wrong passphrase under (c) derives a
         different *valid* seed and a different *valid* PeerId — the silent re-mint is not a
         bug to be prevented but the default behaviour, and preventing it needs a separately
         stored public-key verifier that can drift from the thing it verifies. Under (a) the
         AEAD tag carries the refusal for free and there is one failure mode, not two
         mechanisms that must agree.
      2. **There is no rotation.** New passphrase → new seed → new PeerId → the certificate
         issued against the old key is orphaned. "Change my password" and "become a
         different node" are the same operation. The only rotation story is to store a
         random seed wrapped under the derived key — which is shape (a) with one extra
         indirection, so (a) is the honest name for it.
      3. **The identity's entropy becomes the passphrase's entropy, and becomes reproducible
         from it anywhere.** Under (a) an attacker needs the passphrase **and** the disk;
         under (c) the passphrase alone reconstructs the node from any machine on earth. This
         phase's threat is the imaged disk, which (c) also covers — but (c) opens a remote
         path that (a) does not have, and it does so in exchange for properties this fabric
         does not need.
      **What (c) would have bought, and it is not nothing:** criterion 1 satisfied by
      *absence* rather than by ciphertext — no seed bytes to hold, which is a strictly
      stronger reading — and recovery of an identity from the passphrase alone after an
      IndexedDB eviction, which is a real answer to `whenSeedIsGone` that shape (a) does not
      have. Record both as a candidate future requirement rather than as a discarded idea.

    Also record **how §3.9's "two keys, two jobs" split lands on `AUTH-06`'s three
    artefacts**, because the design's answer and this phase's answer are not the same and the
    difference must be visible:

    - §3.9 puts the **node identity key** on the *hardware-gated, passphrase-free* side
      (*"Gated by hardware, not live passphrase entry"*) and the **user key** on the
      *passphrase + non-extractable hardware key* side.
    - All three of `AUTH-06`'s artefacts — node seed, provider key, certificate — are on the
      **node-identity** side of that split. None is §3.9's user key. §3.9's user key is
      already implemented, correctly, as `visitor-key.ts:134`'s non-extractable pair, which
      `AUTH-06` excludes for exactly that reason.
    - **§3.9's node-identity mechanism has no implementation on either of `AUTH-06`'s
      tiers.** libp2p needs the raw ed25519 bytes for the Noise handshake, so the seed cannot
      live behind a non-extractable handle anywhere; and a TypeScript agent running in a tab
      has no OS keystore to be gated by. So `AUTH-06` is **not** §3.9's user key and **not**
      a departure from §3.9's node key — it is a **substitute for §3.9's hardware gate on
      tiers that have no hardware gate**, and §3.9's memory-hard-KDF instruction carries over
      to it unchanged. Write it in those words.
    - Record §3.9's own limit against this phase, verbatim: *"Derivation moves the risk from

  <files>.planning/consults/2026-09-04-non-extractable-keys-and-a-disk-image.md</files>

  <action>
    **The question, stated so it can fail:** does a WebCrypto key created with
    `extractable: false` and stored in IndexedDB leave its raw key material recoverable in a
    browser profile on disk?

    What is already certain and must not be re-measured: `exportKey` throws on such a key,
    and the database cannot be opened from another origin. Those defeat **script-level
    extraction** and **a copy to a different origin**. What is **not** certain, and is the
    whole question, is whether a **full image of the profile directory** yields the bytes.

    **The method, and it is chosen because it makes the search possible at all.** Do not
    generate the key — you would not know what to look for. Instead
    `crypto.subtle.importKey('raw', KNOWN_BYTES, { name: 'HMAC', hash: 'SHA-256' }, false,
    ['sign'])` with a 32-byte `KNOWN_BYTES` you chose, store the resulting `CryptoKey` in
    IndexedDB, and confirm in the page that `exportKey` throws on it. Then close the browser
    cleanly and search the profile directory for `KNOWN_BYTES` as a **byte subsequence**,
    across every file, including LevelDB `.ldb`/`.log` files and any blob subdirectory.

    Drive it with Playwright and a **persistent context** (`launchPersistentContext`) so
    there is a real profile directory on disk to search; a default `browser.newContext()` is
    ephemeral and has no profile, which would make every absence an absence in a directory
    nothing was written to.

    **The positive control is not optional and it is the point.** In the same run, also
    `put` a second record holding `KNOWN_BYTES` as a plain `Uint8Array`. If the search cannot
    find *that*, the search is blind and its verdict on the key is worthless — which is
    precisely the failure `funnel-collector.e2e.test.ts` recorded when it rendered a
    `Uint8Array` as `255,15,66,...` and watched a plant stay green. Run the control first and
    record its result before the key result.

    Run it on **chromium** at minimum. Firefox and WebKit are worth having and their profile
    layouts differ; if either cannot be driven persistently here, **record that as an
    unmeasured arm with the blocker named** rather than generalising from chromium.

    **Write the consult so it says what does and does not follow.** If the bytes are found:
    a non-extractable key does not survive a disk image on that engine, shape (b) is
    disqualified for this threat by measurement rather than by argument, and any future
    "two-factor" claim over a device factor of that kind would be the stronger mechanism's
    language over the weaker mechanism. If the bytes are **not** found: that is *"not found
    by this search on this engine on this platform"* — it is not proof of hardware backing,
    and the consult must say so, name the search's limits (it does not decrypt an
    OS-keychain-wrapped profile, and it does not cover iOS or Android, where a hardware
    keystore plausibly changes the answer), and leave the question open for those.

    **This measurement changes no code in this phase.** Shape (a) is taken on both tiers
    either way. What it settles is whether §3.9's second factor can ever be claimed honestly
    on the browser tier, which is a question the next phase to touch this will need answered.
  </action>

    `BENCH-08` depends on start accumulating sooner. There is also a real second-order cost

    landing *before* a public run means the run measures the new flow with no baseline for
    the old one — whereas landing it after gives a before-and-after on the same cohort.

    **What gating costs.** Phase 39 waits for four plans. On the readings in `42-01` through
    `42-04` that is not a large amount of work, but it is work that has not been done yet and
    whose blast radius on the node tier (`42-02` task 3's sweep) is measured only by running
    the lane.

    exists rather than because it is recommended.** Ship `42-02` and `42-03` — the mechanism

    no persisted identity and re-enrols on each visit, which burns issuance quota under the

    judge, and the quota arithmetic has not been done here.
