<objective>
Measure and guard the X.509 decoder's contribution to the browser bundle — the second
of the two numbers the owner ruling says "this phase owes, not a caveat it may
inherit" (the first, off-the-execution-path, RESEARCH.md §6 already proved against the
current tree and needs no new test).

RESEARCH.md §5 proposed measuring `packages/browser/dist/assets/index-*.js` before and
after the decoder lands, diffed across two builds of the real demo app. This plan
diverges from that literal proposal, deliberately: the demo entry
(`packages/browser/demo/main.ts`) has no reason to import the decoder in this phase (no
certificate is ever issued or verified as X.509 yet — that wiring is explicitly out of
scope, see `25-02-PLAN.md`'s objective), and a bundler's tree-shaking would eliminate
an unused import from the real chunk, making a before/after diff against the live demo
either misleading (a false near-zero delta the moment nothing calls the decoder) or
dependent on inventing an unrelated UI code path purely to defeat tree-shaking. A
purpose-built, minimal Vite library-mode build that genuinely imports and exports a
function calling `decodeX509Certificate` measures the same real quantity — what this
decoder costs a page that actually uses it, under the same bundler and the same browser
target this project ships — without either failure mode, and without touching the
shipped demo's behavior at all.

Purpose: close the second of the two numbers the ruling names, honestly.
Output: `packages/node/src/x509-bundle.e2e.test.ts`, a real measurement, and a sited
`DECODER_BUDGET_BYTES` constant.
</objective>
