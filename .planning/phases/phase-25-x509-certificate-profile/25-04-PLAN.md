<objective>
Build the Ed25519 verification backend the owner ruling of 2026-08-09 requires
(`crypto.subtle` first, libsodium/WASM as the fallback, taken against the standing
`subtle → noble` recommendation and recorded in `25-CONTEXT.md` because it was
overruled) — but scoped to exactly what the ruling's own text obliges as work versus
what it obliges as a **priced analysis**.

The ruling names four things. Two are load-bearing implementation obligations, built
here: (1) a lazy `import()` behind the `globalThis.crypto?.subtle` capability check, so
no secure-context tier ever fetches libsodium's 314.9 KB gzip; (2) a
differential-conformance guard proving every backend enabled on this host returns the
identical verdict over one shared vector set, weighted toward rejections, since
disagreement on a malformed input is the actual hazard a second implementation in a
trust path introduces. The other two are explicitly a **planning-time deliverable** in
the ruling's own words — item 3: *"Price this in planning. Count the call sites and say
the number. If it is large enough to change the shape of the work, say that too"* — and
item 4: re-measure before quoting anything as settled. This plan's third task delivers
both as a cited, measured finding, and **does not** modify `capability.ts` or
`enrollment.ts` — wiring `verifyChain`/`verifyCertificate` onto this backend is
deliberately not planned as work here, for a reason this plan's own research names
precisely rather than asserts.

Purpose: ship a complete, tested, production-ready verification backend that a future
phase can adopt, without pretending its adoption cost is smaller than it measurably is.
Output: `packages/core/src/ed25519-backend.ts`, its test file, and a cited pricing
finding.
</objective>
