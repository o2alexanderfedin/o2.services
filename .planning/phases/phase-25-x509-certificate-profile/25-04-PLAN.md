<objective>
Build the Ed25519 verification **port and adapters** the second owner ruling of
2026-08-09 requires ("ideally, we should use an adapter pattern"), which supersedes
this plan's prior shape ("ship unwired, price the migration as future work").

**The port is a synchronous `verify` behind an asynchronous one-time `init`:**
`{ init(): Promise<void>; verify(sig, msg, pubkey): boolean }`. Measured on this host
(Node v25.9.0): `@noble/curves` and libsodium (after one `await sodium.ready`) both
return a plain `boolean` from `verify` — `instanceof Promise` is `false` for both.
`crypto.subtle` returns an object where it is `true`. A Promise cannot be awaited
synchronously in JavaScript, so **`crypto.subtle` cannot implement this port** — no
portable trick changes that (`Atomics.wait` needs cross-origin isolation, which GitHub
Pages cannot supply — the same constraint that already rules out WASM threads for this
project). The synchronous port therefore has exactly two conforming implementations,
noble and libsodium, and `verifyChain`/`PeerVerifier.verifiedPeers` can call either
**without becoming async** — dissolving the structural obstacle this plan's own prior
research measured, rather than paying to work around it.

This *scopes* the first owner ruling (`subtle` first, libsodium fallback) rather than
reversing it: `crypto.subtle` still wins wherever a call site is already inside an
`async` function, through a **separate** asynchronous port this plan also builds. What
`crypto.subtle` cannot do is win on the synchronous trust path — that arm runs on
noble (secure-context hosts, zero marginal cost, libsodium never fetched) or libsodium
(insecure-context hosts, ~15x faster than noble per verify, and already paid for by the
async port's own fallback need on that arm — the sync port does not trigger a second,
independent fetch).

The ruling names four things this plan must still carry, unchanged: (1) the lazy
`import()` behind the capability check, so libsodium is reachable only on the arm that
needs it, for both ports; (2) the differential-conformance guard, reject-weighted, now
extended to cover the sync/async port boundary itself, since two backends can be live
in the same process at once; (3) — **settled** by the second ruling: the adapter
dissolves the async-migration cost rather than paying it, and this plan's Task 3 keeps
the 10-call-site pricing (corrected this revision from a miscounted 9) and the
`PeerVerifier.verifiedPeers` finding as the cited record of *why* the adapter was
chosen, not as live scope; (4) re-measure before quoting anything as settled.

**What this plan does NOT do:** wire `verifyChain` (`capability.ts`) or
`verifyCertificate` (`enrollment.ts`) onto the new port. The adapter makes that wiring
*possible* without an async migration, but actually doing it needs a decision this
plan's own obligations do not cover — where each of three runtime entry points
(`packages/net`, `packages/node`, `packages/browser`) calls `initEd25519()` before
first use, and what a verification arriving before that resolves should do. Deciding
that inside a single-plan revision would be replanning the phase, which this revision
is explicitly told not to do. Task 3 states this decision plainly, by name, rather than
leaving it implicit.

Purpose: ship a complete, tested, production-ready verification port that a future
phase can wire in with a bootstrap-ordering decision, not a redesign.
Output: `packages/core/src/ed25519-backend.ts`, its test file, and cited pricing +
wiring-decision findings.
</objective>

```typescript
// packages/core/src/ed25519-backend.ts

export type Ed25519Backend = 'noble' | 'libsodium'

/** The synchronous port. verifyChain and PeerVerifier.verifiedPeers can call this
 * without becoming async — that is the entire reason the adapter was chosen. */
export interface Ed25519SyncVerifier {
  readonly backend: Ed25519Backend
  verify(signature: Uint8Array, message: Uint8Array, publicKey: Uint8Array): boolean
}

/** The asynchronous port, for call sites already inside an `async` function.
 * `crypto.subtle` when available; the same lazily-loaded libsodium instance the sync
 * port uses otherwise (never a second, independent import). */
export interface Ed25519AsyncVerifier {
  verify(signature: Uint8Array, message: Uint8Array, publicKey: Uint8Array): Promise<boolean>
}

/** Synchronous factory. No import, never throws, always available. */
export function createNobleSyncVerifier(): Ed25519SyncVerifier

/** Performs the lazy `import('libsodium-wrappers')` and `await sodium.ready`. The
 * only asynchronous step either adapter has — after this resolves, `.verify()` is an
 * ordinary synchronous call. */
export function createLibsodiumSyncVerifier(): Promise<Ed25519SyncVerifier>

/** `undefined` if this host's `crypto.subtle` cannot verify Ed25519 (absent entirely,
 * or present but algorithm-incapable — both read the same way to a caller). */
export function createSubtleAsyncVerifier(): Ed25519AsyncVerifier | undefined

/**
 * One capability check, run at most once, memoised. Decides both ports from the same
 * decision: `crypto.subtle` Ed25519-capable -> sync port = noble, async port = subtle,
 * libsodium never imported. Not capable -> sync port = libsodium, async port wraps the
 * same libsodium instance, imported exactly once for both.
 */
export function initEd25519(): Promise<void>

/** Throws `Ed25519NotInitializedError` if `initEd25519()` has not yet resolved — the
 * port has no silent default, so a caller cannot forget to initialise it and get a
 * plausible-looking wrong answer instead of an error. */
export function getSyncVerifier(): Ed25519SyncVerifier
export function getAsyncVerifier(): Ed25519AsyncVerifier
```
