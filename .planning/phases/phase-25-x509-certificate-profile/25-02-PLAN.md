<objective>
Complete the X.509 decoder: wire Plan 25-01's generic TLV engine into a full
`decodeX509Certificate` covering all six of this phase's remaining obligations —
algorithm allow-list (X509-01), the four named bans (X509-02), DER canonicalisation as
a certificate-level gate (X509-03), extension size/count ceilings (X509-06), and
duplicate-extension refusal (X509-07) — plus the custom extension mapping (userKey,
operatorId, discoverability, relayIds) from RESEARCH.md §3, and a full test suite: one
planted-mutation test per obligation, watched red, each recording what a naive decoder
would have done instead.

This plan also mints the `X509-01…07` requirement family in `.planning/REQUIREMENTS.md`
(none exist yet — the ROADMAP entry says so explicitly), records X509-05 as
delivered-with-evidence rather than re-implemented work, and — because this repository's
own convention is "`[x]` iff reachable from a runnable entry point" — marks X509-01,
02, 03, 06 and 07 as `[ ]` **Built, not wired**, honestly: this phase does not wire the
decoder into enrollment, issuance, or any production call path (that is out of this
phase's named scope), so despite being fully implemented and tested, none of the six
has a production caller yet. Only X509-05 is `[x]` Done, because `verifyChain` already
has one (`authorizeCapability`, called from both node factories).

Because the ledger mint is only worth as much as the instrument that checks it, this
plan also widens `acceptance-traceability.node.test.ts`'s two ledger-row patterns
(`REQUIREMENT_ROW`, `TRACEABILITY_ROW`) in the same commit as the mint: as filed, both
patterns are `[A-Z]+-\d+` — uppercase letters only before the hyphen — which cannot
match `X509-0N` (a letter followed by digits). Minting the rows without this fix would
make them pass the guard by being invisible to it, the exact "ledger edited to satisfy
its own checker" failure mode this repository's own test docblocks name as a prior real
incident.

Purpose: deliver the seven-obligation profile the ROADMAP goal names, each refusal
proved rather than asserted in prose — and prove the ledger's own instrument can see
what it claims to check.
Output: a complete, tested `x509.ts`; a new `X509-01…07` block in `REQUIREMENTS.md`;
`acceptance-traceability.node.test.ts`'s row patterns widened so those rows are
actually checked.
</objective>

export type X509Failure =
  | { readonly kind: 'certificate-too-large'; readonly bytes: number; readonly limit: number }
  | { readonly kind: 'malformed-der'; readonly detail: string; readonly offset: number }
  | { readonly kind: 'unrecognised-algorithm'; readonly oid: string }
  | { readonly kind: 'algorithm-parameters-present'; readonly oid: string }
  | { readonly kind: 'non-canonical-encoding'; readonly reason: string }
  | { readonly kind: 'extension-too-large'; readonly oid: string; readonly bytes: number; readonly limit: number }
  | { readonly kind: 'too-many-extensions'; readonly count: number; readonly limit: number }
  | { readonly kind: 'duplicate-extension'; readonly oid: string }
  | { readonly kind: 'unrecognised-extension'; readonly oid: string }
  | { readonly kind: 'unique-identifier-present' }
  | { readonly kind: 'multi-valued-rdn' }
  | { readonly kind: 'generalized-time-present' }

export interface X509Certificate {
  readonly version: number
  readonly serialNumber: string // hex
  readonly issuerCommonName: string
  readonly notBefore: number // unix ms
  readonly notAfter: number // unix ms
  readonly subjectCommonName: string
  readonly subjectPublicKey: string // hex, 32 bytes
  readonly userKey: string // hex, 32 bytes — custom extension
  readonly operatorId: string // custom extension, <=64 bytes UTF-8
  readonly discoverability: 'seed' | 'via-relay' // custom extension
  readonly relayIds: readonly string[] // custom extension, dag-cbor
  readonly signature: string // hex, 64 bytes
}

export type X509Result =
  | { readonly ok: true; readonly certificate: X509Certificate }
  | { readonly ok: false; readonly failure: X509Failure; readonly reason: string }
