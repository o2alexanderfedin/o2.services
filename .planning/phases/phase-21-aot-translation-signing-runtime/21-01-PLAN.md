# Phase 21 · Plan 01 — the lift pipeline names what it produced

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Requirement IDs closed by this plan:** AOT-02 (the cache-key half: a
`TranslationRecord` covering input digest, toolchain versions, target and feature
set, emitted by the pipeline itself rather than available to a caller who thinks to
build one).

<objective>
`translationCid` has been correct and unreachable since Phase 10. Every hit in the
tree is its own definition (`packages/aot/src/cache-key.ts:126`), the barrel
re-export (`packages/aot/src/index.ts:41`), or its own spec. `TranslationRecord`
(`cache-key.ts:171`) is constructed nowhere at all — not in production, not in a
test. Meanwhile `tools/aot/lift.ts` assembles all four of the key's inputs within
twenty lines of each other (`:735`, `:747`, `:748-756`) and names none of them; it
mentions `translationCid` twice, both times in prose (`:5`, `:236`).

This plan closes that. `liftElf` calls `translationCid` at the one point where every
input is already in hand, `LiftedArtifact` gains `translation` as a **required**
field for the reason `:226-229` gives for `findings`/`undecoded`/`blindSpots` —
there is no value of this type that carries the bytes without them — and a lift that
cannot be named becomes a `LiftFailure` rather than a success with `'unknown'`
hashed into its identity.

Purpose: an artifact that cannot be named cannot be cached, dispatched by name, or
compared against another host's. The name is not metadata attached afterwards; it is
part of what a successful lift *is*.
Output: `translationKeyOf` and a populated `TranslationRecord` out of
`tools/aot/lift.ts`, plus a shared stub harness under `tools/aot/` that Plan 21-02
drives the CLI through. Plan 21-02 makes the operator see the name; this plan makes
the name exist.
</objective>

```ts
/**
 * The CID a block gets from its bytes.
 *
 * Matches `MemoryBlockstore` exactly, including its use of the dag-cbor codec for
 * every block regardless of content. …
 */
export async function blockCid(bytes: Uint8Array<ArrayBuffer>): Promise<CID> {
  const digest = await sha256.digest(bytes)
  return CID.create(1, dagCbor.code, digest)
}
```

The identical two lines appear in `packages/core/src/blockstore/memory.ts:24-25` and

opaque produces a well-formed CID that no `blockstore.get` in this repository ever
