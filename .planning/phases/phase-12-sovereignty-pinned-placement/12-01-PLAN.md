<objective>
Give `submitJob` — the one production job path — a per-shard sovereignty label, a node
descriptor set to place against, and a placement engine that consults
`sovereignty.ts`'s existing, unit-verified `planPlacement`/`eligibleNodes` instead of
`executorsFor`'s unconditional round-robin. This is the structural cause DATA-03/DATA-04
exist to fix: the gate has been complete since Phase 4 and nothing on a runnable path
has ever called it.

**Position on Risk 2 (submitJob's error model changes shape).** The whole-job
`not-enough-executors` precondition is retired. It cannot survive contact with
sovereignty — an owner with one live node is the expected case, not an error — and
`sovereignty.ts`'s own `Placement` type already models "fewer replicas than asked"
as `degraded: true`, not a failure. The mechanism moves from a single upfront
job-level check to a per-shard placement decision: a shard degrades when its
eligible node count is below the requested redundancy, and is `unplaceable` only
when there are zero eligible nodes. This applies uniformly to public and sovereign
shards (the mechanism doesn't distinguish; `eligibleNodes` already treats a public
request as "every node is eligible"), which is why the blast radius is every
existing `submitJob` caller, not just the sovereignty-specific ones — enumerated
below and swept in Task 2. `JobResult.complete` changes definition to also require
`!degraded` per shard, preserving the *intent* of the old check (never report
verified agreement a job did not achieve) through the new mechanism.

Purpose: turn the two structural gaps CONTEXT.md names — no label on `JobSpec`
shards, no label on `Task` — into real fields, and make `submitJob` the caller
`eligibleNodes` has never had.
Output: a compiling, green kernel where every existing job (all public, all
sufficiently provisioned) behaves exactly as before, and the placement mechanism
underneath it is now sovereignty-aware.
</objective>
