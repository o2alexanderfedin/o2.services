# Phase 19 · Plan 07 — The cost, on the binary the criterion names

**Closes:** criterion 5 and AUTH-04's cost clause.

> **Depends on Plan 19-05's blocking decision.** Everything below is written against the
> `invitation` option. If the owner chose otherwise, this plan is replanned rather than
> adapted.

<objective>
Plan 19-05 built the mechanism in the portable tier and left it with no host. This plan gives
it one on both tiers and measures the criterion where the criterion asks: **across real
processes, through the binary, with the provider restarted in the middle.**

Two things Phase 17 measured are the targets, and both must move:

- **Twenty distinct user keys all enrolled unslowed**, because the limiter keys on `userKey`
  and a user key is one `ed25519.keygen()`. Removing the rate guard entirely left that
  assertion green. After this plan the same twenty are refused, and the refusal names what
  they did not present.
- **The budget was per provider *process*.** `#history` is a `Map` in the authority object;
  a restart forgets it, and a second provider defeats it without a second user key. After
  this plan the spend record lives beside `.identity.key` and `.provider.key` in the
  provider's own `--dir`, carrying exactly the authority the filesystem permissions there
  already carry — the same argument RULING B made for the duty-cycle control file, and for
  the same reason: `serveAgent` serves unauthenticated, so anything a peer could set is
  something any peer able to dial could set.

**This does not create a node class.** Both tiers hold the same authority, the same
invitation check and the same refusal; what differs is where a durable record is kept, which
is the same platform fact as a blockstore on the filesystem versus IndexedDB. `FabricNode`
and `BrowserNode` already differ that way in three places and it has never been a capability
difference.
</objective>

## Recorded decisions

- **The spend record lives under `--dir`**, carrying exactly the authority the filesystem
  permissions protecting `.identity.key` and `.provider.key` already carry. Not a wire frame:
  `serveAgent` serves unauthenticated, so a request that could clear a spend record would let
  any peer able to dial the provider re-open every invitation.
- **A spent nonce is never forgotten.** Pruning re-opens the replay. Growth is an expiry
  question, and an invitation carries one.
- **The measurement is a refusal, not a duration.** Contention on this host has invalidated
  timing readings twice, and "refused for want of something unmintable" is the stronger claim
  anyway.
- **Both tiers, one mechanism.** Only the storage differs, as it already does for blocks and
  for the identity key.

## Out of scope

- The rate limit. Unchanged and still proven; it bounds a burst by an already-admitted user,
  which is a different question.
- Revocation. An invitation expires and is single-use; withdrawing one already spent is a
  certificate-lifecycle question and no requirement here asks for it.
- Any change to what a certificate contains. An invitation is consumed at issue time.
- The flag fold at `bin/agent.ts`. Carried forward, not attempted.
