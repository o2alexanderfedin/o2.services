# Phase 19 · Plan 07 — The budget, on the binary the criterion names

**Closes:** criterion 5 and AUTH-04's cost clause.

> **Replanned 2026-08-02 after the owner's ruling.** An earlier draft of this plan was written
> against a provider-issued invitation, chained to an owner key and spent single-use. That
> option is off the table along with proof-of-work and a bigger rate limit. **The mechanism is
> the persistent cross-process issuance budget and nothing else**, and certificate lifetimes
> are explicitly *not* part of the argument — see `19-CONTEXT.md`'s signing-triangle section
> and the four radius bullets in it.

<objective>
Plan 19-05 built both budgets in the portable tier and left them reading a ledger with no
durable host. This plan gives them one on both tiers and measures the criterion where the
criterion asks: **across real processes, through the binary, with the provider restarted in
the middle.**

Two things Phase 17 measured are the targets, and both must move:

- **Twenty distinct user keys all enrolled unslowed**, because the per-user limiter keys on
  `userKey` and a user key is one `ed25519.keygen()`. Removing the rate guard entirely left
  that assertion green. After this plan the same twenty meet a provider that has signed its
  stated number of certificates and stops, and the refusal names the aggregate budget.
- **The budget was per provider *process*.** `#history` was a `Map` in the authority object; a
  restart forgot it, and a second provider defeated it without a second user key. After this
  plan the record lives beside `.identity.key` and `.provider.key` in the provider's own
  `--dir`, carrying exactly the authority the filesystem permissions there already carry — the
  same argument RULING B made for the duty-cycle control file, and for the same reason:
  `serveAgent` serves unauthenticated, so anything a peer could set is something any peer able
  to dial could set.

**The restart is the load-bearing reading.** A per-process budget passes every other assertion
in this file. Nothing here is evidence of anything until a provider has been stopped, confirmed
dead, restarted on the same directory, and refused the request that would have been the first
of a fresh budget.

**This does not create a node class.** Both tiers hold the same authority, the same two budgets
and the same refusals; what differs is where a durable record is kept, which is the same
platform fact as a blockstore on the filesystem versus IndexedDB. `FabricNode` and
`BrowserNode` already differ that way in three places and it has never been a capability
difference.
</objective>

## Recorded decisions

- **The record lives under `--dir`**, carrying exactly the authority the filesystem permissions
  protecting `.identity.key` and `.provider.key` already carry. Not a wire frame: `serveAgent`
  serves unauthenticated, so a request that could clear an issuance record would let any peer
  able to dial the provider hand its budget back.
- **The Node tier's write is synchronous; the browser tier's gap is one issuance and is
  stated.** An unstated asymmetry is how a node class gets invented by a later reader.
- **Issuance timestamps expire with the window; they are not kept forever.** Both budgets filter
  to the window, so an older entry decides nothing. This differs deliberately from a spend
  record, which can never be forgotten — a reader coming from the earlier invitation draft will
  expect that rule and this is not it.
- **The measurement is a refusal, not a duration.** Contention on this host has invalidated
  timing readings twice, and "refused because the provider has signed its quota" is the
  stronger claim anyway.
- **Both tiers, one mechanism.** Only the storage differs, as it already does for blocks and
  for the identity key.
