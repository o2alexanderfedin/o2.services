# Phase 19 · Plan 05 — The budget that a restart does not hand back

**Closes:** criterion 5's mechanism half, in the portable tier. AUTH-04's cost clause.

> **This plan no longer opens with a decision.** An earlier draft asked the owner to choose
> between an invitation chain, a persistent budget and proof-of-work. **The owner ruled on
> 2026-08-02 and none of those three is the answer as it was framed**: the scarce thing an
> identity must present *already exists* — a provider-issued certificate an attacker cannot
> mint, because `verifyCertificate` refuses an untrusted issuer. What is not scarce is
> **issuance**, and that is what this plan makes scarce. Proof-of-work, invitations and a
> bigger rate limit are all off the table. `19-CONTEXT.md`'s *"The signing triangle"* section
> carries the ruling; read it before this file.

<objective>
Phase 17 measured its own rate limit and found what it does not buy. **The burst limit is
real and fully proven** — a stated threshold read out of the refusal the peer received,
`limit: 5 / windowMs: 3_600_000`, on the wire. But AUTH-04 asks that mass fake-node creation
be *"measurably costly"*, and Phase 17's verification established two things that defeat it:

- **The limiter keys on `userKey`** (`enrollment.ts:224`, `#history` is
  `Map<PublicKeyHex, number[]>`), and a fresh user key is **one `ed25519.keygen()`**. Twenty
  requests under twenty distinct user keys all succeed, and **removing the rate guard
  entirely leaves that test green.**
- **The budget is per provider *process***. `#history` is an in-memory `Map`, so a restart
  forgets it, and a second provider defeats the limit without needing a second user key at
  all — asserted across two spawned providers.

So the cost clause is measured **false**, not unmeasured. REQUIREMENTS.md's AUTH-04 row says
so in those words.

**Both findings have one root and this plan pulls it.** Nothing in an enrolment request is
scarce: `userKey`, `operatorId` and `relayIds` are all attacker-chosen. A budget keyed on any
of them is a budget the attacker rotates around — which is Phase 17's first finding restated,
not a separate problem. The only durable scarcity available without a mechanism the owner
ruled out is **the provider's own aggregate issuance budget**: how many certificates one
provider will sign per window, held somewhere a restart cannot clear.

**Say what that is, in these words, wherever it is written down: a bound made durable, not a
per-identity price.** This repository has been burned twice by a mechanism whose description
outran its measurement, and the honest description of this one is short. It does not make each
identity cost an attacker something they can pay unilaterally. It makes identities **finite per
provider per window**, and makes exhausting them **durable and visible**. Under the four radius
bullets in `19-CONTEXT.md` — signed attributable results, N-version comparison rather than
identity trust, one quorum slot per operator whatever the sybil count, and sovereign data that
never moves — that is proportionate.

Output: an authority whose two budgets are both readable from outside its own heap, and a call
site that cannot get the forgetful version without naming it.
</objective>

## Recorded decisions

- **The aggregate budget is the mechanism, and the only one.** Owner ruling 2026-08-02. Nothing
  in a request is scarce, so a budget keyed on a request field is one the attacker rotates
  around — Phase 17's finding, restated rather than fixed.
- **It is a bound made durable, not a per-identity price**, and it is described that way
  everywhere it is described at all.
- **`enrol` stays synchronous.** `agent.ts:710` records that it is, *and* that this is why the
  branch takes no capacity slot. The port is synchronous so that argument survives.
- **The per-user window is reported first.** Both orderings are correct on state; the one that
  tells a requester the more specific true thing about their own request wins.
- **The aggregate refusal names nothing about the requester.** They did nothing wrong.
- **Both new options are required with named sentinels.** A default in either direction is a
  policy nobody chose, and for this option specifically the default *is* the defect.
- **No certificate-lifetime change.** Owner correction 2026-08-02; the radius does not justify
  it and renewal churn is not built.

## Out of scope

- Both node factories' *durable* ledgers, `bin/agent.ts`, and the cross-process measurement.
  All of that is Plan 19-07, which depends on this one.
- The existing per-user rate limit. It stays, unchanged and still proven. It bounds a burst by
  an already-admitted user, which is a different question from how many the provider will sign.
- Any wire change. A budget the provider keeps needs none; the earlier invitation draft did.
- Any change to `verifyCertificate`, to what a certificate contains, or to its lifetime.
- Revocation. It is non-renewal on the certificate's own clock, there is no list, and nothing
