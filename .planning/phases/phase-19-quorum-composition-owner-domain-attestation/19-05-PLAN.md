# Phase 19 · Plan 05 — What an identity must present

**Closes:** criterion 5's mechanism half, in the portable tier. AUTH-04's cost clause.

> **This plan opens with a blocking decision.** Its second and third tasks are written
> against one of three candidates. If the owner chooses differently, **stop after Task 1**
> and say so — this plan and Plan 19-07 are then both replanned, which is cheaper than
> building the wrong protocol.

<objective>
Phase 17 measured its own rate limit and found what it does not buy. **The burst limit is
real and fully proven** — a stated threshold read out of the refusal the peer received,
`limit: 5 / windowMs: 3_600_000`, on the wire. But AUTH-04 asks that mass fake-node creation
be *"measurably costly"*, and Phase 17's verification established two things that defeat it:

- **The limiter keys on `userKey`** (`enrollment.ts:224`, `#history` is
  `Map<PublicKeyHex, number[]>`), and a fresh user key is **one `ed25519.keygen()`**. Twenty
  requests under twenty distinct user keys all succeed, and **removing the rate guard
  entirely leaves that test green.**
- **The budget is per provider *process***. `#history` is an in-memory `Map`, so a restart
  forgets it, and a second provider defeats the limit without needing a second user key at
  all — asserted across two spawned providers.

So the cost clause is measured **false**, not unmeasured. REQUIREMENTS.md's AUTH-04 row says
so in those words.

This lands here rather than in Phase 17 because the remedy is a design decision this phase is
already making — **what scarce thing an identity must present** — and because this phase owns
AUTH-05 and the attestation machinery, so the natural candidates all sit beside work already
scheduled here.

Output: an enrolment that costs an attacker an input they cannot mint, and a refusal that
names which scarce thing was missing.
</objective>

  <name>Task 1: what scarce thing must an identity present</name>
  <decision>
    Which scarce input enrolment requires, so that creating the N-th fake identity is
    demonstrably more expensive than creating the first.
  </decision>
  <context>
    The rate limit is proven and does not buy this. It keys on `userKey`, which is one
    `ed25519.keygen()`; and the budget lives in a `Map` inside one provider process, so a
    restart or a second provider defeats it. AUTH-04's cost clause is measured **false**.

    The ROADMAP names three candidates: *a provider-issued invitation chained to an owner
    key, a persistent cross-process budget, or proof-of-work.* All three are protocol
    changes, and this project's standing rule is that a decision changing how nodes ask each
    other for things is the owner's, not an executor's — the same rule that sent the
    `PeerVerifier` re-ask question, the offer/exec reservation question, and the combine-bound
    question to the owner rather than letting a plan choose.

    One fact bears on all three and is easy to miss: **a certificate from an untrusted issuer
    already buys nothing.** A peer takes blocks only from peers whose certificate verifies
    against an issuer it pinned, and Phase 17 proved the `untrusted-issuer` refusal
    cross-process. So *"a second provider defeats the limit"* is a statement about one
    provider's budget, not about the fabric's resistance. What must become costly is mass
    creation against a **trusted** provider.
  </context>
  <options>
    <option id="invitation">
      <name>An invitation chained to an already-certified user key, single-use, durably spent</name>
      <pros>
        The scarce input is a signature by a key the provider has already certified, which an
        attacker cannot generate — this is the only candidate whose scarcity is not
        purchasable with CPU or with another keygen. It composes with AUTH-05, which this
        phase is already wiring: an invitation IS a chain to an owner key. Cost escalates
        naturally: the first identity is free to an invited owner and the (k+1)-th needs a
        further invitation somebody else must issue. It reuses `@noble/curves`, already a
        dependency, and the refusal is measurable as a refusal rather than as a duration —
        which matters on a host whose load has invalidated timing readings before.
      </pros>
      <cons>
        The largest blast radius of the three: every enrolment path changes
        (`bin/agent.ts`, both factories, `protocol.ts`, and every spec that enrols). It needs
        a durable spend record, so it also carries the persistence half of option B. And it
        needs a bootstrap rule — somebody has to be enrollable first.
      </cons>
    </option>
    <option id="durable-budget">
      <name>A persistent cross-process budget for the existing limiter</name>
      <pros>
        Smallest change: the `Map` becomes a file under the provider's `--dir`, and the
        existing refusal, threshold and wire shape are untouched. Closes the restart hole
        and the two-process hole exactly as Phase 17 described them.
      </pros>
      <cons>
        **Does not close the clause.** The limiter still keys on `userKey`, so twenty fresh
        user keys still enrol unslowed — which is the finding, not a side effect of it. It
        would make the limit durable without making it cost anything. Choosing this means
        criterion 5 stays open and should be said so rather than scored.
      </cons>
    </option>
    <option id="work">
      <name>Proof of work, with a difficulty schedule</name>
      <pros>
        No new trust relationship and no bootstrap problem: anybody can enrol by spending
        CPU. Self-contained in the portable tier.
      </pros>
      <cons>
        A fixed difficulty makes the N-th identity cost exactly what the first did, so the
        criterion's *"more expensive than the first"* needs an escalating schedule — and any
        key the schedule escalates on is a key the attacker can rotate, which is the defect
        being fixed. Escalating on the provider's total issuance penalises honest users. It
        also puts a CPU cost on every browser tab that joins, against BROW-01's whole
        posture, and this repository's vocabulary discipline exists precisely because a
        reviewer greps for this shape and does not stop to read the sense.
      </cons>
    </option>
  </options>
  <resume-signal>Select: invitation, durable-budget, or work — and if not `invitation`, say so plainly, because Tasks 2 and 3 below and the whole of Plan 19-07 are written against it and must be replanned.</resume-signal>

## Recorded decisions

- **The mechanism is the owner's to choose**, and Task 1 is blocking for that reason. A
  change to what nodes must present each other is a protocol decision, and this repository
  has sent every one of those to the owner.
- **`enrol` stays synchronous.** `agent.ts:710` records that it is, and the serving branch
  calls it inline. The durable spend record is therefore a snapshot in and a callback out,
  never an `await` inside.
- **Three refusal kinds, not one.** Absent-or-invalid, wrong-user, and spent-or-expired are
  three different things an operator has to be able to tell apart.
- **The bootstrap set is written by the caller.** A default in either direction is a policy
  nobody chose, and this repository's convention is that such a value is named at the call
  site.

## Out of scope

- Both node factories, `bin/agent.ts`, and the cross-process cost measurement. All of that is
  Plan 19-07, which depends on this one.
- The existing rate limit. It stays, unchanged and still proven. It bounds a burst by an
  already-admitted user, which is a different question from admission.
- Any change to `verifyCertificate` or to what a certificate contains. An invitation is
  consumed at issue time and is not a field of the certificate — a certificate says who a
  node is, not how its owner came to be admissible.
