# Phase 19 · Plan 03 — Three engines, one relay, no harness dialling

**Closes:** criterion 4 and NET-06's reading half — *two browser peers opened against the
static demo bundle — no seed process running, no `/bootstrap.json`, nothing dialed by a test
harness — discover each other via the wired hooks and complete a job together.*

<objective>
The three pieces this needs all exist and **have never been combined**.

- **Isolated contexts** exist (`two-tabs.e2e.test.ts:106`, `browser-capability.e2e.test.ts`).
- **A locally-started relay** exists (`two-tabs.e2e.test.ts:146-153`,
  `built-bundle.e2e.test.ts:81-85`).
- **The static bundle with no `/bootstrap.json`** exists (`built-bundle.e2e.test.ts:56-72`,
  a dumb 404-ing file server; `?relay=` at `:249-251`) — but that file opens **one** page and
  never discovers a peer.
- **Multiple engines** exist only in the `browser` vitest project. **All ten `*.e2e.test.ts`
  specs are chromium-only** — zero occurrences of `firefox` or `webkit` under
  `packages/node/src/*.e2e.test.ts`.

And every existing multi-tab test **dials from the harness** — `two-tabs.e2e.test.ts:223`,
`colouring-demo.e2e.test.ts:139`, `background-tab.e2e.test.ts:255`,
`duty-cycle-tab.e2e.test.ts:273`. Criterion 4 forbids exactly that.

The closest analogue that does not dial is `seed-discovery.e2e.test.ts:264-345`, which states
in its own comment that it deliberately calls no `window.o2.dial`. It fails three of this
criterion's conditions: a live `SeedServer` serves the page, `/bootstrap.json` is the
answering directory, and both pages are `context.newPage()` on **one** context, so they share
origin storage.

**The mechanism this test drives, stated so nobody looks for a missing one.** A tab holds no
reservations of its own — `browser-node.ts:1187` supplies `reservations: 'relays-for-nobody'`,
a named absence — so tabs do not answer each other's rendezvous. **They both ask the relay**,
which is a `FabricNode` holding a real thunk (`fabric-node.ts:1589`), and it answers with the
peer ids reserved on it. `findReservedPeers` (`rendezvous.ts:76-102`) turns each into
`/p2p/<relay>/p2p-circuit/webrtc/p2p/<holder>`, and the tab dials that. The relay carries SDP
and drops out; the job runs over direct WebRTC, which is what `PROJECT.md` requires — a
relayed circuit is a signalling channel and may not carry a job.

**This is not a node-class decision and must not be planned as one.** A tab answering
`reservations` would be reporting on peers it learned from a relay, which is a different
claim than the hook makes. The asymmetry is about *what each node knows*, not about what it
is permitted to do. Giving the browser tier a real `reservations` thunk is deferred, by
decision, and is out of scope here.
</objective>

## Recorded decisions

- **Two tabs discover each other by both asking the relay.** No browser-tier protocol change.
  A tab holds no reservations of its own, so a tab answering `reservations` would be
  reporting on peers it learned from a relay — a different claim than the hook makes.
- **One engine per peer rather than one context per peer.** Separate `launch()` calls give
  separate storage *and* separate implementations, which is strictly stronger than the
  standard asks for and no more code.
- **An engine that cannot take part is published as excluded with its reason.** Playwright's
  webkit is not Safari, and this file is the first WebRTC-over-relay reading taken in it.

## Out of scope

- **Giving the browser tier a real `reservations` thunk.** Decided against for this phase. If
  a later phase wants tabs answerable directly, it is a protocol question about what the hook
  asserts, not a wiring task.
- **Multi-browser coverage for the other nine e2e specs.** This brings the standard to one
  spec; retrofitting the rest is its own measured task.
- Anything about attestation. Criterion 4 is about routing, and this file's job is the
  smallest one that proves two peers computed together.
