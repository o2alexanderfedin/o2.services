# Phase 19 · Plan 16 — The aggregation is signed too

**Closes:** the half of the third leg that `PROJECT.md`'s headline claim actually rests on.

<objective>
**Signing `exec` alone would have left the project's own claim resting on an unsigned step.**
Owner decision 2026-08-02, recorded in `19-CONTEXT.md` under *"The combine result is signed
too"*. `PROJECT.md` states the split as: *the owner's contribution is trusted; **the
aggregation over contributions is verified***. `reduce.ts:280-287` repeats it verbatim in
`ReduceRun.redundancy`'s own doc. Sign only map results and a map/reduce job ends with **signed
map results feeding an unsigned aggregation** — exactly the half claimed to be the verified one.

**What is unsigned today, precisely.** `ReduceOutcome.executedBy` is a
`ReadonlyMap<treeNodeId, executorId>` (`reduce.ts:301-302`) — peer id **strings**. That is the
combine verb's exact analogue of `VerificationResult.agreeing`'s node-id strings before Plan
19-14: the requestor's own record of who it asked, not anything the answering node said. A
third party cannot check it and the requestor cannot show it to anyone.

**No sovereignty complication, and the reasoning is already in the tree.** Combine partials are
the outputs of **public** map tasks and are public by construction — the argument
`agent.ts:386-398` records when Phase 16 bounded combine at the `capacity` hook rather than the
`authorize` hook, because *"there is nothing on this frame to authorize"*. Nothing changes about
that. The question this plan answers is narrower: whether the aggregation can be shown to
somebody who was not there.

**One signer, both verbs, and that is a decision this plan makes on purpose.** `exec` signs
through the `attestResults` wrapper Plan 19-13 built, because `exec` goes through an `Executor`.
A combine does not — `serveAgent` runs it itself in `combineAdmitted` — so the signer has to
reach `serveAgent` directly. Rather than leave two independent ways for a node to acquire a
signing key, this plan puts **one required `AgentOptions` hook** there and has the combine
branch use it. `agent-contract.test.ts` already proves that file's hooks are required at compile
time, which is a stronger guarantee than the textual composition guard leg 1 and Plan 19-15 use,
and it covers the two bench rigs as well as the two factories.

Output: an aggregation a stranger can check, and a `ReduceOutcome` that says who signed each
step of it.
</objective>

From `packages/core/src/reduce.ts:257-313` — the two types this plan widens:
```ts
export interface CombineDispatch {
  (task: CombineTask, executorId: string): Promise<CID | null>
}

export interface ReduceOutcome {
  readonly ok: boolean
  readonly rootCid: string | null
  readonly combines: number
  readonly recomputes: number
  readonly executedBy: ReadonlyMap<string, string>   // tree node id → executor id
  readonly failed: readonly string[]
  readonly disagreements: readonly { readonly nodeId: string; readonly resultCids: readonly string[] }[]
  readonly minReplicas: number
}
```
`CombineDispatch` returning `CID | null` is the reason the attestation has nowhere to go today,
and `null` is defined to mean *that executor is gone* (`combine.ts:84-89`) — a meaning the wider
return must preserve exactly.

From `packages/net/src/agent.ts:400-409` — **the identity argument this plan's challenge
reuses rather than re-deriving**, in the source's own words: *"A combine's output is a pure
function of `inputCids` — same inputs, same bytes, same CID — so the input set **is** the work's
identity."* And the rejected alternative, also recorded there: `combineId` is *"the tree node's
derived id and therefore a requestor's claim about where in a tree this sits, so keying on it
would let one peer split identical work across N keys by renaming it."*

From `packages/net/src/agent.ts:456-560` — `combineAdmitted`, which produces
`{kind:'combine', resultCid, reason}` on every path: `unauthorized:`, a missing input, an
oversized partial, an undecodable input, an unencodable result, and the success path at the end
where `canonicalCid(fabricCombiner(inputs))` is already computed. **That last value is the
`resultCid` a signature covers, and it is already in hand** — signing costs no second hash.

From `packages/net/src/agent.ts:115-268` — `AgentOptions`' seven required hooks, every one a
union with a named sentinel, each carrying the recorded reason from `.planning/PROJECT.md`:
*an optional hook with a silent default is a hole*. `packages/net/src/agent-contract.test.ts`
proves the requirement at compile time. An eighth hook follows that pattern exactly.

From `packages/net/src/protocol.ts:189-195` and `:880-883`, `:965-975` — the combine response's
type, encode and parse. It crosses the wire as `{kind, found, reason}` plus `resultCid` when
found, and `found: false` is what `remoteCombineDispatch` reads as *try the next executor*.

From `packages/net/src/combine.ts:114-196` — `remoteCombineDispatch`, which parses the reply,
fetches the produced block by CID, **verifies it against the CID that was claimed** (`:177`) and
writes it locally before resolving. That existing verification is content addressing; this plan
adds the orthogonal question of *who computed it*.

From `packages/net/src/combine.test.ts:948-958` — two `Object.keys(...).sort()` guards on the
**request** bodies (the combine request's four keys, and the block request's two). They hold the
request shape, which this plan does not change; say in the summary that they were checked rather
than assumed unaffected.
