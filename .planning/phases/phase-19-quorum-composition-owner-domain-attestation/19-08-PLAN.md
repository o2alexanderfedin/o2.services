# Phase 19 · Plan 08 — One operator cannot fill a quorum, measured across processes

**Closes:** criterion 1 as reworded by owner ruling 2026-08-03 — *a verification quorum
assembled during a job run through `bin/agent.ts` rests on no single shared reachability
dependency and contains no two replicas from the same operator — a run engineered to try to fill
a quorum from one operator's nodes is refused rather than silently accepted, and so is one whose
members all hang off the same relay.*

> **Two rulings changed this plan after it was first written, and both must be read before it is
> executed.** The **anchor rule is retracted** — `discoverability === 'seed'` keyed on node kind,
> which `STATE.md:479-480` forbids, and Phase 3 had already dialled an iPhone at its
> `/p2p-circuit/webrtc` address and watched it run half of a 2×-redundant job. The "no anchor"
> fabric this plan used to build **does not exist any more**; the shared-relay fabric replaces it,
> which is what the reworded criterion asks for. And **the quorum is the default and it is
> optional**: an uncomposable quorum *degrades* unless the caller asked for refusal, so the
> engineered fabrics below appear **twice** — once on each arm of Plan 19-18's dial.

<objective>
**The entry point needs a substitution, and it is recorded here rather than discovered at
verification.** `bin/agent.ts` never submits a job — zero hits for `submitJob`, `JobSpec` or
`executeVerified` — it is a serving node whose only stdout is a handshake JSON at `:601`.
*"A job run through `bin/agent.ts`"* is satisfiable only as **"a job run *across*
`bin/agent.ts` processes"**, the shape `packages/node/src/discovery-agents.node.test.ts`
already uses for Phase 18's criteria 1 and 2. Plan 19-03 wrote the substitution into
`ROADMAP.md`; this file states it in its own header too, because a substitution that lives
only in a planning document reaches nobody reading the test.

Everything below the entry point is real. Each agent is a separate operating-system process
that generated its own identity key, enrolled against a spawned provider, and got a
provider-signed certificate naming the `--operator-id` it was started with. The requestor
discovers them by content CID, qualifies them against pinned issuer keys, and — since Plan
19-01 — receives their certificates in the descriptors it places on. `operatorId` is
therefore not a fixture field; it is what a provider signed about a process.

**The engineered case is the criterion's real content, and after the 2026-08-03 ruling it has
two halves.** Anything can be arranged to place two replicas on two nodes. What criterion 1 asks
is what happens when it *cannot*:

- **By default the shard degrades** — it runs at whatever redundancy is available, is marked
  degraded, and the receipt reads `owner-domain` rather than `independent`. Criterion 1's
  load-bearing word is *silently*, and a label that names the weaker outcome is not silence.
  This is the arm every existing caller takes.
- **Under the strict dial the shard is refused**, in the composer's words, reaching the
  requestor. That is a caller stating that a weaker answer is useless to it.

**Running both over one fabric is what makes either a reading.** If only the refusal were
measured, the plan would be measuring a configuration rather than a rule; if only the degrade
were, nothing would show that the composer noticed at all.

And both have to be distinguishable from a fabric that was never reached — the same
distinguishability problem NET-05 solved one layer down, solved the same way: assert the
requestor reached and qualified those candidates in the same run, before reading either
outcome.
</objective>

That file also records what it does **not** measure, in these words: ***"Quorum membership
and relay use remain unmeasured. Neither is gated on the verified set, and nothing in this
file reads them."*** This plan is the file that reads them, and that sentence should be
updated by this plan to point here rather than left standing.

From `packages/node/src/bin/agent.ts:169` — `--operator-id` already exists and is **required**
alongside `--provider-addr`, with the recorded reason: *"`operatorId` is the unit of quorum
diversity — a silent default would make every node one operator, or every node its own."*
So the engineered case needs no new flag: it is the same spawn with the same string.

From `packages/node/src/fabric-node.ts:609` — `discoverability: canRelay ? 'seed' : 'via-relay'`,
where `canRelay` is true when the node bound a non-circuit listening address. A spawned agent
with a `--port` is a `seed`; one started with only `--relay-addr` and no `--port` binds no
listening address of its own, is `via-relay`, and carries that relay in `relayIds`
(`fabric-node.ts:887-905`). **That is how the shared-relay fabric is built without inventing
anything** — point every agent at **one** relay and their certificates all name it, which is
exactly the concentration `sharedRelay` exists to catch. It is the topology a browser peer is
forced into, driven from the Node tier, and Plan 18-11 already made it reachable.

**Note carefully which way round this is now.** In the retracted design, pointing agents at one
relay was the *mistake* to avoid because it would refuse for the wrong reason. After the
retraction it is the *fixture* — a single shared relay is a single point of failure over which a
redundancy of two is not a redundancy, which is what eclipse resistance means.

From `packages/core/src/quorum.ts` after Plan 19-02 and its retraction — the refusal union is
`insufficient-operators` (with `wanted`/`distinctOperators`), `shared-relay-dependency` (with
`relayId`), and `no-candidates`. **There is no anchor kind.** 19-02's retraction also measured
that rule 2 must run over the **chosen member set** rather than the candidate pool: a pool of
relay-1/relay-1/relay-2 passes a pool-level check and then draws two members both on relay-1.

From `packages/core/src/job/submit.ts` after Plans 19-18 and 19-06 — `JobSpec.onQuorumShortfall`,
required, two named arms, read only where composition was attempted and refused.
