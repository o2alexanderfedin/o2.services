# Phase 19 · Plan 08 — One operator cannot fill a quorum, measured across processes

**Closes:** criterion 1 — *a verification quorum assembled during a job run through
`bin/agent.ts` contains at least one backbone-anchored replica and no two replicas from the
same operator — a run engineered to try to fill a quorum from one operator's nodes is refused
rather than silently accepted.*

<objective>
**The entry point needs a substitution, and it is recorded here rather than discovered at
verification.** `bin/agent.ts` never submits a job — zero hits for `submitJob`, `JobSpec` or
`executeVerified` — it is a serving node whose only stdout is a handshake JSON at `:601`.
*"A job run through `bin/agent.ts`"* is satisfiable only as **"a job run *across*
`bin/agent.ts` processes"**, the shape `packages/node/src/discovery-agents.node.test.ts`
already uses for Phase 18's criteria 1 and 2. Plan 19-03 wrote the substitution into
`ROADMAP.md`; this file states it in its own header too, because a substitution that lives
only in a planning document reaches nobody reading the test.

Everything below the entry point is real. Each agent is a separate operating-system process
that generated its own identity key, enrolled against a spawned provider, and got a
provider-signed certificate naming the `--operator-id` it was started with. The requestor
discovers them by content CID, qualifies them against pinned issuer keys, and — since Plan
19-01 — receives their certificates in the descriptors it places on. `operatorId` is
therefore not a fixture field; it is what a provider signed about a process.

**The engineered case is the criterion's real content.** Anything can be arranged to place
two replicas on two nodes. What criterion 1 asks is what happens when it *cannot*: a fabric
whose every candidate belongs to one operator must be **refused**, in the composer's words,
reaching the requestor. And that refusal has to be distinguishable from a fabric that was
never reached — which is the same distinguishability problem NET-05 solved one layer down,
and it is solved the same way: assert the requestor reached and qualified those candidates in
the same run, before reading the refusal.
</objective>

alongside `--provider-addr`, with the recorded reason: *"`operatorId` is the unit of quorum

From `packages/node/src/fabric-node.ts:609` — `discoverability: canRelay ? 'seed' : 'via-relay'`,

with a `--port` is a `seed`; one started with only `--relay-addr` and no `--port` binds no
listening address of its own and is `via-relay` (`fabric-node.ts:887-905`). **That is how the
no-anchor fabric is built without inventing anything** — it is the topology a browser peer is
forced into, driven from the Node tier, and Plan 18-11 already made it reachable.

From `packages/core/src/quorum.ts` after Plan 19-02 — the refusal union, including
`insufficient-operators` with `wanted`/`distinctOperators`, and the anchor kind.
