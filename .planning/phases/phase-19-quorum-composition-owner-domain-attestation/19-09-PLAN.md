# Phase 19 · Plan 09 — One owner, two nodes, and a label that says so

**Closes:** criterion 2, criterion 3's job-result half, and AUTH-05.

<objective>
**Criterion 2 has been unreachable for a reason nobody had closed, and the tree already says
whose it is.** A discovery-derived descriptor's `ownerId` is `certificate.userKey` — a hex
public key — while `OwnerId` is an opaque string (`sovereignty.ts:27`) and `--owner-id` takes
an operator label. Two different things in one field. A `PlacementRequest.ownerId` that is an
operator label matches no discovery-derived descriptor, and the shard comes back
`unplaceable` **with nothing obviously wrong**.

Both `packages/net/src/discover-candidates.ts:46-58` and
`packages/node/src/sovereignty-placement.node.test.ts:279-284` already assign this to
AUTH-05 / Phase 19 by name. `net/src/sovereign-execution.test.ts` dodges it by making the
owner id *be* a hex key. This plan closes it.

**Then criterion 2 is reachable, and it is the same expression criterion 3 uses.** Two of one
owner's nodes agree: two certificates, one `userKey`, one `operatorId`, so
`classifyAttestation` reads `owner-domain`. One node agrees: `owner-attested`. Nothing
special-cases either. That is what makes the pair worth trusting, and it is why both readings
belong in one file.

**One constraint from Phase 13 governs the fixture and must not be worked around.** Raw
sovereign data does not move between nodes, *including two nodes the same owner controls* —
`EgressGuard.send` refuses any frame carrying a registered sovereign payload rather than
forwarding it. So criterion 2 is reachable only if the owner has already placed the input on
both of their live nodes; **the fabric will not fetch it onto the second one.** Pre-seed both
agents' `--dir`, before the spawn, exactly as `discovery-agents.node.test.ts` does.
</objective>

## Recorded decisions

- **A disagreement between `--owner-id` and the enrolled user key is exit 2**, not a
  precedence rule. Precedence would let a mistyped flag produce a node cleared for an identity
  nobody will ask about — the same silent stall, one step earlier.
- **`--owner-id` survives for unenrolled nodes.** It is the only way to clear one, and every
  existing spawn using it keeps working.
- **The two arms live in one file.** `owner-domain` and `owner-attested` are one expression on
  different inputs, and a plant that reddens both is the evidence for that.
- **The fixture pre-seeds both owner nodes.** Phase 13's egress rule forbids moving the raw
  row between them, including between two nodes one owner controls.

## Out of scope

- A requestor-side unification of arbitrary owner strings. What is closed is that a node's own
  clearance cannot disagree with its certificate; a requestor pinning a shard to a string that
  is not a user key still gets an unplaceable shard, correctly.
- `composeQuorum`. A sovereign shard never reaches it — Plan 19-06's gate — and trying to
  route one through it would mean relaxing anti-affinity.
- Any display of the receipt. CLI is 19-10, demo UI is 19-11.
