# Phase 34, Plan 1 — Two Fallback Rungs Below Direct WebRTC (the remaining half)

**Goal, verbatim from ROADMAP.md:** *As a browser visitor, I want a pair that cannot connect
directly to fall to TURN, and a pair that cannot use TURN to fall to a relayed connection whose
budget is written down at 64 KiB **each way** and tested on the relayed path, so that my tab
still joins and no design assumes twice the room it has.*

## The four success criteria, VERBATIM from `.planning/ROADMAP.md`

Each clause is load-bearing. Plan and verify against these words, never against a paraphrase —
including the ones in this plan's own task titles.

  1. A pair that fails to connect directly connects over TURN, with credentials supplied through `rtcConfiguration`'s function form and short-lived: a credential captured from one session is refused after its stated lifetime, and a request from outside the fabric is refused. Both are verified **before** Phase 39 invites anyone, not after
  2. TURN is sharded to match the three bootstrap regions, and a cross-continent pair is observed using its own region's rung rather than one city's. Cross-continent pairs concentrate exactly where TURN is absent, which is why the sharding is part of the requirement and not an optimisation
  3. The protocol specification states the relayed budget **per direction** — 64 KiB each way, not 128 — and a boundary test drives the **relayed** path to the cut and observes it. A test that exercises only direct WebRTC cannot fail this way and does not count. The Circuit Relay v2 data limit is enforced bidirectionally: out plus back plus the reply in flight is `131072` in every framing measured, so a symmetric request/response protocol gets half of what the figure reads as
  4. A pair that falls all the way through is reported as **control-only**, not as a working data path, and a job that would need bulk data over that pair is refused with a named reason rather than stalling

**This plan covers criteria 1 and 2 only.**

(`packages/libp2p/src/libp2p-transport.ts:512`) answers `'unconnected'` / `'control-only'` /

`Libp2pTransport.send` (`:405`) raises `SendRefused` with reason `'control-only-path'`
(`packages/core/src/ports.ts:227`) for a message that cannot fit its own direction, carried to

**Criterion 4's residual, carried forward verbatim because a task here touches the same
path:** the refusal lands at whichever node would *send* the oversized frame, so a job whose
bulk arrives as a **reply** is refused by name at the serving side while the requestor sees a
timeout. Nothing in this plan repairs that and nothing in this plan may make it worse.

**One `pathTo` note, so nobody reports a false finding.** A pair connected over **TURN** is a
WebRTC connection at the libp2p level, not a circuit. `isControlPath` therefore answers false

limit applies to a TURN'd data channel. It is also precisely why TURN is billed and a circuit
is not. Criterion 4's residual is untouched by this phase.

## The provider is Cloudflare, and it was ruled on a probe rather than on documentation

**Owner ruling 2026-09-02, recorded in `.planning/consults/2026-09-02-turn-provider-measured.md`.**
Read that file in full before Task 2; it is 153 lines. The instruction was first *"use Google"*
and a measurement corrected it: `tools/turn-provider-probe.mjs` sends each host a STUN Binding
(the positive control) and an unauthenticated TURN Allocate (the question), in the same run
under the same budget.

| host:port | STUN Binding | TURN Allocate |
|---|---|---|
| `turn.cloudflare.com:3478` | `0x0101` success | **`0x0113` error 401** |
| `turn.cloudflare.com:53` | `0x0101` success | **`0x0113` error 401** |
| `stun.l.google.com:19302` | `0x0101` success | **no reply, 2 s** |
| `stun1.l.google.com:19302` | `0x0101` success | **no reply, 2 s** |
| `stun.l.google.com:3478` | `0x0101` success | **no reply, 2 s** |

Google answers STUN and does not implement TURN — the silence is not a network failure,
because the same socket got a Binding success immediately before. Cloudflare demands
credentials, which is a TURN server behaving as RFC 5766 §6.2 specifies.

**Cloudflare answers TURN on port 53 as well as 3478, and both ports belong in the
configuration with the reason beside them.** Port 53 survives the restrictive corporate and
mobile-carrier firewalls that drop 3478 — precisely the population TURN exists to serve, and
precisely the population `BENCH-08` is supposed to count. **Not measured and not to be
assumed:** whether both ports are equally reachable from the cohort's networks. That is a
question the public run answers.

**The free tier is real and does not reach this topology.** Cloudflare's TURN is free of charge
when used natively alongside their Realtime **SFU**. An SFU forwards media tracks; this
fabric's peer path is a WebRTC **data channel** carrying control messages and small partials.
No media, no SFU, so this use is the standalone kind and is billed on relayed traffic. **That
is a billing fact, not a protocol fact, and nothing in this repository can measure it** — see
Task 6's runbook for the only honest check.

## THE TRAP — read this before writing any ICE code

**A returned `RTCConfiguration` without an `iceServers` key is not "no opinion". It is an
instruction to use the four package defaults**, one of which — `stun.services.mozilla.com` —
answers `NXDOMAIN` on `8.8.8.8`, `1.1.1.1` and `9.9.9.9`, confirmed against
`stun.cloudflare.com` resolving on the same resolvers in the same breath.

So `iceConfiguration()` must return an explicit `iceServers` array on **every** path:

- a credential is held and unexpired → the explicit STUN list **plus** the TURN entries;
- the credential fetch failed, or no minting endpoint is configured, or TURN is switched off →
  the explicit STUN list, **alone, never `undefined` and never `{}`**.

The no-TURN default must be the explicit STUN-only list for a second reason: roughly forty
existing e2e specs construct browser nodes with no TURN endpoint and must stay green
unchanged. **TURN activates by URL parameter and by a `BrowserNodeOptions` field**, following
the `?relay=` precedent at `packages/browser/demo/main.ts:1392`.

**A second trap, inherited from Phase 35 and still live: the demo page's figure catalogue.**
Every visible figure on the demo page is declared in `packages/browser/src/demo-regions.ts` and
counted by `UI_SPEC_TALLY`. **This plan adds no visible figure and must not.** If you find
yourself putting a TURN status on screen, stop: you then own `REGIONS`, all three
`UI_SPEC_TALLY` fields, and UI-SPEC §4.x plus §12, in the same commit. Nothing in criteria 1 or
2 asks for a visible figure.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| any HTTP client → the hosted minter | The new route is reachable by the whole internet. Before this phase the hosted tier's only membership check was an IP header, so this boundary had no gate at all — CORRECTION 1 |

| the ICE configuration → the network | Every entry in the list is a third party this project must have chosen deliberately. The default list rotted with nothing saying so |
| a local test server → the machine's network interfaces | A TURN server bound to anything but loopback is an open relay on somebody's LAN |
| the owner's Cloudflare account → this repository | A key, a deploy or a preview deployment created from here is money spent without the alert that was supposed to precede it |
