<objective>
**This is the gate.** Phase 26's roadmap entry says of it: *"a negative here changes the
whole shape of the work."* Nothing after this plan is authored, and that is deliberate.

The question is item 7 of the roadmap entry, and it is marked INFERRED, NOT YET
MEASURED: the clang *driver* needed WASIX because a driver spawns `cc1` and a linker,
which is fork/exec. `elflift` is not a driver — it links LLVM as a library, reads one
ELF and writes one `.bc` in a single process. If it needs no fork/exec, no signals and
no non-local jumps, it may fit plain `wasm32-wasi` where the clang driver cannot.

## What this plan measures, and what it does not

It measures two things and it must not be read as claiming a third.

1. **elflift's own sources, compiled for `wasm32-wasi`** (AOTW-04). This is a real
   build of the elfconv/remill half, by the pinned wasi-sdk, per translation unit, with
   each failure carrying its own error text. It is the same method roadmap item 11(ii)
   used to get *"22 of 22 non-test TUs pass, 0 fail"* under `em++ -fsyntax-only` — with
   `--target=wasm32-wasi -c` instead of `em++`, and producing objects rather than only
   syntax-checking, because objects carry a symbol table and a syntax check does not.

2. **The unresolvable symbol residue of the elflift link** (AOTW-05). Undefined symbols
   demanded, minus what the preview1 sysroot provides, classified by family, every
   remainder named.

It does **not** produce a linked `elflift.wasm`, and must not be written up as if it
had. That needs LLVM, gflags, glog and XED cross-compiled to `wasm32-wasi` — hours of
compute at minimum, and precondition 3 in `26-CONTEXT.md` establishes that no
wasm32-wasi LLVM exists on this host (the prebuilt one is Emscripten). **The whole
reason for measuring the symbol surface first is to decide whether spending those hours
is justified.** Plan 26-03 states that scope explicitly in the verdict: a NO-GO here is
conclusive, because a symbol preview1 does not have will not appear because the build
took longer; a GO here is necessary and not sufficient, because it says nothing about
whether LLVM itself cross-compiles.

## Why the residue is read three ways

A single reading would encode one toolchain's `#ifdef`s and pass as the answer.
Measured this session:

- **Reading A — the produced wasm objects.** Undefined symbols of the objects Task 1
  actually emits. Authoritative for elfconv's and remill's own code, and for nothing
  else.
- **Reading B — host LLVM 16 archives in the image.** `/usr/lib/llvm-16` is present
  (verified 2026-08-10). These are x86/aarch64 host objects compiled with
  `LLVM_ON_UNIX`, so their undefined set OVERSTATES what a wasm build would demand.
  Useful as an upper bound, biased in the safe direction.
- **Reading C — the wasm-compiled LLVM 17 archives.**
  `/Volumes/ProjectsSSD/Projects/hupyy/libclang-wasm/out/build/lib` holds 66 archives,
  and five of the six libraries `backend/remill/CMakeLists.txt:53-57` names are there:
  `libLLVMSupport.a`, `libLLVMCore.a`, `libLLVMIRReader.a`, `libLLVMBitReader.a`,
  `libLLVMBitWriter.a`. **`libLLVMPasses.a` is absent**, exactly as that CMakeLists's
  own comment records. These are real wasm objects, so their undefined set is far
  closer to a wasi build's than reading B is. Two caveats and both must be written into
  the report rather than into a footnote: they are **Emscripten**, not WASI (so
  `__EMSCRIPTEN__` branches were taken, not `__wasi__` ones), and they are **LLVM
  17.0.6** against the image's 16.0.6.

**Reading C uses a neighbouring checkout, and that is allowed here for one specific
reason.** `26-CONTEXT.md` forbids depending on `Projects/hupyy/...` as a *build system*
— *"a green build that only works on one laptop is the thing this project's conventions
exist to refuse."* Reading C is not a build dependency; it is a **measuring
instrument**, and its absence must degrade the report rather than break it. If the
directory is not there, the harness records `readingC: null` with the reason, and the
verdict in Plan 26-03 states the narrower basis out loud. What it must never do is skip
silently — that is deficiency D21's shape, and this repository has already written up
eighteen cases that reported green by reporting nothing.

Purpose: answer the gating question with named symbols, at a cost of minutes rather than
hours, so the decision to spend the hours is made against a measurement.

Output: `tools/aot/elflift-wasi-gate.sh`, `tools/aot/elflift-wasi-gate.node.test.ts`,
`gate.json`, and the `vitest.config.ts` re-site the new spec forces.
