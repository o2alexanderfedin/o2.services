# Phase 26: elfconv Compiled to Wasm — Translation as a Fabric Workload - Context

**Gathered:** 2026-08-09
**Status:** Ready for planning
**Mode:** Smart discuss (autonomous), 3 areas, all accepted as proposed

<domain>
## Phase Boundary

The AOT translator runs as a wasm module on any node, so producing a lifted artifact stops
being a Docker-host privilege and becomes a job the fabric can schedule. It closes the
asymmetry where the fabric can RUN lifted artifacts anywhere but only PRODUCE them on one
machine — and where a RISC-V host can contribute fabric work but never translation.

**This phase ships stage 1 only.** The pipeline is ELF → bitcode (`elflift`) and then
bitcode → wasm (`wasi-sdk clang++` + `lld`); both halves are LLVM. Stage 1 is the
deliverable; stage 2 is **priced but not built**, because the roadmap entry requires the
two be stated up front and priced separately, and because a node that runs only stage 1
still needs a toolchain host for stage 2.

**Everything is gated on the first experiment.** Build `elflift` for `wasm32-wasi` and
find out whether it needs fork/exec, signals or longjmp. The entry says plainly: *"a
negative here changes the whole shape of the work."* No wave beyond that experiment
should be planned as if its answer were known.
</domain>

<decisions>
## Implementation Decisions

### What this phase actually ships

- **Stage 1 (`elflift`: ELF → bitcode) is the deliverable.** Stage 2 is measured and
  priced, not built.
- **The fork/exec experiment runs first and gates the rest.** The inference to test — and
  the entry marks it INFERRED, NOT YET MEASURED — is that the clang *driver* needed WASIX
  because a driver spawns `cc1` and a linker, while `elflift` links LLVM as a *library*,
  reads one ELF and writes one `.bc` in a single process. If that holds, plain
  `wasm32-wasi` may suffice where the clang driver could not.
- **A measured negative closes this phase honestly.** If `elflift` cannot be built for
  preview1, that result — measured, with the blocking syscall named — is the phase's
  output. Precedent: AOT-05 is carried as *"a measured negative, reported unmet rather
  than reworded."*
- **The build recipe is vendored and reproduced, or the archives pinned and published.**
  The wasm LLVM artifacts currently live in a neighbouring working tree
  (`Projects/hupyy/...`), outside this repository. The entry: *"Depending on another
  checkout is a spike, not a build system"* — and *"a green build that only works on one
  laptop is the thing this project's conventions exist to refuse."*

### The dependency wall

- **Port the loader onto LLVM's own `object::ELFObjectFile` + `DWARFContext` before
  porting anything.** This deletes three of the six non-LLVM dependencies (`-lbfd`,
  `-ldwarf`, `-lelf`) rather than performing those ports, and LLVM is already in the wasm
  build. **This is not speculative here**: the same loader port was done natively in
  earlier work with byte-identical output verified, so the approach is known to preserve
  behaviour. Measure before committing, but try it first.
- **LLVM must be cross-compiled to wasm32-wasi from source.** Measured 2026-08-07: the
  shipped `/usr/lib/llvm-16/lib/*.a` are host objects — `readelf -h` on a member reports
  `Machine: Advanced Micro Devices X86-64`. This is the dominant cost and is not avoidable
  by linking what the image already ships.
- **C++ exceptions stay off.** wasi-sdk-24's libc++ has no EH (`wasm-ld: undefined symbol:
  __cxa_allocate_exception`), and the codebase already accommodates it: `utils/Util.cpp`'s
  `elfconv_runtime_error` carries a `#if defined(__wasm__)` branch that `vprintf`s and
  `abort()`s, so all 17 throw sites funnel through a wasm-aware helper. LLVM's own defaults
  are `LLVM_ENABLE_EH=OFF` / `LLVM_ENABLE_RTTI=OFF`.
- **The 4 GB wasm32 ceiling is hard; measure against it rather than blocking on it.**
  wasi-sdk-24.0 ships no `wasm64-wasi` sysroot at all, so Memory64 is unavailable to this
  toolchain regardless of browser support. Whether it binds in practice is this phase's to
  measure: the 900-function static-glibc lift produces 4.4 MB of bitcode, so peak residency
  may sit well under the ceiling for modest inputs. **Size the claim to what is measured.**
- **Threads are available if needed** — `wasm32-wasi-threads` + `-pthread` built a
  `std::thread`/`std::mutex` program at 1 175 165 bytes (measured 2026-08-07).

### What counts as proof

- **The produced `.bc` must be `sha256`-identical to native elfconv's on the same input.**
  This is the method the entry names, and the same non-regression check used for the amd64
  front-end work.
- **The fixture is a committed ELF from `tools/aot/fixtures/elf/`** — `hello_static`, the
  accepted-lift case — so the comparison is reproducible. Note these fixtures are
  gitignored build output regenerated by `tools/aot/build-elf-fixtures.mjs`; the plan must
  build them rather than assume them.
- **The wasm `elflift` runs in Node under `@bjorn3/browser_wasi_shim`, WASI preview1.**
  The stack decision uses that shim on both platforms deliberately, so host semantics are
  identical everywhere. WASIX is explicitly out of reach: Wasmer's clang-in-wasm proves the
  concept but targets WASIX (~100 MB), a superset adding fork/exec, signals and sockets
  that preview1 does not have and that o2's execution tier cannot run.
- **New `AOTW-01…` requirement IDs**, one per obligation the phase closes.
- **elfconv's exit code is never trusted.** It exits `0` on binaries it could not fully
  translate — 174 addresses on a hello-world — so the driver measures the produced module.
  That existing project constraint applies unchanged to a wasm elfconv.
- **It must not report success on a module that was never run.**

<specifics>
## Specific Ideas

- **Prior art settles feasibility and must not be written down as a blocker.** Wasmer
  ships the full clang compiled to WebAssembly and runs it in Chrome, Safari and Firefox.
  "LLVM cannot be compiled to wasm" is FALSE. What is true is that their artifact targets
  WASIX and is ~100 MB, so it proves the concept and is not a drop-in.
- **Stage 2's C++ runtime sources do not change per job** (`Entry.cpp`, `Memory.cpp`,
  `Runtime.cpp`, `VmIntrinsics.cpp`, `Util.cpp`, `elfconv.cpp`, `SyscallWasi.cpp`), so they
  can be compiled to bitcode once, natively, and shipped as a fixed input. If that holds,
  the fabric never needs a compiler frontend — only a backend and a linker. Worth pricing
  in the stage-2 estimate.
</specifics>
