<objective>
Build the instrument the gate needs, and pin it to something that is not a laptop.

Phase 26 turns on one experiment — can `elflift` be built for `wasm32-wasi`, and if not,
which syscall blocks it. That experiment cannot be run, let alone believed, until two
things exist: a wasm32-wasi toolchain that is pinned rather than found, and a measured
statement of what WASI preview1 actually supplies. Both are this plan.

**The preconditions in `26-CONTEXT.md` say `wasi-sdk` is not installed on this host. That
is true and it is not the whole reading.** Measured by the planner on 2026-08-10 with
`docker run` against the image this repository already uses:
`ghcr.io/yomaytk/elfconv:arm64` ships **wasi-sdk-24.0 at
`/root/wasi-sdk-24.0-arm64-linux`** — `clang version 18.1.2-wasi-sdk`, default target
`wasm32-unknown-wasi`, with all five sysroots present (`wasm32-wasi`,
`wasm32-wasi-threads`, `wasm32-wasip1`, `wasm32-wasip1-threads`, `wasm32-wasip2`). The
image also carries LLVM 16.0.6 dev and `/root/elfconv/build/compile_commands.json` with
27 entries. It is 6.08 GB, already pulled, and its `third_party/elfconv/Dockerfile`
records `WASI_VERSION=24` at line 49.

So the acquisition step the roadmap did not budget costs **zero bytes of download**, and
the honest pin is not a version string in a fetch script — it is the image **digest**,
`sha256:22a404f31c9f7bb5c49e3193081d4876718253d86747aae3d30fcfd971f19c05`, read from
`RepoDigests` on this host on 2026-08-10. A tag is mutable; a digest is not. This is
also strictly better than the alternative `26-CONTEXT.md` warns about: the neighbouring
`Projects/hupyy/libclang-wasm` checkout is one laptop's directory, whereas a published
image digest is reproducible anywhere Docker can pull.

**A 108 MB host-side `wasi-sdk-24.0-arm64-macos.tar.gz` is deliberately NOT fetched.**
It exists (verified against the GitHub release API on 2026-08-10) and it would be needed
for a host-side stage-2 toolchain. The gate does not need it, and fetching a
hundred-megabyte dependency this plan cannot use is the kind of unbudgeted cost the
preconditions section exists to prevent, not create. If a later wave needs a host
toolchain, that wave acquires it, pins its SHA-256, and says why.

Purpose: give Plan 26-02's gate a pinned toolchain and a measured `provided` set to
subtract from, and establish the two proof rules this phase is held to — the exit code
is never trusted, and a module that was never run is never a success — as mechanisms
rather than as sentences.

Output: `tools/aot/wasi-preview1-surface.sh`,
`tools/aot/wasi-preview1-surface.node.test.ts`, and the `vitest.config.ts` re-site the
new spec forces.
</objective>

    sockets — `socket`, `connect`, `bind`, `listen`;
    threads — `pthread_create`, `pthread_mutex_lock`;
    and a control group that MUST be present or the probe is measuring nothing —
    `printf`, `malloc`, `memcpy`, `write`, `exit`.

    container; running it is the spec's job, on the host, under the shim this project
    actually ships — that is the whole point of AOTW-02.

    Exit codes, documented at the top of the file in the same shape

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Published container image → this repository's measurements | Everything this phase concludes is read out of an image pulled from `ghcr.io`. A different image would produce different numbers under the same file names |
| Container root → host filesystem | The harness runs as root inside the container with a bind-mounted output directory; anything it writes is written as root onto the host |
| Container-produced `.wasm` → host Node process | `smoke.wasm` is a binary produced by a toolchain inside a container and then instantiated in this repository's own test process |
