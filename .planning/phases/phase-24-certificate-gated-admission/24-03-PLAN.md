### THE ORDERING — corrected 2026-08-05, and the correction changes what task 1 will see

> **What this block said, retained for the reasoning:** *"Ordering inside `#compose`, and it matters
> for task 1: `createLibp2p` → the `relayAddrs` dial loop → `Libp2pTransport.start` →
> `PeerVerifier.start` → `serveAgent`. **Enrolment is a separate, earlier
> `await libp2p.dial(multiaddr(enrollment.providerAddr))` inside the `Dialed` block on both tiers**,
> independent of `relayAddrs`."*
>
> **That is backwards, measured on both tiers.** The enrolment dial is the **later** one, not the
> earlier one. The reasoning behind the error was sound and is worth keeping: enrolment does not
> route through a reservation, so it was assumed to have been arranged to happen first. It was not
> arranged at all — it is independent, which is a stronger property than being ordered.

**The measured order, both tiers, cited by symbol:**

- `packages/node/src/fabric-node.ts` — `createLibp2p({` → `for (const address of relayAddrs) {` →
  `Libp2pTransport.start(` → `resolveCertificate({` → `PeerVerifier.start({` → `serveAgent({`. The
  file says so itself at the `PeerVerifier` construction: *"Constructed **after**
  `resolveCertificate`, which dials the provider."*
- `packages/browser/src/browser-node.ts` — `BrowserNode.#compose`: `for (const address of
  options.relayAddrs) {` → `Libp2pTransport.start(` → `new RpcEndpoint(` → `resolveCertificate({`.
  The enrolment dial lives inside `resolveCertificate` as
  `await libp2p.dial(multiaddr(enrollment.providerAddr))`.

**What follows, and it is why the conclusion survives:**

1. **The enrolment dial is independent of the reservation regardless of order.**
   `denyInboundRelayReservation` is called by the circuit-relay-v2 *reservation handler*, never on
   connection establishment. Order is irrelevant to the exemption; it was never the mechanism.
2. **A node reaches the door before it can possibly hold a certificate.** Since `resolveCertificate`
   runs *after* the relay-dial loop, a first-boot node is refused on that first pass by
   construction. That is not a bug in the seam; it is what task 1 must actually observe.
3. **A refused reservation does not fail `#compose`.** The relay-dial loop asserts only that the
   *dial* resolved — `const connection = await libp2p.dial(multiaddr(address))` — and nothing in
   `#compose` reads whether a reservation was granted. So the door stays open for enrolment **even
   in the separated topology**, and for a stronger reason than co-location.
4. **The consequence no plan in this phase has named until now.** A peer whose reservation is
   refused still completes its relay dial, still starts, enrols against the provider address, and
   then **holds a certificate and can re-reserve**. Whether the second reservation attempt happens
   on its own — through libp2p's reservation retry — or requires an explicit re-reserve is
   **UNMEASURED**. Task 1 must record which, verbatim. If it requires an explicit call, the tab that
   enrols is a tab that never gets in, and that is a finding, not a detail.

### THE HINGE — how the gater learns a peer's certificate. ADDED 2026-08-06, AND IT IS NOT SETTLED

**This is the phase's load-bearing unknown and task 1 now owns measuring it.** Task 2's `<action>`
carried the sentence *"at reservation time the peer is connected and identified, so the same records
exchange `PeerVerifier` uses is available."* **On the first pass that is false**, and four facts make
it false rather than merely doubtful:

1. **The hook is handed a peer id and nothing else.**
   `denyInboundRelayReservation?(source: PeerId): Promise<boolean> | boolean`. There is no
   certificate, no connection, no record on that signature. Everything the gate knows it must go and
   ask for.
2. **`PeerVerifier` gets its answer by asking the peer.** `PeerVerifier.#decide` is `async` and its
   one network call is `this.#rpc.request(peerId, encodeRequest({ kind: 'records', nodeKey: expected }))`
   — the module's own header: *"The only network call this class makes is the `records` request."*
3. **On the JOINING node nothing is serving yet when the gate fires.** The measured order is
   `createLibp2p` → the `relayAddrs` dial loop → `Libp2pTransport.start` → `resolveCertificate` →
   `PeerVerifier.start` → `serveAgent(`. The reservation is asked for inside libp2p's own loop off
   that dial — i.e. **before `serveAgent(` exists on the joiner**. So the relay's `records` request
   has nobody to answer it.
4. **This exact failure is already recorded as measured, in `peer-verifier.ts`'s own header**, and
   the plan does not get to rediscover it: *"a gate dialled a tab before the tab's `serveAgent` was
   up, the `records` request went unanswered for the full 30 s RPC budget, and the `unreachable`
   that eventually settled would have stood forever even though the tab held a valid certificate
   from the pinned issuer the whole time."*

**What this does NOT mean.** It does not mean the seam is wrong; §*THE ORDERING* item 2 already
established that a first-boot node meets the door with nothing to present, and that is *expected*.
What it means is that **the mechanism by which the gate reaches a verdict is undesigned**, and a
plan that designs it from the false premise above would produce the admit-while-pending hole the
proof block already names — *"an async gater that always answers 'allow' while a lookup is in flight
is a fail-open hole wearing a gate's clothes"* — while believing it had avoided it.

**Task 1 measures which of these is actually available, and task 2 may not be designed until it
has.** Candidates, none endorsed here:

- the identify exchange's own payload, if anything certificate-shaped rides it (**unmeasured**);
- a `records` request from the relay to the joiner, which item 3 says has nobody to answer it at
  first-boot (**measure whether that is true at the moment the hook fires**, not at `#compose` time);
- a certificate the joiner volunteers *before* asking for the reservation, which is a wire change and
  therefore a different plan;
- refusing every first-boot reservation by construction and admitting only on the re-reservation
  after enrolment — which is only viable if the re-reservation question below answers "yes".

**Two questions this plan already flags are therefore LOAD-BEARING, not incidental**, and neither
may be left as a line in a summary:

- **(i) Does `@libp2p/circuit-relay-v2` re-consult the gater on reservation RENEWAL?** If not, the
  revocation window is unbounded (sub-decision 3), *and* the last candidate above dies with it.
- **(ii) Does a peer refused at first boot obtain a reservation after enrolling, WITHOUT a restart?**
  If not, the criterion's own subject — a node that enrols and then joins — has no path, and 24-04
  task 2's single-page-load transition does not exist.

Both are **UNMEASURED today**. Task 1 answers both or names which it could not and why.
