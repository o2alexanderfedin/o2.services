# Phase 24 · Plan 03 — Arm the door, and only the door

**Closes (mechanism, final third):** criterion 1's refusal. The reading across real processes and
real tabs is 24-04.

<objective>
`circuitRelayServer` is constructed with capacity limits only, so a joining peer presents a Noise
handshake and nothing else. This plan makes the relay consult `RelayAdmission` — the union 24-01
threaded and nothing has read yet — at the one moment the owner's ruling names: the reservation.

**The mechanism is `connectionGater.denyInboundRelayReservation`.** Measured in the installed tree
2026-08-04 and **re-measured 2026-08-05 in both halves**:

- `node_modules/@libp2p/circuit-relay-v2/dist/src/server/index.js` calls
  `await this.components.connectionGater.denyInboundRelayReservation?.(connection.remotePeer)` and
  refuses when it `=== true`.
- `node_modules/@libp2p/interface/dist/src/connection-gater.d.ts` **declares it**:
  `denyInboundRelayReservation?(source: PeerId): Promise<boolean> | boolean`, with a docblock
  beginning *"denyInboundRelayReservation tests whether a remote peer is allowed make a…"*.

> **Contingency removed 2026-08-05.** This plan previously carried an abort branch for the case
> where the hook is present in the shipped JS but absent from the type declarations. **It is present
> in both.** The branch does not fire. It is recorded here rather than deleted silently, because the
> reason it existed — a JS-only hook would have forced a cast at the one place in this repository
> that decides who gets in — is still the right reason to have checked.

**Arming is exactly one change**: supply `connectionGater.denyInboundRelayReservation` on
`createLibp2p` in `packages/node/src/fabric-node.ts`. There is no second edit, no
`circuitRelayServer` argument, and no new package.

Three properties carry the design and **each is re-measured in task 1 before anything is built on
it**:

1. It fires on the **reservation** and on nothing else, so a plain connection — the one enrolment
   uses — never reaches it. **The `enrol` exemption is by construction, not by an `if`.**
2. It is optional-called (`?.`), so a node supplying no gater behaves exactly as today.
3. It is per-peer, so certificate-holding stays a **fact about a node**, never a node kind.

**And a fourth property is what makes the criterion's other two clauses fall out for free**, which
is a claim this plan states and 24-04 measures: `BootstrapInfo.peerAddrs` and `agent.ts`'s
`reservations` answer are **both derived from `node.reservedPeerIds`**. A peer that never obtains a
reservation therefore never appears in either — structurally, with no filter to add and no `if` to
forget. That is the same property `peer-gate.node.test.ts`'s header protects for the block-source
thunk, and it is the strongest single argument for this seam over any other.

**Do NOT gate at the `Transport` layer.** `peer-gate.node.test.ts`'s header records keeping
`Transport` a certificate-ignorant three-member datagram port as a **protected property**.
</objective>

### THE ORDERING — corrected 2026-08-05, and the correction changes what task 1 will see

> **What this block said, retained for the reasoning:** *"Ordering inside `#compose`, and it matters
> for task 1: `createLibp2p` → the `relayAddrs` dial loop → `Libp2pTransport.start` →
> `PeerVerifier.start` → `serveAgent`. **Enrolment is a separate, earlier
> `await libp2p.dial(multiaddr(enrollment.providerAddr))` inside the `Dialed` block on both tiers**,
> independent of `relayAddrs`."*
>
> **That is backwards, measured on both tiers.** The enrolment dial is the **later** one, not the
> earlier one. The reasoning behind the error was sound and is worth keeping: enrolment does not
> route through a reservation, so it was assumed to have been arranged to happen first. It was not
> arranged at all — it is independent, which is a stronger property than being ordered.

**The measured order, both tiers, cited by symbol:**

- `packages/node/src/fabric-node.ts` — `createLibp2p({` → `for (const address of relayAddrs) {` →
  `Libp2pTransport.start(` → `resolveCertificate({` → `PeerVerifier.start({` → `serveAgent({`. The
  file says so itself at the `PeerVerifier` construction: *"Constructed **after**
  `resolveCertificate`, which dials the provider."*
- `packages/browser/src/browser-node.ts` — `BrowserNode.#compose`: `for (const address of
  options.relayAddrs) {` → `Libp2pTransport.start(` → `new RpcEndpoint(` → `resolveCertificate({`.
  The enrolment dial lives inside `resolveCertificate` as
  `await libp2p.dial(multiaddr(enrollment.providerAddr))`.

**What follows, and it is why the conclusion survives:**

1. **The enrolment dial is independent of the reservation regardless of order.**
   `denyInboundRelayReservation` is called by the circuit-relay-v2 *reservation handler*, never on
   connection establishment. Order is irrelevant to the exemption; it was never the mechanism.
2. **A node reaches the door before it can possibly hold a certificate.** Since `resolveCertificate`
   runs *after* the relay-dial loop, a first-boot node is refused on that first pass by
   construction. That is not a bug in the seam; it is what task 1 must actually observe.
3. **A refused reservation does not fail `#compose`.** The relay-dial loop asserts only that the
   *dial* resolved — `const connection = await libp2p.dial(multiaddr(address))` — and nothing in
   `#compose` reads whether a reservation was granted. So the door stays open for enrolment **even
   in the separated topology**, and for a stronger reason than co-location.
4. **The consequence no plan in this phase has named until now.** A peer whose reservation is
   refused still completes its relay dial, still starts, enrols against the provider address, and
   then **holds a certificate and can re-reserve**. Whether the second reservation attempt happens
   on its own — through libp2p's reservation retry — or requires an explicit re-reserve is
   **UNMEASURED**. Task 1 must record which, verbatim. If it requires an explicit call, the tab that
   enrols is a tab that never gets in, and that is a finding, not a detail.
