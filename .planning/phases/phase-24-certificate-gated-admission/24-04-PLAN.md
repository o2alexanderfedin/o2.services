# Phase 24 · Plan 04 — Read the criterion, and measure what it does not fix

**Closes:** criterion 1 — *"a node that cannot present a provider-issued certificate cannot join the
fabric, advertise itself, or be dialled by another node"* — and the residual the criterion's own
rationale requires be pinned rather than argued away.

<objective>
Three plans built a door. This one is the only plan entitled to say it works, and the criterion has
**three separate clauses** — join, advertise, be dialled. 24-03 measured the first at close range
and made a **structural claim** about the other two: that `BootstrapInfo.peerAddrs` and `agent.ts`'s
`reservations` answer are both derived from `node.reservedPeerIds`, so a peer that never reserved
cannot appear in either. **A structural claim is a hypothesis until something reads it**, and this
is where it gets read — across real `bin/agent.ts` processes, not in a unit fixture, because
`reservedPeerIds` is in-process state and an in-process reading would be asking the same object
twice.

And there is a fourth thing to measure, which is the honest part: **this phase does not stop a
provider spending CPU refusing enrolments.** It cannot — enrolment must stay open, because it is how
a node gets its first certificate. What changes is that the attacker gains **no foothold** for it.
Phase 19 measured the old ratios (refuse-over-mint ~3.0, refuse-over-replay ~1397). Those numbers do
not improve here and **must not be presented as if they did**. What improves is what the minted
identity is worth, and that is a different measurement.
</objective>

### The enrolment fixture's topology — corrected 2026-08-05

> **What this block said:** *"`browser-enrollment.e2e.test.ts` — the provider-and-relay-are-one-node
> topology."* **That names two of the three roles and merges the third.**

The fixture stands up **three** independent participants:

1. **`provider`** — `FabricNode.start` with `issuesCertificates`, its signing key persisted under
   its own `blockstoreDir: join(workdir, 'provider')`. `provider.issuerKey` is the real pinned key.
2. **`gate`** — a **separate** `FabricNode`, its own `blockstoreDir: join(workdir, 'gate')`, its own
   listen address, started with `trustedIssuers: [issuer]`. **This is the node that pins.** It is
   not met at start: the tab reaches it afterwards through `meetGate()`.
3. **the tab** — given `relayAddrs: [provider]` and `enrollment.providerAddr: provider`, i.e. the
   *same address twice*.

**So what is co-located is the tab's RELAY and its ENROLMENT PROVIDER. The gate is a third party.**
The fixture says so itself: *"**The provider, not the gate.** `relayAddrs` is dialled *inside*
`start`… The gate is dialled after start, by `meetGate`."*

**Why the correction matters for task 2.** A reading written as though one node plays all three
roles will hand the page a single address and conclude that "the tab was refused and then enrolled
through the same address" proves the co-located case. It proves less than that: in this fixture the
node that *refuses* and the node that *issues* are different processes. Task 2 must decide, and
state, which topology it is reading — the co-located one (relay and provider one node, which is
what sub-decision 1 is about) or this fixture's three-node one — and **not describe one while
building the other**.

### `bin/agent.ts`, the seed, and the advertisement surfaces

`bin/agent.ts` takes `--provider-addr` **optionally**, and 24-01 measured what an
operator-boundary refusal would cost. `bin/seed.ts` gained `--trusted-issuer` in 24-01.

`seed-server.ts` builds `BootstrapInfo.peerAddrs` as `[seedAddr, ...node.reservedPeerIds.map(…)]`.
Its docblock: *"The first entry is the seed itself… a page's relay and a page's peer are one node."*
**So the seed itself is always in `peerAddrs` regardless of admission** — do not read its presence
as an admission failure.

`agent.ts`'s `reservations` branch answers `options.reservations()`; `fabric-node.ts` passes
`reservations: () => node.reservedPeerIds`. **The wrinkle, measured 2026-08-05 and previously
omitted:** the branch **short-circuits** —
`peerIds: options.reservations === 'relays-for-nobody' ? [] : options.reservations()`. The type is
`(() => readonly string[]) | 'relays-for-nobody'`, and the string arm is *a named absence, not an
omission*, per the option's own docblock.

**Why that matters here.** `browser-node.ts` passes `'relays-for-nobody'`, so **a browser tab
answers an empty list about itself whatever its admission state** — the thunk is never called and
`reservedPeerIds` is never consulted. Task 2's browser reading therefore **cannot** be taken from
the tab's own `reservations` answer: an empty list there is the tab's permanent, correct answer and
says nothing about whether it was admitted. **Read the tab's admission from the relay's
`reservedPeerIds`, never from the tab's own RPC answer.** A reading built on the tab's answer is a
tautology that passes before and after the gate — exactly the shape two criteria in this repository
already sit at PARTIAL for.

`mutation-ledger.ts` already carries an entry whose `find` is
`'      reservations: () => node.reservedPeerIds,'` — verified 2026-08-05 to match the source
byte-for-byte including the six-space indent. **If this phase changed that line, that entry is stale
and `mutation-guard.node.test.ts` will say so.**
