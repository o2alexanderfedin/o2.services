# Phase 15 · Plan 01 — the audience key and the authorizer

> **Numbers in this plan are configuration choices, not derived claims. Any quantity
> describing runtime behaviour must be measured before it is written down anywhere,
> including in a source comment.**

**Closes (in part):** AUTH-03. This plan builds the two pieces the serving half needs and
proves them in isolation. Nothing is wired to a factory here and no existing test changes.

<objective>
Build the two mechanisms this phase's wiring will compose, each on its own, each proven
against a real fabric rather than a mock:

1. `audienceKeyOf` in `@o2/libp2p` — `VerifyOptions.audience` (`capability.ts:132-133`) is an
   ed25519 public key in hex, and nothing in the repository derives one today. 15-CONTEXT.md
   decision 1 settles where it comes from: the libp2p peer id both ends already exchange. The
   serving node computes it from its own `libp2p.peerId`; the requestor computes the identical
   key from the `nodeId` string it already passes to `new RemoteExecutor(nodeId, rpc)`. No
   enrollment, no new protocol request, no key file. The binding is the point — only the holder
   of that private key could have completed the noise handshake as that peer id, so the chain's
   audience and the authenticated transport identity are the same key by construction.
2. `authorizeCapability` in `@o2/net` — the first real `Authorizer` in the repository. Every
   production call site passes `'serves-unauthenticated'` today (`fabric-node.ts:419`,
   `browser-node.ts:272`, `bench.ts:152`, `bench.ts:177`); the only functions of this shape
   anywhere are two test literals at `distributed.test.ts:534` and `:580`.

Purpose: `verifyChain` has been complete and fuzzed since Phase 4 and has zero production
callers. This plan gives it a caller-shaped adapter, and gives that adapter a key to verify
against, so Plan 15-03 has something to hand `serveAgent`.
Output: two exported functions, barrel-exported from their packages, each with its refusals
proven and named. Plan 15-02 builds the dispatching half in parallel; neither depends on the
other.
</objective>

`describeFailure`'s exact texts, which this plan must not reword to make an assertion pass
(`capability.ts:101-122`):


`PeerId` is a union over identity kinds. `peerId.type` is one of `'Ed25519' | 'secp256k1' |

the others; `publicKey.raw` is the 32 raw bytes for Ed25519.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| peer id string → audience key | A requestor derives the serving node's audience from a string it was given. A wrong derivation mints chains no node can use; a *forgiving* derivation would mint chains the wrong node can use |
| dispatched frame → `authorizeCapability` | The chain is attacker-controlled input that has already survived `parseRequest`'s per-field validation. Everything it asserts about itself is checked against configuration this node holds locally, never against the frame |
| node configuration → the pinned owner key | `ownerKey` is supplied by whoever started the node. This module cannot tell a correct pin from a wrong one; it can only refuse when there is none |
